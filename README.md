## What exists today

- **The engine** (`packages/engine`): dependency-free TypeScript that detects the project's build, test, lint and type-check commands (Node and TypeScript, PHP and Laravel, Python), routes each request (fast, standard or full), records test-first runs, runs the gates and writes the evidence.
- **The `crew` command**: the engine's interface, bundled into one file, `plugins/core/dist/crew.mjs`. `crew help` lists the commands.
- **Hooks**: a Claude Code plugin (`plugins/core`) wires SessionStart, UserPromptSubmit, PreToolUse and Stop to `crew hook <event>`. A turn cannot end while watched source files have unproven changes, the agent cannot write the engine's files, and decisions that belong to the user (skips, approvals, accepting changed state) go through a permission prompt. The agent runs those commands; by default the user's yes in the conversation is the signature and no prompt appears, with the record saying the agent relayed it, and a team whose policy says `attendedDecisions: prompt` gets the permission prompt instead ([ADR 0005](docs/adr/0005-attended-decisions-by-relay.md)). When no person can answer (a headless session, or bypassPermissions or dontAsk mode) the hook requires `--mode <mode>` on those commands: the record says the agent decided, and the decision counts for the proof only if the team's policy says so.
- **The crew skill** (`plugins/core/skills/crew`, command name `crew-method`: a skill claims the bare `/<name>`, and `/crew` belongs to the mod): the method the agent follows, phase by phase, with the checklists by kind the gap round reads (`skills/crew/checklists/`) and the rubrics the judgement gates are ruled by (`skills/crew/rubrics/`).
- **The roles** (`plugins/core/agents/`): ten subagents with clean contexts and read-only tools, launched by the skill and never on their own. For the judgement gates, five reviewers (sonnet; opus on the full route or a risk area) and the judge (fable); for the debate, the researcher, the experts, the devil's advocate and the fault-finder (opus), closed by the judge, who also acts as validator where no person watches. They return text; the session saves it under `.crew/work/<id>/review/` and `conclave/` and records it through `crew`, so nothing a role says becomes a verdict without the engine.
- **The mod** (`plugins/core/hooks/register.js`, Claude Code 2.1.287 or later): a status strip above the prompt (`crew <id> · phase · route · proven · gates`, or `not proven (<first reason>)` in place of `proven`; a planned gate that has not run shows as `…`), a line under each answer (`Proven: ...` or `Not proven: ...`), and `/crew` with `status`, `panel` and `mode <partner|guide|pilot>`; a mark per judgement gate after the gate marks; the panel lists the gap round's decisions, the objections and one row per judgement gate. It only shows the engine's state; the hooks and the command carry the guarantee, so disabling the mod changes nothing about what is enforced.

Requirement: Node.js 20 or later on `PATH` (the hooks and the `crew` command run on it). Development uses Bun.

The profile may also hold the project's environment (start, health, stop, logs, url), detected from a compose file, a Laravel `artisan`, a Makefile target or a `package.json` script and proposed for the user to confirm (`crew profile set environment.<key>`, `crew profile confirm environment`); `crew env start | health | stop | status` drive it, and an environment the user already had running is never stopped by the engine. The e2e gate runs the project's end-to-end command around that environment when the change touches an interface or a public-api path, reads the browser's console (`console.json`, written by the project's test run or the crew's Playwright fixture) and the environment's logs, and fails on the first error or warning; a project without an environment yet skips the gate on the user's say. A todo whose files touch a page or a risk path is judged by the reviewers its files ask for before it counts as gated, and a policy may carry a standing grant of two rounds past each cap (team.continuations: granted) so the user is not woken at every cap. `crew workspace status` lists every project of the workspace from the records alone (live, open items, unread mail, open threads, unconfirmed priorities, environment), `crew status --json` carries the threads, the priority and the environment, and the mod shows them (the priority in the strip, the mail as threads and the workspace in the panel, `/crew workspace`, `/crew thread <id>` and `/crew brief T-n`), as the plugin's test harness proved.

A request enters in three ways (SP3): from the CLI, from a task manager the session reads through its MCP tools (ClickUp first), or from a document in the repository; `crew start --source '<json>'` records the channel, the connector and the id or the document's path, and the brief quotes the original text verbatim under `## Source`. The business priorities of a workspace are a file the user writes once and signs (`crew workspace priorities accept --file <path>`, under the user's crew directory, `workspaces/<name>/priorities.md` with the engine's signature beside it; `crew workspace priorities` says whether it is signed, changed since, unsigned or absent). A ticket's urgency is a proposal: at start the lead confirms it or lowers it with a reason against the signed priorities, never raises it, and without a signed file the proposal stays unconfirmed on record, which the status, the report and the mod's strip say.

A doubt stops the work and asks, on record (rule 7): `crew question <id> add "<text>"` records the question with the channels it was posted to (the conversation when a person is present, the questions file beside a request document, a notice to the project's own mail) and the ones left for the skill to post (the ticket, marked with `crew question <id> posted`), and holds the item for the user as `crew await` does; the answer is a person's (`crew question <id> answer Q-n "<answer>"`, refused in a session nobody watches), recorded with who and when in the item and the decision register; open questions come first in `crew status`, are counted by `crew workspace status`, listed in the report and shown first by the mod (`/crew questions`).

An issue is analysed before it is designed (rule 11): `crew analyse <id> --paths <files>` writes `analysis/origin.json` from git and the engine's own records, for each path the newest twenty commits with the lines the blame still attributes to them and the crew items whose artifacts they carried, each item summarised from the records (title, kind, roles, tasks, decisions, mail); the lead writes `analysis.md` with the origin, the cause and the blast radius, the guard out of the phase reads both, `crew status` says the analysis's size and the report lists it. Outside git the file is empty with a note and the document alone is asked.

Jev, TypeSafe's System One model, is the crew's second reader when a key is set (`WIZARDINGCODE_JEV_API_KEY`; the endpoint and the model by `crew config jev.endpoint|jev.model`, a `file://` canned transport for the tests): an upheld defect at `crew judgement record`, the validator's rule at `crew approve --validator`, a researcher's facts at `crew research <id> verify` and a source's urgency at `crew start --source` are asked as typed questions with probabilities, every answer recorded on the item (`evidence.verifications`, the report's Verifications table) and the agreement in `crew metrics`. A verdict only tightens from it: a disputed defect stays a defect and is said, a disputed validator condition refuses the approval and makes the item wait for a person, a triage is a proposal capped at the source's and never the record; Jev down is said as `unverified (jev unavailable: …)` and a full-route item waits. The policy's `verify` block says what leaves the machine (`claims` by default, no code; `claims-and-snippets` adds the cited lines), which asks are made (`verify.asks`), how many claims per item and the threshold.

## Packs

A pack is knowledge that installs apart from the core (vision §11), as data the engine serves (ADR 0010): a folder with `pack.json`, checklists for the gap round, knowledge files for the expert, a detector rule and a team template. It has no code, no agent, no hook and no skill; the crew skill reads what the engine prints for it. The two first packs live in this repository under `packs/`:

- `wizardingcode-pack-laravel`, a stack pack: its rule proposes Laravel's test, lint and type-check commands and the scoped test template, tags the target `laravel`, and the expert reads its knowledge file (verified against Laravel 13.x).
- `wizardingcode-pack-agentic-os`, a team pack: its template seats the agentic team as the expert's knowledge seat on the paths where agents, skills, prompts and hooks live.

Each pack ships with a with/without pair of eval cases that shows its difference on the same tree (the pack's gate proposed with its name and the knowledge path served; the seat and the knowledge path), run and recorded in [`docs/evals/2026-10-21-sp6-results.md`](docs/evals/2026-10-21-sp6-results.md).

Install one from the marketplace (`claude plugin install wizardingcode-pack-laravel@wizardingcode-plugins`; the engine registers it at the next session start) or from a path (`crew pack add <path>`); `crew pack list` says the state of each. A pack's gate command enters the profile as proposed and runs only once a person confirmed it in the project (`crew profile confirm <gate>`). A pack ships with the cases that show its difference against the agent without it (`plugins/core/evals`); `plugins/core/skills/crew/references/packs.md` says how one is written and measured.

## Runtimes

The method runs in Claude Code as a plugin, and in Codex CLI, Cursor, GitHub Copilot CLI, Gemini CLI and OpenCode through one table of adapters in the engine (ADR 0011): `crew hook <event> --runtime <name>` reads the runtime's payload into the engine's and writes the engine's answer in the runtime's shape, so the rules never change per runtime. Install from the release asset: extract `wizardingcode-developer-crew-<version>.tar.gz`, put the extracted `bin/` on PATH, and in the project run `crew runtime install <name>` (`--scope user` for the home); it merges crew's entries into the runtime's hook configuration (a foreign hook stays), copies the skill as `crew-method` under `.agents/skills`, generates the agents under `crew-` names in the runtime's format, prints every file written and the trust step the runtime asks for (Codex's `/hooks` review, Gemini's first-run warning). `crew runtime check <name>` reads it back: the root, one line per event, the copies by hash and the guarantee table below; `crew runtime remove <name>` is the rollback (crew's entries out of the configuration, the foreign ones and the other keys kept, crew's files gone); `crew runtime list` prints the table. Where the table says a filing is requested, the session files a role's answer with `crew answer file <id> --role <role> --file <path>` and the record says so.

**Testing on another runtime.** The sessions on Codex CLI, Cursor, Gemini CLI and OpenCode are run by outside testers (the user's decision of 2026-10-21, [real use](docs/real-use/README.md)). To test one: install the release asset as above, with Node.js 20 or later on PATH (`crew --version` prints what you installed); in a git repository of your own run `crew runtime install <name>` and `crew runtime check <name>` (every line `ok`, then the guarantee table); open the runtime in that repository and ask it for a small change. The first session runs `crew detect` and takes the change through the method; the turn cannot end while the change is unproven; and on every runtime but Claude Code an ask becomes a deny, so a person-only command (`crew profile confirm`, `crew approve`, `crew policy set`) is run by you in a shell. What the runtime does not enforce is in its table below. Report what you see through the repository's issues with the runtime report template (`.github/ISSUE_TEMPLATE/runtime-report.yml`; https://github.com/WizardingCode-io/wizardingcode-developer-crew/issues/new?template=runtime-report.yml): the runtime and its version, `crew --version`, the output of `crew runtime check <name>`, the command or prompt, what happened and what you expected, and the hook's answer or a log when you have it. Each report is a finding of the real-use phase.

## Benchmark

`bun scripts/benchmark.ts` runs the cases tagged `benchmark` (the set and its categories, functional, security and cost, in `plugins/core/evals/benchmark.json`) through the eval kit as the whole suite runs, with the plugin and without it, and writes `docs/benchmark/<date>-<version>.md` and `.json` from the kit's aggregate result alone: no figure is typed by hand. It needs Claude Code with the eval kit and a key in the environment; the cost of a run is what the newest record under `docs/benchmark/` says, and the first record is written at the close of the subproject that added the benchmark. `bun scripts/benchmark.ts --from <aggregate.json>` writes the report from a saved result. `docs/benchmark/README.md` says what the benchmark measures, how a record is read and what it does not measure.

## Where state lives

- **`.crew/` in the repository.** Crew is active in a git repository, or in a folder that already holds `.crew/` (`crew detect` creates it); anywhere else it stays silent.
  - `profile.json`: the detected project profile and gate commands.
  - `policy.json` (optional): the team policy, written by a person. `unattendedDecisions` (`wait`, the default, `count`, or `validator`) says what a user-only decision taken with no person watching is worth: nothing until a person decides, the agent's own word, or the validator's decision under a rule (a spec approval with a complete gap round, a decision's stated default); the validator never waives an objection or skips a gate. `riskPathExclusions` lists globs of paths that never raise the route (ADR 0003); the report names them when they applied, and `crew policy set riskPathExclusions "<glob>"` adds one glob (`--remove` takes it out), a user-only command asked even under `relay` and recorded in the decision register. `attendedDecisions` (`relay`, the default, or `prompt`) says how the user signs a decision with a person present: the agent relaying the user's yes from the conversation with no prompt, recorded everywhere as "by the user, relayed by the agent", or the permission prompt the agent's command raises (ADR 0005). `allowSkips` (`["tdd"]` by default) lists what may be skipped: gates are mandatory unless a person names one here. `crew policy set <key> <value>` writes `attendedDecisions` and `unattendedDecisions` through the engine; it is asked even under `relay`.
  - `work/<id>/`: one folder per work item, with `work.json` (state, including the gap round's decisions), `brief.md`, `spec.md`, `conclave.md` (the gap round's four lists, written by the agent and checked for structure), `plan.md`, `objections.json` (the objection ledger, engine-owned), `evidence.json` (test-first records and gate runs), `report.md` (the delivery report), `logs/` (full command output, ignored), `review/` (the diff and the files the gate run cut for the reviewers with the fingerprint they describe, their findings, the judge's ruling; the session's to write; `review/ui/` captures are ignored by the engine's `.gitignore`) and `conclave/` (the debate's research, proposals, objections and ruling; the session's to write).
  - `local/`: per-machine state such as the session baselines (ignored).
- **`~/.wizardingcode/crew/` for the user**: `config.json` (mode and settings) and `integrity/`, the hashes the engine uses to notice state changed outside it.

## Install

```sh
claude plugin marketplace add WizardingCode-io/wizardingcode-plugins
claude plugin install wizardingcode-developer-crew@wizardingcode-plugins
```

Open a session inside a git repository and ask for a code change; the crew skill takes it from there. `crew status` shows where the work stands. The marketplace points at a released version; `claude plugin update wizardingcode-developer-crew` moves to the next one.

The harness improves by itself ([ADR 0015](docs/adr/0015-the-loop-runs-always-and-releases-what-it-proves.md)): a launchd agent on the maintainer's Mac (`bun scripts/improve-loop.ts install`) runs the improvement loop every hour when there is something new or a case unmeasured for a week, has the judge validate a kept harness, and releases it as a patch when every gate passes, so each release carries the best proven harness; the records are under [`docs/improve/`](docs/improve/README.md).

## Develop

```bash
bun install && bun run build
claude --plugin-dir ./plugins/core      # loads the plugin for one session, instead of the installed one
bun run plugin:check      # validate --strict and the mod tests
```

Development note: `bun run check` runs the engine tests under `packages/`; the mod's tests need the plugin runtime and run only through `bun run plugin:check`.

## What is next

The eval suite (`plugins/core/evals/`) measures the method on fixture projects against plain Claude Code. Its first runs are recorded in [`docs/evals/2026-10-12-sp1b-results.md`](docs/evals/2026-10-12-sp1b-results.md): every case passes with the plugin, including the one that stops at the spec approval the full route reserves for the user, and a trivial fix on the fast route costs about 1.7–1.9× the baseline after the fast route was cut to three calls, from 2.3× on the first run. The 1.2× the design hoped for is below the floor of a method that records red, green and the gates; the record says what is left to take out.

Release 0.7.0 (2026-10-18) is SP7b, the environment, the priorities and the visibility of a workspace ([design](docs/specs/2026-10-17-sp7-teams-agents-workflows-and-rules-design.md), [plan](docs/plans/2026-10-18-sp7b-environment-priorities-visibility.md), [ADR 0008](docs/adr/0008-everything-before-the-next-real-use.md)). A message carries a priority the receiver confirms or lowers on record with its reason and never raises (`crew mail accept <id> [--priority <p>] --reason`), an item takes its origin's confirmed priority, and a message's status moves along one table the engine alone drives (sent, read, accepted or refused, in progress, blocked, done, expired). Threads hold up to four parties (`crew mail send --thread`, `crew mail thread`), and a reply to a change request may carry contracts the engine checks at the branch's tip before anything is recorded (an openapi or schema file that parses, a types file in the child's diff, a clause in the body) with the file's hash, together with the child's evidence; the todo's brief lists the contracts received and a criterion binds to one (`crew criteria <id> add --contract`). The profile holds the project's environment (start, health, stop, logs, url, timeout), detected from a compose file, a Laravel `artisan`, a Makefile target or a `package.json` script and confirmed key by key; `crew env start|health|stop|status` runs it, with the process the engine started recorded by pid and start time, never stopping what the user had running. The e2e gate is planned once per item when the change touches an interface or a public-api path (or the policy requires it) and runs around the environment: the project's end-to-end command with the artifact folder and the console file named in its variables (`plugins/core/e2e/playwright.mjs` records the console for Playwright), the console and the logs graded as data with the first offence named, the captures listed for the UI/UX review, the stop command run whenever the profile has one; `gate:e2e` is the one gate skip the default policy allows. A todo's gate plans the judgement its files ask for (UI/UX for interface files, security for a risk path), cuts the todo's inputs under `review/T-n/` and records each ruling with `--task`, so a todo is gated only when every planned judgement is proven on the current code; `team.continuations: granted` is a standing grant of rounds past a cap, up to the cap plus two, each recorded as the user's. The review folder is the engine's except `ui/` and `e2e/`; a here-document is read as commands unless a listed reader takes it through a clean pipe chain (finding 67). `crew workspace status` lists every project of the workspace from the records alone (live, open items, unread mail, open threads, unconfirmed priorities, the environment's record), `crew status --json` carries the threads, the priority and the environment, and the mod shows the priority in the strip, the mail as threads and the workspace in the panel (`/crew workspace`, `/crew thread <id>`, `/crew brief T-n`). Four eval cases join the suite under the `environment`, `priority` and `contracts` tags, none needing an opener, recorded in [`docs/evals/2026-10-18-sp7b-results.md`](docs/evals/2026-10-18-sp7b-results.md). By ADR 0008 the next real use waits for SP3, SP8, SP4 and SP6 (0.8.0 to 0.11.0); the debt this release carries is in [findings 67 to 81](docs/real-use/findings.md).

Release 0.11.1 (2026-10-21) is the release asset the outside testers of the other runtimes install, cut from the first days of the real-use phase: the skill page's front matter made strict YAML, since Codex CLI, Cursor, GitHub Copilot CLI, Gemini CLI and OpenCode read `.agents/skills/crew-method/SKILL.md` with a strict parser and dropped it with the unquoted description of 0.11.0 ([finding 121](docs/real-use/findings.md)); `crew policy set riskPathExclusions "<glob>"` and `--remove`, the one loosening of ADR 0003 written by the command, recorded as the user's decision before the file is written and refusing a glob with no literal character ([finding 120](docs/real-use/findings.md)); the runtime report template under `.github/ISSUE_TEMPLATE` and the "Testing on another runtime" paragraph above. The engine's rules, the hooks and the packs are those of 0.11.0; the packs move to 0.11.1 with the core bound.

Release 0.11.2 (2026-10-22) carries the hardening of the real-use phase's first days to the same testers, by ADR 0004's rule for a `blocks` or `false-proof` fix ([findings 119 and 122 to 130](docs/real-use/findings.md)): the report lists every pause under `## Waits` and the shared checkout's paths as a count under `## Checkout`; a role's answer already on disk is archived, never overwritten, and a lead's file already recorded is refused; a skill page's front matter that is not strict YAML is refused at `crew runtime install` and named at `crew runtime check`; where nobody watches, a policy command is denied with the person's way to change it; `crew abandon <id> --reason` closes an item the user drops; `crew criteria supersede AC-n --by AC-m` retires a recorded criterion for one of equal or stronger proof; `crew tdd red` refuses a run that ran no test; the report's knowledge line names a pack's files as `<pack>:<path>`; the eval and benchmark scripts take their results folder from `WIZARDINGCODE_CREW_EVAL_RESULTS`. The packs' content is that of 0.11.1; the packs move to 0.11.2 with the core bound.

Release 0.11.0 (2026-10-21) is SP6, packs, runtime adapters and the public benchmark ([plan](docs/plans/2026-10-20-sp6-packs-adapters-and-benchmark.md), [ADR 0010](docs/adr/0010-packs-as-data-served-by-the-engine.md), [ADR 0011](docs/adr/0011-runtime-adapters.md)), opened by the hardening of SP4's debt (findings 104 to 109: a validation round counted per lead and per revision read, a resumed role's reply filed as one document, a knowledge ref's item nullable, the hook's shell rule reading the engine-owned work files from one list). A pack is data the engine serves and never code: a folder with `pack.json`, checklists the gap round reads, knowledge files the expert reads, a detector rule that refines a core target's gates as proposed commands a person confirms, and a team template that adds path globs to a team and nothing else; `crew pack add|remove|list|show|files|sync` register it per machine under the crew home after a check of its shape, its core range, its files, its secrets and its template, and a marketplace-installed pack is discovered at session start. The first two ship from this repository: `wizardingcode-pack-laravel` (a stack pack: `php artisan test`, Pint and Larastan proposed on a tree with `artisan`, three checklists, one knowledge file) and `wizardingcode-pack-agentic-os` (a team pack: the `agentic-os` seat on `agents/**`, `skills/**`, `prompts/**`, `hooks/**`, `**/*.prompt.md` and `.claude/**`, with the policy's `team.template` and `team.specialists`); a pack's seat is planned from the change's paths before the watch's exclusions, so an agent's Markdown seats it, and the gate run keeps the seat for the report. The runtime adapters are one table in the engine for Claude Code, Codex, Cursor, Copilot, Gemini and OpenCode: `crew hook <event> --runtime <name>` reads each runtime's payload and writes its answer in the runtime's shape, `crew runtime install|remove|check <name>` writes the skill, the agents and the merged hook configuration and prints the guarantee table (enforced where the runtime documents the mechanism, requested elsewhere), `crew answer file` files a role's answer where no subagent hook exists, and the plugin folder is the distribution for the runtimes that are not Claude Code (`bun scripts/build.ts --tarball`, the release asset). The public benchmark is a tag on eighteen cases with a category each (functional, security, cost; `plugins/core/evals/benchmark.json`) and `bun scripts/benchmark.ts`, which runs the set through the eval kit with the plugin and without it and writes `docs/benchmark/<date>-<version>.md` and `.json` from the kit's aggregate alone, whatever the kit's exit status, refusing a run the runner flags `needs-rerun`; the first record is [`docs/benchmark/2026-10-21-0.11.0.md`](docs/benchmark/2026-10-21-0.11.0.md). Four eval cases join the suite under the `packs` tag, two with/without pairs that show each pack's difference on a tree without PHP (a shim runs the fixture's `artisan`), recorded in [`docs/evals/2026-10-21-sp6-results.md`](docs/evals/2026-10-21-sp6-results.md); the debt this release carries is in [findings 110 to 118](docs/real-use/findings.md). The real-use phase of ADR 0008 runs next, on everything at once ([real use](docs/real-use/README.md), the phase after 0.11.0).

Release 0.10.0 (2026-10-20) is SP4, the knowledge base, the learning and the CTO ([design](docs/specs/2026-10-17-sp7-teams-agents-workflows-and-rules-design.md) §6.5, §12, §15, §16 and §18, [plan](docs/plans/2026-10-19-sp4-knowledge-base-learning-and-cto.md), [ADR 0009](docs/adr/0009-knowledge-base-store.md)), opened by the hardening of SP8's debt (findings 98 to 103: one table of shells, wrappers and valued options for the test-first rule and the hook, `crew audit run --only` refused when HEAD moved, the audit's filed lines named apart, the PDF's timeout as a type). The base is one protected JSON file under `~/.wizardingcode/crew/knowledge/`, written by the engine alone under a lock, with five kinds of entry (a stack preference, a validated solution, a documentation entry, a root cause, a general note), each with its origin workspace and a confidentiality mark: an unmarked entry is read everywhere, a marked one inside its workspace alone, every entry enters marked, and only a person removes a mark (`crew knowledge unmark`; rule 13). A person adds material with `crew knowledge add` (from the project's own tree, through the secrets scanner) and disputes an entry with `crew knowledge contradict`. The lookup is deterministic (paths, stacks and the request's words, a reason per hit, visibility first); Jev reorders the hits and marks them, never dropping one. At Recognize the engine looks the base up for the request and writes `knowledge.md` with the hits, the status and the report say what was listed, and a strategy cites an entry as `[K:<id>]`. After Deliver comes Learn: `crew learn <id>` enters the proven item's solution, an issue's root cause, the research's facts that carry a source and the workspace's stack preference, every text scanned first, confirms the entries the item cited and tells the workspace's other projects; a root cause the base already holds is refused unless confirmed (rule 17). On the issue side, `crew analyse` names the base's root causes on the origin's paths and the guard out of Analyse refuses the next phase until each is cited in `analysis.md` with what the fix does differently or contradicted on record. The CTO reads the records: `crew cto review --workspace <ws>` writes its inputs (the workspace's metrics, the last plan, the base's figures and rows) and `crew cto record` files the plan and enters it in the base, marked; `crew metrics` carries the knowledge figures and the report links the latest plan. Three eval cases prove it in the sandbox: a marked entry of another workspace is never reused, a known root cause is named before the fix, and the CTO's plan comes from the records ([evals record](docs/evals/2026-10-20-sp4-results.md)).

Release 0.9.0 (2026-10-19) is SP8, the strategy stage and the audit ([design](docs/specs/2026-10-17-sp7-teams-agents-workflows-and-rules-design.md) §6.2, §7.1, §7.3, §7.5, §13 and §15, [plan](docs/plans/2026-10-19-sp8-strategy-and-audit.md)), opened by the hardening of SP3's debt (findings 82 to 97: a shell with more words after `-c` refused before any run, a Jev dispute held until a person clears it, `crew profile unset`, the help lines, the eval runner's `needs-rerun`). The kinds and the phases grow: `audit` is a kind of work with its own four phases on every route (`receive`, `recognize`, `audit`, `deliver`), always full, with no criterion and no build; `strategy` sits between `understand` and `specify` for a new project, and a feature the conclave finds to be a project is raised to one with `crew kind <id> raise`. A new project's strategy is a document the engine checks and the judge rules before the spec: five sections (Viability, Cost, Time, Stack, Scaling phases), every claim ending in a mark on a fact line of the researcher's file, no knowledge mark until SP4, a scaling table with at least one trigger; `crew strategy <id> check` writes the review inputs and names the reviewer (the CTO on the full route, the judge alone on standard), the ruling is recorded through `crew judgement` stamped with the hash of the two files and goes stale when either changes, and the guard out of the phase needs it proven on the current hash. An existing codebase is audited end to end: `crew audit <id> run` runs the project's own build, test, lint, typecheck and dependency audit over the whole tree with no baseline through the gate runner, scans the tree for secrets, records every result (a failure as a `fail` run with its log, never a block, e2e as unavailable), lists the files the roles read and the scope with its risk areas, and refuses a tree over the walk's cap with nothing recorded; the seats follow the scope (the researcher on the dependencies, security, architecture, code quality, test quality, data or infra by the risk areas), the hook files their findings under `audit/`, and `crew audit <id> report` parses them, checks every finding's proof (a file and a line that exist inside the root, or a log inside the item's logs; the rest left out and named), computes the verdict (`critical`, `attention`, `sound`) and renders the report in Markdown, in one inert HTML page under the brand (the lockup and the mark shipped with the plugin under their licence note, every value escaped, every log tail and finding text through the secrets scanner) and as a PDF by the project's own Playwright or a browser on the machine, or says why not; a person signs it (`crew approve <id> audit`, never unattended, never on a stale report) and the three formats carry the signature. The fast route's cost is measured again on what the fast route is for, a one-spot chore at 2.03×, and the issue's cost on its own case at 3.5× (finding 93), the ceilings read per case by `scripts/eval-overhead.ts`. Five eval cases join or change in the suite under the `strategy`, `audit` and `cost` tags, recorded in [`docs/evals/2026-10-19-sp8-results.md`](docs/evals/2026-10-19-sp8-results.md); the debt this release carries is in [findings 98 to 102](docs/real-use/findings.md).

Release 0.8.0 (2026-10-19) is SP3, reception, triage, issues and Jev ([design](docs/specs/2026-10-17-sp7-teams-agents-workflows-and-rules-design.md) §7.1, §7.2, §7.4, §10 and §11, [plan](docs/plans/2026-10-19-sp3-reception-triage-issues-and-jev.md)), opened by the hardening of SP7b's debt (findings 73 to 81). The kind of work is data: `crew start` records it from the typed answers, `phasesFor` gives each kind its phases, and an issue (a fix) walks through `analyse` first. A request has a source: a ticket read from a task manager through the session's tools or a document in the repository (`crew start --source`), quoted verbatim in the brief under its own section, its proposed priority triaged against the business priorities the user wrote once and signed (`crew workspace priorities accept`), confirmed or lowered with a reason on record and never raised. A doubt stops the work: `crew question <id> add` posts it to the channels the policy names (the cli when a person is present, the ticket, a questions file beside the document, the project's mailbox), the item waits, and `crew question answer` records who answered and how; `crew status` lists open questions first. An issue is analysed before it is fixed: `crew analyse <id> --paths` writes the origin from git and the records (the commits that still hold the lines at HEAD and the items whose artifacts they carried), `analysis.md` names the cause and the blast radius, and a regression test with a preserve baseline are the guard before build. Jev, TypeSafe's System One model, verifies four things when configured (an upheld defect at the judgement record, the validator's rule at the approval, a researcher's facts, a source's triage), each answer recorded with its confidence and the model that gave it, with a canned `file://` transport for the tests and the evals; a verdict only tightens: a disputed defect stays a defect, a disputed validator condition makes the approval wait for a person, a triage proposal is capped at the source's, and Jev down marks unverified and makes a full-route item wait. The skill page names the source on every route. Four eval cases join the suite under the `reception`, `jev` and `issue` tags, recorded in [`docs/evals/2026-10-19-sp3-results.md`](docs/evals/2026-10-19-sp3-results.md); the debt this release carries is in [findings 82 to 93](docs/real-use/findings.md).

Release 0.6.0 (2026-10-18) is SP7a, the team and the tech lead ([design](docs/specs/2026-10-17-sp7-teams-agents-workflows-and-rules-design.md), [plan](docs/plans/2026-10-17-sp7a-teams-and-tech-lead.md), [ADR 0007](docs/adr/0007-teams-first-roadmap-re-cut.md)). The engine has a registry of nine teams and plans every seat of an item from its route, its risk areas and its paths before anything runs (`crew team <id>`): nothing on the fast route; tech leads, researcher, QA, security and the judge on standard; everything on full. Three reviewers join (architecture, data, infra) and five personalities give the debate's experts different lenses, recorded in the evidence. A tech lead per mandatory team validates the spec before the plan and the delivery before the report, with returns tied to a file and a line (`crew validation <id> record`); a contradiction is refused, a changed spec makes a validation stale. Rounds are bounded by the policy's `team` block and refused past the cap: two judgement rounds, two validation rounds, two gate rounds per todo, one more only by the user (`crew continue`). Each todo of the plan ends with its own gate on the files it touched (`crew task <id> gate T-n`, the test command narrowed where the profile knows how, each file one quoted shell word) and a brief (`crew task <id> brief T-n`). Every decision of a project lands in `.crew/decisions.json` and is read in Understand (`crew decisions`). `crew metrics` counts items, rounds, tokens per role and personality, defects per reviewer and minutes per phase; `crew cto record` files the CTO's plan per workspace. The mod shows the team, the todo with its checks, the roles working and the branch (`/crew todo`, `/crew team`). The twenty rules of the organization are in `references/rules.md`, each with what enforces it today. Six eval cases join the suite under the `team` tag, recorded in [`docs/evals/2026-10-18-sp7a-results.md`](docs/evals/2026-10-18-sp7a-results.md). The real use of this release (three workspaces, ten items) is the exit to SP7b ([real use](docs/real-use/README.md)); the debt it carries is in [findings 48 to 65](docs/real-use/findings.md).

Release 0.5.0 (2026-10-17) is SP2c, mail between agents inside a workspace and the team of an item ([design](docs/specs/2026-10-15-sp2c-mail-evals-and-hardening-design.md), [plan](docs/plans/2026-10-15-sp2c-mail-evals-and-hardening.md)). The engine is a local mailbox between the agents, items and projects of one workspace (`policy.json` `mail.workspace`, declared per project; mail never leaves it): four message types, a receiving policy applied as refusals, an inbox and an outbox per project under `~/.wizardingcode/crew`, a copy in the item's `mail.json` and a Mail section in the report. When no session is live at the destination the engine opens a bounded one there: read-only for a question, on a branch for a change request the policy allows, with the tools the method needs, never merging or deploying, listed and stoppable with `crew mail status|stop`. A task of a plan goes to an implementer in a worktree on its own branch (`crew task <id> open|list|merge`), runs the method as its own item and comes back as a reply the lead merges; the merge credits the child's proof to the parent's criteria. A turn may end waiting for the user, for the roles or for a reply (`crew await <id> user|role|mail`); the SubagentStop hook records each role's answer and tokens. The mod shows unread mail, the inbox and the tasks. Eleven eval cases join the suite (the eight of the SP2 design and three for mail), recorded in [`docs/evals/2026-10-17-sp2c-results.md`](docs/evals/2026-10-17-sp2c-results.md) with the sandbox run, the end-to-end mail run and what they found ([findings 33 to 43](docs/real-use/findings.md)); four of those are fixed in this release: a project with no detected target is no longer proven by the secrets gate alone, liveness comes from a session's hooks and not from any command, and a branch session gets the grants it needs. 0.5.1 (2026-10-17) closes four more of those findings: the SubagentStop hook finds the judge's JSON inside an answer that explains around it, a merged task's worktree goes when only the engine's own files are dirty in it, the gap round asks whether a redirect's target exists in the repository before assuming, and the skill page is back to its 0.4.0 size with the fast-route overhead measured at 2.03×, the method's floor at this context (six model requests against the baseline's three, plus the plugin's fixed context).

Release 0.4.0 (2026-10-15) is SP2b, the roles and the judgement gates ([plan](docs/plans/2026-10-14-sp2b-roles-and-judgement-gates.md)). Ten subagents with clean contexts and read-only tools under `plugins/core/agents/`: the judge (fable), five reviewers (sonnet, opus on the full route or a risk area) and the four debate roles (opus). The engine plans the judgement gates from the route, the risk areas and the diff (code and test quality on standard and full, security on full or a risk area, UI/UX when interface files change, risk on full, plus the team policy's `judgementGates`), cuts the item's change for the reviewers into `.crew/work/<id>/review/` and prints what will run; the judge's ruling is recorded with `crew judgement <id> record --ruling`, validated, stamped with the code it judged and refused when the review inputs describe other code; a planned gate is proven, not proven with findings tied to a file and line, or not run with a reason, never passed by default, and a finding outside the change is debt, named and never a failure (ADR 0006). The gap round reads a checklist per kind of change (`skills/crew/checklists/`), the debate is recorded (`crew debate open|close`) and holds the plan while open, and the panel shows the decisions, the objections and the judgement gates. An item in flight across the upgrade on the standard or full route becomes not proven until its judgement gates run.

Release 0.3.0 (2026-10-14) is the experience release, built the evening the user said a decision is theirs in words and that gates are never skipped ([findings 20, 22 and 23](docs/real-use/findings.md)). Decisions reach the user only when they exist, in one message with the why, the facts and the evidence, and their positive word is the signature: the team policy's `attendedDecisions` defaults to `relay` ([ADR 0005](docs/adr/0005-attended-decisions-by-relay.md), amended), and a spec with nothing pending is approved under the `complete-gap-round` rule with a person present, so a full-route item asks nothing unless the gap round found a decision. Gates are mandatory (`allowSkips` defaults to `tdd`) and judge the item, not the repository's debt ([ADR 0006](docs/adr/0006-gates-judge-the-item.md)): the dependency audit runs in JSON and is compared with the item's base commit, so only new advisories fail and the known ones are counted on every report; an abandoned package never fails `composer audit`; lint and typecheck fail only on problems in files the item changed, the rest is named as debt. The profile follows the manifests at every gate run and session start, detection reads the `test:*` convention (`test:lint` is the lint gate, `test:types` the typecheck, the rest the test gate) and `bun test`, and `crew profile set` sets and confirms in one step. The stamp the evidence vouches for is taken after the build gate, so a build that rewrites a committed bundle proves in one run (finding 18); the test gate has twenty minutes by default and any gate its own `--timeout`.

Release 0.2.0 (2026-10-14) is the engine side of the conclave, the first half of SP2 ([SP2 design](docs/specs/2026-10-14-sp2-conclave-and-judgement-gates-design.md), [SP2a plan](docs/plans/2026-10-14-sp2a-conclave-in-the-engine.md)): a `conclave` phase between Specify and Plan on the standard and full routes, guarded by a `conclave.md` with the gap round's four lists; decisions only the user can make, recorded with `crew decision add` and answered with `crew decide`, without which there is no plan; an objection ledger (`objections.json`, engine-owned, `crew objection add|resolve|waive`) where a blocking objection left open keeps the item unproven and the report names who waived; the `observed` criterion kind for a behaviour proved by a passing run and a stated reason; and a validator that, with no person watching, approves a spec under the `complete-gap-round` rule the engine checks and takes a decision's stated default, counting only under `unattendedDecisions: validator`. From the same days: a flag before a user-only verb no longer dodges the prompt ([finding 21](docs/real-use/findings.md)); the Stop hook blocks a turn that tells the user to type a crew command ([finding 22](docs/real-use/findings.md)); and the team policy may say `attendedDecisions: relay`, under which the agent runs a user-only command with no prompt once the user has said yes and every line of the record says "by the user, relayed by the agent" ([ADR 0005](docs/adr/0005-attended-decisions-by-relay.md)), set once per repository with `crew policy set attendedDecisions relay`.

Release 0.1.7 (2026-10-14) closes the real-use phase's open findings in one go ([findings 1, 7, 9 and 14](docs/real-use/findings.md)): `crew start` takes `--preserve "<text>"` beside `--criterion`, so the fast route can say that existing tests stay green, and every command refuses a flag it does not know instead of ignoring it; `start` warns and records it when another item is still being worked on in the same checkout with uncommitted changes, and says to use a worktree; the team policy's `riskPathExclusions` keeps named paths out of the risk patterns, the one way a policy loosens a default, written down in [ADR 0003](docs/adr/0003-risk-path-exclusions.md) and named in the report when it applied; and a gate run that proves an item already in its gate phase delivers it, so the second run after a build gate rewrote the bundle no longer leaves the item one phase short.

Release 0.1.6 (2026-10-14) puts the user's signature back where it belongs ([findings 3 and 19](docs/real-use/findings.md)): auto mode shows the prompt a hook asks for, so a user-only decision (an approval, a skip, a confirmation) is asked there as in default mode and the user answers yes or no; the agent runs the command and never asks the user to type it. Only a headless session (`claude -p`, in any mode) or bypassPermissions and dontAsk mode take the `--mode` path, where the record says the agent decided. `crew gate run` exits non-zero while the work is not proven, so a command chain stops there (finding 18).

Release 0.1.5 (2026-10-14) answers the first two days of real use on two client projects ([findings 8 to 17](docs/real-use/findings.md)): a folder with two manifests (a Laravel app with a `package.json` beside it) has one target per manifest, keyed by path and stack, and every target's gates run and are reported under their own name, where before the second target's commands never ran (`crew profile set --stack` names one); the dependency audit runs on every route when the change touches a manifest or a lockfile, not on every item ([ADR 0002](docs/adr/0002-dependency-audit-on-dependency-changes.md)); a watch list left by an earlier release follows the current default by itself at session start; a Node project with several lockfiles and no `packageManager` field gets proposed commands to confirm instead of a guess; the hook takes a user-only `crew` verb for the command only at the command position, so a `grep` that quotes it is not stopped; and the Stop block names `crew await` as the way to end a turn with a question.

Release 0.1.1 (2026-10-12) closed what SP1 left open: a workspace member package is covered by the package that lists it, so a monorepo (this repository included) can be proven; `.claude/**` is unwatched by default; a new work item starts from the previous item's proven state instead of inheriting its uncommitted files; a read of an engine file with stderr silenced is no longer denied; `bun scripts/eval.ts` runs the eval suite; and the interactive check of the mod found and fixed `/crew` being taken by the plugin's own skill ([record](docs/plans/2026-10-07-sp1a-e2e-results.md), "Interactive check"). After upgrading, run `crew detect --refresh` once in each repository: a profile written by 0.1.0 keeps its watch list and knows no workspaces until it is re-detected, and the session start says so.
