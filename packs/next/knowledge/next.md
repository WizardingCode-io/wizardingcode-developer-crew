# Next.js 16.x

What a model trained on Next.js 15 or earlier gets wrong in Next.js 16, how work in it is verified and where the documentation is. Each line is a fact read on 2026-10-28 from the pages listed at the end; nothing here is a tutorial.

## What the model gets wrong

- Two routers: `app/` is the App Router and `pages/` the Pages Router, and both may sit in one project (under `src/` when the project keeps its code there). The App Router runs on React's canary builds, with React 19.2's features; the Pages Router uses the React version `package.json` declares. The documentation's new-app defaults are TypeScript, ESLint, Tailwind CSS, the App Router, Cache Components, Turbopack and the `@/*` alias.
- The project's files: `next.config.js`, `next.config.mjs` or `next.config.ts` (the `.cjs` and `.cts` forms are not supported; `next.config.ts` imports `NextConfig` from `next`; a function form receives the `phase`); `proxy.ts` at the root or under `src/`; `instrumentation.ts`; `eslint.config.mjs`; `tsconfig.json`, with `next-env.d.ts` generated by `next dev`, `next build` or `next typegen`, never edited and kept out of git; `public/` for static files; `.env`, `.env.local`, `.env.development`, `.env.production`.
- The App Router's routing files: `layout`, `page`, `loading`, `not-found`, `error`, `global-error`, `route`, `template` and `default`, rendered in the order layout, template, error, loading, not-found, page; a folder is a URL segment and becomes public only with a `page` or `route` file; `[slug]`, `[...slug]` and `[[...slug]]` are the dynamic segments; `(group)` folders leave the URL, `_folder` folders leave routing, `@slot` folders are parallel routes and `(.)`, `(..)`, `(..)(..)` and `(...)` prefixes intercept; in 16 every parallel route slot needs a `default.js`, or the build fails. The root layout is required and holds `<html>` and `<body>`.
- Server and client components: layouts and pages are Server Components by default; `'use client'` at the top of a file declares the boundary, and every module it imports and every component it renders directly joins the client bundle, while a Server Component passed as `children` or another prop is rendered on the server and arrives as rendered output. Server Components render to the RSC payload; Client Components are prerendered to HTML and hydrated. Props crossing to a Client Component must be serialisable. React context is not available in a Server Component, so a provider is a Client Component wrapping `children`; a third-party component that uses client features is wrapped in a file with `'use client'`; the `server-only` and `client-only` imports make a wrong-side import a build error; only `NEXT_PUBLIC_` variables reach the client bundle, the rest are replaced by an empty string.
- The request-time APIs are asynchronous with no synchronous access in 16: `cookies()`, `headers()` and `draftMode()` return promises, `params` and `searchParams` of `page`, `layout`, `route`, `default` and the metadata image files are promises (a Client Component reads them with React's `use`), the `id` of a generated image or sitemap is a promise; the 15.x synchronous compatibility is gone, and the `next-async-request-api` codemod migrates. `next typegen` (also run by `next dev` and `next build`) writes the global helpers `PageProps<'/blog/[slug]'>`, `LayoutProps` and `RouteContext`. `searchParams` is a plain object, not `URLSearchParams`, and reading it opts the page into dynamic rendering. `cookies().set` and `.delete` run only in a Server Function or a Route Handler, never while a Server Component renders, and never after streaming starts.
- Caching under Cache Components: `cacheComponents: true` with `partialPrefetching: true` in the config (the create-next-app default; the first alone logs a warning) replaces `experimental.ppr`, `experimental.dynamicIO` and `experimental.useCache`, requires the Node.js runtime and refuses the `runtime` segment config. Data fetching is dynamic by default; `use cache` at the top of a file, a component or a function (each async) caches its return value, with the cache key made of the build id, the function id and the serialisable arguments and closed-over values; `cookies()`, `headers()` and `searchParams` cannot be read inside a cached scope (read outside and pass the value), `children` and Server Actions pass through uninspected, `React.cache` is isolated. `cacheLife` sets the lifetime (the implicit `default` profile is stale 5 minutes, revalidate 15 minutes, never expiring; the client router keeps a minimum stale time of 30 seconds), `cacheTag` names an entry, `revalidateTag` now takes a profile as a required second argument (`revalidateTag('posts', 'max')`), `updateTag` expires and refreshes within a Server Action, `refresh` refreshes the client router from one; `unstable_cacheLife` and `unstable_cacheTag` lost their prefix. Uncached data and runtime reads sit inside `<Suspense>` so the route keeps a static shell (Partial Prerendering is the default behaviour), `connection()` defers a random value or a timestamp to request time, and the dev overlay names a blocking read. The default store is in-memory and ephemeral on serverless; `use cache: remote` goes to a cache handler, `use cache: private` keeps runtime-dependent results in the browser; no entry survives a new deploy.
- `middleware.ts` is `proxy.ts`: the file exports `proxy` (named or default, one per file), runs on the Node.js runtime with no `runtime` option, takes `NextRequest` and `NextFetchEvent`, and keeps `config.matcher` (strings, `path-to-regexp` patterns, `has` and `missing` conditions); without a matcher it runs on every request, static files included. It runs after `headers` and `redirects` of the config and before `beforeFiles` rewrites and the filesystem routes; Server Function calls are POSTs to their route, so a matcher that skips the path skips them too. `skipMiddlewareUrlNormalize` is `skipProxyUrlNormalize`; the `middleware-to-proxy` codemod renames both the file and the function; the `edge` runtime stays with `middleware` alone.
- Turbopack is the default bundler of `next dev` and `next build` (the `--turbopack` flag is no longer needed; `--webpack` opts out); the `experimental.turbopack` block is the top-level `turbopack` key (`rules`, `resolveAlias`, `resolveExtensions`, `root`); a custom `webpack` config fails `next build` unless `--turbopack` or `--webpack` says which; Turbopack does no type checking, uses Babel when a config file exists, keeps a file-system cache for dev and build, writes dev output to `.next/dev` so `next dev` and `next build` run side by side, and a lockfile stops two servers on one project; webpack plugins, Yarn PnP, `sassOptions.functions` and the legacy `~` Sass import are not supported.
- `next/image` in 16: `images.qualities` defaults to `[75]` (a `quality` outside the list is coerced to the closest one and an unlisted `q` returns 400), `images.minimumCacheTTL` to 14400 seconds (four hours), `images.imageSizes` no longer holds 16, `images.maximumRedirects` to 3; a local image with a query string needs `images.localPatterns.search`; a local IP source needs `images.dangerouslyAllowLocalIP`; `images.domains` is deprecated for `images.remotePatterns`; `next/legacy/image` is deprecated; `preload` replaces the deprecated `priority` prop. `src`, `width` and `height` (or `fill`) and `alt` stay required.
- `next/font`: `next/font/google` and `next/font/local` self-host the files at build time, with no request from the browser to Google; `display` defaults to `swap`, `preload` to `true`, `subsets` are preloaded when `preload` is on, `weight` is required for a font that is not variable, `variable` names a CSS custom property used with Tailwind's `@theme inline`, and a definitions file exports each font once; `@next/font` was renamed `next/font` in 13.2.
- React 19.2 in the App Router: `<ViewTransition>` from `react` animates an element only when its update runs inside a Transition (`startTransition`, a Suspense reveal, `useDeferredValue`), chooses `enter`, `exit`, `update` or `share` itself, maps each to a class under the browser's `::view-transition-old` and `::view-transition-new` pseudo-elements, takes `addTransitionType` to pick a class per navigation, calls `startViewTransition` itself and does nothing for `prefers-reduced-motion` on its own; `useEffectEvent` and `<Activity>` ship with it; the React Compiler is stable through `reactCompiler: true`, off by default. The stack's transitions and `motion/react` are the frontend pack's `knowledge/motion.md`.
- Gone in 16: `next lint` and the `eslint` key of the config (`next build` runs no linter); `serverRuntimeConfig` and `publicRuntimeConfig` (environment variables instead, `connection()` before a runtime read); AMP; `unstable_rootParams` (`next/root-params`); the `devIndicators` keys `appIsrStatus`, `buildActivity` and `buildActivityPosition`; the `scroll-behavior` override during navigation (`data-scroll-behavior="smooth"` on `<html>` restores it); the `size` and `First Load JS` columns of the build output. The minimum Node.js is 20.9 and the minimum TypeScript 5.1; the browsers are Chrome, Edge and Firefox 111 and Safari 16.4.
- Versions on 2026-10-28: Next.js 16.4.3 (released 2026-10-23; the package's engines field says Node.js 20.9 or newer) beside React 19.3.1, eslint-config-next 16.4.3 (ESLint 9 or later; 16.4.0 and later support ESLint 10), Vitest 5.0.5, ESLint 10.13.0, @vitejs/plugin-react 6.1.2 (Vite 8), vite-tsconfig-paths 6.1.1, jsdom 30.1.3 and TypeScript 7.0.2 (TypeScript 7 has no JavaScript compiler API yet, so `next build` uses the project-local `tsc` CLI by default).

## How work is verified

- Vitest: the documentation's setup is `vitest`, `@vitejs/plugin-react`, `jsdom`, `@testing-library/react`, `@testing-library/dom` and, with TypeScript, `vite-tsconfig-paths`, a `vitest.config.mts` with the React and tsconfig-paths plugins and the `jsdom` environment, and a `test` script of `vitest`, which watches; `vitest run` is one run without watch and `vitest related <files> --run` runs the tests that import the files. An `async` Server Component is outside Vitest's reach, so the documentation sends it to end-to-end tests. Test files live under `__tests__/` or beside the code in `app/`.
- The crew's e2e gate runs the profile's e2e command (`npx playwright test`, proposed from a Playwright config) with `WIZARDINGCODE_CREW_E2E_DIR` and `WIZARDINGCODE_CREW_CONSOLE_FILE`, so a Playwright spec of a Next page runs under the gate as any Playwright spec does, beside the capture spec of an interface item (`tests/e2e/<page>.crew.spec.ts`).
- Lint: `eslint-config-next` ships the flat configs `eslint-config-next` (Next.js, React and React Hooks rules), `eslint-config-next/core-web-vitals` (the Core Web Vitals rules raised to errors; the create-next-app default) and `eslint-config-next/typescript` (typescript-eslint's recommended rules), spread into `eslint.config.mjs` with `defineConfig` and `globalIgnores` from `eslint/config`; the `@next/eslint-plugin-next` rules include `no-img-element`, `no-html-link-for-pages`, `no-async-client-component`, `no-sync-scripts` and `google-font-display`; `eslint .` runs it, `next lint` no longer exists, `next build` runs no linter, and the `next-lint-to-eslint-cli` codemod moves a project's scripts.
- Type check: `next build` runs the project's type check and fails on an error (`typescript.ignoreBuildErrors` skips it, `typescript.tsconfigPath` picks another file; the project-local `tsc` CLI is the default checker in 16, `experimental.useTypeScriptCli: false` uses the compiler API instead); the documentation's own check for CI is `tsc --noEmit`, which the crew's core detects from `tsconfig.json` as `npx tsc --noEmit`; `.next/types/**/*.ts` and `next-env.d.ts` sit in the `include` of `tsconfig.json`, and `typedRoutes: true` types every `href` of `next/link` and `next/navigation`.
- The versions this file was verified against: Next.js 16.x (v16.4.3, the latest tag on 2026-10-28), Vitest 5.0.5, ESLint 10.13.0, eslint-config-next 16.4.3, @vitejs/plugin-react 6.1.2.
