# wizardingcode-pack-next

A stack pack for the WizardingCode Developer Crew: data the crew engine serves, never code. It holds one detector rule and one knowledge file the expert reads. It has no checklist, no skill, no agent and no hook; the crew skill reads what the engine prints for it (`crew pack files`), and the engine refuses it whole when a check fails (ADR 0010 of the core repository).

Verified against: Next.js 16.x, Vitest 5.0.5, ESLint 10.13.0, eslint-config-next 16.4.3, @vitejs/plugin-react 6.1.2 (the documentation read on 2026-10-28; the latest tag was v16.4.3, released on 2026-10-23).

## What it changes in a project

- **The profile.** In a folder whose `package.json` sits beside a `next.config.js`, `next.config.mjs` or `next.config.ts`, the rule refines the core's Node target: the test gate `npx vitest run`, the lint gate `npx eslint .` and the scoped test template `npx vitest related {files} --run`, and the target is tagged `next`. The package manager stays the core's (the lockfile's, or the `packageManager` field of `package.json`), and so do the gates the rule does not name: the `build` script and the type check the core detects from `tsconfig.json` as `npx tsc --noEmit` (both `detected`, with no pack mark), an end-to-end runner proposed from a Playwright or Cypress config, and the environment the core proposes from the `dev` script on port 3000. Each of the pack's commands enters the profile as proposed and runs only once a person confirmed it in that project (`crew profile confirm <gate>`; `crew profile confirm test` confirms the scoped template with the test gate); until then the gate says `unavailable: pack wizardingcode-pack-next's command is not confirmed`, and `crew tdd` without `--` refuses it with the same text.
- **`npx` and a package the project has not installed.** `npx` runs the project's own binary under `node_modules`, and for a package that is not installed it fetches one from the registry. Confirm a command only in a project that has installed what it names (`vitest`; `eslint` with `eslint-config-next`): the hold above is the guard, and a project that runs its checks another way sets its own command (`crew profile set test "<cmd>"`) or unsets the gate (`crew profile unset lint`).
- **The lint.** `next lint` is gone in Next.js 16 and `next build` runs no linter: the project runs ESLint's CLI over `eslint.config.mjs`, a flat config that spreads `eslint-config-next/core-web-vitals` (and `eslint-config-next/typescript` for TypeScript) with `defineConfig` and `globalIgnores`; `eslint-config-next` 16 needs ESLint 9 or later and supports ESLint 10 from 16.4.0. A project without the config sets its own lint command or unsets the gate.
- **The type check.** The rule names none: `next build` runs the project's type check itself and fails on an error, and the documentation's own check for CI is `tsc --noEmit`, which the core already detects from a project's `tsconfig.json` as `npx tsc --noEmit` (or the manager's form). A project with `tsconfig.json` keeps that detected gate beside the pack's two.
- **The expert.** When the item's changed files sit in the tagged target, `crew pack files knowledge --item <id>` prints `knowledge/next.md` and the expert reads it before proposing.
- **No checklist.** A Next page is a screen: the core's `screen` checklist and the frontend pack's `screen`, `motion` and `design-contract` checklists serve the gap round, and the stack's transitions (`<ViewTransition>`, `motion/react`) are the frontend pack's `knowledge/motion.md`. Install `wizardingcode-pack-frontend` beside this pack and set its template and specialists in the project's policy for the pages (`{ "team": { "template": "frontend", "specialists": ["wizardingcode-pack-frontend:frontend", "wizardingcode-pack-frontend:motion"] } }`). A checklist for a Route Handler or a Server Action is a later revision of this pack.

## Install

From the WizardingCode marketplace, with the core plugin at 0.16.0 or later, the release that ships this pack (the brace marker and the empty package manager of the rule are the core's since SP9 Task 9; `pack.json`'s `core` bound is the engine's version at each release, written by the release script, so until that release it carries the engine's current one):

```sh
claude plugin install wizardingcode-pack-next@wizardingcode-plugins
```

The engine registers it at the next session start (`crew pack list` shows it). From a checkout of the core repository, in any runtime:

```sh
crew pack add packs/next
```

## The cases

The pack ships with the cases that show its difference (`plugins/core/evals` of the core repository, SP9 Task 12): `pack-next-refines-the-gates` (a Next-shaped Node tree with the pack registered: the profile's two gates proposed with the pack's name, `test=npx vitest run [proposed] (pack wizardingcode-pack-next)`, the target tagged `next`, the knowledge path printed by `crew team`; the kit's sandbox has no `npx`, so the prompt relays, as the person's decision, `node` commands over faked local packages committed in the fixture for the two gates, and the gate runs green) beside `pack-next-absent` (the same tree without the pack: the core's Node target, no pack mark, no tag, no knowledge path). Their figures are in the item's evals record, `docs/evals/2026-10-28-sp9-task-12-results.md` of the core repository.
