# Nuxt 4.x

What a model trained on Nuxt 3 gets wrong in Nuxt 4, how work in it is verified and where the documentation is. Each line is a fact read on 2026-10-28 from the pages listed at the end; nothing here is a tutorial.

## What the model gets wrong

- The source directory is `app/`: `srcDir` defaults to `app` and the `~` alias points at it; `assets/`, `components/`, `composables/`, `layouts/`, `middleware/`, `pages/`, `plugins/`, `utils/`, `app.vue`, `error.vue` and `app.config.ts` live under it, while `nuxt.config.ts`, `server/`, `public/`, `shared/`, `modules/`, `layers/` and `content/` stay at the project root. A project that keeps the v3 layout sets `srcDir: '.'` and `dir: { app: 'app' }`.
- Auto-imports scan `app/components/`, `app/composables/` and `app/utils/`, top-level files alone: a composable in a nested folder is not scanned unless `app/composables/index.ts` re-exports it or `imports.dirs` names the folder (`~/composables/**` scans all). `utils/` and `composables/` differ in meaning alone and are scanned alike; they serve the Vue part of the app, and `server/utils/` is auto-imported in `server/` alone. A default export is named after its file in camelCase (`use-foo.ts` as `useFoo`). Explicit imports come from `#imports`; `imports.autoImport: false` turns auto-imports off, `imports.scan: false` keeps the framework's and drops the project's own, `components.dirs: []` stops the project's components and not a module's. Vue's `ref`, `computed` and lifecycle hooks are auto-imported, and an auto-imported `ref` or `computed` is not unwrapped in a component's `<template>`. The types come from `.nuxt/imports.d.ts`, written by `nuxt prepare`, `nuxt dev` or `nuxt build`, so a composable added before a prepare reads as `Cannot find name`. A composable is called in the right context and synchronously; the error `Nuxt instance is unavailable` says it was not.
- Data fetching: `useFetch` is the first choice (a wrapper over `useAsyncData` and `$fetch` that fetches once in universal rendering and adds the response to the payload, so the client does not fetch again at hydration), `useAsyncData` serves a third-party query layer or several `$fetch` calls, and `$fetch` alone is for a client-side, event-driven call; a bare `$fetch` in setup fetches twice, on the server and again at hydration, which can cause hydration issues. `useFetch` is called in setup, a plugin or a route middleware; its name is reserved and a custom variant is made with `createUseFetch`; a string `data` instead of parsed JSON points at an import of `useFetch` from `@vueuse/core`. The key comes from the URL, the options and the call's place in the source, so two components fetching one URL get two keys unless `key` is given; `useAsyncData` takes its first argument as the key when it is a string. In v4 `data` is a shallow ref (`deep: false`; `deep: true` for nested reactivity), `data` and `error` default to `undefined`, calls sharing a key share `data`, `error` and `status` and must agree on `deep`, `transform`, `pick`, `getCachedData` and `default`; `dedupe` is `'cancel'` (the default) or `'defer'`, the booleans gone; `status` is `'idle'`, `'pending'`, `'success'` or `'error'` and `pending` is true only while the status is pending; with `immediate: false` a key change fetches only once something was fetched, so the first fetch is `execute()`; `lazy: true` (or `useLazyFetch`) does not block navigation; `server: false` fetches on the client alone; `timeout` has no default; `clear` resets `data` to the default, clears `error`, sets `status` to idle and cancels a pending request. A relative URL in `useFetch` proxies the request's headers and cookies through `useRequestFetch` (never `host`); `$fetch` on the server passes `useRequestHeaders(['cookie'])` itself.
- `useState` is the SSR-friendly `ref`: its value is serialised to JSON into the payload and shared by every component with the same key, so no class, function or symbol goes in. A `ref` declared outside `setup` is shared across the server's requests (Vue calls it cross-request state pollution: one user's data leaking into another's request), so shared state is a composable wrapping `useState` (`const useColor = () => useState('color', () => 'pink')`); `clearNuxtState` invalidates it (and resets it to the initial value under `compatibilityVersion: 5`); `callOnce` in `app.vue` sets an asynchronous initial value; Pinia is the official store recommendation.
- Hydration: universal rendering returns server-rendered HTML and the browser then runs the same code to match each component to its DOM nodes and attach the listeners. A mismatch is the pre-rendered DOM differing from the client's render; Vue names invalid HTML nesting (a `<div>` inside a `<p>`, which the browser closes early), random values in the render data and a time zone difference between the server and the client; a browser API is read in `onMounted`; Vue recovers from a mismatch at a rendering cost. `<ClientOnly>` renders its default slot on the client alone (tree-shaken out of the server build, so its components' CSS may not be inlined in the first HTML) with `fallback` or `placeholder` (and `fallbackTag` or `placeholderTag`) for the server's side, and a template ref inside it is watched once mounted; Vue 3.5's `data-allow-mismatch` suppresses an inevitable mismatch. `ssr: false` renders in the browser alone (`app/spa-loading-template.html` for the loading screen); `routeRules` set `prerender: true`, `ssr: false`, `swr` and `isr` per route, and not with `nuxt generate`.
- `definePageMeta` is a compiler macro for `app/pages/`: `name` (from the path), `path`, `alias`, `redirect`, `props`, `layout`, `middleware`, `keepalive`, `key`, `pageTransition`, `layoutTransition`, `validate`, `scrollToTop`, `viewTransition` (experimental, enabled in the config), `groups` (from 4.3, from the folders) and custom keys. In v4 `name` and `path` live on the route (`route.name`, not `route.meta.name`), page metadata is read after `pages:extend` so an override goes in `pages:resolved`, `app.pageTransition` and `app.layoutTransition` default to `false`, and under `future.compatibilityVersion: 5` (Nuxt 4.2 and later) page components are named by their route (`pages/foo/index.vue` as `foo`), routing is case-sensitive and `experimental.typedPages` is on.
- Nitro: `server/api/` handlers answer under `/api` (`api/hello.ts` as `/api/hello`), `server/routes/` without the prefix, `server/middleware/` runs before every request, `server/plugins/` are Nitro plugins, `server/utils/` holds the server's own helpers. A handler is `export default defineEventHandler(...)` (or `eventHandler`) returning data, a promise, or ending the response itself. A method suffix (`.get.ts`, `.post.ts`) limits the handler to that method and the others get a 405; `index.[method].ts` namespaces a folder; `[name].ts` gives `getRouterParam(event, 'name')` or `event.context.params`, `[...].ts` catches the rest in `event.context.params._` and `[...slug].ts` in `slug`. `readBody(event)` throws a 405 in a GET handler; `getQuery` and `parseCookies` read the request; an uncaught error is a 500, `createError` takes `status` and `statusText`, `setResponseStatus(event, 202)` and `sendRedirect(event, path, 302)` set the answer; `useRuntimeConfig(event)` so the environment's overrides apply at runtime. Server code never imports the app and the app never imports the server; `server/types/` is scanned one level for the server alone, and Nuxt 4 generates a project reference for `server/`.
- Runtime config: a key directly under `runtimeConfig` is private (server only, read-only there), a key under `runtimeConfig.public` is public (writable and reactive on the client). An uppercase environment variable starting with `NUXT_` overrides a key defined in `nuxt.config` at runtime, `_` separating the keys and the case changes (`NUXT_API_SECRET` for `apiSecret`, `NUXT_PUBLIC_API_BASE` for `public.apiBase`), its value cast by `destr` unless wrapped in double quotes; a variable of another name works at build time alone. The `.env` file is read by the CLI in dev, build and generate and not by the built server. `useRuntimeConfig()` in the app and in `defineNuxtPlugin`, `useRuntimeConfig(event)` in a server route; `runtimeConfig.app` is reserved; the type is generated, or augmented in `nuxt/schema` (`RuntimeConfig`, `PublicRuntimeConfig`).
- TypeScript: Nuxt 4 generates `.nuxt/tsconfig.app.json`, `.nuxt/tsconfig.server.json`, `.nuxt/tsconfig.node.json` and `.nuxt/tsconfig.shared.json` (`.nuxt/tsconfig.json` kept for compatibility), used through project references from a root `tsconfig.json` with `files: []` and a `references` list, and no `extends` of `.nuxt/tsconfig.json`; a hand-written server `tsconfig.json` goes; `noUncheckedIndexedAccess` is on and `typescript.strict` is on; a type augmentation lives under `app/`, `server/` or `shared/` and nowhere else; `typescript.typeCheck` is `false` by default (`true` checks in dev, `'build'` at build time alone) and needs `typescript` and `vue-tsc`.
- Versions on 2026-10-28: Nuxt 4.6.3 (released 2026-10-27) needs Node.js 22.x or newer (the installation page recommends the active LTS and an even version; the package's engines are 22.22.3, 24.15.0 or 26 and up); a project is created with the `create nuxt` command of the package manager; the dev server listens on port 3000; the `nuxt` package ships the bins `nuxi` and `nuxt`, and `@nuxt/cli` 4.0.1 ships `nuxi`, `nuxt`, `nuxi-ng` and `nuxt-cli`.

## How work is verified

- Vitest: `vitest run` is one run without watch; the bare `vitest` watches in a terminal and runs once in CI or without a TTY; `vitest related <files> --run` runs the tests that import the files (static imports alone, paths relative to the root) and `--run` keeps it from watching; a file filter is a substring of the path, a file and line (`basic/foo.test.ts:10`) since Vitest 3; `--bail <n>`, `--reporter`, `--passWithNoTests`.
- `@nuxt/test-utils` (4.3.4; `vitest`, `@vue/test-utils`, `happy-dom` or `jsdom`, and `playwright-core` as its peers): `defineVitestProject` from `@nuxt/test-utils/config` beside `defineConfig` from `vitest/config`, one project per environment chosen by `include` globs (`test/unit/`, `test/nuxt/`, `test/e2e/`) and not by a `@vitest-environment` comment (it skips the Nuxt Vite plugins); the `nuxt` environment (`environment: 'nuxt'`, `environmentOptions.nuxt` with `rootDir`, `domEnvironment` happy-dom by default or jsdom, `overrides`, `mock`); the runtime helpers `mountSuspended`, `renderSuspended`, `mockNuxtImport`, `mockComponent` and `registerEndpoint` from `@nuxt/test-utils/runtime`, the `intersectionObserver` and `indexedDb` mocks; the end-to-end helpers `setup`, `$fetch`, `fetch`, `url`, `createPage` (Playwright, waiting for hydration), `getServerLogs` and `clearServerLogs` from `@nuxt/test-utils/e2e`, with `setup`'s `browser`, `browserOptions.type` and `runner` (`vitest`, `jest` or `cucumber`); the unit environment supports vitest alone; the end-to-end runners are Vitest, Jest, Cucumber and Playwright (`@nuxt/test-utils/playwright` under `@playwright/test`); the runtime and the e2e helpers never share a file.
- The crew's e2e gate runs the profile's e2e command (`npx playwright test`, proposed from a Playwright config) with `WIZARDINGCODE_CREW_E2E_DIR` and `WIZARDINGCODE_CREW_CONSOLE_FILE`, so a Playwright spec that uses `@nuxt/test-utils/playwright` runs under the gate as any Playwright spec does, beside the capture spec of an interface item (`tests/e2e/<page>.crew.spec.ts`).
- Lint: the `@nuxt/eslint` module (1.17.0) writes `eslint.config.mjs` at the first server start (`autoInit`, off with `eslint.config.autoInit: false`), importing `withNuxt` from `./.nuxt/eslint.config.mjs`, so the `.nuxt` folder exists before the first lint; it is flat config (ESLint 9's default, supported from 8.45) and the legacy `.eslintrc` is not; the recipe's scripts are `eslint .` as `lint` and `eslint . --fix` as `lint:fix`; `eslint.config.stylistic` adds ESLint Stylistic, `eslint.config.standalone: false` drops the default JS, TS and Vue setup, `eslint.checker: true` runs ESLint beside the dev server.
- Type check: `nuxt typecheck` (the documentation's form; `nuxi typecheck` is the same bin) runs vue-tsc or Golar (`--checker`, Golar the default with a `golar.config.*`), offers to install a missing checker, takes `--cwd`, `--logLevel`, `--dotenv` (repeatable, the later files winning) and `--extends`, `--build` or `--no-build` for project references (a solution config is detected), `--incremental` on by default with the cache under `.nuxt/cache/typecheck` (kept by `nuxt prepare` and `nuxt dev`), sets `NODE_ENV` to `production` and gives vue-tsc a heap of up to 8 GB (`NODE_OPTIONS` overrides); the skeleton's script form is `nuxt prepare && vue-tsc -b --noEmit`.
- The versions this file was verified against: Nuxt 4.x (v4.6.3, the latest tag on 2026-10-28), Vitest 5.0.5 (Node 22.12, 24 or 26 and up), ESLint 10.13.0, @nuxt/eslint 1.17.0, @nuxt/test-utils 4.3.4 (Node 20.19, 22.12 or 24 and up), vue-tsc 3.3.13, @nuxt/cli 4.0.1.
