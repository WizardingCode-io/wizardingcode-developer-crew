# Evals

`claude plugin eval` runs each case in an isolated session with only this plugin loaded, once with the plugin and once without, and reports the difference. Every case scaffolds its own git repository (`fixture.sh`), because the engine is inactive outside a repository. The harness runs each `fixture.sh` from its own folder (the run of 2026-10-17 scaffolded all fourteen sandbox cases that way), so a fixture reaches the shared ones in `fixtures/` with `. "$(dirname "$0")/../fixtures/<name>.sh"`: `node-plain.sh` is a Node project with one passing test, `two-projects.sh` the two-project workspace described below.

The suite lives inside the plugin (`plugins/core/evals/`) because `claude plugin eval` only accepts an eval directory below the plugin root. Two things differ from a normal session and are handled by the runner, `scripts/eval.ts`:

- The plugin's `bin/` is not on the Bash tool's PATH inside an eval run, so `crew` must be put there.
- On macOS `/usr/bin/git` is a shim that cannot write its `xcrun` cache inside the eval sandbox, so every git call fails there. The engine then counts every watched file as the change (its no-git behaviour), which is honest but makes the deps audit a planned gate; the runner puts the real git (`xcrun --find git`) first on PATH instead, and refuses to run when `xcrun` cannot say where it is.

## Run the suite

From the repository root:

```bash
bun scripts/eval.ts
```

It prints the `claude plugin eval` command it runs, which is:

```bash
PATH="$PWD/plugins/core/evals/fixtures/bin:$PWD/plugins/core/bin:$(dirname "$(xcrun --find git)"):$PATH" WIZARDINGCODE_CREW_REPO="$PWD" claude plugin eval plugins/core \
  --scaffold --trust-plugin --no-publish --keep-temp \
  --output-dir plugins/core/evals/results/<UTC stamp>-suite \
  --model claude-sonnet-5-5 --judge-model claude-opus-5-5 \
  --concurrency 3 \
  --tag cost enforcement method risk stacks gap kind validator judgement team environment priority contracts reception jev issue strategy audit knowledge benchmark packs ui \
  <the tool grant> \
  --report plugins/core/evals/results/report.html --json plugins/core/evals/results/last.json
```

Before the kit starts it prints `estimated cost: about <usd> USD (<source>)` from the last recorded figures: the SP7a suite at 38.80 USD for the whole suite (`docs/evals/2026-10-18-sp7a-results.md`; the suite has grown since, so a run of it costs more), and 5 USD at most for one case (its cap). The whole suite runs with no cost cap unless one is given: `bun scripts/eval.ts --max-cost-usd <usd>` passes it to the kit, and a value that is not a positive number is refused before the kit starts. Run only the cases a change affects, with `--case`, one at a time (about 0.3 to 2.3 USD each); the whole suite is for a release (the user's decision of 2026-10-22, finding 63).

On Linux the PATH has no `xcrun` part. `plugins/core/evals/fixtures/bin` holds `wizardingcode-crew-repo`, a helper that prints the repository's root, and `WIZARDINGCODE_CREW_REPO` names it too: the kit strips the runner's environment before a scaffold runs and keeps PATH, so a pack fixture takes the variable when set and the helper otherwise, copies `packs/laravel` or `packs/agentic-os` into the scaffold and registers the copy (the kit's sandbox lets the plugin read its own folder and the scaffold, not the repository beside them); a with fixture that finds neither stops rather than scaffold the absent case. The Laravel pair needs `php` on the machine that runs the evals (the fixture's `artisan` is a PHP script with no framework): a session's PATH is Claude Code's, with the plugin's own `bin/` added, never the runner's, so nothing the runner puts on its PATH reaches the engine's gates inside a session. `--keep-temp` keeps each run's scaffold and `out/trace.jsonl` under the system temp directory (sealed read-only; `chmod 700` to inspect, delete when done). The tool grant is `ALLOW_TOOLS` in `scripts/eval.ts`, and only there: Write, Edit and Bash whole (findings 64 and 95: the narrow per-command grants denied the agent's compound commands and its reads of the plugin's references, and already held `sh`, `node` and `env`, which run any code); the kit's OS sandbox confines what Bash reaches. The kit's session receives only the environment names of `kitEnvironment`'s allowlist (`PATH`, `HOME`, `TMPDIR`, `LANG`, `LC_*`, `TERM`, `SHELL`, `USER`, `LOGNAME`, `ANTHROPIC_API_KEY`, `CLAUDE_*`, `WIZARDINGCODE_*`, none that names a token, secret, password, credential or key); every other name is dropped. A run the runner flags `needs-rerun` is run once more; a second flag is recorded in the results note and the run stands.

One case while iterating (one run, no baseline arm, the suite's judge model for its llm graders, the sandbox kept, a 5 USD ceiling):

```bash
bun scripts/eval.ts --case false-done
```

The agent under test runs on Sonnet 5.5 and the judge on Fable 5.1 (the owner's choice: the judge must not be weaker than the agent it grades). If a model id is rejected, use the aliases `sonnet` and `fable`. On Linux, Bash in evals needs `bubblewrap` and `socat`; macOS has its own sandbox.

On the standard and full routes the method pauses for the user's decisions (`crew await <id> user`): the assumptions in Understand, and on the full route the approval of the spec before any source file changes. An eval has a single turn, so the prompts of `proven-test-first` and `risk-escalation` state the decisions and ask the agent not to wait. `results/` is ignored by git; the recorded runs live in `docs/evals/`.

An llm grader is scored only where the case has a baseline arm to compare it with; the kit's llm graders take no `target` and judge the final message alone, so what must be read in the trace is a regex grader, anchored on what ran (a Bash call's `"command"` field, a tool result's `"content"`) rather than on text a reference or the agent's own words may hold. The `needs-real-opener` mail cases are recorded from an end-to-end run, not scored by the suite (finding 65).

Each run of `scripts/eval.ts` gives the kit a folder of its own under `results/` through `--output-dir` (the kit's own UTC stamp shape, suffixed `-suite` or `-case-<name>`; created before the kit starts and refused if it exists; the kit run with the repository root as its working directory wherever the script was started from) and reads that folder alone after the run, never the newest folder by name (finding 118). A run whose folder holds no aggregate is refused as `eval: the kit exited <status> and wrote no aggregate in plugins/core/evals/results/<folder>`. The runner then prints one `needs-rerun` line per run whose kept trace (the sandbox file the aggregate names as `tracePath`) shows a plugin reference denied to the agent, read from the trace's own marks: a tool result flagged `is_error` or rejected in its permission metadata whose call named the reference (a Read's path, a Bash command, the references folder itself), or the error's text naming it, or the agent's own words reporting the denial with no accepted Read of that path in the trace; a trace with no readable line is flagged `trace unreadable`. An accepted read is never a denial, whatever the reference's own text says (finding 118: the references hold the words "permission" and "bypassPermissions", and every accepted call carries `permission_decision: accept`). Such a run is re-run rather than scored (finding 95).

## The canned Jev transport

`jev-tightens-never-loosens` sets `crew config jev.endpoint "file://jev-answers.json"` from its fixture (a path the engine reads from the folder `crew` runs in, the scaffold root, so the sandbox may move the scaffold): a JSON object keyed by question id whose values are answers as the API returns them, `{ "type": "noul", "noul": 0.95 }` (`v1` and `v2` are the validator's two conditions; a value without its `type` is a malformed answer, Jev unavailable, and the approval proceeds unverified, which the first run of 2026-10-19 showed), read by the engine's canned transport instead of the network. Every record it makes says `model: "file"`: the dispute the case measures is the fixture's word, never a model's verdict, and no key exists in the sandbox. The runner gives each fixture its own crew home (`WIZARDINGCODE_HOME`), where that config and the signed business priorities of `ticket-triaged-against-business` land; the eval-runner test checks both.

The tag `benchmark` marks the set the public benchmark runs: the cases named in `benchmark.json` beside this file, with a category each (functional, security, cost). `bun scripts/benchmark.ts` runs them through the kit with the tag list alone replaced and writes the record under `docs/benchmark/` from the aggregate result alone (`docs/benchmark/README.md`). The tag is in the runner's sandbox list, so the whole-suite run keeps every case of the set.
