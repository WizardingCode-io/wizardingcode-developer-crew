# Gate

```
crew gate run <id>
```

The engine runs what the route requires: the project's build, tests, lint and type checks, a secret scan of the change, the `prose` scan of the change, and, when the change touches a manifest or a lockfile, a dependency audit. Each run has a log in `.crew/work/<id>/logs/`; the last lines are in the output.

- **A gate fails:** read the log, fix the cause, run again. Never change the gate command, delete a test or edit the profile to make a gate pass.
- **A gate is unavailable** (no command, no tool): first run the gates again. The profile follows the manifests at every gate run, so a script or a lockfile the work added is picked up by itself; never edit the profile for that. A built-in gate (`secrets`, `prose`, `design-lint`) has no command to set: `crew profile set` refuses it, and unavailable there means the change could not be read (no diff and a tree over the walk's cap; the reason says which), so run it again from a git checkout whose base the engine knows, or the user lists the gate under `allowSkips` in `policy.json` and skips it with the reason. If the project really has no command, the user gives one: `crew profile set <gate> "<cmd>"`, set and confirmed in one step (replacing a command a person already confirmed needs `--force`). Gates are mandatory: `crew skip <id> gate:<name> --reason "<why>"` is refused unless the team's `policy.json` lists that gate. Both are the user's decisions: under the default policy you run the command once the user has said so, with no prompt; under `prompt` the permission prompt appears; only in a headless session, or in bypassPermissions or dontAsk mode, the hook asks for `--mode <mode>` and the record says the agent decided (it counts only if the policy says so).
- **A gate times out:** the test gate has twenty minutes by default (any gate, the target's ten); a flow that needs more gets its own limit with `crew profile set test "<cmd>" --timeout <minutes>`, the user's decision like any `profile set`. Never shorten a flow to fit.
- **Lint and typecheck** are judged by the files they name: problems only in files the item never changed are the repository's debt ("pass: 19 untouched files with problems, none of the item's"), problems in a file the item changed fail ("fail: problems in src/a.ts"). Fix the item's files; name the debt to the user. A tool that names no files is judged by its exit code.
- **The dependency audit** is judged against the item's base commit: advisories the repository already had are counted and named ("pass: 162 known before, none new"), only new ones fail ("fail: 1 new (GHSA-…)"). Say both to the user; the known debt is theirs to schedule, not this item's failure. An abandoned package in `composer audit` is in the log, never a failure.
- **The route was raised:** the diff touched a risk path. The engine says which. The guards of the new route now apply; `crew phase <id> next` lists what is missing.
- **Unconfirmed command:** a command the detector only guessed ran (two lockfiles and no `packageManager` field). Say which guess it was; once the user says it is right, `crew profile confirm <gate>`; until then the work is not proven.

`crew gate run <id> --only test` runs a subset while you iterate; the verdict still needs every gate. A gate run that proves the work writes the report and moves the item to the deliver phase.

- **A blocking objection is open or bound to an unproven criterion:** the verdict says "blocking objection O-n open" or "bound". Prove the criterion it is bound to, bind it (`crew objection <id> resolve O-n --criterion AC-k`), or let the user waive it (`crew objection <id> waive O-n --reason "<why>"`, which asks them). The verdict line of the report then says how many were waived.

## The environment

The profile may hold how the project runs (`environment`: start, health, stop, logs, url, timeout), detected from a compose file, a Laravel `artisan`, a Makefile target or a `package.json` script and proposed like a guessed test command; `crew profile set environment.<key> "<value>"` sets a key and confirms it, `crew profile confirm environment` confirms the proposed ones (a proposed command runs until then, as a proposed gate does, and the report says so). `crew env start` starts it detached and waits for health, `crew env health` checks it, `crew env status` says where it stands, `crew env stop` stops what the engine started. An environment that answers health before `crew env start` is the user's: the engine records it as such and never stops it. The e2e gate uses the same four steps around a run.

## The e2e gate

Planned once per item when the change touches an interface file or a public-api path, or when `policy.json` lists `e2e` under `requiredGates`; it runs on the first target with an e2e command (a `test:e2e` or `e2e` script, detected; a Playwright or Cypress config beside the manifest, proposed; or `crew profile set e2e "<cmd>"`), never on a todo's gate. The run: health first, so an environment the user has running is used and never stopped; otherwise the engine starts the profile's environment and waits for health; the e2e command then runs from the target's folder with two variables, `WIZARDINGCODE_CREW_E2E_DIR` (the run's folder, `.crew/work/<id>/review/e2e/`) and `WIZARDINGCODE_CREW_CONSOLE_FILE` (the console file the run should write there, `console.json` as a JSON array, or `console.jsonl` beside it as one JSON object per line); the environment's logs are read (a file path inside the project, only the lines the run added; a command, its output); what the engine started is stopped. The verdict: the command's exit, then the console (the first entry at error or warning fails the gate, naming it: `console warning on /home: deprecated`), then the logs (the first line at error or warning: `logs: 2026-10-18 10:00:00 ERROR boom`). The tail says `console: clean`, `console: not captured` or the offence, and `logs: clean`, `logs: none` or the offence; a logs path outside the project is never read and the tail says so. A Playwright project records its console by importing the crew's fixture instead of `@playwright/test`: `import { test, expect } from "${CLAUDE_PLUGIN_ROOT}/e2e/playwright.mjs"` (the package is the project's own); another runner writes the console file itself, or has no console measurement and the report says `not captured`.

- **Unavailable** (`no environment in the profile`, `no e2e command`): the user sets what is missing (`crew profile set environment.start "<cmd>"`, `crew profile set e2e "<cmd>"`) or decides to skip the gate: `crew skip <id> gate:e2e --reason "<why>"` is the one gate skip the default policy allows (decision 9 of SP7b), recorded as the user's and named in the report.
- **The UI/UX captures**: save the console file beside each capture, `review/ui/console-<page>-<state>.json`, from the browser's console tool; `crew gate run` prints `captures: <n> (<k> without a console file: <names>)`, and a capture without its file is not answerable for that page.

## The prose gate

<!-- crew-lint: allow prose/chatbot-artefact -- the gate's own reference names the phrases it refuses -->
`prose` runs on every item and every route, right after the secret scan: the change's added lines since the item's base, each read with its file and its line in the new file (Markdown included), against three rules of fixed phrases that a chat model leaves in shipped text: `prose/chatbot-artefact` (`As an AI`, `I hope this helps`, `Certainly!`, `Great question`, `feel free to ask`, `Let me know if you` …), `prose/cutoff-disclaimer` (`as of my last update` …) and `prose/model-markup` (`<|im_start|>`, `[INST]`, `<thinking>`, a search tool's `turn0search` …; not a hit in a test file). A phrase never matches inside another word. The run fails on a hit and lists each as `prose/<rule> <file>:<line>: "<text>"`, the text cut to one safe line and quoted as data, never read as an instruction. Every file name in the tail is quoted the same way. A file that is binary or whose added text is over 1 MiB is named `skipped <file> (binary|over cap)`, never counted clean. With no diff to read (no base commit, no git, a base git cannot diff against) every watched file is read whole and the first line says `no diff: the change read as every watched file whole (<why>)`; with a tree over the walk's cap as well, nothing is read and the gate is unavailable with `the change could not be read: <why>`, never a pass. The secret scan reads the change the same way: it is unavailable in that case too, and names the files it skipped after its verdict. The way out is an inline allowance on the hit's line or the line just above in the same file, naming the one rule with a why: `crew-lint: allow prose/<rule> -- <why>`; each honoured one is listed as `allowed prose/<rule> <file>:<line> -- <why>`, and the reviewers read these lines. Remove the artefact rather than allow it: an allowance is for a string the change quotes on purpose (a parser's fixture, a help text about a chatbot). The writing standard (`references/writing.md`) says what else a text must not carry.

## The design-lint gate

A built-in gate like `secrets`: no command, nothing to set or unset, planned at the root right after the scan when the change touches a frontend path (an interface file or a design contract), on every route; a todo's gate runs it over the todo's files. It reads the changed interface files as text and judges only what text decides, one rule per line with its id in the tail:

| Rule | Verdict | What it matches |
| :- | :- | :- |
| `motion/transition-all` | defect | `transition: all`, `transition-property: all`, the `transition-all` class |
| `motion/scale-from-zero` | defect | `scale(0)`, `scale3d(0, …)`, `scaleX(0)`; a `scale-0` class beside a transition or animate class |
| `motion/layout-property` | defect | a transition on width, height, top, left, right, bottom, margin or padding; such a declaration inside `@keyframes` |
| `motion/duration-over-500` | defect | a literal over 500 ms in a transition or animation value, or a `duration-N` class over 500 |
| `motion/ease-in` | advisory | `ease-in` (never `ease-in-out`) |
| `motion/reduced-motion-missing` | defect | the change adds motion and no project file names `prefers-reduced-motion`, `useReducedMotion`, `reducedMotion` or `motion-reduce:` |
| `hover/unguarded` | advisory | `:hover` in a file with no `(hover: hover)` query, once per file; a `hover:` class never |
| `perf/will-change` | advisory | more than two `will-change` declarations in one file |
| `tokens/raw-colour` | defect | a raw colour literal when `DESIGN.md`'s frontmatter declares `colors` |
| `craft/gradient-text` | defect | `background-clip: text`, `-webkit-background-clip: text`, the `bg-clip-text` class |
| `craft/emoji` | defect | a pictograph (Unicode `Extended_Pictographic`) in an interface file outside a comment; ©, ®, ™, arrows, • and ✓ are not |
| `copy/placeholder` | defect | `lorem ipsum`, `John Doe`, `Jane Doe` and `Acme` as whole words, `example.com` as a host, outside a comment and an input's `placeholder` attribute; never in a test file |
| `craft/glass` | advisory | `backdrop-filter`, the `backdrop-blur` classes |
| `layout/100vh` | advisory | `100vh`, the `h-screen` and `min-h-screen` classes (use `svh` or `dvh`) |

A duration written as `var(--x)`, `$name`, `@name`, `theme()`, `calc()` or `env()` is `unresolved`, counted and never judged. The run fails on a standing defect (`reason: <rule> <file>:<line>, +<n> more`) and passes with advisories alone; the tail lists every hit, the unresolved count and `inventory: <n> animated declarations (review/design-lint.json)`, the engine-owned file the UI/UX reviewer and the frontend lead read: the hits, the unresolved and every animated declaration of the change (file, line, kind, property, duration, easing). What text never decides is the reviewer's: whether to animate at all, springs, computed durations, GSAP timelines, Blade and Livewire runtime classes.

The four craft devices a design can adopt on purpose are declared, never mentioned: a `devices:` list in `DESIGN.md`'s front matter naming `gradient-text`, `emoji`, `glass`, `full-viewport` turns off `craft/gradient-text`, `craft/emoji`, `craft/glass` or `layout/100vh` for the project, the tail saying `<rule> off: DESIGN.md declares <device>`; a mention in its prose changes nothing ("never use emoji" leaves the rule on), and a device the change itself declares counts once committed (the tail says `<rule> on: DESIGN.md declares <device> in this change; it takes effect once committed`), so a change cannot switch a rule off for itself. `copy/placeholder` has no device: placeholder copy is never a design. The five craft rules distil taste-skill (MIT, Leonxlnx, tag v2.1.2, commit `b9ca2fd`) and ai-slop-cleaner of oh-my-claudecode (MIT, commit `8690a21`), in the crew's words (ADR 0017).

On a Persuade or Experience page at `surface` or `world` the lint also holds the rules a new site is held to: `font/overused`, `colour/ai-palette`, `label/eyebrow`, `label/micro`, `label/numbered`, `craft/costume-mono`, `link/dead`, `a11y/missing-alt`, `craft/side-border`, `copy/stock-phrase`, `copy/generic-action` as defects, `craft/gradient`, `craft/resting-shadow`, `craft/hairline`, `motion/looping` as advisories, and a duration over 900 ms instead of 500. On the standard and full routes every interface change answers to the process: `process/no-surface` with no recorded surface, `process/brief`, `process/direction`, `process/copy`, `process/deal` and `process/design-md` for a file the amount of invention requires, missing or malformed (`crew design <id> check` says which). The fast route is `extend`. The e2e run then grades the page's readings (`references/frontend-site.md`, Proportion) and the likeness to earlier sites; after the review, `crew design <id> score` records the bar: under 8.5, a cap or a disposition other than `ship` keeps the item not proven.

A false positive carries its rule id: an inline comment `crew-lint: allow <rule> -- <why>` on the hit's line or the line above allows that one hit with its why (counted, named in the tail); `policy.json`'s `ui.lint.disabled: ["<rule>"]` keeps a rule's hits as disabled, named in the tail; `crew skip <id> gate:design-lint` only when a person lists the gate under `allowSkips` (it is not there by default). Never weaken a rule to pass: the values are the standard's (`references/frontend.md`).

## Judgement gates

After the deterministic gates pass, `crew gate run <id>` cuts the change for review (`.crew/work/<id>/review/diff.patch`, `.crew/work/<id>/review/files.txt`) and prints the plan: `Judgement gates to run: code-quality (standard route), test-quality (standard route), security (risk area auth), ui-ux (interface files)`. Code quality and test quality run on standard and full; security on full, and on standard when a risk area is touched; UI/UX on any route when interface files changed; risk on full; architecture on full (the architects' seat); data when the change touches a data migration, on the full route (ETL's seat); infra when it touches infrastructure (a CI pipeline, a container, Terraform, Kubernetes or Helm, a deploy script), on the full route (DevOps's seat); and whatever the team policy adds (`team.always`, `judgementGates`). The gate run prints the team it planned on the change, as `crew team <id>` does, with each seat's reason: launch exactly those, no other. The roles run as subagents with clean contexts; the engine records their ruling and judges the verdict from it. A judgement gate is never passed by default: it is proven, not proven with findings, or not run with a reason.

1. **Reviewers, in parallel.** Launch the role: in Claude Code one Agent call by its scoped name; in another runtime as `references/runtimes.md` says, and file its answer with `crew answer file` where the table says the filing is requested. One Agent call each in the same message, `subagent_type` one of `wizardingcode-developer-crew:review-code-quality`, `wizardingcode-developer-crew:review-test-quality`, `wizardingcode-developer-crew:review-security`, `wizardingcode-developer-crew:review-ui-ux`, `wizardingcode-developer-crew:review-risk`, `wizardingcode-developer-crew:review-architecture`, `wizardingcode-developer-crew:review-data`, `wizardingcode-developer-crew:review-infra`. Pass `model: opus` on the Agent call on the full route or when the diff touches a risk area; pass nothing otherwise (the file's default, sonnet). The prompt gives the id, the two review paths and the criteria (id, kind, text; the recorded reason of an `observed` one), plus per gate: security, the risk areas and the paths that raised each; risk, the paths of `spec.md` and `plan.md`; architecture, the path of `spec.md` and where the project keeps its base (its architecture document, its data model, its contracts); data and infra, their risk areas (`data-migration`, with `personal-data` when present; `infra`) and the paths that raised each; ui-ux, the manifest `review/ui-evidence.json`, the evidence folder `review/ui/`, `review/design-lint.json`, the standard `references/frontend.md` and the project's `DESIGN.md` or `none`. The engine saves each role's answer from the SubagentStop hook (`review/<gate>.findings.md`, `review/ruling.json`). The engine owns the files under review/ except ui/ and e2e/: when a file is missing after a role returned (the hook could not read its transcript), resume the role with SendMessage so the hook files its answer, or record the gate --not-run; never write it yourself. Then `crew await <id> role`: the roles answer in the background and the turn may end once; rule 5 of the skill page says when the wait clears.
2. **UI/UX needs evidence.** The e2e gate produces it: the fixture's captures, snapshots, axe results and motion samples under `review/ui/`, graded into `review/ui-evidence.json`. Read the manifest before launching the reviewer: a declared state it lists as missing is a fix of the capture spec and a new `crew gate run <id>`, never a note to the reviewer. A project without Playwright keeps the manual path: with a browser the session can drive, open each page the diff changes in each state its criterion names and save one capture per page, state and viewport as `review/ui/<page>-<state>.png` (`<page>-<state>@<w>.png` with its width) with its console file `console-<page>-<state>.json`, read as `by: "session"`, before launching the reviewer. With neither, do not launch it: `crew judgement <id> record ui-ux --not-run --reason "no evidence"`. The reviewer's prompt gives the manifest, the standard, `review/design-lint.json` and `DESIGN.md` or `none`.
3. **The judge, once**, `wizardingcode-developer-crew:judge`, "as judge of the gates": the id, the diff path, every findings file and each gate's rubric path (`${CLAUDE_PLUGIN_ROOT}/skills/crew/rubrics/<gate>.md`). The engine saves the judge's JSON as `review/ruling.json` from the SubagentStop hook; when it is missing after the judge returned, resume the judge with SendMessage so the hook files it; never write it yourself. Leave `tokens` at 0: `crew judgement record` fills it with `tokens` from its own record of each role (the SubagentStop hook's count); a number you give stands. `tokens` is the only field of a ruling the session fills; the verdicts and the findings are the judge's (rule 2).
4. **Record**: `crew judgement <id> record --ruling .crew/work/<id>/review/ruling.json`. The engine keeps the round's files at the record (<gate>.round<n>.md, ruling.round<n>.json), so a later gate run's reset loses nothing. With Jev configured (`references/jev.md`) each upheld defect is asked and marked under the gate's line (`verified by jev (0.93)`, `disputed by jev (0.95)`, `unverified: <reason>`); a disputed defect stays a defect; Jev down on a full-route item makes it wait for a person, said in the last line. The verdict follows: a not-proven gate lists its findings by file and line. Fix them (the diff changes, so the next `crew gate run <id>` cuts it again and plans the gates again) or the user decides (`crew skip` only when `policy.json` lists the gate). A round past the cap (`team.maxJudgementRounds`) is the user's decision: under `relay` their standing word, given once in the conversation, is set as the policy's standing grant with `crew policy set team.continuations granted`, the user's own words quoted in the message that runs it, after which every round past a cap runs and is counted in the register and the report, never a `crew continue` asked per round.
4a. **A reviewer's open question on a runtime's behaviour** (what a hook, a kit or a shell does in a case the diff relies on) is a probe the session runs before the judge rules: run the case, keep its output in the item's `probes/` folder (the session's; `review/` is the engine's), and give the judge its path; never a note dropped at the ruling (finding 115).
4b. **A role that ended on an API error** (the Agent call says "terminated early due to an API error", a usage limit or an overload) is launched once more with the same prompt; in Claude Code the plugin probes a role's model with one token (at most 20 seconds) before the launch and moves it to the next model of the ladder fable, opus, sonnet, haiku when its own is at its limit (finding 154), so this relaunch is rare, and the report's Roles table shows the model it ran on. A second failure is said to the user with the error; the gate is not recorded.
5. **A gate that cannot run** for any other reason (a reviewer answered with nothing under "Findings" and `all · …` under "Not answerable"): `crew judgement <id> record <gate> --not-run --reason "<why>"`. Not run leaves the item not proven until the user decides.

## The judge's one question

When the judge's answer asks where a finding's line is (a reviewer cited a line of the patch instead of the file), relay it once: `crew mail send --to . --agent review-<gate> --type question "<the judge's question>"`, resume that reviewer with `SendMessage` to its agent id and the same words; the hook appends its answer to `review/<gate>.findings.md` under `## Clarifications` and records the reply. Then resume the judge once with "the reviewer's clarification is under ## Clarifications in <file>"; the hook saves its new ruling as `conclave/judge-reply.md` (a role's first answer is never overwritten), and you record that file: `crew judgement <id> record --ruling .crew/work/<id>/conclave/judge-reply.md`. One question per item; the judge never receives the conversation.

Never edit a findings file or a ruling; never launch the judge before every planned reviewer has answered; never re-launch a reviewer to get a different answer. The report's "Judgement gates" section names each gate's verdict, the number of findings and the tokens.
