# Gate

```
crew gate run <id>
```

The engine runs what the route requires: the project's build, tests, lint and type checks, a secret scan of the change, and, when the change touches a manifest or a lockfile, a dependency audit. Each run has a log in `.crew/work/<id>/logs/`; the last lines are in the output.

- **A gate fails:** read the log, fix the cause, run again. Never change the gate command, delete a test or edit the profile to make a gate pass.
- **A gate is unavailable** (no command, no tool): first run the gates again. The profile follows the manifests at every gate run, so a script or a lockfile the work added is picked up by itself; never edit the profile for that. If the project really has no command, the user gives one: `crew profile set <gate> "<cmd>"`, set and confirmed in one step (replacing a command a person already confirmed needs `--force`). Gates are mandatory: `crew skip <id> gate:<name> --reason "<why>"` is refused unless the team's `policy.json` lists that gate. Both are the user's decisions: under the default policy you run the command once the user has said so, with no prompt; under `prompt` the permission prompt appears; only in a headless session, or in bypassPermissions or dontAsk mode, the hook asks for `--mode <mode>` and the record says the agent decided (it counts only if the policy says so).
- **A gate times out:** the test gate has twenty minutes by default (any gate, the target's ten); a flow that needs more gets its own limit with `crew profile set test "<cmd>" --timeout <minutes>`, the user's decision like any `profile set`. Never shorten a flow to fit.
- **Lint and typecheck** are judged by the files they name: problems only in files the item never changed are the repository's debt ("pass: 19 untouched files with problems, none of the item's"), problems in a file the item changed fail ("fail: problems in src/a.ts"). Fix the item's files; name the debt to the user. A tool that names no files is judged by its exit code.
- **The dependency audit** is judged against the item's base commit: advisories the repository already had are counted and named ("pass: 162 known before, none new"), only new ones fail ("fail: 1 new (GHSA-…)"). Say both to the user; the known debt is theirs to schedule, not this item's failure. An abandoned package in `composer audit` is in the log, never a failure.
- **The route was raised:** the diff touched a risk path. The engine says which. The guards of the new route now apply; `crew phase <id> next` lists what is missing.
- **Unconfirmed command:** a command the detector only guessed ran (two lockfiles and no `packageManager` field). Say which guess it was; once the user says it is right, `crew profile confirm <gate>`; until then the work is not proven.

`crew gate run <id> --only test` runs a subset while you iterate; the verdict still needs every gate. A gate run that proves the work writes the report and moves the item to the deliver phase.

- **A blocking objection is open or bound to an unproven criterion:** the verdict says "blocking objection O-n open" or "bound". Prove the criterion it is bound to, bind it (`crew objection <id> resolve O-n --criterion AC-k`), or let the user waive it (`crew objection <id> waive O-n --reason "<why>"`, which asks them). The verdict line of the report then says how many were waived.

## Judgement gates

After the deterministic gates pass, `crew gate run <id>` cuts the change for review (`.crew/work/<id>/review/diff.patch`, `.crew/work/<id>/review/files.txt`) and prints the plan: `Judgement gates to run: code-quality (standard route), test-quality (standard route), security (risk area auth), ui-ux (interface files)`. Code quality and test quality run on standard and full; security on full, and on standard when a risk area is touched; UI/UX on any route when interface files changed; risk on full. The roles run as subagents with clean contexts; the engine records their ruling and judges the verdict from it. A judgement gate is never passed by default: it is proven, not proven with findings, or not run with a reason.

1. **Reviewers, in parallel**, one Agent call each in the same message, `subagent_type` one of `wizardingcode-developer-crew:review-code-quality`, `wizardingcode-developer-crew:review-test-quality`, `wizardingcode-developer-crew:review-security`, `wizardingcode-developer-crew:review-ui-ux`, `wizardingcode-developer-crew:review-risk`. Pass `model: opus` on the Agent call on the full route or when the diff touches a risk area; pass nothing otherwise (the file's default, sonnet). The prompt gives the id, the two review paths and the criteria (id, kind, text; the recorded reason of an `observed` one), plus per gate: security, the risk areas and the paths that raised each; risk, the paths of `spec.md` and `plan.md`; ui-ux, the capture folder. Save each answer verbatim with Write as `.crew/work/<id>/review/<gate>.findings.md`.
2. **UI/UX needs captures.** With a browser the session can drive, open each page the diff changes in each state its criterion names and save one capture per page and state as `.crew/work/<id>/review/ui/<page>-<state>.png` before launching the reviewer. Without a browser, do not launch it: `crew judgement <id> record ui-ux --not-run --reason "no browser"`.
3. **The judge, once**, `wizardingcode-developer-crew:judge`, "as judge of the gates": the id, the diff path, every findings file and each gate's rubric path (`${CLAUDE_PLUGIN_ROOT}/skills/crew/rubrics/<gate>.md`). Save its JSON as `.crew/work/<id>/review/ruling.json`; set each ruling's `tokens` to the reviewer's and the judge's reported usage when you have it, else leave 0: `tokens` is the only field of a ruling the session fills, the verdicts and the findings are the judge's (rule 2).
4. **Record**: `crew judgement <id> record --ruling .crew/work/<id>/review/ruling.json`. The verdict follows: a not-proven gate lists its findings by file and line. Fix them (the diff changes, so the next `crew gate run <id>` cuts it again and plans the gates again) or the user decides (`crew skip` only when `policy.json` lists the gate).
5. **A gate that cannot run** for any other reason (a reviewer answered with nothing under "Findings" and `all · …` under "Not answerable"): `crew judgement <id> record <gate> --not-run --reason "<why>"`. Not run leaves the item not proven until the user decides.

Never edit a findings file or a ruling; never launch the judge before every planned reviewer has answered; never re-launch a reviewer to get a different answer. The report's "Judgement gates" section names each gate's verdict, the number of findings and the tokens.
