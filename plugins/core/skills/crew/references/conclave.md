# Conclave

Standard and full routes, after the spec. Goal: say what the request leaves out before a line is written, and let the user decide what only they can. The gap round is yours, in this context, from the checklists; the debate, when it opens, runs in roles with their own contexts.

## The gap round, always

Pick the checklists for the kind of change, `checklists/<kind>.md` in this skill's folder (beside `references/`): `endpoint`, `auth` (a login or a permission), `payment` (a checkout or a payment), `upload`, `migration-or-restore`, `sync` (a third party), `link-target` (a redirect or a link), `deletion`, `merge`, `screen`; a registered pack serves `motion` (an animation or a transition) and `design-contract` (a `DESIGN.md` or its tokens). A change is often two kinds (a deletion behind a permission: `deletion` and `auth`); read each. A registered pack adds its own: `crew pack files checklists <kind>` prints their paths, read beside the core's (`references/packs.md`). Then write `.crew/work/<id>/conclave.md` with the four headings below, each with content or the word "none", answering the checklists' questions for this request. The engine refuses `crew phase <id> next` into Plan until all four have content, until every decision has a counted answer, and until every blocking objection is bound to a criterion or waived.

## Assumed by good practice

What you will do without asking, stated so the user can refuse: "The endpoint is authenticated and paginated." Each line becomes a criterion (`crew criteria <id> add "<text>"`), `preserve` when it keeps something as it is.

## Decisions only the user can make

What two competent engineers would build differently. Record each one as you find it: `crew decision <id> add "<question>" --default "<the conservative answer>"`. Present them on one screen, each with what is being decided, why, the facts, the evidence and the default you propose (mark the work with `crew await <id> user` when the answers need a turn). The user's positive word is the signature: record each answer with `crew decide <id> D-n "<answer>"` yourself; under the default policy no prompt appears and the record says "by the user, relayed by the agent". With Jev configured and `decision` among the policy's asks, each decision gets its marks under its line (`jev: default conservative 0.91; the user's call 0.84`, or `disputed by jev: the default is not the conservative answer (conservative 0.10)`, which the validator's stated-default rule refuses where nobody watches), and each answer its own: one that changes a risk area puts the area among the item's and raises the route (`references/jev.md`). A decision without a counted answer blocks Plan. In an unattended session (headless, bypassPermissions or dontAsk), and only when `policy.json` sets `unattendedDecisions` to `validator`, the validator takes the stated default (see The validator): `crew decide <id> D-n --mode <mode> --validator stated-default`. No default, no validator: the item waits for a person.

## Proposals

Optional improvements, each with its reason. The user takes or leaves each; a taken one becomes a criterion.

## Warnings

What the request asks for that goes against good practice, and why. Each one is an objection: `crew objection <id> add "<text>" --by gap-round --severity advisory`, or `blocking` when building it as asked would be wrong. A blocking objection is answered by binding it to the criterion whose proof resolves it (`crew objection <id> resolve O-n --criterion AC-k`) or by the user's waiver (`crew objection <id> waive O-n --reason "<why>"`, which asks the user and shows in the report as decided by the user). Plan is refused while a blocking objection is neither; the item is not proven while one is open or bound to an unproven criterion. The report lists every objection with its status, and its verdict line says how many were waived.

## When the debate opens

The debate opens on consequences, never on the route alone: a blocking objection from the round, a warning the user wants to build anyway on a risk area, a decision whose answer changes a risk area (who holds a permission, what is hard-deleted, which side of a conflict wins), or the user asking for it. A choice the user's words leave to the team ("the team decides", "your call", "debate it") is debated, not asked: those words are the decision to debate, and the reason names them. It never stands for a decision whose answer changes a risk area: that one is still the user's. Say why in one line: `crew debate <id> open --reason "<the consequence>"`. It is capped: one research pass, at most three experts, one revision.
A role of the debate that ended on an API error is launched once more with the same paths; in Claude Code the plugin moves it to the next model when its own is at its limit (`references/gate.md`, 4b).

## The debate, step by step

Each role is a subagent of this plugin with a clean context and read-only tools. Launch the role: in Claude Code one Agent call by its scoped name; in another runtime as `references/runtimes.md` says, and file its answer with `crew answer file` where the table says the filing is requested. Pass paths and questions, never transcripts; the files under `.crew/work/<id>/conclave/` are yours to write (the ledger is not). The engine saves each role's answer from the SubagentStop hook to its file under `conclave/`; save it yourself only when the file is missing after the role returned (the hook could not read the transcript), and say so. Add up the token usage the Agent tool reports for each call.

1. **Researcher**, `wizardingcode-developer-crew:researcher`: the id, the paths of `brief.md`, `spec.md`, `conclave.md` and `knowledge.md` (the base's entries the engine listed: its "Prior solutions" come from there, by id and title), the open decisions (D-n and question). Save as `conclave/researcher.md`. On a new project the researcher of the strategy is resumed with the open decisions (`SendMessage` to its agent id), never relaunched: its answer is appended to the same file and the verification below runs again.
1b. **Verify the facts**: `crew research <id> verify` checks each quote of `conclave/researcher.md` in its source and, when Jev is configured (`references/jev.md`), asks it whether the source supports the claim; the marks land in `conclave/researcher.verification.json`, which `crew debate <id> close` requires on the current file. Pass that file to the experts with the researcher's.
2. **Experts**, `wizardingcode-developer-crew:expert`, in parallel in one message, at most three, the three lenses shared over the open decisions with consequences: one decision takes all three experts, each proposing its own design; two decisions take two and one (the two on the one with the most consequence); three take one each. Each gets the same paths, `conclave/researcher.md` and `conclave/researcher.verification.json` when it exists, and its one decision, with the knowledge files `crew pack files knowledge --item <id>` prints under a `## Knowledge` line of the prompt (`references/packs.md`). Give each its personality from `${CLAUDE_PLUGIN_ROOT}/skills/crew/personalities/<name>.md`, conservative, creative, adventurous in that order over the experts, so no two experts share a lens; each proposal's second line is `personality: <name>`, which the engine records. Save as `conclave/expert-<n>.md`. Then write `conclave/proposals.md`: each expert's `## Proposal` section only, its `Alternative rejected:` line with it, headed `## P-<n> (D-<m>)`, several to a decision when it has several experts; never its `## Reasoning`.
3. **Devil's advocate**, `wizardingcode-developer-crew:devils-advocate`, and **fault-finder**, `wizardingcode-developer-crew:fault-finder`, in parallel, each given one path, `conclave/proposals.md`, and nothing else. The fault-finder is sceptical and the judge professional by their files; the devil's advocate argues the opposite of each proposal whatever its lens. Save as `conclave/devils-advocate.md` and `conclave/fault-finder.md`. File each of the fault-finder's lines: `crew objection <id> add "<text>" --by fault-finder --severity blocking|advisory`.
3b. **The reply round**, once per item: each expert answers the devil's advocate's case and the fault-finder's objections to its proposal. For each expert, in one message: `crew mail send --to . --agent expert-<n> --type question --file .crew/work/<id>/conclave/proposals.md` (the engine records it relayed), then resume that expert with `SendMessage` to its agent id, giving it the two paths `conclave/devils-advocate.md` and `conclave/fault-finder.md` and the words "answer the objections to your proposal". The SubagentStop hook saves its answer as `conclave/expert-<n>-reply.md` and records the reply; you write nothing. Then write `conclave/replies.md`: each reply under `## R-<n> (P-<n>)`. What the judge receives in step 4 gains `conclave/replies.md`: the replies, never the conversation, never the experts' reasoning.
4. **Judge**, `wizardingcode-developer-crew:judge`, "as judge of the debate": `conclave/proposals.md`, `objections.json`, `conclave/researcher.md`, `conclave/devils-advocate.md`, `conclave/replies.md` (when the round ran), and the decisions with the answers given so far (from `crew status --json`). Save as `conclave/judge.md`.
5. **One screen to the user**: the proposals in a line each, with each proposal's rejected alternative and why, the objections with their severity, the ruling, what it leaves open. Each decision in the form rule 4 asks (what is being decided, why, the facts, the evidence, the default you propose); their positive word is the signature, `crew decide <id> D-n "<answer>"`. The user may decide against the ruling: `crew objection <id> waive O-n --reason "<their words>"`, which asks them, and the report says "decided by the user".
6. **One revision**: when an answer changes a proposal, the judge once more, with the user's answers in the prompt, on the same files; it replaces `conclave/judge.md`. No second round of experts.
7. **Close**: `crew debate <id> close --tokens <the sum>`. Amend `spec.md` from the ruling (Design, criteria); add each criterion it names (`crew criteria <id> add "<text>" --kind <kind>`); bind each blocking objection (`crew objection <id> resolve O-n --criterion AC-k`). What the judge left open stays a decision: answered, or `crew await <id> user`.

## The leads' validation

Standard and full routes, after the gap round (and the debate, when it opened). With the spec and the conclave written, `crew team <id>` prints the seats: launch every `lead-<team>` seat in parallel, one Agent call each, `subagent_type` `wizardingcode-developer-crew:tech-lead`, the team and `--what spec` in the prompt, with the paths of `spec.md`, `conclave.md`, your team's findings when they exist, and the item's decisions as `crew status --json` prints them. The hook saves each answer as `conclave/lead-<team>.md`. A lead resumed for another round answers into `conclave/lead-<team>-reply.md`, the earlier reply archived beside it as `.round<n>.md`; record that file, never the round-1 file, since the engine refuses a file whose content it already recorded for that lead. Record each: `crew validation <id> record --what spec --by lead-<team> --file .crew/work/<id>/conclave/lead-<team>.md`. A `returned` reopens Specify: revise the spec from the returns (each names a file, a line and what must change), then record the leads again; a new spec is a new round, `team.maxValidationRounds` is two, then the user decides (`crew continue <id> validation` once, or their own answer). The plan waits for every lead's `validated`.

## The validator

The validator decides only what a rule covers: a spec approval under `complete-gap-round` and, where no person watches, a decision's stated default. With a person present, when the round found nothing to decide, you approve under the rule yourself: `crew approve <id> spec --validator complete-gap-round`, refused by the engine while a section, a default or a binding is missing, and counted because the person is there to object; the judge does not run. Where no person watches (headless, bypassPermissions or dontAsk) and `policy.json` sets `unattendedDecisions` to `validator`, the judge reads the rule first: launch `wizardingcode-developer-crew:judge` "as validator" with `spec.md`, `conclave.md`, `objections.json` and the rule's name; save the answer as `conclave/validator-<rule>.md`. "holds": run the command with `--mode <mode> --validator <rule>` (`crew approve <id> spec …` or `crew decide <id> D-n …`). "does not hold": do what its "Missing" names when it is yours to do (a section, a default), otherwise `crew await <id> user`. Under policy `wait` or `count`, as before. The validator never waives an objection and never skips a gate or a test-first record. The record always says "by the validator (rule: …)", never "by the user".

## Then

`crew phase <id> next` into Plan, and on as the method says.
