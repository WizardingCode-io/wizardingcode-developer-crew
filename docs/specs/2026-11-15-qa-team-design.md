# The QA team: subjects, sources, tools, MCP servers and skills. Design

- Status: decided by the user on 2026-11-15, point by point. A definition: no engine, plugin or pack change comes with it
- Source: the request document `docs/requests/2026-11-15-qa-team-definition.md`
- The sources, the tools, the MCP servers and the skills were read on the web on 2026-11-15, each at the URL beside it; a URL followed by "(not opened)" was not read that day

## 1. Why

The engine has a `qa` team (`packages/engine/src/team.ts`, `TEAMS.qa`) with one member, `review-test-quality`, the gate `test-quality`, a seat on every item and `validates: true`. Nothing in the engine or the plugin says where that team reads about what it reviews, which tools it runs, or which MCP servers and skills it uses.

The user gave no sentence on what the team is for, so this document quotes none.

This document records what the user decided, so the item that builds it starts from decisions and asks none of them again.

## 2. What exists today

- The team's entry (`packages/engine/src/team.ts`, `TEAMS.qa`): the lead `lead-qa`, the member `review-test-quality`, the gate `test-quality`, mandatory on every item (`kind: "always"`), `validates: true`.
- The test-quality reviewer (`plugins/core/agents/review-test-quality.md`) reads the tests a change added or changed, and the code they cover, against the item's criteria. It does not run them: the test gate did. For each `behavior` criterion it names the test that fails when the behaviour is reverted; it reads a mutation report when its prompt names one; on an audit item it reads the listed files whole. It has Read, Grep and Glob, runs no command and names no outside source.
- The rubric (`plugins/core/skills/crew/rubrics/test-quality.md`) asks eight questions: which test fails if a `behavior` criterion's behaviour is reverted; whether a test is true by construction (it asserts its own mock's return, its own fixture's content, only that nothing threw, or a snapshot with no expectation stated); whether a `preserve` criterion names the tests it relies on and those tests exercise the preserved behaviour; whether an `observed` criterion's recorded reason holds; whether a test asserts what a caller sees and not private names, call counts or the order of internal calls; whether a test's name and failure message say which criterion broke; whether a mutant survived on a line of the diff, when a report exists; whether a fixture names a client, a customer or a real workspace. It names Stryker and Infection as the mutation tools a profile may have, and it judges the change alone, never the repository.
- `crew tdd` (`plugins/core/skills/crew/references/build.md`) records the proof of each criterion: `red` and `green` for a `behavior` criterion, a red that passes being rejected and a green with no earlier red being rejected; `before` and `after` for a `preserve` criterion; `observed`, with a reason why no red run can exist, for an `observed` criterion.
- The `e2e` gate (`plugins/core/skills/crew/references/gate.md`) is planned once per item when the change touches an interface file or a public-api path, or when the policy requires it. It checks the environment's health, starts the profile's environment when nothing answers, runs the project's end-to-end command, reads the console file and the environment's logs, and stops what the engine started. Its verdict is the command's exit, then the first console entry at error or warning, then the first log line at error or warning. A Playwright project records its console by importing the crew's fixture (`plugins/core/e2e/playwright.mjs`).
- The team's lead (`plugins/core/agents/tech-lead.md`) validates a spec and a delivery, read-only. On a spec, the criteria the team will have to prove are observable and provable: for QA, "a test or a run names each". On a delivery, every brief says what changed, what was proven and what is left, and the gates the team owns passed on the merged tree.
- The rubric has no question on strategy and levels, flaky tests, test data and state, property-based testing and fuzzing, the suite in CI or the testing of systems with AI; of test doubles it asks only whether a test asserts its own mock's return (question 2).
- The backend team's definition (`docs/specs/2026-11-14-backend-team-stacks-design.md`) names the stacks and the frameworks this document refers to as "the project's stack" and "the project's framework", and installs Laravel Boost with Laravel.
- The security team's definition (`docs/specs/2026-11-15-security-team-design.md`) gives the sources for personal data, and already installs promptfoo's plugin of four skills, SonarQube's server and Trail of Bits' skills; it holds GitHub's server as this definition does (section 5, the row "GitHub"), and it leaves promptfoo's server out, by the user's decision of 2026-11-16. It has no row on fuzzing: what it gives this team on that subject is Trail of Bits' set, which holds the fuzzing skills section 5 names.
- The ETL team's definition (`docs/specs/2026-11-15-etl-team-design.md`) gives the sources for schema and migrations.
- The researchers team's definition (`docs/specs/2026-11-15-researchers-team-design.md`) gives Context7, for the documentation of the version a project uses.
- The architects team's definition (`docs/specs/2026-11-15-architects-team-design.md`) gives the sources for contracts, for boundaries and integrations and for AI and agents, runs Schemathesis, Pact and promptfoo, measures load and performance, and already installs promptfoo's server, Laravel Boost's, Sentry's, Datadog's and SonarQube's, and Matt Pocock's skills. Rule 6 of section 5 closes the point its section 6 left open.
