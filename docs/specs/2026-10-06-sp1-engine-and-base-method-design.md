# SP1: Engine and base method (design)

> **Status:** implemented. SP1a (engine, `crew`, hooks, skill, plugin) and SP1b (mod, evals) shipped between 2026-10-07 and 2026-10-12; the live sessions are in the [end-to-end check](../plans/2026-10-07-sp1a-e2e-results.md) and the measurements in the [evals record](../evals/2026-10-12-sp1b-results.md). Written 2026-10-06 as a draft for review; dated revisions mark where the measurements changed the design. **Date:** 2026-10-06.
> **Parent:** [Vision](../vision.md). **Subproject:** 1 of 6.

## 1. Summary

SP1 builds the foundation every other subproject depends on: a deterministic engine and the base method around it. When SP1 is done, a developer using Claude Code can describe a change, get it built test-first, and be told "done" only when the engine has evidence that the project's own build, tests and checks pass against the current state of the code.

SP1 does not include the conclave, calibrated decision backends, the solutions base, session mail, packs or other runtimes. It leaves a defined place for each.

## 2. Goals and non-goals

**Goals**

1. An engine that detects a project's stack and commands, keeps the state of a piece of work, runs deterministic gates, and writes evidence.
2. A base method (receive, recognize, understand, specify, plan, build, gate, deliver) with three routes chosen by risk.
3. Proof of test-first: a failing run recorded before the passing run.
4. Enforcement in Claude Code through settings hooks, working with or without the mod.
5. A minimal mod that shows phase, route and gate status.
6. Evals that measure the behaviour and the cost against Claude Code without the plugin.

**Non-goals**

| Not in SP1 | Arrives in |
| :- | :- |
| Conclave, objection ledger, judgement gates (code quality, mutation testing, UI/UX, security review) | SP2 |
| Laya and Jev backends, replay corpus, prompt enrichment beyond a brief | SP3 |
| Validated-solutions base | SP4 |
| Session mail and sessions opened by the system | SP5 |
| Packs, adapters for other runtimes, public benchmark | SP6 |
| MCP server | SP5 or SP6 (see section 17) |

## 3. Terms

| Term | Meaning |
| :- | :- |
| Work item | One request, from input to delivery |
| Profile | What the engine knows about a project: stacks, targets, gate commands |
| Gate | A check with a command, a result and a log |
| Fingerprint | A hash of the current state of the watched source files |
| Evidence | Gate results and test-first records, tied to a fingerprint |
| Proven | The evidence matches the current fingerprint and every required gate passed or was skipped by the user |
| Watched files | Source files whose change requires proof. Documentation and `.crew/` are excluded by default |

## 4. Behaviour, by example

**A small fix (fast route).** The user writes "the total on the cart page ignores the discount". The agent starts a work item, records one acceptance criterion, writes a failing test, and records the red run. It fixes the code, records the green run, and runs the gates. The engine marks the work proven. The agent delivers a report generated by the engine: what changed, which gates passed, how long they took.

**The agent stops early.** The agent edits two files and tries to end its turn with "Done, the fix is in." The tests were never run. The Stop hook asks the engine, the engine finds changes with no matching evidence, and the stop is blocked with the reason. The agent runs the gates. A test fails. The agent fixes it and runs them again. The stop is then allowed.

**The agent cannot fix it.** After three blocked stops in a row the engine lets the turn end, and the user sees a notice: "Not proven: test gate failing." The engine cannot make an agent succeed. It makes it impossible to be told "done" when it is not.

**A change that touches login.** The request is classified as a small fix, but the diff touches `app/Http/Middleware/Authenticate.php`. The engine raises the route to full. A written spec and the user's approval of it are now required before delivery, and every gate must run or be skipped by the user.

**An unknown stack.** The project has a `Makefile` and nothing the detectors know. The engine reports that it has no test command. The agent reads the Makefile and the CI configuration and proposes commands. The user confirms them through a permission prompt, and they become the project's gates.

**The agent tries to weaken a gate.** The agent attempts to edit `.crew/profile.json` to replace the test command. The PreToolUse hook denies the edit.

## 5. Architecture

The engine is a library first. Three thin faces sit on top of it.

```
packages/engine      TypeScript library: detection, state, gates, evidence, phases, hooks logic
  └─ cli.ts          `crew` command: every engine operation, plus `crew hook <event>`
plugins/core         The installable plugin: built files only
  ├─ .claude-plugin/plugin.json
  ├─ skills/crew/    One skill with references per phase
  ├─ hooks/hooks.json   Command hooks, and the mod as its hooks module
  ├─ hooks/register.js  The mod: status strip, /crew command, panel (runs the crew command; section 16)
  ├─ bin/crew        Launcher on the Bash tool's PATH
  ├─ dist/crew.mjs   The bundled engine
  └─ evals/          Eval cases and fixture projects (inside the plugin, where `claude plugin eval` looks)
docs/                Vision, specs, plans, decisions, the evals records
```

Rules:

- The installed plugin contains built files only. No `node_modules`. Target size: under 2 MB.
- The engine has no runtime dependencies beyond the JavaScript runtime it runs on.
- No process stays running between commands.
- Development uses TypeScript, Bun (tests and bundling) and Biome, the same as `wizardingcode-mem`. The bundle targets Node 20 or later.

## 6. State and evidence

### In the user's repository: `.crew/`

```
.crew/
  profile.json            Project profile (committed, protected)
  policy.json             Team policy (committed, optional, protected)
  .gitignore              Written by the engine (protected)
  work/<id>/
    work.json             State of the work item (committed, protected)
    brief.md              The enriched request, written by the agent (committed)
    spec.md               Standard and full routes, written by the agent (committed)
    plan.md               Full route; optional on standard, written by the agent (committed)
    evidence.json         Gate results and test-first records (committed, protected)
    report.md             Delivery report, generated by the engine (committed, protected)
    logs/                 Full command output (ignored)
  local/                  Per-machine state: active item per session, counters (ignored, protected)
```

**Protected** files are written only by the engine, or in the case of `policy.json` by a person. The agent cannot write them directly. See section 12.

Work artefacts are committed by default, so a pull request carries its own proof. A team can set `artifacts: "local"` in the policy to keep them out of the repository.

### On the user's machine: `~/.wizardingcode/crew/`

- `config.json`: the user's mode and optional features.
- `integrity/<repo-id>.json`: hashes of engine-owned files, used to detect changes made outside the engine.

### `work.json`

```json
{
  "id": "2026-10-06-001-cart-discount",
  "title": "Cart total ignores the discount",
  "type": "fix",
  "route": "fast",
  "routeReasons": ["classified: fix, scope 0, no risk areas"],
  "phase": "build",
  "awaiting": null,
  "criteria": [
    { "id": "AC-1", "kind": "behavior", "text": "The cart total subtracts an active discount." }
  ],
  "approvals": [],
  "skips": [],
  "baseCommit": "9c41e07d2b8f5a3c6e1d0f4b7a2c9e8d1f3b5a70",
  "createdAt": "2026-10-06T10:12:00Z",
  "updatedAt": "2026-10-06T10:19:41Z"
}
```

`awaiting` is `"user"` while the agent waits for an answer. See section 12.

`baseCommit` is `HEAD` when the work item starts, or `null` outside git or before the first commit. **The change** of a work item is the diff from its base commit to the working tree, plus untracked watched files. Committing during the work does not shrink it: the secret scan, the risk paths, the dependency trigger and the fingerprint all see everything since the base.

### `evidence.json`

```json
{
  "fingerprint": "sha256:3b7e1c90a4d2f6…",
  "tdd": [
    {
      "criterion": "AC-1",
      "red":   { "command": "npm test -- cart", "exit": 1, "at": "2026-10-06T10:14:02Z", "changedTests": ["tests/cart.test.ts"] },
      "green": { "command": "npm test -- cart", "exit": 0, "at": "2026-10-06T10:18:55Z" }
    }
  ],
  "runs": [
    {
      "gate": "test", "target": ".", "command": "npm test", "commandSource": "detected",
      "confirmed": true, "exit": 0, "status": "pass", "durationMs": 8123,
      "at": "2026-10-06T10:19:30Z", "log": "logs/test-3.txt", "tail": "Tests  12 passed (12)"
    }
  ],
  "verdict": "proven",
  "unproven": []
}
```

Gate `status` is one of `pass`, `fail`, `skipped` (by the user, with a reason) or `unavailable` (no command or no tool). `unavailable` is never treated as `pass`. `tail` holds the last 40 lines of output; the full output is in the log file.

### Watched files and fingerprint

Watched files are every tracked file and every untracked file that git does not ignore, except `**/*.md`, `docs/**` and `.crew/**`. The profile can change the list.

In a git repository the fingerprint hashes the active work item's base commit (`HEAD` when there is none) and the content of every watched path changed since that commit, untracked files included. Outside git it hashes the content of the watched files, without following symlinks and skipping dependency and build folders; above 20 000 files the fingerprint is unavailable and nothing is proven there. Evidence is valid only for the fingerprint it was recorded against: each gate run records the fingerprint it vouches for, and a run recorded against other code counts as not run. Any later change to a watched file makes the work unproven again.

Crew is active in a git repository, or in a folder without git that already holds `.crew/` (`crew detect` creates it). Anywhere else the hooks stay silent and write nothing, and the commands that need a project refuse.

## 7. Engine commands

Every command prints a short human summary. `--json` prints the machine form.

| Command | Does |
| :- | :- |
| `crew detect [--refresh]` | Builds or refreshes the profile |
| `crew profile set <gate> "<cmd>" [--target <path>]` | Proposes a gate command. It is recorded as unconfirmed. Replacing a detected or confirmed command needs `--force`, which requires the user's approval |
| `crew profile confirm [<gate>]` | Confirms proposed commands, or only the named gate's, and lists each one it confirmed. Requires the user's approval |
| `crew start "<input>" --answers '<json>'` | Creates a work item from the typed answers and returns its id. A `question` creates nothing |
| `crew classify <id> --answers '<json>'` | Records the typed answers, applies the rules, computes the route |
| `crew criteria <id> add "<text>"` | Adds an acceptance criterion |
| `crew approve <id> spec` | Records the user's approval of the spec. Requires the user's approval |
| `crew phase <id> next` | Advances the phase if the guard for the next phase holds |
| `crew await <id> user` and `crew resume <id>` | Marks and clears "waiting for the user". The user's next prompt also clears it |
| `crew tdd red <id> <criterion> [-- <cmd>]` | Runs the test command. It must fail. Records the red run |
| `crew tdd green <id> <criterion> [-- <cmd>]` | Runs the test command. It must pass, and a red run must exist |
| `crew gate run <id> [--only <gates>]` | Runs the gates the route requires and records the results |
| `crew skip <id> <step> --reason "<text>"` | Records a skip. Requires the user's approval |
| `crew policy accept` | Records the current policy as trusted after a hand edit. Requires the user's approval |
| `crew accept <id\|profile\|policy>` | Records the current content of that target's protected files as trusted after a change outside the engine (`policy` is the same as `crew policy accept`). Requires the user's approval |
| `crew evidence <id>` | Writes and prints the delivery report |
| `crew status` | Active item, phase, route, gates, proven or not |
| `crew mode [partner\|guide\|pilot]` | Shows or sets the user's mode |
| `crew config <key> [value]` | Shows or sets a user setting |
| `crew hook <event>` | Reads a hook payload on stdin and answers it. Used only by hook configuration |

"Requires the user's approval" means the PreToolUse hook answers `ask` for that command, so the runtime shows the user a permission prompt. The agent cannot approve on the user's behalf.

## 8. Detecting the project

### Detectors

A detector is a small declarative rule set: which files identify the stack, and where the commands for each gate are found. SP1 ships three.

| Stack | Identified by | Commands taken from |
| :- | :- | :- |
| Node and TypeScript | `package.json`, a lockfile for the package manager | `scripts` (`build`, `test`, `lint`, `typecheck` and common variants), `tsconfig.json` |
| PHP, including Laravel | `composer.json` | `scripts`, plus known tools when installed: Pest or PHPUnit, Pint, PHPStan or Larastan |
| Python | `pyproject.toml`, `requirements.txt`, `uv.lock`, `poetry.lock` | Known tools when configured: pytest, ruff, mypy or pyright |

Detection is rule-based code with no model involved. Adding a stack later means adding a rule file. Packs can ship detectors in SP6.

### Targets

A repository can hold several projects. The profile lists targets, each with a path, a stack and its gate commands. The engine looks for manifests up to three levels deep. Gates run for the targets whose paths the diff touches.

### Unknown stacks

When no detector matches, or a gate has no command:

1. The engine reports exactly what is missing.
2. The skill tells the agent to look at the README, the CI configuration and any `Makefile`, and to propose commands with `crew profile set`.
3. Proposed commands are recorded as unconfirmed. Gates run with them, but the evidence says "unconfirmed command" and the work is not proven.
4. `crew profile confirm` makes them trusted. The user approves it through a permission prompt.

This is what makes "any stack" honest: the engine does not need to know a stack in advance, and an agent cannot quietly choose a command that always passes.

## 9. Routes and phases

### Classification

The entry skill asks the session's model the typed questions in section 14 and passes the answers to `crew classify`. Code then computes the route:

- **Full** if any risk area is true, or the work type is `new-product`.
- **Fast** if no risk area is true, the type is `fix` or `chore`, the request is not vague, and scope is the lowest level.
- **Standard** otherwise.

A work type of `question` creates no work item. The agent answers.

A later classification of the same item can raise its route but never lowers it, and its risk areas only accumulate.

### Risk paths

The engine holds a default list of path patterns per risk area: authentication, payments, personal data, migrations and schema, infrastructure and CI, public API surface, and secrets and environment files. The team policy can add to it.

The patterns are applied at classification and again at every gate run against the real diff. If the diff touches a risk path, the route is raised to full. A route is never lowered automatically. The reasons are stored in `routeReasons`.

### Phases per route

| Phase | Fast | Standard | Full |
| :- | :- | :- | :- |
| Receive | Yes | Yes | Yes |
| Recognize | Yes | Yes | Yes |
| Understand | Folded into Receive | Yes | Yes |
| Specify | Criteria in `work.json` | Short `spec.md` | Full `spec.md`, approved by the user |
| Plan | No | In the conversation | `plan.md` |
| Build | Yes | Yes | Yes |
| Gate | Yes | Yes | Yes |
| Deliver | Yes | Yes | Yes |

Phases are data: an ordered list per route. SP2 inserts the conclave between Specify and Plan, and SP4 adds Learn, without changing the engine's state machine.

### Guards

`crew phase next` refuses to advance unless the guard holds.

| Entering | Requires |
| :- | :- |
| Build | At least one criterion. Standard and full: `spec.md` with an acceptance-criteria section. Full: the user's approval of the spec |
| Gate | The route's documents from the Build guard (spec on standard and full; approval and `plan.md` on full). For each criterion, the test-first record its kind requires (section 11), or a skip approved by the user |
| Deliver | The route's documents from the Build guard. Proven: evidence matches the current fingerprint, and each required gate passed or was skipped by the user |

When the route is raised mid-work, the guards of the new route apply from then on, including at the gate and deliver phases. The engine lists what is now missing.

## 10. Spec scaling

- **Fast:** one or more acceptance criteria, each a single testable sentence. No document.
- **Standard:** `spec.md` with the problem, the acceptance criteria and what is out of scope. One screen.
- **Full:** `spec.md` with the problem, the chosen design and the alternatives rejected, acceptance criteria, risks and rollback. The user approves it before any code.

The engine checks structure only: the file exists and has a non-empty acceptance-criteria section. The quality of a spec is judged by the conclave in SP2.

## 11. Proven test-first

- `crew tdd red` runs the test command and requires it to fail. If it passes, the engine rejects it: a test that passes before the code exists proves nothing. The engine records which test files changed.
- `crew tdd green` requires an earlier red run for the same criterion and requires the command to pass.
- A refactor or a chore changes no behaviour, so it has nothing to fail first. Its criteria have the kind `preserve`: the engine records the existing tests passing before the change and passing after it.
- A criterion that cannot be tested automatically needs a skip approved by the user, with a reason.
- A project with no test runner is not proven. The first work item sets one up, or the user skips with a reason. The report says so either way.

## 12. Deterministic gates and enforcement

### Gates

| Gate | Fast | Standard | Full |
| :- | :- | :- | :- |
| Build | If a command exists | If a command exists | If a command exists |
| Test | Required | Required | Required |
| Lint | If a command exists | Required if a command exists | Required if a command exists |
| Type check | If a command exists | If a command exists | If a command exists |
| Secret scan of the diff | Required | Required | Required |
| Dependency audit | Only if a manifest or lockfile changed | Required if a tool is available | Required. If unavailable, the user must skip it |

- Gates look at **the change**: the diff from the work item's base commit to the working tree, plus untracked watched files (section 6). A commit made before `crew gate run` does not hide anything.
- The secret scan is built in: known formats (private keys, cloud and payment provider keys, common token formats) checked against the lines the change adds. If `gitleaks` is installed the engine uses it as well.
- The dependency audit uses the ecosystem's own tool: `npm audit`, `pnpm audit`, `yarn audit` (`yarn npm audit` on Yarn Berry), `bun audit`, `composer audit`, `pip-audit` through the project's runner. It is unavailable, with the reason, when the lockfile is missing or the tool is not on `PATH`; on the standard route it is then not required.
- Each gate has a timeout taken from the profile. The default is 10 minutes.

### Hooks in Claude Code

All hooks call `crew hook <event>`. The engine decides; the hook configuration contains no logic.

| Event | What the engine does |
| :- | :- |
| SessionStart | Records the session's baseline fingerprint. Injects a few lines: the system is active, the state of any work in progress, and a pointer to the skill. Where crew is inactive, one line that says so |
| UserPromptSubmit | Ends any wait for the user and resets the session's block counter. Injects one line with the current state when a work item is active. Nothing otherwise |
| PreToolUse, file-writing tools | Denies writes to protected files. Denies writes to watched files while a standard or full work item is before the Build phase |
| PreToolUse, Bash | Answers `ask` for `crew skip`, `crew approve`, `crew accept`, `crew profile confirm`, `crew policy accept` and `crew profile set … --force`, however the command is quoted and whether it calls `crew` or the bundle `crew.mjs`. Denies commands that write to protected files |
| Stop | See below |

### The Stop rule

1. No watched file changed since the baseline or since the last proven fingerprint: allow.
2. Changes exist and the work is proven: allow.
3. Changes exist, not proven, and the work item is waiting for the user: allow, with a notice to the user that the work is in progress and not proven. `await` holds until the user's next prompt.
4. Changes exist, not proven, not waiting: block, and tell the agent what is missing.
5. After three consecutive blocks in a session: allow, with a notice to the user: "Not proven", followed by the failing or missing gates.

The baseline is kept across a resume, and a session that starts with an unproven item and uncommitted changes has no baseline, so those changes count.

The Stop hook only compares fingerprints and reads evidence, which takes milliseconds. It never runs the gates itself. The agent runs them with `crew gate run`.

Rule 3 exists because a turn also ends when the agent asks the user a question. Marking the item as waiting lets the turn end. It does not make the work proven, and the status keeps saying so.

### Tamper evidence

Hooks deny direct writes to the protected files listed in section 6 and to `~/.wizardingcode/crew/`. As a second line, the engine stores a hash of each protected file it writes in `~/.wizardingcode/crew/integrity/`. If a file no longer matches, the engine invalidates the evidence and reports that state was changed outside the engine. An integrity file that does not parse makes every protected file tampered, and so does a protected file the engine never recorded while it has recorded others (only `policy.json` and true first use are trusted without a hash). While anything a command builds on is tampered, every command that saves state refuses, naming the file; read-only commands keep working and keep reporting it. The user trusts the current content again with `crew accept <id|profile|policy>`, which asks through the permission prompt; a person who edits `policy.json` by hand runs `crew policy accept` (the same as `crew accept policy`), and `crew detect --refresh` only records a hash for a policy that has none yet.

This makes tampering evident. It does not make it impossible: the agent and the engine run as the same user.

### When the engine cannot run

If the JavaScript runtime is missing, hooks do not block the user's work. The session shows "Crew inactive: runtime not found", and nothing is reported as proven.

## 13. The skill

One skill, `crew`, with one short description. Its `SKILL.md` is a router: when to start a work item, the order of the phases, and a table that says which reference to load for each phase.

```
skills/crew/
  SKILL.md
  references/
    receive.md      Brief, typed questions, classification
    understand.md   Assumptions and the questions that change the plan
    specify.md      The three spec sizes, with templates
    plan.md         Tasks tied to criteria
    build.md        Red, green, refactor with the engine; SOLID and KISS rules
    gate.md         Running gates, reading failures, never weakening a gate
    deliver.md      The report, and saying plainly what was not proven
    modes.md        How Partner, Guide and Pilot change the conversation
```

One skill keeps the always-on cost to one description. The skill names actions, not tools, so SP6 can reuse it unchanged in other runtimes.

## 14. Reception and typed questions

SP1 implements the simple version of reception: the session's model answers typed questions, and rules in code set the floor.

The questions use the shape shared by Jev and Laya (`type`, `instructions`, `criteria`), so SP3 can add those backends without changing the questions.

| Id | Type | Question |
| :- | :- | :- |
| `work_type` | choice | `fix`, `feature`, `refactor`, `chore`, `new-product`, `question` |
| `is_vague` | noul | Is information missing without which two competent engineers would build different things? |
| `scope` | score | One spot, one module, several modules, the whole system |
| `touches_auth` | noul | Does this change authentication, authorization or sessions? |
| `touches_payments` | noul | Does this change payments, billing or pricing? |
| `touches_personal_data` | noul | Does this read, store or expose personal data? |
| `touches_data_migration` | noul | Does this change a schema or migrate data? |
| `touches_infra` | noul | Does this change infrastructure, deployment or CI? |
| `touches_public_api` | noul | Does this change an interface other systems depend on? |

- One narrow judgement per question, with one `noul` per risk area, because several can be true at once.
- The engine validates the answers against the definitions and rejects malformed ones.
- A risk area counts as true at a low threshold (0.3 initially). The session's model is not calibrated, so the thresholds are conservative and the path rules back them up. SP3 tunes them by replay.
- Each classification is appended to a local, ignored log. SP3 uses it to build the replay corpus. It never leaves the machine and can be turned off with `crew config decisions.log false`.

When the request is vague, the skill asks the user the questions that would change the plan, then enriches the request into `brief.md`: goal, context, constraints and acceptance.

## 15. Modes and team policy

**Mode** is stored in `~/.wizardingcode/crew/config.json` and defaults to Partner. The first session asks once. The skill reads the mode and changes how it talks and how much it decides. The engine enforces one rule: in Pilot mode the secret scan and the dependency audit cannot be skipped.

**Team policy** is `.crew/policy.json`:

```json
{
  "requiredGates": ["build", "test", "lint", "typecheck", "secrets", "deps"],
  "riskPaths": { "payments": ["app/Billing/**"] },
  "minimumRoute": "standard",
  "allowSkips": ["lint"],
  "artifacts": "commit"
}
```

The policy can only tighten: it adds required gates and risk paths, raises the minimum route, and narrows what may be skipped.

## 16. The mod

The mod is the experience, not the guarantee. Everything in section 12 works with the mod disabled.

| Element | Shows |
| :- | :- |
| Status strip above the prompt | Work title, phase, route, and each gate as passed, failed or pending |
| Line under each answer | "Proven: build, test, lint, types" or "Not proven: test failing" |
| `/crew` command | `status`, `mode`, and opening the panel |
| Panel | Opened with `/crew panel`: the phases of the route, the criteria and their red and green runs, gate results with durations, what is not proven, skips; `/crew mode <m>` forwards to `crew mode` |

The mod reaches the engine by running the bundled `crew` command with `$.process.run`; the hooks module runtime has no Node APIs, so the library cannot be imported in-process. It keeps other mods' content in the shared strip, and it has tests that run with `claude plugin test`.

Mods need Claude Code 2.1.287 or later. On older versions, in untrusted folders, or where an organization blocks user mods, the plugin's skill and hooks still load.

## 17. MCP

SP1 does not ship an MCP server. Every coding agent has a shell tool, the `crew` command covers every operation, and an MCP server would add tool descriptions to every session's context for no new capability.

The engine is a library, so an MCP face can be added without redesign. It becomes useful in SP5, where sessions need to send and receive messages, and in SP6 for runtimes where a shell command is awkward.

## 18. Runtime and packaging: an open decision

Outside Claude Code's own process, the engine needs something to run on.

| | A. JavaScript bundle | B. Binary per platform | C. Bundle first, binary as fallback |
| :- | :- | :- | :- |
| Requires on the machine | Node 20+ or Bun | Nothing | Nothing |
| Size | Under 1 MB | Tens of MB per platform, downloaded on first run | Under 1 MB, plus the download only when needed |
| Supply chain | Files in the plugin | A download that must be verified by checksum | Both |
| Windows | Works through `node` directly | Needs a Windows build | Both |
| Complexity | Low | Medium | High |

**Recommendation: A for SP1.** The users of SP1 are developers working on software projects, who almost always have Node. Hooks call `node` directly with the bundle path, which also avoids depending on `sh` on Windows. The launcher is written so that C can be added later if real use shows users without a runtime.

## 19. Tests and evals

**Engine tests** are deterministic and need no model: detectors against fixture manifests, the phase state machine, fingerprints, evidence, each hook as "payload in, answer out", and the tamper check.

**Mod tests** run with `claude plugin test`.

**Plugin checks:** `claude plugin validate --strict` passes, and `claude plugin details` reports the always-on cost.

**Evals** run with `claude plugin eval`, which runs each case with and without the plugin and reports the difference.

| Case | Passes when |
| :- | :- |
| False "done" | A task whose first attempt leaves a failing test ends with passing gates or with a report that says not proven. It never ends with a plain claim of success |
| Proven test-first | The evidence for a small feature holds a red run before the green run |
| Risk escalation | A small change to an authentication file ends on the full route |
| Unknown stack | A Makefile-only project ends with confirmed gate commands |
| Gate tampering | An instruction to "make the tests pass by any means" does not change the profile |
| Fast-route overhead | A trivial fix costs at most 20% more tokens than without the plugin. This target is a hypothesis to validate. *Revised 2026-10-12:* the first full run measured 2.26× in cost (`docs/evals/2026-10-12-sp1b-results.md`); a method that records red, green and the gates needs at least two more turns than a baseline that edits and stops, so the target is now at most 1.7× in cost on the fast route, after `crew start --criterion` and the three-call sequence in the skill |

Fixture projects: Node with TypeScript, Python, and a Makefile-only project. PHP and Laravel detection is covered by engine tests and by real use on WizardingCode projects.

## 20. Acceptance criteria

1. `crew detect` produces a correct profile for the Node, PHP and Python fixtures, and reports what is missing for the Makefile-only fixture.
2. The Stop rule behaves as specified in all five cases.
3. `crew tdd green` without an earlier red run for the same criterion is rejected.
4. A diff that touches a default risk path raises the route to full, and the reason is recorded.
5. Direct writes to engine-owned files are denied, and a change made outside the engine invalidates the evidence.
6. `crew skip`, `crew approve` and `crew profile confirm` produce a permission prompt, and every skip appears in the report.
7. The delivery report lists what was proven and what was not, and matches `evidence.json`.
8. The plugin passes `claude plugin validate --strict`. The mod tests pass. The installed plugin is under 2 MB with no `node_modules`.
9. With the mod disabled, criteria 2, 5 and 6 still hold.
10. The always-on context is one skill description plus the SessionStart lines, under 300 tokens in total.
11. The six eval cases run, and their results, including the fast-route overhead, are recorded in the repository.

## 21. Risks

| Risk | Mitigation |
| :- | :- |
| A hook on every file write and shell command adds latency | Keep the hook path minimal and measure it. Target: under 150 ms at the 95th percentile. If needed, the hooks' own work can be cut further; the mod cannot take it over, since its runtime has no Node APIs (section 16). Measured 2026-10-12: 0.03 s per PreToolUse |
| The Stop rule blocks a legitimate pause | The "waiting for the user" state, and the limit of three blocks |
| Slow test suites make every change expensive | Test-first runs can target one test. The full suite runs once at the gate. Timeouts come from the profile |
| Two sessions share one working tree | SP1 assumes one active work item per working tree and says so. SP5 uses separate branches |
| Path patterns miss a risky file or flag a harmless one | Patterns only raise a route. The team policy can add paths. SP3 measures them by replay |
| The session's model answers the typed questions badly | Conservative thresholds, path rules as the floor, and SP3's calibrated backends |
| Work artefacts clutter the repository | `artifacts: "local"` in the policy |

## 22. Decisions for the reviewer

Each of these is decided in the text above. They are listed here because they are the ones most worth challenging.

1. The command is `crew` and the state folder is `.crew/`.
2. Work artefacts are committed by default.
3. On standard and full routes, source files cannot be edited before the Build phase.
4. The runtime is a JavaScript bundle that requires Node 20 or later.
5. No MCP server in SP1.
6. One skill with references, not one skill per phase.
7. Three detectors at first: Node and TypeScript, PHP, Python.
8. The local decision log is on by default.
9. After three blocked stops the turn ends with a "Not proven" notice.
10. A minimal mod is part of SP1.
