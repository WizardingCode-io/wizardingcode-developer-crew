# The security team: subjects, sources, tools, MCP servers and skills. Design

- Status: decided by the user on 2026-11-14 and 2026-11-15, point by point. A definition: no engine, plugin or pack change comes with it
- Source: the request document `docs/requests/2026-11-15-security-team-definition.md`
- The sources, the tools, the MCP servers and the skills were read on the web on 2026-11-15, each at the URL beside it; a URL followed by "(not opened)" was not read that day

## 1. Why

The engine has a `security` team (`packages/engine/src/team.ts`, `TEAMS.security`) with one member, `review-security`, the gate `security`, a seat on every item and `validates: true`. Nothing in the engine or the plugin says where that team reads about what it reviews, which tools it runs, or which MCP servers and skills it uses.

This document records what the user decided, so the item that builds it starts from decisions and asks none of them again.

## 2. What exists today

- The security reviewer (`plugins/core/agents/review-security.md`) reads a change against the rubric `plugins/core/skills/crew/rubrics/security.md`, scaled to six risk areas the engine finds: `auth`, `personal-data`, `payments`, `public-api`, `data-migration`, `infra`. It has Read, Grep and Glob, runs no command and names no source.
- The engine runs two security checks of its own: the `secrets` gate on every item (`packages/engine/src/secrets.ts`) and the `deps` gate, which is `npm audit` on a Node project.
- Where a project's profile has a static-analysis tool, the reviewer receives the path of its report. The engine installs no such tool.
- The backend team's definition (`docs/specs/2026-11-14-backend-team-stacks-design.md`) names the stacks and frameworks this document refers to as "the project's stack" and "the project's framework".

## 5. MCP servers and skills

### The rules

1. The backend team's rule holds: an MCP server or a set of skills enters only when the tool's or the service's own team makes it. Nothing from the community, with the one exception of rule 4. A tool with no server of its own runs from the command line.
2. The server of a tool of section 4 is installed with the tool.
3. The server of a service is installed only where the project already uses the service. Two servers do not enter by this rule, by the user's decision of 2026-11-15 (the DevOps team's definition (`docs/specs/2026-11-15-devops-team-design.md`, section 5, rule 6)): HashiCorp Vault's server is left out, because its answers can show a secret to the model, and of Cloudflare's plugin the skills alone are installed, without its server, which acts on the account. The decision names these two alone; the other rows of this table that write or act stand as they were, and section 6 lists them.
4. Six sets of skills are used in every team's work on an application, backend, ETL, frontend and every other: the user's word was "sempre". One of them, the Cybersecurity Skills, is a community project and enters by the user's own choice.
5. A command that takes a token or a key is written with the variable's name or the page's placeholder and no value.

## 6. What the code needs, not decided here

The item that builds this definition settles each of these:

- Where a subject's sources, a kind's tools and their servers and skills are declared. The rubric names none, and `PackManifest` (`packages/engine/src/packs.ts`) has no field for them.
- What a tool that is not installed means for a gate. A gate does not pass because its tool is absent.
- How "installed with the tool" and "installed in every team's work" are carried out, and by whom: the engine, a pack or the session. An install command runs its publisher's code in the project and on our side, so the version and the page are checked again at the install.
- An ADR for installing outside skills. It stands beside ADR 0010, under which a pack ships no skill, and ADR 0017, under which an outside source enters distilled, and it covers the one community source: how sixteen domains of the Cybersecurity Skills are installed without the others when the page's command installs the whole library, and how a community library is read again at each install.
- How the servers are confined:
  - where each server's credential is held and with what scope;
  - that the hosted servers (GitHub's remote form, Semgrep's, GitGuardian's, Socket's, Prowler's and Stripe's) and Snyk Agent Scan send project data outside the machine, that promptfoo's server can share a run's results outside it, and that Snyk Studio's page does not say what it sends to Snyk;
  - that the servers of GitHub, Semgrep AppSec Platform, SonarQube, GitGuardian, Prowler, 1Password, Doppler, Infisical, Stripe, OWASP ZAP, Burp Suite and promptfoo can write or act, and which of them have a read-only form (GitHub's, SonarQube's and Doppler's by their pages);
  - that a secret manager's server can show a secret to the model: HashiCorp says so of its own, which is why it is left out, and 1Password's, Doppler's and Infisical's servers stay, each with what its row says of values;
  - how Cloudflare's plugin is installed as the skills alone, the research giving the plugin's lines only; Vault is read through its CLI, names only, as the DevOps team's definition says (`docs/specs/2026-11-15-devops-team-design.md`, section 4, the row "Secrets and identities");
  - whether the user's rule of 2026-11-15 reaches the servers of this table that still write or act (Semgrep AppSec Platform's, GitGuardian's, Prowler's, 1Password's, Doppler's, Infisical's and Stripe's): the decision named Vault's and Cloudflare's alone, and this is not decided here;
  - that these are not stable by their publishers' labels: OSV-Scanner's and Scorecard's servers and Doppler's (experimental), Semgrep's hosted server and skills and 1Password's plugin (beta), Prowler's (a preview), Socket's ("early development"), Infisical's (before 1.0) and Snyk's installer (the `--experimental` flag).
- How everything that sends requests to a running application is held to the project's own local or test environment: the tools of the running application in section 4, the Penetration Testing and Network Security skills, and the two servers that send requests themselves, OWASP ZAP's add-on and Burp Suite's extension.
- How the six-phase audit is seated: which roles run it, what "the change touches one of the ten subjects" reads from when the engine detects six risk areas, the sandbox it needs to run the target's code, and its cost per item.
- The security team itself: its members beyond `review-security`, and whether the four subjects the engine does not detect become risk areas.
