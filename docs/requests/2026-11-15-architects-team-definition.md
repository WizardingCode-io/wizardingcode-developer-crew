# Architects team: subjects, sources, tools, MCP servers and skills

## Context

After the definitions of the backend developer team (`docs/specs/2026-11-14-backend-team-stacks-design.md`), the security team (`docs/specs/2026-11-15-security-team-design.md`), the ETL team (`docs/specs/2026-11-15-etl-team-design.md`) and the researchers team (`docs/specs/2026-11-15-researchers-team-design.md`), the user named the architects team as the next one to define. The engine has an `architects` team (`packages/engine/src/team.ts`, `TEAMS.architects`) with one member, `review-architecture`, the gate `architecture`, `validates: true`, and a seat on the full route; the risk review, which no team's gate rules, sits with it. Its reviewer reads a change against `plugins/core/skills/crew/rubrics/architecture.md`, which asks six questions: layers and boundaries, data model, contracts, integrations, the spec's Design, consistency with neighbours. Nothing in the engine or the plugin says where the team reads about each of them, which tools it runs, or which MCP servers and skills it uses.

The user chose a written definition first, decided with them point by point on 2026-11-15. Mid-way they sent four links to skills on software architecture, with no words beside them. This plan writes that definition into the repository as one document, with a test that reads it. The engine, the plugin and the packs do not change in this work.

## What will be done

One crew item (a chore) that writes `docs/specs/2026-11-15-architects-team-design.md`, in English, following `plugins/core/skills/crew/references/writing.md`, holding the definition below as decided, and `packages/engine/tests/architects-team-definition.test.ts`, which reads the document by section and by table row through `packages/engine/tests/definition-document.ts`, as the four other definition tests do.

- Every source and tool carries the URL it was opened at on 2026-11-15. A page that was not read that day is marked "(not opened)".
- Every MCP server and every set of skills carries the URL it was read at and its install command, word for word from the research of 2026-11-15. A command that takes a token is written with the variable's name or the page's placeholder and no value. A row the research gives no command for says so.
- A name the research found wrong, renamed, moved, archived or no longer maintained is written as the page gives it, with the name the user was offered beside it.
- The document ends with a section "What the code needs, not decided here".

### 3. MCP servers and skills

Rules, the user's:

1. The other teams' rule: only an MCP server or skills made by a tool's own team. A tool with no server of its own runs from the command line.
2. The server of a tool of point 2 that is local and needs no account is installed with the tool: Nx (where the project uses Nx), Structurizr (read-only), PlantUML, jscpd, knip, OpenSSF Scorecard, Jaeger, the MCP Inspector, promptfoo, and Laravel Boost, as on the backend team. k6 and Lighthouse run from the command line: Grafana's mcp-k6 (experimental, its licence file and its README disagree) is left out. Chrome DevTools MCP (it drives a browser and sends usage statistics by default) was left out on 2026-11-15; by the user's decision of 2026-11-16, written as rule 3 of the frontend team's definition (`docs/specs/2026-11-16-frontend-team-design.md`, section 5), its server is installed and always run on the project's test and development environments, never against a production environment or a real user's session, which is the session's reading of "test and development", told to the user, and Lighthouse from the command line stays.
3. The server of a service with an account is installed only where the project already uses the service, in read-only mode where the server has one: Redocly, SmartBear (PactFlow and Swagger), Apollo, draw.io, Excalidraw, Miro, Lucid, Grafana, Sentry, Datadog, Honeycomb, New Relic, SonarQube, CodeScene, Socket, Snyk. A server that writes and has no such mode is left out: Postman, Mermaid Chart, Moderne. Three exceptions, the user's choice of 2026-11-15, told that each writes and gives no read-only mode: SmartBear's, Miro's and New Relic's enter where the project already uses the service.
4. A knowledge server of a cloud only where the project is on that cloud: the AWS Knowledge MCP, the Microsoft Learn MCP, Google's Developer Knowledge MCP, Cloudflare's. The frameworks' servers as on the backend team; Context7 as on the researchers team.
5. Outside skills, installed as they are and always, the user's choice: Anthropic's plugins feature-dev, code-modernization, plugin-dev, mcp-server-dev and agent-sdk-dev; the skills of Nx, Redocly, buf, PactFlow, Apollo and jscpd; the clouds' skills: Google's Well-Architected skills, Microsoft's azure-skills and the AWS Agent Toolkit; Matt Pocock's improve-codebase-architecture, codebase-design and domain-modeling; Trail of Bits' audit-context-building and spec-to-code-compliance.
6. The user's four links are distilled into the team's own skills, written by us, each rule with its row in the sources ledger (ADR 0017). None is installed, and text under the GPL is not copied:
   - `https://github.com/45ck/software-architecture-skills`
   - `https://www.skillsdirectory.com/skills/artubss-software-architecture`
   - `https://github.com/davila7/claude-code-templates/blob/main/cli-tool/components/skills/development/software-architecture/SKILL.md`
   - `https://github.com/dandgabr/skills/blob/main/skills/roles/software-architect/SKILL.md`
7. The team's own skills, five, defined here and written in a later item: architecture (the thirteen subjects as references, each with its sources); decision (generate options, weigh the trade-offs, choose by the case measured or estimated in writing, write the ADR in the project's form); boundaries and contracts (review the boundaries of components and layers, map the integrations, catch a contract that changes without its file); quality attributes and risk (quality attribute scenarios, availability, the hot spots of scale, the risk in production and what undoes it); views (context, containers and components of the C4 model, the runtime view and the deployment view, as diagrams in code).
