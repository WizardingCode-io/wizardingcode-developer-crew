# DevOps team: subjects, sources, tools, MCP servers and skills

## Context

After the definitions of the backend developer team (`docs/specs/2026-11-14-backend-team-stacks-design.md`), the security team (`docs/specs/2026-11-15-security-team-design.md`), the ETL team (`docs/specs/2026-11-15-etl-team-design.md`), the researchers team (`docs/specs/2026-11-15-researchers-team-design.md`), the architects team (`docs/specs/2026-11-15-architects-team-design.md`) and the QA team (`docs/specs/2026-11-15-qa-team-design.md`), the user named the DevOps team as the next one to define. The engine has a `devops` team (`packages/engine/src/team.ts`, `TEAMS.devops`) with the lead `lead-devops`, one member, `review-infra`, the gate `infra`, `validates: true`, and a seat that the risk area `infra` makes mandatory. Its reviewer (`plugins/core/agents/review-infra.md`) reads a change to pipelines and deployment against `plugins/core/skills/crew/rubrics/infra.md`, which asks six questions: pipelines, secrets, permissions, rollback, hosts, reproducibility. `crew env` (`plugins/core/skills/crew/references/gate.md`) starts the environment the project's profile declares, waits for its health, says where it stands and stops what the engine started. Nothing in the engine or the plugin says where the team reads about each of these, which tools it runs, or which MCP servers and skills it uses.

The user chose a written definition first, decided with them point by point on 2026-11-15. This plan writes that definition into the repository as one document, with a test that reads it. The engine, the plugin and the packs do not change in this work.

The same day the user decided one rule that also corrects two other definitions: no server that acts on an account enters by a set of skills or by another team's row. The architects' document installs the Agent Toolkit for AWS and Microsoft's azure-skills by their plugins, which also connect such a server; the security team's document installs Vault's server and Cloudflare's plugin with its hosted server. This work writes the rule into both documents too.

## What will be done

One crew item (a chore) that writes `docs/specs/2026-11-15-devops-team-design.md`, in English, following `plugins/core/skills/crew/references/writing.md`, holding the definition below as decided, and `packages/engine/tests/devops-team-definition.test.ts`, which reads the document by section and by table row through `packages/engine/tests/definition-document.ts`, as the six other definition tests do. The same item changes two more documents, each with its test where that text is pinned: `docs/specs/2026-11-15-architects-team-design.md`, on its rows of the Agent Toolkit for AWS and azure-skills and in its rule 5, and `docs/specs/2026-11-15-security-team-design.md`, on its rows of HashiCorp Vault and Cloudflare's plugin.

- Every source and tool carries the URL it was opened at on 2026-11-15, or the URL a sibling definition opened it at. A page that was not read that day is marked "(not opened)".
- Every MCP server and every set of skills carries the URL it was read at and its install command, word for word from the research of 2026-11-15. A command that takes a token is written with the variable's name or the page's placeholder and no value. A row the research gives no address or no command for says so.
- A name the research found wrong, renamed, moved, quiet, no longer maintained or under a licence that is not open is written as the page gives it, with the name the user was offered beside it.
- The research on servers and skills did not check every tool: the document says which tools were not checked, and lists as having nothing of their own only those that were.
- The document ends with a section "What the code needs, not decided here".

### 3. MCP servers and skills

Rules, the user's:

1. The other teams' rule: only an MCP server or skills made by a tool's own team. A tool with no server of its own runs from the command line.
2. The server of a tool of point 2 enters only where the project uses the tool, and always reading: OpenTofu's, Terraform's (only where the project already uses Terraform), Prometheus's, Kubecost's, OpenCost's, Infracost's and Ansible AAP's. Argo CD's and Flux's enter with the read-only switch on, as the two exceptions to rule 3, the user's choice and not the option recommended: only where the project already uses them, and only after the building item shows the install command with the switch (`MCP_READ_ONLY=true`; `--read-only`). A server admitted whose reading alone the research did not confirm is not installed until the building item shows that it only reads: Infracost's. Left out: Pulumi's, which can approve changes, Vault's, which returns secret values, and Docker's gateway and Hub servers; those tools run from the command line, only up to the plan.
3. No server that acts on a cloud account, a platform or a cluster enters, with or without a read-only switch: Red Hat's Kubernetes server, AKS's, EKS's, GKE's, the AWS MCP Server and the AWS API server, the Azure MCP Server, gcloud's, Cloud Run's, Cloudflare's API server, Vercel's, Netlify's, Render's, Fly.io's, Railway's, Heroku's, DigitalOcean's. The two exceptions are Argo CD's and Flux's servers, under rule 2. The team reads state through the platform's CLI with read-only credentials and rehearses up to the plan. The reason said to the user: two of the switches are called not guaranteed by their own publishers ("best-effort", "not a security boundary"), and an error here deletes real infrastructure. The clouds' knowledge servers, which serve documentation, stay as on the architects team.
4. The server of a service with an account (CI, delivery, incidents, observability) enters only where the project already uses the service, and always reading: GitHub's and Buildkite's, as on the QA team, Azure DevOps's, Harness's, with `HARNESS_READ_ONLY`, Rootly's, incident.io's, Grafana's, as on the architects team, Sentry's and Datadog's, as on the other teams. A server admitted whose reading alone the research did not confirm is not installed until the building item shows that it only reads: Sentry's. Left out, as writing with no read-only mode found: GitLab's, CircleCI's, Jenkins's, env0's, Spacelift's, PagerDuty's, Better Stack's, JFrog's (no licence), Vantage's, Octopus's (deprecated).
5. Outside skills: each set only where the project already uses that tool or platform, the rule decided on the QA team, and the skills alone: without the hooks that approve a CLI by themselves (Render's and Railway's plugins) and without the servers that act on the account (the AWS, Azure, Cloudflare and Fly plugins). Skills that publish or approve stay out: HashiCorp's four Packer skills and `pulumi-neo-handoff`. A skill inside an admitted set that deploys, triggers a pipeline, installs on a host or spends enters with its set, the user's choice and not the option recommended; the research names `netlify-deploy`, `azure-deploy`, `render-deploy`, `buildkite-cli`, the `dd-agent-install-*` skills, `aws-agents-for-devsecops` and `fix-findings`. When one of them is used, the rule applies that a deploy to production, and any command that deletes or changes a real resource, is a person's decision. The sets: HashiCorp's, Pulumi's, Flux's, Buildkite's, Infracost's, Render's, Fly's, Railway's, Grafana's, Netlify's, Cloudflare's, Datadog's, Sentry's, Vercel's (vercel-plugin), and the clouds' already on the architects team (the Agent Toolkit for AWS, azure-skills, Google's). With no licence, left out: `vercel-labs/agent-skills`, `docker/claude-plugins`, CircleCI's. Trail of Bits' and Matt Pocock's skills already enter by other definitions.
6. The conflict with two other definitions, decided for all three teams: no server that acts on an account enters by a set of skills or by another team's row. The architects' document is corrected in the same item, on the rows of the Agent Toolkit for AWS and azure-skills and in rule 5: of each the skills alone are installed, where the project is on that cloud, without the server that acts on the account. The security team's document (`docs/specs/2026-11-15-security-team-design.md`) is corrected in the same item: Vault's server and the server of Cloudflare's plugin are left out there as well, and of Cloudflare's plugin only the skills are installed.
7. The team's own skills, seven, defined here and written in a later item: devops (the fifteen subjects as references; the entry); pipelines (the gates before a deploy, jobs that run, pinned actions, the pipeline's supply chain); secrets and identities (where secrets live, least privilege, nothing widened); environment and containers (bringing the project up, health and logs, Dockerfile and images, pinned versions, nothing tied to one machine); infrastructure as code (validate and plan, never apply, policy and the plan's cost); deploy and rollback (the strategy, the release, what undoes each destructive step, backups and the restore rehearsal); operation (logs, metrics, traces, alerts, incidents and runbooks).
