# QA team: subjects, sources, tools, MCP servers and skills

## Context

After the definitions of the backend developer team (`docs/specs/2026-11-14-backend-team-stacks-design.md`), the security team (`docs/specs/2026-11-15-security-team-design.md`), the ETL team (`docs/specs/2026-11-15-etl-team-design.md`), the researchers team (`docs/specs/2026-11-15-researchers-team-design.md`) and the architects team (`docs/specs/2026-11-15-architects-team-design.md`), the user named the QA team as the next one to define. The engine has a `qa` team (`packages/engine/src/team.ts`, `TEAMS.qa`) with one member, `review-test-quality`, the gate `test-quality`, `validates: true`, and a seat on every item. Its reviewer reads a change's tests against `plugins/core/skills/crew/rubrics/test-quality.md`, which asks eight questions; `crew tdd` records the red and the green of each criterion; the `e2e` gate runs the project's end-to-end command and reads the console and the logs; the team's lead validates that the spec's criteria are observable and provable. Nothing in the engine or the plugin says where the team reads about each of these, which tools it runs, or which MCP servers and skills it uses.

The user chose a written definition first, decided with them point by point on 2026-11-15. This plan writes that definition into the repository as one document, with a test that reads it. The engine, the plugin and the packs do not change in this work.

The same day the user decided one rule that also closes a point the architects team's definition left open in its section 6: which rule wins where an outside skill "installed always" belongs to a service or a tool the project may not have. This work writes that rule into the architects' document too.

## What will be done

One crew item (a chore) that writes `docs/specs/2026-11-15-qa-team-design.md`, in English, following `plugins/core/skills/crew/references/writing.md`, holding the definition below as decided, and `packages/engine/tests/qa-team-definition.test.ts`, which reads the document by section and by table row through `packages/engine/tests/definition-document.ts`, as the five other definition tests do. The same item changes `docs/specs/2026-11-15-architects-team-design.md` where its rule 5 and its section 6 speak of the open point, and its test where that text is pinned.

- Every source and tool carries the URL it was opened at on 2026-11-15. A page that was not read that day is marked "(not opened)".
- Every MCP server and every set of skills carries the URL it was read at and its install command, word for word from the research of 2026-11-15. A command that takes a token is written with the variable's name or the page's placeholder and no value. A row the research gives no command for says so.
- A name the research found wrong, renamed, moved, archived or no longer maintained is written as the page gives it, with the name the user was offered beside it.
- The research on servers and skills did not check every tool: the document says which tools were not checked, and lists as having nothing of their own only those that were.
- The document ends with a section "What the code needs, not decided here".

### 3. MCP servers and skills

Rules, the user's:

1. The other teams' rule: only an MCP server or skills made by a tool's own team. A tool with no server of its own runs from the command line.
2. The server of a tool of point 2 is installed with the tool: Laravel Boost and promptfoo, as on the architects team. Playwright's and Chrome DevTools' servers are installed and always run on the project's test and development environments, the user's decision of 2026-11-16, written as rule 3 of the frontend team's definition (`docs/specs/2026-11-16-frontend-team-design.md`, section 5) and naming end-to-end errors in its own words: "é para ignorar esta regra eu nao quero mais erros de e2e ok quero que corra isto sempre caso contrario como é que testam o frontend ??? [...] indicaçõa clara é para correr ambientes de teste e desenvolvimento nao tem dados que sejam sensiveis". The rule on a server that writes or acts and has no read-only mode (rule 3) does not hold them back there, though both drive a browser and neither has a read-only mode. Never against a production environment or a real user's session: this last clause is the session's reading of "test and development", told to the user. Playwright from the command line and the crew's fixture stay as well. Bruno runs from the command line: its server sends real requests and has no read-only mode. Every other tool of point 2 runs from the command line.
3. The server of a service with an account is installed only where the project already uses the service, and always in read-only mode: Cypress Cloud, SonarQube, Sentry, Datadog, Chromatic, Checkly, Trunk. A server that writes or acts and has no read-only mode is left out: Postman, WireMock Cloud, Confident AI, BrowserStack, Sauce Labs, LambdaTest, Currents, Qase, Zephyr (SmartBear), Allure TestOps, ReportPortal, mabl, Katalon, QA Wolf, Applitools. One exception, the user's choice: LocalStack's server enters only where the project already uses LocalStack. Zephyr's tools come in SmartBear's package, which the architects team's definition admits for PactFlow and Swagger: where that package is installed, Zephyr's tools stay off and this team does not use them, the user's decision of 2026-11-15.
4. The server of a CI, to read the tests' runs and logs, only where the project uses that CI and in read-only mode: GitHub's and Buildkite's. GitLab's and CircleCI's have no read-only mode and are left out; there the runs are read from the command line. The DevOps team's definition may revisit this.
5. Outside skills, installed as they are, the user's choice of "all installed", which was not the option recommended (the recommended one left superpowers out, because its fifteen skills of method overlap the crew's): Anthropic's webapp-testing; Microsoft's playwright-cli; Cypress's ai-toolkit; Testcontainers'; Currents' playwright-best-practices; Checkly's; Allure's; Laravel Boost's testing skills; ai-evals-course's evals-skills (Hamel Husain and Shreya Shankar); promptfoo's; Confident AI's eval-skills; inspect-skills; obra's superpowers, with its fifteen skills. Skills with no licence stay out: CircleCI's, BrowserStack's, `laravel/agent-skills`. Matt Pocock's and Trail of Bits' skills already enter by the architects' and the security team's definitions.
6. Where rule 5 meets rules 3 and 4, the user decided on 2026-11-15: a skill that serves a service with an account, or a tool the project does not have, is installed only where the project already uses that service or tool (Checkly's, Allure's, Currents', Confident AI's, Cypress's, promptfoo's and inspect-skills; Laravel Boost's on Laravel projects). The general skills are installed always (webapp-testing, playwright-cli, evals-skills, superpowers, Testcontainers'). The same rule closes the open point of the architects team's definition, section 6: the AWS Agent Toolkit, Microsoft's azure-skills, PactFlow's plugin and Nx's skills are installed only where the project uses that cloud, service or tool.
7. The team's own skills, six, defined here and written in a later item: testing (the sixteen subjects as references, each with its sources; the entry); proof (a test per criterion, red first, preserve and observed criteria, criteria observable in the spec); test design (levels, doubles, data and state, determinism, nothing true by construction, behaviour and not implementation); end to end and API (the environment, the console and the logs clean, Playwright from the command line, HTTP tests); measuring the tests (mutation, properties and fuzzing, the diff's coverage, flakiness, the suite in CI); evals (testing systems with AI, judges and cost).
