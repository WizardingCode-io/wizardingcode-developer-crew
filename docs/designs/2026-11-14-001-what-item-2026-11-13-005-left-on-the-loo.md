# What item 2026-11-13-005 left on the loop

## Problem

This item makes the improvement loop's clearing of git locks tell a replaced lock from an untouched one, and puts under test the one part of the loop's script that no test runs: the code that picks what each command acts with. It also orders one test and moves two comments.

Terms used below:

- **The loop** is the improvement loop, `scripts/improve-loop.ts`, which launchd runs hourly on this machine as an agent. One run of it is a **tick**. It works in a checkout of its own, its **clone**.
- **The entry block** is the `if (import.meta.main)` block at the end of that script: it reads the command (`tick`, `install`, `uninstall`, `status`, `stop` and others) and runs it. The last item's records call it `main`; the script has no function of that name.
- A command's **real dependencies** are the functions it uses to act on the machine (its `sh` and `git`, among others). Three exported **builders** make them: `realTickDeps`, `realInstallDeps` and `realStopDeps`.
- **The clearing** is `clearClone`: a tick that holds the loop's lock removes the git lock files a killed git left in the clone.
- An install's **command file** is `install-in-progress.command` in the loop's home, which names the command an install is running.

Item `2026-11-13-005` (commit `f4118c3`) gave every command of the loop a time bound. Its code review ended with the six review gates ruled proven, and with points recorded as advisories. Each was a correct observation, not a defect. None was fixed in that item, because any change of code after a ruling repeats the whole review. Four of those points are closed here, before the next release of the plugin:

1. The clearing waits for a lock younger than a minute and takes it only when it is unchanged after the wait, identified by its modification time alone. Another file put at the lock's path with the same modification time, within the file system's timestamp resolution, reads as the same lock and is removed.
2. Before that wait the tick logs `a git lock made in the last minute: waiting <n> s before it is taken: <path>`. The test checks the line's form, not that it is logged before the wait.
3. The entry block chooses, for each command, which builder makes its real dependencies, and gives the install its command file. No test runs the entry block: a change that stopped passing the install's command file, or gave the `stop` command a command file, would pass every test.
4. Two comments are out of place: the constant `PROBE_WAIT_S` stands between `install`'s doc comment and `install`, and `clearClone`'s comment has a broken line.

Who this reaches: the person who runs the loop, which works with nobody there. Point 1 keeps a tick from removing a lock a living git has just taken in the loop's clone. Point 3 means a wrong edit of the entry block (an install that loses its command file, so the next install cannot end what an interrupted one left) fails a test before it reaches the agent. Points 2 and 4 change nothing that runs: a test that proves what its name says, and comments a reader finds where they belong.

## Goals and Non-Goals

Goals:

- (Point 1.) The clearing takes a waited lock only when the file's inode and its modification time are both unchanged.
- (Point 2.) The test of the wait's line fails when the line is logged after the wait.
- (Point 3.) The entry block's dispatch is one exported function that takes the commands' implementations as parameters; a test calls it for `tick`, `install`, `uninstall`, `status` and `stop` and reads the dependencies each implementation receives.
- (Point 4.) Each doc comment stands above what it describes.

Non-Goals:

- A living git that holds one lock file for more than a minute without rewriting it still loses that lock. The Risks of item `2026-11-13-005` state this limit, and the clone is reset to `origin/main` at every tick.
- A test of the one line left in the entry block, the call of the dispatch function with the process's arguments: it is checked by reading (Risks).
- The wording of item `2026-11-13-005`'s closed spec.
- Any change to what a tick, an install or a release does, beyond the lock's identity.

## Open Questions

None.

## Critical User Journeys

- **A git retakes its lock during the wait.** Given a lock file younger than a minute, when a living git replaces it during the tick's wait with another file that has the same modification time, then the tick leaves it and logs `a lock a git still holds is left: <path>`.
- **The agent installs.** Given a loop's home with no install running, when the script is run with `install`, then the install's commands carry `install-in-progress.command` in that home.
- **A person stops, uninstalls or asks the status.** Given a tick that may be running, when the script is run with `stop`, `uninstall` or `status`, then that command's own commands carry no command file, so they cannot replace the record of the tick's running command.

## Design

### The lock's identity

`clearClone` reads, before the wait and after it, the lock's inode and modification time, both from the `statSync` each reading makes today, read with `bigint: true`: the inode as a bigint, so two inodes never compare equal by rounding, and the modification time in nanoseconds (`mtimeNs`), the resolution the file system gives. Under that option the millisecond field is cut to whole milliseconds (probed here under Bun 1.4.3 on 2026-11-14: `1794655088141n` beside `mtimeNs` `1794655088141764031n`), so comparing it would be coarser than today's reading. The lock is taken only when both are equal; a missing file is skipped as today; any difference logs `a lock a git still holds is left: <path>`. The comment says "the same inode and modification time".

### The wait's line, in order

The clearing's test records the log and the wait in one list, and asserts the line stands before the wait's call, which stands before the removal's line.

### What the entry block runs

The entry block's body becomes one exported function, `runLoopCommand(argv, at)`, which returns the exit code. `at` holds the loop's home, the command runner (the real one when not given), and the commands' implementations (`tick`, `install`, `uninstall`, `statusText`, `stopLoop`; the real ones when not given). The function does what the entry block does today, branch for branch: it builds `realTickDeps` for `tick`, `realInstallDeps` with the install's command file for `install`, `realInstallDeps` with no file for `uninstall` and `status`, `realStopDeps` for `stop`, and passes them to the implementation; `pause`, `resume`, `secret set` and the usage line are unchanged. The entry block is then one line: it calls the function with the process's arguments and exits with its answer.

A test calls `runLoopCommand` once per command, in a temporary home, with a recording runner and implementations that run one command through the dependencies they are given. It reads from the runner which command file that command carried: the tick's for `tick`, the install's for `install`, none for `uninstall`, `status` and `stop`. No launchd is touched and no real home.

### The comments

`PROBE_WAIT_S` and its comment move above `install`'s doc comment. `clearClone`'s comment is rewrapped.

## Alternatives considered

- **Running the entry block in a child process for point 3.** Rejected: an install or a stop run for real would act on launchd and on the loop's home.
- **A function that only answers each command's dependencies (`commandDeps`).** This was the design until its review. Rejected: it moves the untested choice one level down. An install branch that asked for the uninstall's dependencies would type-check and pass every test.
- **A test that reads the entry block's source text.** Rejected: it pins the spelling of the code, not what the code does, and fails on a harmless rewrite.
- **The change time (`ctime`) in place of the inode.** Rejected: a test cannot set it, so no test could stage a replaced lock that has the time it had and prove each half of the identity apart. The inode identifies a file replaced by rename.
- **A lock's content compared, for point 1.** Rejected: git writes the new index or the new ref into its lock, so a retaken lock can hold the same bytes as the one before, and the content of a lock a living git is still writing says nothing of whose it is. The inode tells a new file.

## Acceptance criteria

Four criteria, numbered as `crew criteria <id> list` numbers them: AC-1, AC-3, AC-7 and AC-8. They cover the preserve and points 1 to 3; point 4, the two comments, is checked by the code reviewer reading the diff.

- AC-1 (preserve): the tests of `packages/engine/tests/improve-loop.test.ts` pass before and after; no test of an earlier item is edited except the clearing's test of item `2026-11-13-005`, which gains assertions.
- AC-3 (the wait's line): the clearing's test asserts the line logged before the wait stands before the wait's call, and the wait's call before the removal's line.
- AC-7 (the lock's identity): a lock replaced during the wait with another file that has the modification time it had is left, and the tick logs so; so is a lock rewritten in place during the wait with a time that differs by less than a millisecond; a lock untouched during the wait is removed as before. The test pins the first lock to a whole-millisecond modification time, gives the second file the same one, checks itself that the two inodes differ and the two times are equal, and fails on today's code.
- AC-8 (what the entry block runs): `runLoopCommand`, called for each of `tick`, `install`, `uninstall`, `status` and `stop` with a recording runner and implementations given by the test, hands each implementation dependencies whose commands carry the tick's command file for `tick`, the install's for `install`, and none for `uninstall`, `status` and `stop`, and the options its arguments name (`--relaunched` and `--dry-run` for the tick, `--clone-from` for the install); a command it does not know answers 1 with the usage line.

## Risks and rollback

- **An inode reused at once.** A file system can give a new file the inode of one just removed. The modification time is still compared, so the check is never weaker than today's; the test keeps both files in existence at once, so its two inodes differ on any file system.
- **The gap that stays in the clearing.** Between the second reading and the removal a git can still release and retake the lock, and the new one is removed. The window is the same as today's.
- **The entry block's one line is read, not tested.** The call of `runLoopCommand` with the process's arguments runs only as the script's entry. It is one line, checked by reading at each change, and the delivery cites it.
- **Moving the entry block's body.** The move is branch for branch; the tests of each command's implementation are unchanged, and the new test runs the moved code for five commands. `pause`, `resume`, `secret set` and the usage's other paths move with no test of their branch, as they have none today; the test never calls `secret set`, which reads standard input.
- **Rolling back** is reverting the commit; no state's shape changes.

## Non-Functional Requirements

- Performance: no extra system call: two `statSync` per young lock, as today.
- Security: no new file, signal or command.

## Phase 2: what the entry block runs (AC-8)

1. Test (AC-8), `2026-11-14-001 AC-8: …`, with the existing helper `recordingRunner()` (it records each command's `timeoutMs` and `commandFile`) and a temporary home. For each command the test calls `runLoopCommand([<command>], { home, run: <the recording runner>, actions })`, each with its own literal, where `actions` holds the implementation for that command, given by the test:
   - `tick`: an implementation that calls `deps.sh(["true"], { cwd: home })` and returns 0. Recorded `commandFile`: `join(home, TICK_COMMAND_FILE)`.
   - `install`: the same through its `deps`. Recorded: `join(home, INSTALL_COMMAND_FILE)`.
   - `uninstall`: the same. Recorded: undefined.
   - `status`: an implementation that calls `deps.sh` and returns a text. Recorded: undefined.
   - `stop`: an implementation that calls `deps.sh` and returns a text. Recorded: undefined.
   Each implementation proves it was the one called: it returns a code of its own (7 for `tick`, 8 for `install`, 9 for `uninstall`; `status` and `stop` a text of their own, which the test reads from `out`) and runs a command named after itself (`["true", "<command>"]`), and the test asserts both. Two more calls cover the arguments a moved branch could drop: `["tick", "--relaunched", "--dry-run"]`, whose implementation receives `{ dryRun: true, relaunched: true }`, and `["install", "--clone-from", <a path>]`, whose implementation receives `{ cloneFrom: <the path> }` and after which the home's `config.json` names that path as `userCheckout`. The test never calls `secret set`. `runLoopCommand(["no-such-command"], …)` returns 1 and writes the usage line to the `err` given by the test. Red (`runLoopCommand` does not exist).
2. `runLoopCommand`, exported, placed after `realStopDeps` and before `USAGE`'s use, with the doc comment "The script's commands, by name (2026-11-14-001): what the entry block runs, as a function a test can call with its own runner and implementations; each command gets the real dependencies built for it, the install's with the install's command file, the uninstall's, the status's and the stop's with none.":

   ```ts
   export interface LoopActions {
     tick: typeof tick;
     install: typeof install;
     uninstall: typeof uninstall;
     statusText: typeof statusText;
     stopLoop: typeof stopLoop;
   }
   export async function runLoopCommand(
     argv: readonly string[],
     at: {
       home: string;
       run?: CommandRunner;
       actions?: Partial<LoopActions>;
       out?: (line: string) => void;
       err?: (line: string) => void;
     },
   ): Promise<number>
   ```

   Its body is the entry block's body of today, branch for branch, with `home` from `at.home`, `config` read from it, `run` passed to `realTickDeps(home, config, run)`, `realInstallDeps(home, run, join(home, INSTALL_COMMAND_FILE))` for `install`, `realInstallDeps(home, run)` for `uninstall` and `status`, `realStopDeps(home, run)` for `stop`; each implementation taken from `at.actions` or the real one; `console.log` replaced by `at.out ?? console.log` and `console.error` by `at.err ?? console.error`; the code returned in place of `process.exit`.
