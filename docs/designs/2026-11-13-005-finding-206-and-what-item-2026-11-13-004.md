# Finding 206 and what item 2026-11-13-004 left to the loop

## Problem

This item makes the improvement loop safe to leave alone: no command of it can wait for ever, a failed install is tried again, and the loop pays for no improvement run whose release cannot go out.

Terms used below:

- **The loop** is the improvement loop, `scripts/improve-loop.ts`, which launchd runs hourly on this machine. One run of it is a **tick**. It works in a checkout of its own, its **clone**, under its **home** (`~/.wizardingcode/crew-improve`).
- **The sync** is the part of a tick that brings the clone to `origin/main`.
- **The bootstrap** is what makes a clone able to run: the packages (`bun install --frozen-lockfile`) and **the shell**, Playwright's headless browser (`chromium-headless-shell`), which the eval suite's `ui` cases copy. The loop installs the shell into the clone's own `node_modules/.cache/ms-playwright`.
- A tick is **due** when the loop decides an improvement run should start. A **dry run** (`tick --dry-run`) says whether the tick is due and runs nothing.
- **The back-off** is the wait the loop sets after a failed tick: until it passes, a tick runs no improvement.
- A case is **measured** when a record holds a judged figure for it. A case never measured is picked first; a measured one waits **the stale window** before it is picked again.
- **The probe** is what the loop wrote of what it can reach (`probe.json`); since item `2026-11-13-004` it says whether the release's account had a token, `found` or `missing`.
- **The release** is `scripts/release.ts`, which a tick calls when it adopts a change. Its work is thirteen numbered steps; **step 1** writes the version. A release left unfinished after its push is **pending**, and a later tick **resumes** it.
- **The eval kit** is `claude plugin eval`, which an improvement run calls.

Eight points are open on the loop (`analysis.md`). Points 3 and 5 cover every command the loop runs through its command runner, not the bootstrap's and git's alone.

1. (Finding 206.) A changed lockfile installs the shell at the sync, before a pending release's resume, the back-off's check and a dry run's return.
2. (Finding 206.) The shell's check accepts any finished build, so a Playwright bump whose install failed at the shell is never tried again.
3. (Finding 206.) The loop's commands have no time bound: the bootstrap's, the probe's `claude auth status` and keychain reads, the notification, the install's `launchctl` calls. A stalled one holds the tick and its lock.
4. (Finding 206.) A case whose baseline errored counts as measured, and waits out the stale window.
5. (Left by item `2026-11-13-004`.) The loop's git commands have no bound and can ask a terminal, the first clone among them.
6. (Left by item `2026-11-13-004`.) A release that stops before step 1 leaves no line in the day's failures. A resume that stops because another release is running in the clone reads as "nothing to resume", so the loop forgets a version that is on origin.
7. (Left by item `2026-11-13-004`, and decided by the user.) A tick pays for an improvement run while the release's account has no token, and the adoption's release then stops at its token.
8. (Left by item `2026-11-13-004`.) A paused loop with that account logged out runs the probe's commands every hour.

Who this reaches: the loop runs with nobody there. A tick held by one command runs no later tick, and a run whose release cannot publish costs up to the run's ceiling for nothing that reaches a user. The person who reads the day's report learns of a release that stopped only from the log.

The user's decision on point 7, of 2026-11-13: a tick skips its improvement run while the release's account has no token.

## Goals and Non-Goals

Goals:

- (Point 1.) The sync installs the packages, at every tick, and leaves the shell to the place before a run.
- (Point 2.) Before a run, the tick runs the shell's install, which installs the build the clone's Playwright names and does nothing when it is there.
- (Points 3 and 5.) Every command the loop runs through its `sh` and its `git` has a bound, and a git command asks no terminal.
- (Points 3 and 5.) What a bound brings with it is handled: `stop`, the install and the uninstall end a bounded command of the tick they end; a tick ends the commands a dead tick left and clears what a killed git left in the clone; an install ends the command an interrupted install left and never takes a half-made clone for a finished one.
- (Point 4.) A case whose baseline errored once is not measured; one whose baseline errors twice running waits the stale window.
- (Point 6.) A new release that stops before step 1 is a line of the day's report and of the tick's notification, with the stop's name, made safe for a public file. A resume that stops keeps its release pending, and a due tick whose release is pending runs no improvement and says so in the day's report.
- (Point 7.) A due tick reads the release's token itself, before the run. With none it runs no improvement, says so once a day in the report and by a notification, and runs again by itself after a login.
- (Point 8.) A paused loop takes the probe again only when it has none.

Non-Goals (the one list of what is left out):

- Running the cases that need no browser when the shell cannot be installed: the loop does not know which cases need it, and a tick whose install fails runs none of them and fails under the back-off, as today.
- A bound on the improvement run itself, on the judge's calls and on the tick's relaunch of itself: the run has its own ceilings and the eval kit its own timeouts, and a relaunched tick is a tick, bounded command by command.
- `secret set`: it calls the keychain's command itself, with the token on its standard input, and a person answers it. It is not touched.
- An install whose clone needs a credential that asks: the loop's git asks no terminal, in the install too. A loop under launchd has none, so such a clone would install a loop that cannot fetch.
- The release's own advisories of item `2026-11-13-004` (a log line before step 8's delete, a test for the archive's and the lock's removals).
- Changing what makes a tick due, or the adoption's ruling.

## Open Questions

None. Point 7 was the one question, and the user answered it.

## Critical User Journeys

- **The lockfile changes on origin.** Given a clone whose `bun.lock` differs after the sync, when the tick goes on, then `bun install --frozen-lockfile` runs and the shell's install does not; a pending release is resumed and a tick that is not due ends, whatever the download would have done.
- **The packages' install fails once.** Given a tick whose `bun install` failed after a sync that brought a new lockfile, when the next tick runs, then it runs `bun install` again, though the lockfile no longer changes.
- **Playwright is bumped and its shell's install fails.** Given a clone with an older finished build and a lockfile whose Playwright names another, when a due tick reaches the run, then the install runs and downloads the new build; when it fails, the tick fails under the back-off, and the next due tick runs the install again.
- **The download stalls.** Given a due tick whose shell's install never returns, when 15 minutes pass, then the command and its process group are killed, the tick fails with `the headless shell's install timed out after 900 s`, and its lock is released.
- **A tick is stopped during a download.** Given a due tick waiting on the shell's install, when a person runs `stop`, then the install's process group is signalled, the tick fails at its bootstrap and releases its lock, and `stop` says the tick ended.
- **A tick dies during a push.** Given a tick killed while its `git push` runs, when the next tick takes over its lock, then that push's group is killed, a lock file it left in the clone's `.git` is removed, and the tick goes on.
- **A case's baseline errors once.** Given a record whose baseline for a case errored and no earlier error, when the next tick decides, then that case is still never measured and is picked first. Given the next record errors for it too, then it counts as measured at that record's time.
- **Origin does not answer.** Given a tick whose `git fetch` never returns, when 5 minutes pass, then the command is killed and the tick fails with git's command and `timed out after 300 s`.
- **The release's account is logged out.** Given a due tick and an account with no token, whatever the probe file says, when the tick reaches the run, then it reads the token, runs no improvement, logs and notifies `skipped: the release's account (<account>) has no token: log in to it with gh auth login; a later tick probes again`, and writes the line under the report's "Skipped ticks". The next ticks of the day log the skip alone. After a login, the next due tick reads a token and runs.
- **A release stops before step 1.** Given an adoption whose release stops for a journal it cannot write, when the tick writes the day's report, then "Failed steps" holds `- run <run>: the release stopped before step 1: <the stop's name>`, on one line, with the loop's home written `<loop home>`, and the notification says the same.
- **A resume stops because a release is running.** Given a pending release at step 9 and a release still running in the clone, when a due tick resumes, then the release stays pending at step 9, the stop's line is in the log, and the tick runs no improvement and writes that under the report's "Skipped ticks".
- **The loop is paused with the account logged out.** Given `paused` in the configuration and a probe file that says `missing`, when a tick runs, then it runs no command of the probe.
- **An install is interrupted during its clone.** Given an install a person interrupted while `git clone` ran, when the person runs the install again, then the first install's lock is found stale, the left clone's group is killed, its half-made folder is removed, and the install clones again and goes on.

## Design

In short: one wrapper gives every command of the loop a bound; a command with a bound runs in a process group of its own, so the tick and the install each name their running command in a file that `stop`, the next tick and the next install read; the bootstrap is split so the sync installs the packages alone; the release reports a stop before step 1; the tick reads the token before it pays for a run.

Names that are new: `loopCommands`, `realInstallDeps`, `realStopDeps`, `cloneInto`, `installPackages`, `ensureShell`, `stopName`, `recordedProcess`, `leftCommandOf`, the two command files `tick-in-progress.command` and `install-in-progress.command`, and the install's lock `install.lock`. `recordedProcess` is the release's present rule for a recorded process (gone, the same, or another), taken out of `release` into a function of its own. Names that change: `realTickDeps` (exported), `readCommandFile` and `leftCommand` (they take the file's name), `boundOf` (it knows `clone`), `lastMeasuredOf`, `ReleaseOutcome` (it gains `stopped`). `cloneHasShell` goes.

### The sync installs the packages alone

`bootstrapClone` stays one function: the packages, then the shell. The tick no longer calls it. It calls two functions of its own: `installPackages` after its sync, at every tick, and `ensureShell` at the one place before a run. So nothing before that place downloads a browser: not the first clone, not the sync, not a pending release's resume, not a dry run.

The tick no longer compares the lockfile before and after the sync. That comparison installed once: after a failed or cut install the clone already stood on the new lockfile, the next tick saw no change, and the packages were never installed again. Run at every tick, the install is its own retry. Measured here on 2026-11-13: with nothing to install it takes 8 ms, also with every request sent to a dead proxy, so it touches no network.

### Before a run, the shell's install

`ensureShell` runs the shell's install (`node_modules/.bin/playwright install chromium-headless-shell`, with the clone's `PLAYWRIGHT_BROWSERS_PATH`), every due tick. Playwright itself then decides which build it wants: it downloads the build the clone's version names when that build is not finished, whatever older builds sit beside it, and does nothing when it is. Measured here on 2026-11-13 with Playwright 1.64.1: with the build there, the install exits 0 in 0.2 s, and also with every request sent to a dead proxy, so it touches no network.

The check `cloneHasShell` and its any-build rule go. A failed install fails the tick before the run, as today, and the next due tick installs again.

### Bounds on every command of the loop

The loop's command runner is the release's (`spawnRunner`), which kills a bounded command with its process group (item `2026-11-13-004`). The loop wraps it once, in `loopCommands`: a call through its `sh` that names no bound gets 2 minutes, the release's bound for a local command, and a call through its `git` gets the bound below.

Each place that builds the loop's real dependencies takes its `sh` and `git` from that wrapper: `realTickDeps` for a tick (its read of the provider's secrets from the keychain, `readSecret`, goes through that `sh`, where today it calls the runner directly), `realInstallDeps` for the install, the uninstall and the status, and `realStopDeps` for `stop`. The three are exported and take the runner as a parameter, so a test runs what `main` runs; `main` only picks one.

So every command a tick, an install, an uninstall, a status and a stop run through `sh` or `git` has a bound. What has none is the Non-Goals' list: the improvement run, the judge's calls, the tick's relaunch and `secret set`.

| Command | Bound | Measured here on 2026-11-13 |
| :- | :- | :- |
| `bun install --frozen-lockfile` | 5 minutes | 8 ms with nothing to install. 0.5 s into an empty folder with `BUN_INSTALL_CACHE_DIR` set to an empty folder: a real download on this link (the same command fails with the network blocked), 111 MB unpacked; the compressed size was not measured |
| the shell's install | 15 minutes | 0.2 s with the build there; 5.4 s for a download of the build into an empty folder (206 MB on disk) |
| `git clone` of origin | 5 minutes | 3.3 s (34 MB) |
| `git fetch`, `ls-remote`, `push` | 5 minutes | not measured here: the release's own bound |
| any other command (`claude auth status`, the keychain's reads, `gh`, the notification, `launchctl`, `ps`, `sysctl`, `which`, a local git command) | 2 minutes | each answers in under a second here |

The shell's 15 minutes let a link of 1.8 Mbit/s finish 206 MB. That figure is a floor for the link: the download is compressed and smaller than the 206 MB on disk. A slower link fails the tick under the back-off, and a download cut at its bound is started again by the next due tick; a packages' install cut at its bound is started again by the next tick.

A bootstrap command killed at its bound is the bootstrap's error, worded `<what> timed out after <n> s`: `bun install`, `the headless shell's install`. The tick fails as it does for any failed bootstrap: under the back-off, the lock released, the next due tick trying again. The install a person runs uses the same functions, so it has the same bounds.

### A bounded command and `stop`

A bounded command leads a process group of its own, so the signal `stop` sends to the tick's group, and launchd ending a tick, no longer reach it. Item `2026-11-13-004` settled this for the release's commands with a command file; the tick's own commands get the same.

Every command of the tick's `sh` and `git` carries a command file, `tick-in-progress.command` in the loop's home (the clone may not exist yet), written by the runner's wrapper with the release's four lines: the command's pid and start, the tick's pid and start. The runner removes it when the command ends. The release a tick calls keeps its own file in the clone; a tick runs one command at a time, so each file names at most one. The one command a tick runs before it holds the lock, the boot time's read, carries a bound and no file: a tick that then leaves, because another holds the lock, must not replace the live tick's record.

- **`stop`** signals the tick's own command once, when it signals the tick, with SIGTERM to that command's group. Before this item that command was in the tick's group and got the same signal. `stop` does not ask again, so the commands a stopped tick then runs to write the stopped run's record are left alone, as today. The release's command it kills with SIGKILL and asks for again on each turn of its wait, as today.
- **The install and the uninstall** end a tick through launchd's bootout. They then kill, with SIGKILL, the command that tick started, asking both files: the home's and the clone's release file.
- **A tick that takes over a stale lock** asks both files for a command the dead tick started and kills each group, before any command of its own that carries the file. The journal that tick's release left stays for the next release's recovery, unchanged.
- **A stop between two commands.** A tick notes at its start whether the stop's marker is there (`stop.json`, which `stop` writes and `resume` removes). Before the shell's install it looks again: a marker that appeared during this tick means a stop landed on it, so it logs `stop requested: nothing run` and ends, the marker left for `resume`. So a stop that found no command to signal does not let a 15 minute download start. A marker that was there before the tick started changes nothing here: such a tick runs, and its run is recorded as stopped by the user and the marker removed at the run's end, as today (item `2026-10-28-001`'s test stays as it is).
- **A stop during the shell's install.** The install's group gets `stop`'s SIGTERM and the tick's bootstrap fails. A failure of a tick on which a stop landed (the marker appeared during it) is not a failed tick: it is logged as `stop requested: the tick ends`, with no failure counted, no back-off set and no failure's notification.
- **The uninstall's, the status's and the stop's commands** carry no file: they are short, they are no tick's, and a second writer of the tick's file would replace a running tick's record.

Each kill goes through `leftCommand`'s check: the file's shape first, then a pid signalled only as the living leader of its own group with the start time the file names, and never this process or its group.

A git command killed in the clone can leave a lock file or a rebase in progress, and the next tick's reset would then fail at every tick. So a tick, once it holds the lock and has ended what a dead tick left, clears the clone before its first git command there: it removes each `*.lock` file directly in `.git` and under `.git/refs`, and runs `git rebase --abort` when `.git/rebase-merge` or `.git/rebase-apply` is there, logging each. A lock file made in the last minute can still be a living git's: git's own maintenance, started by the tick before, or a dead tick's git that no command file named. So the tick waits until such a lock is a minute old, and takes it only if it is there with the same modification time then; a lock a git released during the wait, or took again, is left. The lock of a git that was just killed, as by the install's kickstart, is taken after that wait, so the tick's first git command does not fail on it. A removal that fails does not stop the clearing, nor the tick. A rebase's abort that fails is logged and the tick goes on. Nothing of the loop's own commands writes in the clone then: the tick holds the lock, and the commands of a dead tick that a command file named are ended. The release has a narrower rule for the same folder: it removes only the `index.lock` its own timed-out command left, since a release can be run by hand beside a person's git. The tick may go further because the clone is the loop's own and it holds the loop's lock.

The loop's git also runs in the user's checkout, for the fast-forward after a release, and a git killed at its bound there can leave a lock the loop must not remove. When a command of the fast-forward timed out, the tick's line says so: `the user's checkout: git <command> timed out after <n> s; if git then says a lock exists, remove <path>`.

This keeps ADR 0015's note of 2026-10-28 true: a stopped tick's command is ended.

### An interrupted install

The bound of a command is counted by the process that started it. When a person interrupts the install, that process ends, and its running command, in a group of its own, is left with nobody to count its bound: a clone or a download that hangs would stay for ever.

A bounded command cannot stay in the terminal's group instead. At its bound it must be killed with its descendants, and a group's kill would then reach the install itself; killing the one process leaves its children holding the pipes the runner waits on. That is why item `2026-11-13-004` gave a bounded command a group of its own.

So an install holds a lock, `install.lock` in the loop's home (its pid and start time, created exclusively, or in place of a lock it has just read as stale), from before its first command until its work in the clone is done: it removes the lock right before it loads the agent, since the tick that load starts must run for the install to read its probe, and on any earlier exit, before it loads again an agent it had booted out. Its commands carry a command file of their own, `install-in-progress.command`. The command file is no lock: it exists only while a command runs. An install reads both first, before the tools' check and any command of its own:

- the lock names an install that still runs, by the release's rule for a recorded process: this install stops with `another install is running (pid <n>): wait for it`, exit 1, and touches nothing;
- the lock is stale (its install is gone, or it does not parse) or there is none: the command file is read once. The file names its own starter on its third and fourth lines, and that starter is asked too, since a lock removed or damaged by hand says nothing of an install that still runs: when the release's rule says the starter is the same process still running, and it is not this one, this install stops with the same line, signals nothing and leaves the file. Otherwise a command the file names that still lives has its group killed through the check a kill needs (`leftCommandOf`), with `the command an interrupted install left running was killed (pid <n>)`; the command file is removed, with `the file an interrupted install left was removed` when no command lived; a command file off its shape is removed and nothing is killed. Then this install takes the lock.

An install frees its lock only while the lock is its own, so one another install took meanwhile is left.

The install then works in this order, so that no tick runs while it writes in the clone:

1. The tools' check.
2. The tick the tick's lock names is read; `launchctl bootout` ends the agent; the commands of that tick are killed, both files asked.
3. A tick's lock that still names a living tick (one run by hand) stops the install: `a tick is running (pid <n>): wait for it or stop it`.
4. The clone, when there is none (`cloneInto`), and the healing of a clone with no loop, as today.
5. The bootstrap, on every install, not only when it made the clone: an install interrupted during the packages or the shell is completed by the next one.
6. The install's lock removed; the launcher and the plist written; the agent loaded and kickstarted, as today; the probe waited for, 150 seconds where it was 90: the tick the kickstart starts can first wait out the minute of a git lock that the kickstart's kill left, and the probe's own commands come after it.

A failure at steps 3 to 5 never leaves a loaded agent unloaded: when step 2's bootout had booted an agent out, the install loads it again from the plist that is there, says `the agent that was loaded is loaded again`, and exits 1 with what failed; a step that throws takes the same way out, and a reload that fails is said as `the agent that was loaded could not be loaded again`, with no agent loaded. When no agent was loaded, none is loaded, as today. When the load itself fails, the install says `no agent is loaded: run the install again`.

A clone is made beside its place and moved there when it is whole: `cloneInto` removes a folder `repo.cloning` an earlier clone left, clones into it, and renames it to `repo` on success. On a failure or a kill at the bound it removes `repo.cloning`. So a folder `repo` with `.git` is always a finished clone, in the tick and in the install. When something that is no clone stands at `repo`, the move fails, `repo.cloning` is removed, and the clone's error names `repo`: the tick fails with it at each tick, as git's own clone fails there today. An empty folder at `repo` is replaced by the move, which loses nothing.

A tick reads the install's lock whenever it starts, clone or no clone, before it takes its own lock, clears the clone or runs any command: while an install still runs, it logs `an install is running (pid <n>); leaving` and ends, as it does for another tick that holds the tick's lock. So no tick, an agent's or one run by hand, works in the clone while an install writes there, and none removes the folder an install is cloning into. The tick the install's own load starts finds no lock, since the install removed it before the load.

### An errored baseline is not measured, once

A baseline's figure for a case is errored when any of its runs errored (`CaseFigures.errored`); the improvement run itself makes no proposal over such a target. Today `lastMeasuredOf` gives a case the time of the latest record that holds a judged figure for it, a baseline or a proposal's probe.

The new rule adds one exception, for the baseline alone. Reading the records in time order: a record whose baseline for a case errored does not count for that case, through any of its figures, unless the last earlier record with a judged baseline for the case errored too. A probe's error changes nothing. A record with no judged baseline for the case (none, or one not judged because the run reached its judging limit) counts as today and does not change what the next error means.

So a single error is tried again at the next due tick, and a case whose baseline errors every time counts as measured from its second error and waits the stale window, as it does today from its first.

### The loop's git commands

Every call through `loopCommands`' `git` carries the release's bound for that command (`boundOf`, which gains `clone` among its remote commands: 5 minutes for `clone`, `fetch`, `ls-remote` and `push`, 2 minutes for a local command) and the release's environment for git (`gitEnv`: no prompt of git's, ssh in batch mode unless the caller sets its own ssh command).

The loop's git runs in three folders: the home (the clone's making), the clone, and the user's checkout (its fast-forward). Git's configuration can name an ssh command (`core.sshCommand`), which the environment's setting would replace. The loop reads it with `git config --get core.sshCommand` in each folder a command runs in, once per folder and process, with a 2 minute bound, and keeps it with batch mode added, as the release does for its one root. A folder that is no repository answers git's global configuration. A read that could not be made, as in a folder that is not there yet, is not kept: it is made again at the next command there. One folder's ssh command, and with it its key, never reaches another's.

A git command killed at its bound answers a failed result whose first line of stderr is `timed out after <n> s`, so every place of the tick that prints git's first line prints it. The probe's `git ls-remote` and push dry run go through the same `git`.

### A release that stops before step 1

`ReleaseOutcome` gains an optional field, `stopped`: the line of a stop before step 1. The release reports it, with code 1, no failed step and not pending, at every stop after its arguments' check that names no failed step. The version is the one the stop knows: empty before the bump, the bumped one for the token's and the journal's stops, the resumed one for a resume.

- For a new release: a release is pending and must be resumed first; the command file's two stops (a release is running, a left command did not end); the recovery's stops, which today report nothing, with one exception that stays as it is: when the release a journal names was killed after its push reached origin (the recovery's rule 3), the recovery reports that release as pending, to be resumed, with no `stopped`, and that is the one report sent; not on `main`; an unclean tree; origin not reachable; `origin/main` ahead; a version that cannot be bumped; no token; a journal that cannot be written.
- For a resume: the command file's two stops, and a resume that could not ask origin for its tag (the command failed or was killed at its bound): `origin could not be asked for v<version>: <git's line>`. That is no answer about the tag, so the loop keeps the release to resume. A resume whose tag origin answered is not there reports no `stopped`: that is "nothing to resume", as today. A resume with no token reports its failed step, as today.

The stops of the arguments' check (no bump named, `--from-step` or `--resume` off their form) report nothing: the loop never passes such arguments. A stop reports in a real release alone; a dry run logs what would stop, as today. One stop sends one report. The refusal for a release pending stood before any other check; it now stands after the command file's reading, where the stops that report begin, so a command a killed release left is ended before it.

Three tests of item `2026-11-13-004` pin that a recovery's stop reports nothing to the caller; this item changes that, and AC-36 names them.

The loop reads the field in two places.

- **The adoption.** The branch for a failure before the push pushes a failure when the outcome has a failed step, as today, and otherwise, when `stopped` is set, one with step 0 and the stop's name. The day's report prints such a failure as `- run <run>: the release stopped before step 1: <name>`; the status's count of failed steps is the list's length, so it counts it. The adoption's reason, which the tick's notification prints, is then `the release stopped before step 1: <name>` in place of the fixed sentence.
- **The resume.** An outcome with `stopped` leaves `pendingRelease` as it was, logs `the resume of <version> stopped: <line>`, and adds the same failure with run `resumed`, unless the day already holds one with that run and name: a release stuck for a day is one line of the report, not twenty-four. Today the loop reads any outcome with no failed step as nothing to resume and clears the pending release, which would forget a version that is on origin.

A tick whose release is still pending after its resume runs no improvement: the adoption's release would stop at "a release is pending". After the due decision and the dry run's return, such a tick skips, through the function that skips for the day's budget, with a kind of its own, `pending`: once a day it writes `- <hh:mm> UTC: release <version> is pending at step <n>; no improvement run until it is resumed` under the report's "Skipped ticks", pushes the report and notifies. The day's state keeps the skip's reason as it was written, as it does for the budget's skip, so a report written again later in the day, after the release was resumed, says the same words; each hour it logs `skipped: release <version> is pending at step <n>: no improvement run until it is resumed`. This holds for a resume that failed at a step as for one that stopped.

The stop's name is not the stop's line as it came. A stop's line can hold a filesystem error with the home's absolute path, git's first line of stderr, a branch's name, and the journal's `writtenAt`, a string read from a file. The day's report is pushed to a public repository, so the name is made by one function, `stopName`: the line's first line, through the loop's `redact` (the provider's secrets and a URL's userinfo replaced), with the loop's home replaced by `<loop home>` and the user's home by `~` (an empty home replaces nothing), cut to 200 characters with `…` at the cut. The name is what `state.json`, the day's report and the tick's notification hold; the full line goes to the loop's log alone, which stays on this machine, and through `redact` as every line does.

### A due tick with no token for the release

After the due decision and the dry run's return, after the pending release's check above and before the ceilings are read, the tick reads the release's token itself: one call of `accountToken`, the release's own read (`gh auth token -u <account>`, 2 minutes). The probe's word alone would be old: a word `found` is never taken again, so an account logged out after the install would skip nothing and pay for a run every due tick.

- **A token:** `found` is written into the probe file's `releaseToken` and the state's probe, and the tick goes on.
- **No token:** `missing` is written the same way, and the tick skips, as below.
- **The read killed at its bound:** that is not a logged-out account. The tick fails with `the release's token could not be read: gh auth token timed out after 120 s`, under the back-off, and the probe file keeps its word.

The skip goes through the function that skips for the day's budget and for no judge, with a third kind:

- the first skip of the day sets `tokenSkip` on the day's state, logs `skipped: the release's account (<account>) has no token: log in to it with gh auth login; a later tick probes again`, writes the day's report with the line under "Skipped ticks", commits and pushes it, and notifies;
- a later skip of the day logs the same reason followed by `; reported at <hh:mm> UTC` and does nothing else. The notification's body is the first skip's log line.

No record folder is made and `lastRun` does not move, so what made the tick due is unchanged. A pending release is still resumed before this point: the resume reads its own token and keeps the release pending when it has none. A dry run reads no token: it prints its line as today and adds `; the release's account has no token: a real tick would skip` when the probe file's word is `missing`.

The skip ends by itself: the first due tick after a login reads a token, writes `found` and runs. Two things write the word. The due tick's read writes it when a tick is due. Between due ticks, every tick that is not paused still runs the whole probe again while the word is `missing` (item `2026-11-13-004`), so the status and the install's printed probe show a login within the hour, not at the next due tick.

### A paused loop

The first tick writes the probe the install waits for, paused or not, as today. A probe that says `missing` is taken again only by a tick that is not paused: `paused` is read before that second reading. The test of item `2026-11-13-004` that pinned the probe's `gh` calls on a paused second tick changes with it (AC-36).

## Alternatives considered

- **The shell's check, asking Playwright's dry run for its build and reading the answer.** This was the design until its review. Rejected: it adds a command and a reading of Playwright's printed output, and the reason for it was false. The install was said to touch the network when the build is there; measured, it does not.
- **The shell's check, reading Playwright's `browsers.json` for the revision.** Rejected: the file's place depends on how the packages are laid out (here under `node_modules/.bun/`), and its format is Playwright's own.
- **The install's commands kept in the terminal's group, so an interrupt reaches them.** Rejected: a bound then cannot kill the command with its descendants ("An interrupted install").
- **An interrupted install stated as a limit.** Rejected: the bound of a left command is counted by nobody, so a hung clone would stay for ever, and the next install would take its half-made folder for a clone.
- **The loop's bounded commands with no command file, the delay stated.** Rejected: a `stop` would wait out up to 15 minutes of a download, and a stopped tick's push could still land. Item `2026-11-13-004` removed the same delay from the release.
- **The lockfile compared before and after the sync, as today.** Rejected: one failed install is then never tried again.
- **The install guarded by its command file alone.** Rejected: the file exists only while a command runs, so an install between two commands would be invisible to a second install and to a tick.
- **The skip, from the probe's word alone.** Rejected: the word `found` is never read again, so the usual order (installed, then logged out) would skip nothing.
- **The skip, at the tick's start.** Rejected: it would also skip the sync and a pending release's resume; a resume from step 10 on needs no token, and the sync is what brings a fix of the loop's own code.
- **The skip, as a failed tick under the back-off.** Rejected: it would stop asking for hours after a login, and the skip is no failure of the loop's.
- **An errored baseline never measured.** Rejected: a case that errors every time would be picked first at every due tick for ever, and a run with an errored target makes no proposal.
- **The report naming a stop by its kind, the line left to the log.** Rejected: the kinds are a dozen today and each new stop of the release would need a name here; one bounded, redacted line says what happened.
- **The stop before step 1, as a step of its own number.** Rejected: a thirteen-step release with a step 0 in `RELEASE_STEP_NAMES` would move every pinned number. The failure's step 0 lives in the day's state alone.

## Risks and rollback

- **A bound stops a good tick.** A download slower than 15 minutes, or a fetch slower than 5, fails a tick that would have gone on. The tick fails under the back-off and the next due tick tries again; the bounds are constants at the top of `scripts/improve-loop.ts` and in `boundOf`.
- **The shell's install on every due tick.** Should a later Playwright touch the network with the build there, a due tick with no network would fail at the install; such a tick's run needs the network for the model in any case.
- **The skip hides a run somebody wanted.** The skip is said once a day in the report and by a notification, and each hour in the log; it ends at the first due tick after a login.
- **One more command per due tick.** The token's read is one `gh` call, 2 minutes at most; one that hangs fails the tick under the back-off, said in the log.
- **A kill reaches a command that is not the loop's.** Both command files are read with the release's checks: the shape before anything, a pid signalled only as the leader of its own group with the start time the file names, and an install's command never while that install still runs.
- **A bounded command outside the tick's group.** A stop that could not read the home's command file (removed by hand, off its shape) leaves the command to its bound. A stop that lands between two short commands of a tick signals none of them; each has its bound, and the tick reads the stop's marker before its one long command.
- **A lock left in the user's checkout.** A git command killed at its bound during the fast-forward can leave `index.lock` there. The loop removes nothing in the user's checkout; its line names the command and the file.
- **The skip covers a logged-out account only.** A stored token that was revoked or lacks a scope passes the read; the release then fails at its GitHub steps, as today.
- **The clearing and a living git.** A lock younger than a minute is waited for and taken only if it is still the same file a minute after it was made. A living git that holds one lock file for more than a minute would lose it; the loop's own git commands in the clone are short, and the clone is reset to `origin/main` at every tick.
- **The clearing's wait.** A tick that finds a young lock waits up to a minute before its sync and before its probe, and says so before it waits. The install's wait for its first tick's probe is longer by that minute, 150 seconds in all.
- **A person working in the loop's clone.** A git lock of theirs younger than a minute is waited for, and left when their git released or wrote it again; one they hold for more than a minute is removed. The clone is the loop's own, which `docs/improve/README.md` says from this item on.
- **A stop's name in a public file.** The name is one line of 200 characters, through the loop's redaction, with the two homes replaced. The tests check those three things; what else a git message or a branch's name can hold is not checked.
- **ssh in batch mode for the loop's git.** The loop has no terminal under launchd, so a credential that asks already fails there. Read on 2026-11-13: `git ls-remote origin HEAD` with the two settings answers from the loop's clone.
- **A failed install over a loaded agent.** The install loads the agent it booted out again and exits 1; the loop then runs as before the install, on the clone as the failed step left it, and the tick's own packages' and shell's installs try again.
- **A stale install lock.** An install killed outright leaves its lock; the next install finds its process gone and takes over. A process that reuses the pid with another start time reads as another, so the lock is stale.
- **Rolling this item back** is reverting its commit: the day's state gains one optional field, which the older code ignores, and a failure with step 0, which the older code prints as a failed step with that number.

## Non-Functional Requirements

- Performance: every tick runs the packages' install after its sync (8 ms with nothing to install). A due tick runs two commands more, the shell's install (0.2 s with the build there) and the token's read. Each folder's first git command reads its configuration once.
- Security: the token's read keeps the word alone. A stop's line reaches a pushed file only as its name. One folder's ssh command is never used in another. A command file holds four lines of pids and start times, never a command's arguments, output or environment.
