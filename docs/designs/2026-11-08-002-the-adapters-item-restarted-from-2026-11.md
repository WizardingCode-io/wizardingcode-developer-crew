## Problem

This item makes a release reach the crew files that other coding agents keep inside each project, and makes each project say which engine version last brought them up to date. A person who works in a project with Copilot, Codex, Cursor, Gemini or OpenCode then gets the current method and roles after a release, with no reinstall by hand.

A runtime adapter is what lets another coding agent run the crew. `crew runtime install <name>` writes the runtime's hook configuration naming a plugin root (the folder holding `dist/crew.mjs`), copies the skill to `.agents/skills/crew-method/` (one folder the five runtimes share, `AGENTS_SKILLS`, `packages/engine/src/runtimes.ts:911`), and generates the agents under `crew-` names (`runtimes.ts:1234-1288`). A release refreshes the root (the tarball install at `~/.local/share/wizardingcode-developer-crew`, `scripts/release.ts` step 11), but nothing installs the copies inside a project again. On 2026-11-06 the Copilot adapters of cf-ecommerce-v3 and rockport-new were stale: `crew runtime check copilot` said `skill: stale (30 files differ)` and `agents: stale (16 files differ)`. Both projects commit their adapter files (`git ls-files`, checked 2026-11-08). No checkout records which engine version last updated it (finding 223's analysis, item 2026-11-04-001).

A session that starts with no active item remembers the files the gates watch as they were (its baseline) and stops a turn while one of them differs from that memory and no item whose recorded proof covers the changed files exists; so a refresh that rewrites a watched file after a session's baseline makes that session stop, and a commit does not end it (the mechanism and its cost are in Risks, the window bullet). The watch list leaves out `**/*.md`, `docs/**`, `.crew/**` and `.claude/**` (`packages/engine/src/detect/index.ts:15`). So of an adapter's files only these are watched: each runtime's configuration file, OpenCode's plugin file and Codex's `crew-*.toml` agents (`runtimes.ts:879`). The skill copy (all `.md`) and the other runtimes' agents (`crew-*.agent.md` and the like, `runtimes.ts:886-896`) are not. A refresh that changes only unwatched files blocks nothing.

## Goals

- G-1: a stale project-scope adapter is installed again at its project's next session start under the engine whose root it names, with no command from a person, in a project that commits its adapter files (an adapter never committed is held back and the line says how to adopt it).
- G-2: one command, `crew projects update [--dry-run] [--json]`, does the same now for every registered project (the fleet) and reports the user-scope adapters once per run; the release runs it. `--json` is the command's machine form, as every crew command has one (`crew help`: `--json on any command prints the machine form`), for a person or an agent that reads the fleet's state as data.
- G-3: a checkout records, per plugin root, the engine version that last brought its adapters up to date. The record is true when written: it is written only when a check after the refresh reports every adapter on that root ok.
- G-4: no refresh writes into a task worktree's branch, overwrites or removes a file git cannot bring back (an uncommitted edit, an untracked or an ignored file), or re-signs a register changed outside the engine.
- G-5: no refresh loses a session's context: the refresh stays inside the hook's bound, which the 8 s deadline keeps except for a single install that alone outruns the remaining 7 s (Risks).
- G-6: a live session's turn is not blocked by a refresh. Live is a session seen within the last 10 minutes and not ended (`SESSION_LIVE_MS`, `packages/engine/src/state.ts:53`). A refresh is held back while another session is live, and a session takes its baseline only after the `adapters` lock is free, so no baseline is taken while a refresh writes. Two exceptions remain, each only when a watched file changes, with their cost in Risks: a neighbour idle for more than 10 minutes (D-5 of this item), and a start whose wait for the lock outruns its deadline.
- G-7: what each refresh wrote, refused or failed is on record in the project's decision register, not only in the model's context.

## Non-goals

- Writing user-scope adapters (`~/.agents`, a runtime's home folder): they are checked and reported with the command, never written by a refresh (D-6 of this item; R-2 of item 2026-11-04-001).
- Re-rooting an adapter, or a stable-root policy for adapters installed from Claude Code's cache (D-4): an adapter naming another root is reported, never rewritten; an adapter on an older version folder of Claude Code's plugin cache is reported with the command that fixes it, and Design step 2 says why.
- A general migration registry for later releases' changes; the other release migrations finding 223's analysis lists (profile, packs, policy defaults) are already applied on read or at SessionStart.
- A change to the default watch list (D-5 of this item).
- A rollback mechanism beyond a forward patch release, or reinstalling an older root (Risks).
- Refreshing a teammate's clone from this machine: the configuration's absolute root is gone there and is reported so.
- A change to `crew runtime install` and `crew runtime check` beyond these: the write order, the prune, the link refusal at project scope, the configuration written only when it differs, the error that carries what the install had written when it threw (`InstallFailed`), the check's parts as data, and the comparisons of Design.
- Claude Code itself: it loads the plugin, and `runtime.name === "claude"` is skipped everywhere in this item.

## Design

### Why own root only

The engine that runs a runtime's hooks is the engine at the root the runtime's configuration names: a Copilot session in cf-ecommerce-v3 runs `node <tarball>/dist/crew.mjs hook …`. `installRuntime` takes the sources from the root it is given, but the configuration's entries and the agents' format from the running engine's own code (`runtimes.ts:1256, 1281`). So only the engine of root R installs an adapter rooted at R with its configuration, its agents' format and its sources from one release. A Claude Code session (the cache root) never touches a Copilot adapter on the tarball root, and no two engines write the same adapter back and forth (D-4).

An own-root adapter is one whose configuration names the running engine's root; a foreign adapter is one whose configuration names any other root.

### The record

`LocalState` (`packages/engine/src/state.ts:46-50`) gains `adapters?: Record<string, string>`: a canonical plugin root to the engine version that last brought the adapters on that root up to date in this checkout. `loadState` keeps each entry whose key is a string and whose value matches `^\d+\.\d+\.\d+$` (the release script writes only such versions), drops any other, and leaves the field absent when no entry is left. The record is written only through `recordAdapterVersion(paths, root, version)`, which keeps the given root's entry and the entries whose root still holds `dist/crew.mjs`. Claude Code's cache keeps old version folders for some plugins (on this machine `warp/2.2.0` and `warp/2.4.0`, three `frontend-design` folders, `~/.claude/plugins/cache` on 2026-11-08), so the prune drops a version folder's entry once that folder is gone.

The key is `engineRoot = canonical(pluginRoot())`; `canonical` resolves links, so a root and a link to it are one key. The record is only a skip key for SessionStart: under the lock the check alone decides. An engine shipped before this item rebuilds the state without the field (`state.ts:176-183`) and erases it at its next state write; while such a session stays open, each start of this engine pays one check per own-root adapter, and no write follows when the adapters are ok. Accepted, and stated here once.

### Text a repository controls

A root is text a repository wrote (`ROOT_IN_COMMAND` takes any `\S+`, `runtimes.ts:1363`), and so are the paths of an adapter's files and the messages git or a thrown error carry. Every such text that reaches a context line, a register entry or the output of `crew projects update` (`--json` included) passes `quotedText` (`packages/engine/src/quote.ts:8`): one line, no control, C1 or bidi-override character, cut to a cap. `quotedText` today cuts at `SAFE_TEXT_MAX`, 120 characters, and takes no other cap; this item gives it an optional `max` that defaults to `SAFE_TEXT_MAX`, so no other caller changes, and these texts use 200, because a hold-back line names up to three paths of about 60 characters each and 120 would cut the second. Each path is quoted on its own before a list is joined by `, `, at most three paths and then `and <n> more`; each message is quoted the same way (security R-1 of this item; AC-24).

### The refresh of one checkout

A new module `packages/engine/src/adapters.ts` holds `refreshAdapters`, the logic both callers share, at project scope only. Its inputs:

- the checkout's paths;
- the running engine's root and version;
- whether this is a dry run, and a deadline (SessionStart's time budget; none for `crew projects update`);
- four facts the caller knows: a resumed session, an active item, a task worktree, another live session.

It does the whole refresh, the record and the register entry included, and returns:

- one result per own-root adapter, with a status (`up to date`, `updated`, `would update`, `stale`, `refused`, `failed`), the reason, the number of files that differed and the number removed;
- the foreign adapters it found, each with its root and its reason;
- whether the version was recorded and whether an entry was appended, the version recorded before, and the running version.

The signature and the test seams are the plan's (Task 3).

The skill copy is shared: the five runtimes read `.agents/skills/crew-method/`. So when any own-root adapter is stale (its configuration, its agents or the skill copy), every own-root adapter is installed again and checked again. A configuration is written only when its value differs, so a runtime whose configuration was current does not see its hook change. An adapter that was ok at the first check and is installed with the others reports `up to date`.

Steps, in order:

1. For each runtime in `RUNTIME_NAMES` except `claude`, read the project-scope configuration and the root it names (`rootOf`). Absent, or naming no crew hook (`rootOf` returns `null` then, `runtimes.ts:1366-1374`; an empty decoded OpenCode `ROOT` counts the same): not an adapter; skipped, nothing said (assumption 3 of `brief.md`). A configuration that cannot be read, whose root cannot be decoded (a malformed OpenCode `ROOT` string) or whose root is not an absolute path, is a foreign adapter with reason `root unreadable`, and the other runtimes go on.
2. The root it names. A root without `dist/crew.mjs` is `root gone` (tested before the root is made canonical). Otherwise, made canonical and not the running root, it is foreign:
   - `older plugin folder`: a version folder of Claude Code's plugin cache (`/plugins/cache/<market>/wizardingcode-developer-crew/<v>/`) older than the running version. It is reported because Claude Code deletes an older version folder at its next plugin update, which leaves the adapter with no engine, and nothing else tells the person (D-4's requirement; the coupling to the cache layout is in Risks);
   - `another root`: any other root, another engine's. SessionStart says nothing about it; `crew projects update` names it.

   Foreign adapters never hold back the record. A root, like every text shown, follows "Text a repository controls".
3. The own-root adapters: `checkRuntime` at project scope, named explicitly (a null scope falls back to the user scope, `runtimes.ts:1463-1467`). It returns each part's state as data: the configuration, the skill copy, the agents and the hook events it runs on sample payloads, each ok or stale with a count of what differs or failed. The configuration, the skill copy and the agents all ok: every adapter `up to date`, the version recorded unless a dry run, and the refresh ends. A checkout with no own-root adapter ends here too: no adapter file is written there, and later starts at this version only read the state. A stale configuration, skill copy or agents is what a reinstall fixes, and the only thing that triggers one; an event that fails is a fault of the running engine's code, which no reinstall fixes: that adapter is `failed` with the event's line, nothing is installed for it, the version is not recorded, and `crew projects update` exits 1 for it (Risks). Otherwise this first check is kept: it gives the counts and whether a watched file would change (a stale configuration, or a stale Codex agent).
4. The adapters are held back, nothing written, when the first of these holds; every own-root adapter that is not up to date is then `stale` with that reason:
   - `a resumed session`, only when a watched file would change: SessionStart's source is a resume or a compaction, so the session keeps the baseline it took before (D-5 of this item);
   - `an item is active`;
   - `a task worktree`;
   - `a session is live`, only when a watched file would change: another session is live in the checkout;
   - `decisions.json changed outside the engine`: the register reads as tampered (`registerTampered`, `packages/engine/src/decisions.ts:77`), so the entry this refresh would append would re-sign it (`appendDecision` writes protected JSON, `decisions.ts:56-60`).
5. Links (the predecessor item's security return R-1): every path the installs would write or remove, every existing entry under `crew-method/` and every `crew-*` entry of each agents folder, and every parent folder from them up to the project root, the root itself left out. A symbolic link, a path that resolves outside the project root, or a `crew-*` agent entry that is not a regular file gives every own-root adapter `refused` with that path named, since they all write the shared folder. The engine's existing link checks (`packages/engine/src/questions.ts:74-88`, `packages/engine/src/spec-publish.ts:14-52`, `packages/engine/src/audit-report.ts:172-183`, `packages/engine/src/cli.ts` `isLink` and `insideFolder`) each guard one file against one folder and none walks a tree, so this check is new; it lives beside `installRuntime`, which refuses on the same cases at project scope. A dry run that found a problem here returns with the refusals.
6. The git status of the adapters' files, read once: the configuration files of the own-root adapters, `.agents/skills/crew-method`, and each `<agentsDir>/crew-*`. The reader is `gitStatusEntries` of `packages/engine/src/fingerprint.ts` (new in this item: it runs `git -c core.fsmonitor=false status --porcelain=v1 -z --untracked-files=all --ignored=matching -- <paths>` with stderr captured and its output untrimmed, returns each entry with its kind, and throws with git's first stderr line); `gitChangedPaths` (`fingerprint.ts:65-81`) becomes its wrapper and keeps its contract, so its callers do not change. Every git command the refresh and the fleet run in a project, the prune's `ls-files` and `status` inside `installRuntime` included, passes `-c core.fsmonitor=false` (AC-26; Risks, Security). A checkout that is not a git repository holds the adapters back as `stale (not a git repository)`. A changed path holds them back as `stale` with `uncommitted changes in <paths>`; an untracked one with `not committed: <paths>` (an adapter installed and never committed); an ignored one with `files git ignores in <paths>`. A status that cannot be read holds them back with `git status failed (<message>)`, the message git's first stderr line (`gitError`, `packages/engine/src/worktree.ts:66`). Each path and message follows "Text a repository controls".
7. A dry run: `would update` for each stale adapter; nothing is written, recorded or appended. Steps 5 and 6 only read, so the dry run predicts the real run's refusals and hold-backs.
8. Otherwise, under one hold of the lock `<paths.localDir>/adapters` for the whole of this step, waiting at most 2 s for it (a busy lock gives every adapter that is not up to date `stale` with `another session is updating`, and nothing more is written):
   1. The checks run again first. Every one ok: another session refreshed while this one waited, committed or not; every adapter `up to date`, nothing written. Otherwise steps 5 and 6 run again, since a link, an edit or an untracked file may have appeared since they ran outside the lock, and a problem ends the refresh as those steps say (a step-5 refusal's entry is written under this same hold).
   2. `installRuntime` for each own-root adapter in turn, while the deadline has not passed (the deadline is checked before each install); past it, each runtime not yet installed stays `stale (time budget)`. The install is given the root as the configuration names it (whose canonical form is the engine root), so a configuration that names the root through a link keeps its text. A refusal gives `refused` with its text. A throw gives `failed` with its message, and, when the install had written a file before it, `partly written; crew runtime check <name> shows the state`. A refused or failed runtime does not stop the others. After an install that returned, `checkRuntime` again: ok gives `updated` (or `up to date` for an adapter that was ok at the first check); otherwise `failed` with its first problem.
   3. The record, when no own-root adapter ended `stale`, `refused` or `failed`, through `recordAdapterVersion`; and the register entry, when an adapter ended `updated`, `refused` or `failed`: `appendDecision`, a new kind `adapters`, `item: "adapters"`, `by: "the engine"`, with the text `adapters: <the results> (from <the recorded version or none> to <version> at <root>)`, appended only when it differs from the register's last `adapters` entry, so a refusal that stands is written once.

   `withLock` breaks a lock older than 10 s as left by a dead process (`packages/engine/src/lock.ts:4, 99`), and the hold spans the whole step, whose time Task 4 logs (target under 1 s). Should a refresh outlive 10 s, a second writer can take the lock and install the same bytes from the same root, since an install is idempotent: no file ends as a mix of two releases, and at most one duplicate register entry can follow, which the last-entry rule stops when the texts are equal. This paragraph is the one place that states it.

A held-back checkout (steps 4 and 6) appends no entry: its line says why at each start.

### `installRuntime` and `checkRuntime`

These changes hold for `crew runtime install` and `crew runtime check` as well:

- Write order: the skill copy and the agents first, the configuration last, so a failure mid-copy leaves the configuration on its earlier root and content. The configuration is written only when its value differs from the file's (AC-28), so Codex is not asked for trust again, and Gemini does not warn again, at a release that leaves the hook entries as they are. The returned `files` keeps its listed order, configuration first when it was written.
- Prune: the candidates are every file under `crew-method/` the root's `skills/crew` does not hold; at project scope, every `crew-*` file in the agents folder that `generatedAgents` does not produce; at user scope, the same agents. At project scope a candidate is removed only when git tracks it and shows it unchanged, so `git restore` brings it back as it was. At user scope a skill candidate is removed, since every file in `crew-method/` is crew's (as `removeRuntime` treats it, `runtimes.ts:1345-1348`), and an agent candidate is not. A candidate not removed (untracked, ignored, modified, outside a git repository at project scope, or a user-scope agent) is returned as `left`, and `crew runtime install` prints a `left <path>` line for it (the predecessor item's security return R-3).
- Links: at project scope the install refuses, before any write, on the cases of refresh step 5, so a link a repository wrote is never written through and never left. At user scope no link is refused: a person's dotfile manager may make `~/.agents` or a runtime's home folder a link on purpose, and no repository wrote it.
- Configuration comparison: the configuration the install would write for the root the configuration names (a JSON configuration merged into the file's other entries, or the whole file for OpenCode) is computed by one function both use. The check compares a JSON configuration by its parsed value and OpenCode's file by its text, and says `config: stale` when they differ, so a release that changes only the hook entries reaches the adapter and a reformatted file is not stale. Claude Code's row writes no configuration and is not compared.
- Skill copy comparison: on the copy side, a link, and a file under `crew-method/` the source does not hold, count as differing; the copy is walked by `lstat` and a link is never followed, so a dangling one no longer throws. The source side, the plugin's own folder, is walked as today.
- Agents comparison: at project scope, a `crew-*` agent `generatedAgents` does not produce counts as differing; a person's own agent with another name does not. At user scope only the generated agents are compared, so an agent the install leaves never makes the check fail.
- A throw inside the install, after the first write, is rethrown as `InstallFailed` carrying how many paths it had written or removed, which is what `partly written` rests on.
- The check returns its parts' state as data (the configuration, the skill copy, the agents and the events, each ok or stale, the count of files that differ or events that failed, and the list of problems, each the check's own printed line), and renders its printed lines from that data; nothing reads the printed lines back.

### SessionStart

In `onSessionStart` (`packages/engine/src/hooks/session-start.ts`), after the profile refresh (line 61) and the resume check (`continues`, lines 65-67), and before the baseline (line 68), fenced in its own `try` as the pack discovery is (lines 40-58). The deadline is 8 s after entry to `onSessionStart` (`start = Date.now()` at its top, after the bundle has loaded); mail, the sweep, the pack discovery and the profile refresh run before this step (lines 25-61) and spend part of those 8 s.

1. `recorded = loadState(paths).adapters?.[engineRoot]`. Equal to `VERSION`: no refresh, no configuration is read. Any other value, older, newer or none: `refreshAdapters` with the deadline, and:
   - `resumed`: the source is a resume or a compaction and the session is already in the state (`continues`);
   - `activeItem`: `activeWork(paths) !== null`;
   - `worktree`: `worktreeMainRoot(paths.root) !== null`;
   - `live`: `liveSessions(paths)` holds a session other than `ctx.sessionId`. A neighbour's baseline was taken before the write, and its Stop with no item would block on a watched adapter file (the predecessor item's architects return R-1).

   A newer record means the root itself now holds older code (a reinstalled older tarball, a developer tree at an older commit), since only the engine of that root writes its record; the check then reinstalls from the root as it now is.

   Then, whether or not this session refreshed anything, the baseline wait: the step takes and releases the `adapters` lock, waiting until the deadline, so no baseline is taken while another session's or the fleet's refresh (one hold for its whole step 8) is writing; past the deadline it says `another session is updating` in the adapters line and takes the baseline anyway (AC-27; Risks).
2. The adapters line, when any adapter was updated, stale, refused or failed, or a foreign adapter other than `another root` was found: `adapters: ` then the results joined by `; `:
   - `<runtime> updated (<n> differed, <m> removed)`, the runtime's trust text in parentheses after it when its configuration was written and the runtime asks for trust again;
   - `<runtime> <status> (<reason>)` for the others;
   - `<runtime> names <root> (<reason>): run crew runtime install <runtime> with the crew of the root to keep, such as ~/.local/share/wizardingcode-developer-crew/bin/crew` for a foreign one, and `<runtime> root unreadable (<path>)` when the root could not be read.

   Then, in this order:
   - when an adapter was updated, `; applies from each updated runtime's next session` once (when a runtime reads its skill and agents, before or after its hook, is not known, so no earlier effect is claimed);
   - when an adapter was updated, `. Commit: git add -A -- '<path>' … && git commit -m 'adapters refreshed by crew <version>'.` (the `-m` so the command runs with no editor), the quoted pathspecs from the runtime table: each configuration file that was written, `.agents/skills/crew-method`, `<agentsDir>/crew-*` for each agents folder, and `.crew/decisions.json` when an entry was appended. `-A` with a pathspec stages the prune's deletions as well;
   - for a held-back adapter, `; it is updated at a session start with no active item, or by crew projects update` for an active item, `; commit or restore them first` for uncommitted changes, and `; commit them to adopt the adapter, or run crew runtime install <runtime> again` for files never committed (never `git clean`, which would delete the adapter);
   - `; another session is updating` when the baseline wait outran the deadline; with no other result, the whole line is `adapters: another session is updating.`

   SessionStart joins its lines into one paragraph (`session-start.ts:166-167`), so the line ends in a full stop and comes after the `Engine: crew X.` sentence.

   The line reaches the model, not the person, and OpenCode has no context at start at all (`requested`, `runtimes.ts:1146-1148`), so an OpenCode session never shows it. In every runtime a person learns the state the same way: `crew status` prints the checkout's last `adapters` register entry as one line, `adapters: <text>`, after the item's lines (AC-25), the skill's first step runs `crew status`, and `crew projects update` names each project.
3. A throw anywhere in these steps: the line `adapters: not checked (<message>).`, the message following "Text a repository controls", and SessionStart goes on.

The cost at the same version is one read of `state.json` and one take and release of the `adapters` lock (`withLock` makes the folder `.crew/local/adapters` and its lock, `lock.ts:84-90`); the one failure this adds at every version is a stray file at that path, which makes the start say `adapters: not checked (<message>)` (AC-5's fixture). At a new version the cost is, per runtime, one `existsSync` and one read of the configuration; for each own-root adapter, one `checkRuntime`, which hashes the skill folder (52 files at 0.20.1, read on 2026-11-06) and the agents and runs the runtime's hook events on sample payloads in process; and, when one is stale, two `git status` (one outside the lock, one under it). It is measured in the plan's Task 4.

The hook's bound is 15 s: Claude Code's (`plugins/core/hooks/hooks.json:4`) and the other runtimes' (`TIMEOUTS["session-start"]`, `runtimes.ts:108`); OpenCode's `session.created` plugin states none. The bound's other 7 s, after the 8 s deadline, cover the lock wait, the baseline fingerprint and the lines; that rest is not measured, and Task 4 logs the adapter step's own time.

### `crew projects update [--dry-run] [--json]`

The registry is `projects.json` in the engine's own folder (`~/.wizardingcode/crew`, `userDir`, `packages/engine/src/paths.ts:81`); a project enters it at its first hook. In `packages/engine/src/cli.ts`, `case "projects"` dispatches `update` to a new `projectsUpdate` and `standingE2eSkip` to the existing function, the bulk command of finding 223.

The registry loop is shared. `projectLeftOut` (`cli.ts:2091-2108`) splits into the rules every bulk command takes, `registryLeftOut`, in today's order (gone, scratch, not a git checkout, no `.crew`, the root or `.crew` a symbolic link, `.crew` not a folder), and the standing skip's own two checks (`policy.json` a link, no profile), which stay in the standing skip at their place with their text. The update adds one check after the shared rules: a register changed outside the engine leaves the project out with the standing skip's text, `decisions.json changed outside the engine`. Worktree entries of the registry (`worktreeOf`) are left out of the loop, as the standing skip does (`cli.ts:2129`).

Per project not left out, inside a try: `refreshAdapters` with no deadline, `resumed` false, `activeItem` from its `activeWork`, `worktree = worktreeMainRoot(<project root>) !== null` (a worktree registered without `worktreeOf` passes the shared rules, since its `.git` file exists: the predecessor item's architects return R-2), `live` true when `liveSessions` holds any session, and the dry-run flag. A throw gives that project the line `failed (<message>)`, and the loop goes on. Each project's line is printed as its refresh finishes, so a run the release's bound kills leaves the reached projects' lines on the log.

The output, all on stdout, whatever the exit status, in this order: the project lines, one `user scope:` line, the count line, then the commit lines:

- One line per project: `<name> <root>: ` then
  - `up to date` when the project has at least one own-root adapter, every one of them is up to date and no foreign one was found;
  - otherwise each own-root adapter as `<runtime> <status>[ (<reason>)]` and each foreign one as `<runtime> on another root (<root>)`, `<runtime> names <root> (root gone)`, `<runtime> names <root> (older plugin folder)` or `<runtime> root unreadable (<path>)`, joined by `, `;
  - or `no adapter on this root` when it has no own-root adapter and no foreign one, `left out (<reason>)`, `gone`.
- One line for the user scope, once per run: `user scope: ` then, for each runtime whose user-scope configuration names the running root (made canonical), `checkRuntime` at user scope with the home from the environment (as `crew runtime install` takes it, `cli.ts:6251`), as `<runtime> up to date` or `<runtime> stale: run crew runtime install <runtime> --scope user with the crew of this root`; a configuration that cannot be read as `<runtime> unreadable (<message>)`; or `no adapter on this root`. Nothing is written there (D-6).
- The count line. Each project is counted once, in the first bucket its adapters reach in this order of precedence: `failed`, `refused`, `stale`, `would update`, `updated`, `up to date`; a project with no own-root adapter counts as `other root` when it has a foreign one, else `no adapter`; `left out` and `gone` are their own buckets. The line prints the buckets in a fixed order that is not the precedence: `<n> updated, <n> would update, <n> up to date, <n> stale, <n> refused, <n> failed, <n> other root, <n> no adapter, <n> left out, <n> gone`.
- One line per updated project, `commit in <name>: git add -A -- '<path>' … && git commit -m 'adapters refreshed by crew <version>'`, with SessionStart's commit list.

Exit status 1 in these cases, 0 otherwise:

- a project ended `refused` or `failed`;
- a word after `update`;
- `--reason` or `--remove`, which `KNOWN_FLAGS.projects` lets through to the subcommand (`cli.ts:533`) and the subcommand refuses with its usage line; any other flag is refused before the dispatch by `unknownFlag` (`cli.ts:599-610`) with its own text.

A stale user-scope adapter does not change it. `--json` prints the CLI's envelope `{ ok, message, projects, user, counts }` (`cli.ts:6910-6913`) instead of the lines, the message the count line alone, every string value following "Text a repository controls".

The PreToolUse guard asks the person before a `crew projects update` that is not a dry run, and denies it where nobody watches (a session whose permission mode is `bypassPermissions` or `dontAsk`, or a headless run), as it does for `crew projects standingE2eSkip` (`packages/engine/src/hooks/pre-tool-use.ts:657-660, 1143-1146`), because the command writes into every registered project (D-7). The release script runs it as a child process of the person's own command, so the guard does not see it. A release the improvement loop runs with nobody watching (`scripts/improve-loop.ts:768-865, 1404-1417`) runs step 12 the same way and writes into every registered project (D-8 of this item): the person chose this, and the release's notification carries the counts.

### The release

`scripts/release.ts` gets a thirteenth step, `the project update`, before the notification: step 12 is the update, step 13 the notification (`RELEASE_STEP_NAMES` grows to thirteen). The step runs `node <install>/dist/crew.mjs projects update`, the tarball install step 11 swapped in, so the root it refreshes is the tarball; the child gets the release's resolved home (`release.ts:360`). It is skipped when `<install>/dist/crew.mjs` is absent. It is soft (D-3): a failure is logged and the release stands. It has a bound of 300 000 ms: `CommandRunner`'s options gain `timeoutMs` (its `env` option exists already, `release.ts:146-155, 809`), passed to `spawnSync`'s `timeout`, and a killed run reports its signal as a failed step already does (`release.ts:162-166`). The bound rests on this machine's registry (Risks). The script compares versions through the engine's `compareVersions` (`packages/engine/src/version.ts`, moved there from `packs.ts` by this item) and drops its own `compare`, so one comparator exists.

The notification says `Released, published and installed here; projects: <state>`. The state is the step's count line, with the exit status when it is not 0; or `not updated (<why>)` when the step printed no count line, the bound killed it (then with the number of project lines it had printed) or it failed; or `skipped` or `not run` when it did not run. The plan holds the order in which these are chosen (Task 6).

## Alternatives considered

- The running engine refreshes every adapter from the root each names (the brainstorm's hypothesis): two engines in one checkout write each other's format, and the record says a version the copies do not have (`concepts_brief.md`, analysis 1).
- Run the named root's own `crew runtime install` as a child process: coherent, but a process per adapter inside a 15-second hook, and a root older than this item has no refresh to call.
- No record; hash-check every adapter at every start: rejected by D-2 of item 2026-11-04-001 (a project says which engine last brought it up to date).
- Only `crew projects update`, no SessionStart: D-2 of item 2026-11-04-001 chose both.
- Re-root an adapter on an older plugin-cache folder to the running root: the running root is itself a cache version folder, or the developer's tree for a release run from the repository; replaced by D-4 of this item.
- Leave crew's own adapter paths out of the Stop rule's fingerprint, so no session guard is needed: the user kept the watch list (D-5 of this item, option A not taken). Only the configuration files and Codex's agents are watched, so the guards now apply only when one of those would change.
- SessionStart reports only and `crew projects update` alone writes: D-5 of this item, option C not taken.
- Write the user-scope adapters once per run: no git brings an overwritten file back there; D-6 of this item chose report only.
- The skill copy as its own unit, installed once by the first own-root runtime: needs a skill-only install and a check without the skill; installing every own-root runtime writes the same bytes with no new option.
- An older engine never touches a newer record: under own root only, a newer record means the root was rolled back, and the rule would leave newer copies under older hooks for good.
- `removeRuntime` then `installRuntime` to prune: removes the configuration first, so a failure leaves no hook at all; the prune after the install keeps the hook through a failure.
- No committed copy at all: the runtimes read the root's own skill folder, or the adapters stay uncommitted. The five runtimes find their skills and agents at fixed paths inside the project (`.agents/skills`, `.github/agents`, `.codex/agents` and the like, `runtimes.ts` table), and none takes a folder outside it, so the copy must exist in the project; left uncommitted, it would be held back at every start as `not committed` and a teammate's clone would have no crew at all. The committed copy is the root cause of the hold-backs, the one idle-session window and the commit command, and it stays.
- One lock hold per install, so a hold never outlives `withLock`'s 10 s break: a session starting between two installs took its baseline and was then blocked by the next install's write; one hold for the whole refresh closes that, and what two writers produce when a refresh outlives 10 s is stated in Design step 8.

## Risks and rollback

- The same hold-back rule holds across good releases: a project that never commits a refresh is held back at every later release until its files are committed or restored, the engine's own earlier refresh counting as an uncommitted change like a person's edit (D-1 and D-9 of this item; `concepts_brief.md` Analysis 14 names the cost for a project nobody opens). The adapters line gives the exact commit command.
- An adapter installed and never committed is held back at every start (`not committed`); the line says to commit it or reinstall, never to clean it, since `git clean` would delete the adapter and the next start would find nothing to report.
- A refresh killed by the release's bound or by the hook's 15 s bound, or one that threw after a write, leaves part of the files written. A kill by the hook's bound also loses that session's context; the 8 s deadline is there so the hook does not reach its bound, and it is checked before each install, so the one case it cannot stop is a single install that alone outruns the remaining 7 s. The line says `partly written` and names the check when the refresh saw the throw; the next start holds the adapter back until the files are committed or restored, and the check after that installs again. Committing them is safe, since the next refresh overwrites them.
- The mechanism behind the session guards, stated once: with no item active, a session's Stop rule diffs the tree against the session's baseline commit (`noItemTurnEnds` and `sinceBaseline`, `packages/engine/src/work.ts:1066-1102`; `gitChangedSince`, `packages/engine/src/fingerprint.ts:93-98`, committed since or not), so a refresh that changes a watched file (a configuration or a Codex agent) after a session's baseline blocks that session's Stops, up to `MAX_STOP_BLOCKS` (three, `packages/engine/src/hooks/stop.ts:13`) per turn (the count resets at each turn, `stop.ts:43`), for the rest of the session; a commit does not end it; a new session, whose baseline is taken after the write, or an item whose recorded proof covers the changed files does. Two windows remain where this cost falls on a session (D-5 of this item), each only when a watched file changes: a session idle for more than 10 minutes is not live (`SESSION_LIVE_MS`, `state.ts:53`), so a refresh can write after its baseline; and a session whose wait for the `adapters` lock outruns its 8 s deadline takes its baseline while the refresh still writes, which its adapters line names as `another session is updating`. The two other windows the predecessor item named (a session held back as `a session is live` taking its baseline while its neighbour writes; a session starting while `crew projects update` holds the lock) are closed by the baseline wait (Design, SessionStart; AC-27).
- Two sessions starting together can each find the other live (`recordSeen` runs in every hook before SessionStart, `packages/engine/src/hooks/context.ts:62`), so both are held back and neither refreshes when a watched file would change; a person who always keeps a second session open in a project (Claude Code beside Copilot) is held back at every start, and by the fleet, in that case, until they work with one session; the next start with one session refreshes. Today this applies only when a configuration or a Codex agent changes (D-5 of this item).
- An unattended release by the improvement loop writes into every registered project with nobody watching (D-8 of this item). Its writes follow the same rules as a person's release (held back over an active item, uncommitted files or a tampered register; left uncommitted), and the notification names the counts.
- The loop keeps a pending release's failed step by number (`pendingRelease.failedStep`, `scripts/improve-loop.ts:1406-1419`, mapped to a name through `RELEASE_STEP_NAMES` at 1566 and 2002), as `--from-step` does. A release that failed at its notification before this item (step 12 then) and is resumed after it runs step 12 as the update and step 13 as the notification, both soft: one update more, nothing lost. Stated, not guarded.
- Codex skips a changed hook until it is trusted again, and Gemini warns again (`runtimes.ts:986-987, 1118`). A configuration is written only when the release changed its entries (AC-28); then Codex's own prompt asks its user, the refreshing session's line carries the trust text, the register entry names the runtime, and `crew runtime check codex` shows it. An untrusted Codex session runs no crew hook, so it gets no adapters line until the person trusts the hook again.
- Security: the link refusal at project scope, every repository-controlled text shown through `quotedText` (security R-1 of this item), the prune of tracked and unchanged files only, and the tampered register held back at SessionStart and left out by `crew projects update`. A new exposure, named: step 6's `git status` is the first git command the engine runs in a registered project with nobody in it (`crew projects standingE2eSkip` only tests that `.git` exists, `cli.ts:2099`, and `worktreeMainRoot` reads the `.git` file, `worktree.ts:9-16`; the engine's other git calls run inside a project's own hooks, with a person's session there). Git reads the commands it may run from local configuration (`.git/config`, the user's), which a cloned repository cannot write; a tracked `.gitattributes` can only select a filter driver the local configuration defines (git-lfs's, for example), so those filters are the user's own tooling and stay. The one such command that would start a daemon under an unattended run is `core.fsmonitor`, so every git command on the refresh and fleet paths (step 6's status, the same status again under the lock, the prune's `ls-files` and `status` inside `installRuntime`) passes `-c core.fsmonitor=false` (AC-26).
- An event of the check that fails (a hook event run on a sample payload) is a fault of the running engine's code, which no reinstall fixes: the adapter is `failed` with the event's line at every start, the version is not recorded, so each start pays one check per own-root adapter until a release fixes the engine, and `crew projects update` exits 1 for that project. Stated; the alternative, reinstalling at every start, would write the same files for nothing.
- An engine shipped before this item erases the record (Design, The record).
- The record is per checkout, not per branch: checking out a branch with older adapter files under a current record goes unnoticed at SessionStart until the next version; `crew projects update` and `crew runtime check <name>` find it, since under the lock the check alone decides.
- A project whose item stays active for days keeps a stale adapter; the line says so at every start, and `crew projects update` reports it.
- The five runtimes share `.agents/skills/crew-method`. With adapters on two roots in one project, each engine's refresh rewrites the shared folder and the other's check says stale: the folder follows the engine that ran last. Reported, not fixed here.
- The `older plugin folder` reason reads Claude Code's cache layout (`/plugins/cache/<market>/<plugin>/<version>/`); if that layout changes, such an adapter is reported as `another root` by `crew projects update` and not at all by SessionStart.
- An adapter folder git ignores holds the refresh back, so it is never written by a refresh; `crew runtime install` by hand still overwrites its files and leaves the extras.
- `withLock`'s 10 s break and what two writers produce: Design step 8, the one place.
- `crew projects update` writes each updated project's `.crew/decisions.json` and `.crew/local/state.json`; the commit command names the register with the adapter paths.
- The bound of 300 s rests on this machine's registry: 45 root entries on 2026-11-08 (`~/.wizardingcode/crew/projects.json`), two of them known to hold a Copilot adapter (cf-ecommerce-v3, rockport-new). Per project the step costs the configuration reads and up to five checks; no `git status` when every adapter is up to date, two when one is stale (one outside the lock, one under it), and a refresh at the time Task 4 logs (target under 1 s), so 300 s covers the registry at under 6 s a project. Each project's line is printed as it finishes, so a kill at the bound leaves the reached projects on the release's log, and the notification says how many lines were printed.
- Rollback of a bad release: it reaches every adapter on the tarball root at the next session start, and step 11 deletes `${install}.previous` (`release.ts:676-684`). Rollback is a forward patch release, or reinstalling the older tarball, which the next start installs from (a newer record no longer stops it). A refresh is left uncommitted (D-1), so the next start finds its files changed and holds the adapter back (`uncommitted changes`) until a person commits or restores them; then the next start or `crew projects update` installs again.
- Rollback of the item: revert its commit; the earlier engine erases the record at its next write (Design, The record).
