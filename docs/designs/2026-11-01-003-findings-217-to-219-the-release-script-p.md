# Findings 217 to 219: the release's failure output, the local settings file, the Stop hook during a release

## Problem

Releasing this plugin fails or blocks in three ways that have nothing to do with the code being released: a failed check hides which test failed, a file Claude Code writes makes the lint fail, and the engine blocks the session's turns during and after the release because nothing tells it a release happened. Each was met in the release of 0.18.1 on 2026-11-01 (`docs/real-use/findings.md`, 217 to 219).

### Terms

- **The release script**, `scripts/release.ts`, runs twelve numbered steps (ADR 0015): 1 the version files, 2 `bun run build`, 3 `bun run check`, 4 `bun run plugin:check`, 5 the commit and the tag, 6 the push, 7 the tarball, 8 the GitHub release, 9 the marketplace entry, 10 the plugin update here, 11 the local install, 12 the notification. A failure at steps 1 to 6 puts the tree back with `git reset --hard` to the commit the release started from (**the start sha**); a failure at 7 or later is resumed with `--resume vX.Y.Z --from-step N`; step 12 is the soft step, whose failure is logged and never fatal. The script's **step cycle** runs the steps in order and logs one line per step; its first log line is the **title line**, `Release <version>: <reason>` (or `resuming release <version> from step <n>`). The script takes 12 to 20 minutes here, so it runs in the background: a Bash tool call with `run_in_background` (the tool's foreground cap is 10 minutes), or a `!` command, which Claude Code moves to the background after 120 seconds (finding 217's session).
- **The improvement loop**: the launchd job of ADR 0015 that runs this repository's evals in its own clone and releases what it proves, calling the script's `release()` inside its own process. "The loop" names it alone in this document.
- **Watched paths**: the files the profile's watch covers (`.crew/profile.json`, `watch.exclude`: here `**/*.md`, `docs/**`, `.crew/**`, `.claude/**` are out). The **fingerprint** of a git checkout, the one case here, is HEAD plus the content of the watched paths git's status lists as changed, so a file git ignores never counts: the repository's root `/dist/` folder, where the output files and the tarball land, is ignored; the committed bundle `plugins/core/dist/crew.mjs` is tracked and watched. Without git the engine hashes every watched file instead. The fingerprint reads `unavailable` when the tree is too big to walk or git cannot run. The **baseline** is the fingerprint the session took at its start, kept in the session's state. A **learned item** is a work item whose proof entered the **knowledge base** (the engine's record of proven solutions and root causes, `crew knowledge`); its last gate run's fingerprint is its **proven fingerprint**.
- **The Stop rule**: the engine spec's five cases (`docs/specs/2026-10-06-sp1-engine-and-base-method-design.md`, "The Stop rule"): nothing changed; changed and proven; changed, unproven and waiting (for the user, the roles or a reply); changed and unproven, blocked; the third block in a row, let through with a notice. Beside the cases, two **permits**: the **run permit** (finding 146), a marker a gate run or a test-first step writes under the item's `running/` folder for its length, which lets one turn of that session end per run (the permits a session already used are its **spent** list, kept in its state); and the **release marker**, which this item adds (Design, 219, The marker).
- **Work items** run on the fast, standard or full **route** (how much of the method they run); a **chore item** changes no behaviour, and an **observed criterion** is one a person checks where no test can fail first (both words serve Alternatives, option C). **D-1** is this item's architecture decision, how the engine learns of a release, and **D-2** where the release's steps run, both answered by the user (Design, Alternatives). The **decision register** (`crew decisions`) keeps the project's earlier decisions. The **judgement gates** are the reviewers and the judge that rule the diff after the build.

### The three defects

- **217.** When a release step fails, the script prints the first line of the step's captured stderr, or of stdout when stderr is empty, and keeps nothing else. For step 3 that line is bun's echo of the script (`$ bun run typecheck && bun run lint && bun run test`), because bun echoes each script to stderr before the test runner writes its `(fail)` lines there. The first run of 0.18.1 failed at step 3 after about ten minutes and the name of the failed or timed-out test is lost; the same check passed in the two runs after it. Two more ways the cause is lost were found while reading the runner: `spawnSync` captures at most 1 MiB per stream by default and then stops the command with `ENOBUFS` and a null status (read on 2026-11-01 with a 3 MB command), and a command killed by a signal has a null status too; the runner turns both into exit 1 with no cause.
- **218.** Claude Code writes `.claude/settings.local.json` in the repository when the user allows a command outside auto mode, with its `allow` array on one line. The repository's `.gitignore` does not name it; git ignores it only through the user's global ignore file (`~/.config/git/ignore`), which biome does not read (`biome.json`: `vcs.useIgnoreFile: true` reads the repository's `.gitignore`). So `bun run lint` checks the file, fails on its format, and step 3 fails: the second run of 0.18.1 did, with one file more checked than git tracks.
- **219.** With no active work item, the Stop hook compares the tree's fingerprint with the session's baseline and lets the turn end only when they are equal, when the last learned item's proven fingerprint is the current one (`learnedHolds`, finding 141), or at the third block in a row. A release writes 17 watched files (the version files, two tests, the bundle), commits and pushes them, and nothing records it: the run permit's markers are written by `crew gate run` and `crew tdd` alone. Running in the background, the release lets the session's turns try to end while it runs, and each attempt is blocked; after the push the tree differs from the baseline and from every learned fingerprint until the third block, which the finding's session met twice.

## Goals

- A failed release step prints the lines of its output that name a failure, then the output's last lines, and keeps the whole output on disk with the command's exit status, so the next failed check is traced instead of lost.
- `bun run lint` (which runs `biome check .`) and the release pass with `.claude/settings.local.json` present in whatever shape Claude Code writes it.
- With the installed plugin at or above the version that ships the marker's reader and the session restarted: a session's turn ends while a release runs in the background and after its push, and only what the engine checked counts as proven. What the session changes while the release runs is accounted for in Risks ("The window while a release runs"). The one case that keeps the block after the push is a refusal of the release's end record (Risks, "Limits that fail safe").

## Non-Goals

- Tracing the failure of 0.18.1's first run: its output is gone; this item makes the next one traceable.
- Changing the twelve steps of the release, their order, the rollback before the push or the resume after it (ADR 0015).
- A release in another runtime than Claude Code: the record needs the session's id, which Claude Code gives the command's environment as `CLAUDE_CODE_SESSION_ID`; elsewhere the Stop rule stands as it is.
- Reading the user's global git ignore from biome, or moving the lint's include list.
- A record for any other project: there is no verb and the call is in-process, so only this repository's release script writes the marker; its convention is a version of three numbers and the tag `v<version>`.
- A foreground release: the Bash tool stops a command at 10 minutes, and a release cut off there leaves the tree written with no rollback, which is today's behaviour and not this item's. A step that hangs is today's behaviour too: the runner waits as it does now.
- A release run while a work item is active, a second session in the same checkout, and a release longer than 45 minutes: limits that fail safe (Risks).

## Open Questions

None. The one fact the document review left open, whether the session's id reaches the release's process, was read on 2026-11-01 on both paths: `CLAUDE_CODE_SESSION_ID` was printed by the agent's Bash tool and by the user's `! printenv CLAUDE_CODE_SESSION_ID`, the same id the session's hooks receive (the run permit of finding 146 rests on that equality in every gate run).

## Critical User Journeys

1. **A failed check names its failure.** Given a tree where one test fails, when a person runs `bun scripts/release.ts --patch --reason "<why>"` in the background, then step 3 fails and the log prints the step's first line (the step, the status line, the output file, the rollback sentence) and the body (the failure lines, the summary, the output's last lines) as Design 217's rules 3 to 7 say; the tree is back where it started, and `dist/release-<version>-step-3.log` holds the whole output after the rollback. The macOS notification carries the first line alone, the rollback sentence with it.
2. **The local settings file is ignored by git and biome.** Given `.claude/settings.local.json` written by Claude Code with its `allow` array on one line, when `bun run lint` or a release runs, then the file is not among the files biome names and the lint passes; `git status` does not list the file on a machine without the global ignore.
3. **A release inside a session.** Given a session with no active item and a tree the Stop rule would let end (its baseline, or the last learned item's proof), when the release runs in the background (the agent's Bash tool with `run_in_background`, or the person's `!`), then the script logs its title line and records the release's start in the engine; each of the session's turns ends while the release runs with the notice `Crew: release <version> is in progress (started <time>): the turn ends while its process lives; change no file, commit nothing and start no item until it ends: a failure before the push resets the tree, and a change before the push makes the final record refuse.`; right after the push succeeds the script records the release's end, and the next turn ends with no block: the session's baseline is the fingerprint of the tree at the release's commit. The journey holds with the installed plugin at or above the version that ships the reader; what the session changes meanwhile is in Risks. A session the Stop rule already lets end whatever the tree (no baseline, or an unreadable fingerprint) gets no marker: the start record answers that there is nothing to record and the turns end as they did.
4. **A release that fails before the push.** Given the same session, when step 3 fails, then the tree is back at the start sha and the turn ends on the baseline, or on the last learned item's proof; the marker stays on disk, permits nothing once its process has exited, and the next reader that meets it (the Stop hook on a changed tree with no item, or the end record) removes it.
5. **The loop's release.** Given the loop, which calls `release()` in its own process with no record functions wired, when it releases, then it records nothing and the twelve steps run as today.
6. **A session that tries to type the record.** Given any session, when the agent runs `crew release start 0.19.0` under the Bash tool, then the CLI refuses it as an unknown command, exit 1 with the usage on stderr, and writes nothing: the record has no verb; it is written by the release script's in-process call alone. What a script of the session's own making could do is a matter of trust, stated in Risks.

## Design

### 217: the failure lines and the output file

The rules, as the release script behaves:

1. **The runner.** Every step's command runs through the script's one synchronous runner, as today, which now captures up to 64 MiB per stream and answers the status as today (the exit, or 1 when there is none, so every reader of it is unchanged, the loop's included) and, new, the exit as a number or null (null when a signal ended the command or the capture overran), the signal's name and the spawn error's message, each absent when none. The loop's release wrapper passes the same runner it passes today.
2. **A failed step** is one whose command ends with a status other than 0; its message is several lines, logged as rule 7 says; a step that succeeds prints one line, as today. The step's label, `<what>`, is the one each call passes today, none renamed: `the build`, `the check`, `the plugin check`, `git add`, `git commit`, `git tag`, `git push`, `the tarball`, `gh release create`, `the marketplace PUT`, `the marketplace update`, `the plugin update`, `the extraction`, `the notification`; the marketplace read inside step 9's run goes through the same helper with the new label `the marketplace read` (today's text, `the marketplace file could not be read`, is replaced there), while the read inside step 9's done check keeps today's text and writes no file.
3. **The output file** is `dist/release-<version>-step-<n>.log`, a relative path printed as such and written under the root, only when the step failed: the status line, then stdout, then, when stdout is non-empty and does not end with a newline, one, then `--- stderr ---` on its own line, then stderr. The status line is `exit <status>` (`exit null` for a signal or an overrun) with `, signal <name>` and `, <spawn error>` when they apply. `dist/` is created before the write; a write that fails is a clause of the message's first line, `(the output file could not be written: <error>)`, never a thrown error. `/dist/` is git-ignored, so the rollback's `git reset --hard` leaves the file and the fingerprint never counts it.
4. **The message's first line** is `<what> (<the status line>): lines that name a failure, then the output's last lines (the whole output in <file>)`; when no line names a failure, `<what> (<the status line>): no line names a failure; the output's last lines (the whole output in <file>)`; when the output has no non-blank line, `<what> (<the status line>): no output (the whole output in <file>)` and no body.
5. **A failure line** is read over the output's non-blank lines, stdout's then stderr's, each trimmed of its leading whitespace, and every printed line is the trimmed one. The first group: a line that starts with `(fail)` (bun test's failed test) or contains `━━━` (biome's diagnostic header, which names the file and the rule). The second group: a line that starts with `×`, `✗` or the word `error` (`error` followed by a non-word character: bun's `error: expect(received)…`), or contains `error TS` followed by digits (tsc), or starts with `Found ` followed by digits and ` error` (biome's and tsc's counts), and does not start with `(fail)`, `(pass)` or `(skip)` or contain `━━━`. A `(pass)` or `(skip)` line never counts. Across the two groups a line is kept once, each group in the output's order.
6. **The body**: the first 20 lines of the two groups, then `… and N more` when more matched; then bun test's summary, the last line that, trimmed, is digits followed by ` fail`, whatever the cap; then, whenever the output has a non-blank line, a line `last lines:` and the output's last 10 non-blank lines, trimmed, which may repeat a line the groups printed. Every body line is indented by two spaces.
7. **The logged message** of a failed step: before the push, the first line is `step <n> (<name>) failed: ` + the message's first line + `; the tree is back at <sha7>, nothing released`, and the body lines follow; after the push, the first line is `step <n> (<name>) failed: ` + the message's first line, the body lines follow, and the `resume with: bun scripts/release.ts --resume <tag> --from-step <n>` line stays its own line after them, as today; the soft step's is `step 12 (the notification) failed: ` + the first line + ` (not fatal: the release is out)`, the body after. The notification takes the logged first line (the step prefix, the message's first line and the rollback sentence); after the push it carries `; resume with --resume <tag> --from-step <n>` after it, as today.

What bun test prints by default (read on 2026-11-01, bun 1.4.3): the failing test's source excerpt, `error: expect(received).toBe(expected)`, the `(fail) <name>` line, and the summary (`N pass`, `N fail`, `Ran N tests`); `(pass)` lines only under `--verbose`. Biome prints `<path> format ━━━`, an indented `× Formatter would have printed …`, `Found 1 error.` and a closing `check ━━━` block. tsc prints `<path>(<line>,<col>): error TS<n>: <message>` and `Found N errors`.

**Exit statuses.** `bun scripts/release.ts`: unchanged, 0 when the release went through or the step's result already existed, 1 when a step failed and the log names it; a refused or failed record never changes it. `crew release …` typed in a session: exit 1, `unknown command` and the usage on stderr. The record functions answer a typed result, not an exit status.

### 218: the ignore line

`.gitignore` gains, under a comment naming the tool, the line `.claude/settings.local.json`. Git and biome both read it. Nothing else changes: `biome.json`'s `files.includes` stays, and the release's clean-tree precondition (`git status --porcelain`) already ignored the file through the global ignore on this Mac.

### 219: the release recorded by the engine

This is D-1's option A, the user's answer, with D-2's answer that the steps run in the session's checkout.

#### The marker

The script records a release by writing a marker of the same shape as the run permit's (the command, the pid, `ps`'s start time of it, the session, when it was written) with two more fields, the version and the commit HEAD was at, under `.crew/local/running/<pid>.json`, a folder the PreToolUse guard already denies a session's direct writes to. The pid is the script's own process, since the script calls the engine's record functions in-process. One reader serves the two folders, the item's `running/` of the run permit and `.crew/local/running/` of the release, in this order: it removes a marker that is malformed (a field missing or of the wrong type, a release marker without its version or head, a time that does not parse), or misnamed (a file whose name is not its pid), or past its maximum age (whatever its session), or whose process has exited; it leaves in place and ignores another session's marker, one whose process start time differs (a reused pid), and one in the session's spent list (the run permit's one turn per run; the release reader passes an empty list); it returns the first marker of the session that holds. A release marker holds for at most 45 minutes from its writing; the run permit's markers have no age. The session's state and the markers are machine-local files under `.crew/local`, written under the state's file lock and not in the engine's integrity record (as the run permit's markers are not), so a write from the script's process is never read as tampering.

#### The start record

`recordReleaseStart` in `packages/engine/src/release-record.ts` answers a typed result, `recorded` true only when the marker was written, with a text. Its checks, in this order, each failed one a named answer with nothing written: a session (none, or an empty id, records nothing); no active item, read as the Stop hook reads it (a record that cannot be read is a refusal naming the tamper; an abandoned or absent one is no item); the tree is one the Stop rule would let end with no item, decided by the one function the Stop hook itself calls for that case, moved out of the hook (the baseline comparison when the baseline exists and the fingerprint reads, else no change; or the last learned item's proven fingerprint is the current one, `learnedHolds`), where a tree the rule lets end whatever its content (no baseline, or an unreadable fingerprint) answers that there is nothing to record, since the turns end as they are and a marker would only turn the rule on mid-session; and the process's pid is above 1 with a readable start time. On success the marker is written and the text says the turn may end while the release runs.

#### The Stop hook

With no item, the hook reads the marker right after the run permit's read (which needs an item) and before the waits and the three-block cap: a release marker of this session that holds lets the turn end with the notice of journey 3 and resets the block count, a count of 3 carried in included; the permit is not spent, since every turn of a background release must end and the end record ends it. The reader's removals happen on that read. With an item active the marker is not read. The five cases of the rule and the run permit are unchanged; the engine spec's "The Stop rule" section gains one sentence after its list naming both permits and saying only this repository's release script writes the release marker. The session's state is written through the engine's writer under the state's file lock, a read-modify-write of the fresh state inside the lock, by the end record and by the hook alike (the hook writes only the block count and the run permits onto the fresh state), so the two cannot overwrite each other's fields.

#### The end record

`recordReleaseDone`: with no session it records nothing. With one, it reads the session's marker through the same reader (so a marker past its age is removed on that read); a missing marker, or one of another version, is a refusal (unrecorded), and the baseline stays. Then the checks against git, each a named refusal that keeps the marker: no watched path differs from HEAD; HEAD has a first parent and it is the recorded head; the tag `v<version>` points at HEAD; and the current fingerprint reads. When all hold, the session's baseline becomes the current fingerprint and its block count zero, the marker is removed, and the text names the commit.

#### The script

1. `release()` takes an optional `record` pair of functions in its deps (never in its options, which the loop spreads), the start and the end record; the script's entry point wires closures that resolve, inside each call, the repository's paths as the hooks resolve them (the canonical root and the user's home), the profile, and the session from `CLAUDE_CODE_SESSION_ID`, and call the engine's function; paths that cannot be resolved answer an unrecorded result. The loop's release wrapper wires none; the tests wire fakes. Each call is wrapped: a function that throws is logged as a failed record and never fails a step or the release.
2. With the pair wired and the run neither a dry run nor a resume, the script calls the start record right after its title line and logs `  release start: <the text>`.
3. Step 1 keeps the hash of each file it writes (the version files and the two test literals, the script's `written` list) as it writes it; step 2 the bundle's as it builds it; a file absent then is recorded as absent.
4. Step 5, before `git add`, re-hashes them and checks that HEAD is still the start sha, and fails the step before any commit when a hashed file differs, an absent one appeared, or HEAD moved, naming the file or the commit. This is the one check against a change between step 1 and step 5 that would land inside the release's commit or become its parent, which the end record cannot see (`bun run plugin:check` leaves the bundle's hash and the tree unchanged, measured on 2026-11-02). Step 5's `git add` already names the written files and the bundle, never `-A`, so the commit holds those alone.
5. After the step cycle logged step 6's ok line and only when the start recorded, the cycle calls the end record and logs it the same way, so the end line follows the push's line.
6. Step 7's tarball rebuilds the bundle in place with the same source and version, which gives the committed bytes (measured on 2026-11-02: two builds, one hash), so the renewed baseline holds through it.
7. A dry run and a resume call neither record, whatever `--from-step` names (a resume starts after the push, where the earlier run recorded the end or refused, and runs step 5's guard on nothing).

#### Two engines

The script writes the marker and the baseline through the engine source the checkout holds; the hooks read them through the plugin the session loaded (the installed cache copy, live after step 10 and a restart, or `--plugin-dir`). The record works when both know the folder `.crew/local/running/`. When the installed plugin predates the reader, the start records and nothing honours the marker, so the turns are blocked as today, and the end record's renewal of the baseline is still honoured, since every Stop hook reads the session's baseline. No compatibility code: a mismatch fails safe.

#### Documents

CLAUDE.md's Releasing section names the output files and the two records in prose, with no new backticked `.json` or `version.ts` path, because the script's `releaseFiles()` reads every such path of that section as a version file (two tests pin the list it reads: `loop-docs.test.ts` and `version.test.ts`); its convention line, under Conventions, gains the exception (the engine's files are written by the `crew` command, and by the release script through the engine's own module: the release marker and the session's baseline); the engine spec's "The Stop rule" gains its sentence; ADR 0015 takes a note of this item; findings 217 to 219 close with what was kept.

### Alternatives

D-1, how the engine learns of a release, was the user's: option A, the design above, answered on 2026-11-01. Its costs: the two-engine reach, a trust boundary the engine cannot enforce against a session's own script, and the shared tree while the release runs. D-2, where the steps run, was the user's too: in the session's checkout, answered on 2026-11-02. Its costs: the marker and its permit, the notice (no edit, no commit, no item), the age bound, step 5's guard (the hashes and the start sha), an untracked file surviving the rollback, a change counted only after the process exits. The others:

- **D-1, option B: the Stop hook reads git alone.** With no item, a clean tree whose HEAD is reachable from the session's starting commit through commits each tagged `v<the version in package.json at that commit>` counts as proven. Mechanism: no record, nothing in the script; the hook runs `git tag --points-at` on each commit since the baseline's head. It works in every runtime and for a release made by hand. Rejected: it needs nothing from the script, so a tag typed in the session cannot be told from one the script made, and any tagged commit ends the turn; A needs the script's two records under the engine's checks and the script's own guard on what it commits.
- **D-1, option C: the release as a work item.** The release is a chore item on the fast route with one observed criterion, as 0.13.0 and 0.14.0 were (the decision register, `2026-10-24-010`); with an active item the Stop rule counts the item's own change since its base (finding 198), and the release's commit is proven by the item's gate run after it. Mechanism: nothing new in the engine, none of A's costs. Rejected: a second full check (about nine minutes) and the fast route's two judgement gates on a mechanical bump at every release, and the 0.18.0 release, tried on the standard route, was left unproven (its two judgement gates never ran, `2026-11-01-001`).
- **D-2, A-worktree: steps 1 to 6 in a git worktree of HEAD**, the main checkout fast-forwarded to the pushed commit, then the end record's checks renew the baseline; no marker, permit, notice, age bound or step-5 guard, since the session's tree never changes while the release runs. Mechanism: the engine already manages worktrees (`packages/engine/src/worktree.ts`) and the loop releases from its own clone. Costs: the worktree's `node_modules` and Playwright cache (a link to the main checkout's), the build and `claude plugin test` inside the worktree, the fast-forward of the main checkout, the release tests' fixture. Rejected by the user's D-2 answer: the steps run in the session's checkout.
- **219: a `crew release start|done` verb** the script would spawn through the bundle, denied to a session's Bash by the PreToolUse guard. Rejected: a public verb, a help line, a guard rule and a spec row shipped to every project to serve one script, the result read from parsed stdout, the parent pid found through `process.ppid` (a runtime shim could stand between), and a bootstrap where the bundle must ship the verb before the script can use it; the scripts already import the engine's source (`build.ts`, `improve-loop.ts`), so the in-process call needs none of it.
- **219: a field of the session's state instead of a marker.** Rejected: the Stop hook's own save writes only the block count and the run permits, so a dead record would need a second write, and the shape check, the liveness check and the age bound would be written twice, once for the run marker and once for the record.
- **217: the engine's streaming runner (`runCommand`) for the long steps.** Rejected: it takes a shell line and answers no stdout value, it would be a second injected runner with an async step cycle, and the stream to the console, the per-step timeout and the `detached` option it brings are asked for by no goal; one synchronous runner with the 64 MiB capture serves every step, and the file is written when the message is built.
- **217: print the whole output on failure.** Rejected: a failed suite prints hundreds of lines in the conversation and the loop's log; the whole output is kept in the file instead.
- **217: the last N lines alone.** Rejected as the only output: bun test prints each failure where it happens and no recap of the failed names at the end, so the last lines of a long suite name the counts and not the tests; the tail is kept after the named lines instead.
- **218: `files.includes` with `!.claude/**` in `biome.json`.** Rejected: biome's include list would then carry a tool's path git already knows how to ignore, and git would still track the file on a machine without the global ignore.

## Acceptance criteria

The numbering has gaps: the superseded criteria are listed, each with its successor, by `crew status` and the item's report.

217:

- AC-40: When a release step's command fails, the log's first line and the output file follow Design 217's rules 3, 4 and 7: the step, the status line (exit; signal and spawn error when they apply), the file `dist/release-<version>-step-<n>.log` with the rollback sentence on the first line before the push; after the push, the `resume with:` line as its own line after the body; the file is written only for a failed step, holds the status line and the whole output, and survives the rollback; the notification carries the logged first line, with the resume suffix after the push as today; a step that succeeds prints one line.
- AC-37: The body of a failed step's message follows Design 217's rules 5 and 6: the lines that name a failure (`(fail)` and biome header lines first, then the `error`, `×`, `✗`, `error TS` and `Found N error` lines, every line trimmed, each kept once across the groups, no `(pass)` or `(skip)` line), the first 20 with `… and N more`, then bun test's `N fail` summary whatever the cap, then `last lines:` and the output's last 10 non-blank lines, which may repeat a line.
- AC-41: Every step's command runs through the script's one synchronous runner as Design 217's rule 1 says: 64 MiB per stream, the status unchanged for every reader, the exit (null for a signal or an overrun), the signal and the spawn error added; the marketplace read of step 9's run goes through the step helper with its own label.

218:

## Risks and rollback

- **The trust boundary.** The record trusts the release script by convention, as the run permit trusts the engine's own runs. What the engine checks: the marker is written by the engine's function on a tree the engine already lets end by its content, with no item open; the permit holds for the release's length, at most 45 minutes; the end record renews the baseline only on the recorded head's first child, clean and tagged; and step 5's commit is taken on the script's word, with the script's own check that it commits only what it wrote on the commit it started from. What the engine cannot see: a script of the session's own making that imports the same functions, commits and tags an unproven change, and records the end. That is the same class as a script that writes an engine file under `.crew`, which the engine's spec calls evident, not impossible (section 12, "Tamper evidence").
- **The window while a release runs.** The permit holds for every turn end while the marker holds, with no item open, so the notice tells the agent to change no file, commit nothing and start no item until the release ends. What the session does meanwhile: a change to a tracked file before the push is wiped by a rollback, or makes step 5's guard fail when it touches a written file, or makes the end record refuse (a watched change from HEAD); a commit before the push makes step 5's guard fail (HEAD moved) and the rollback resets to the start sha, leaving that commit in the reflog alone; an untracked file survives the rollback and is counted by the Stop hook; and in every case the marker keeps letting the turns end until the process exits, so a change is counted at the first turn end after it. Spending the permit once per turn, as the run permit does, is rejected: a background release spans several turns (finding 219's case) and the three-block cap would return.
- **Limits that fail safe.** An item started while the marker holds: the marker is not read, and the release's commit counts as the item's own change (finding 198), which its gate run proves. A second session in the same checkout: its Stop hook ignores the marker (another session's) and the end record renews the releasing session's baseline alone, so the neighbour meets the rule as today. A refusal of the end record after the push: the baseline stays and the rule meets the three-block cap as today. A release longer than 45 minutes: its marker is removed as aged at the end record, which refuses. A release killed mid-step: the version files stay written with no rollback, as today. While step 7 rewrites the bundle, a Stop hook that reads git's status mid-write may count the file as changed and block that one turn; the next read sees the committed bytes.
- **Two engines**: Design, 219, Two engines. The release that ships the reader is blocked while it runs and free after its push.
- **A marker that outlives its release.** A reused pid gives no permit (the start time differs, the marker is left); an exited process gives none and its marker is removed by the next reader that meets it; a zombie counts as alive until reaped, as for the run permit.
- **The output file in the loop's clone**: Non-Functional Requirements.
- **The failure-line patterns** may miss a runner whose failure lines carry none of them; the tail follows the named lines whenever there is output, and the file holds everything with the status line.
- **Rollback**: revert the commit. A marker left under `.crew/local/running/` is removed by the next reader or ignored by an engine without the reader. Nothing on a remote changes shape.

## Non-Functional Requirements

## Not taken

- A list of the release's files handed to the end record (the security lead's hardening of round 1, the design critic's of round 2): the engine does not know a project's release files, and a list passed by the caller is the caller's word, which the end record already trusts for the commit; step 5's own guard (the hashes and the start sha) covers the cases, and the trust boundary is stated in the spec's Risks.
- A refusal of the start record while another release of the session is alive (round 1): the script's preconditions make two releases at once unreachable, and a second start writes its own pid's marker.
- A `crew release` verb and its PreToolUse denial (rounds 1 to 3): replaced by the in-process call (the spec's Alternatives).
- A refusal in `crew start` while a release marker holds, and a check across sessions (round 3): both fail safe and are named as limits in the spec's Risks.
- Widening the loop's `TickDeps` to a null status (round 3): the runner's `status` stays a number and the new `exit` field carries the cause (round 4).
- The engine's streaming runner for the long steps, with its `detached` option, the console tee and the 30-minute timeout (rounds 3 and 4): one synchronous runner with the 64 MiB capture serves every step (round 5).
- Moving the `io` copies of `cli.test.ts` and `tasks.test.ts` to `helpers.ts`: outside the item's scope; `running.test.ts`'s moves because the new test file shares it.
