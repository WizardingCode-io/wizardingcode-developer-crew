# The commit command of refreshed adapters reaches the person until they commit

Item `2026-11-09-001`. Predecessor: `analysis.md` (an issue has no concept brief).

Terms.

- A *runtime adapter* is what `crew runtime install <name>` writes into a project so that a runtime other than Claude Code runs the crew: a hook configuration, a copy of the skill, and agents.
- An *engine root* is the folder an engine runs from: Claude Code's plugin cache folder for the plugin, `~/.local/share/wizardingcode-developer-crew` for the tarball install. An adapter's configuration names one root; the adapter is *own-root* for the engine running from that root and *foreign* for every other.
- The *refresh* is `refreshAdapters` (`packages/engine/src/adapters.ts`): it installs stale own-root adapters again. SessionStart runs it, and so does `crew projects update` (the *fleet*), which the release runs as its step 12. The refresh *holds back* an adapter when a rule forbids writing now: the adapter stays `stale`, with the reason.
- The *register* is `.crew/decisions.json`, the project's record of decisions and engine events. The refresh appends an `adapters` entry to it.
- A session's *baseline* is the fingerprint of the watched files taken when it starts; the Stop rule compares the tree with it.
- The *judgement* of an item is the review of its diff by reviewers and a judge once the gates pass. An *advisory* is a finding the judge upheld that does not make the item unproven.
- The *loop* is the harness-improvement loop (`scripts/improve-loop.ts`): it releases with nobody present and resumes a release that failed after its push.
- The *bound* of step 12 is 300 s; past it the release ends the fleet's process with a signal.

## Problem

A person working in a project whose adapters a release refreshed is never told to commit the files. The commit command is printed once, by the run that wrote them, and for a release that run is step 12, whose output is the release's log. The next session start on the adapters' root prints nothing, because the version is recorded. A Claude Code session prints nothing, because the adapters name another root. `crew status` shows what was updated and no command. The project is then held back at every later release as `stale (uncommitted changes in …)`, again with no command.

On 2026-11-09 the release of 0.22.0 updated `cf-ecommerce-v3` and `rockport-new`, 47 paths each. The files were committed only because the session that ran the release read its log.

The judgement of the item that built the refresh (`2026-11-08-002`) left eleven advisories that a change can settle. They share this item because they sit in the files `analysis.md` names under Cause.

A second defect surfaced while this spec was drafted. The commit command of 0.22.0 names the register whenever the refresh appended an entry to it. In a project that ignores `.crew/`, `git add -A -- … '.crew/decisions.json'` exits 1 (`The following paths are ignored by one of your .gitignore files`, git 2.54.0, probed in a scratch repository on 2026-11-09), so the `&& git commit` never runs.

Decisions this spec rests on. Of this item: D-1, answered A by the user on 2026-11-09. Of `2026-11-04-001`: D-2 (a checkout records which engine version last brought a root's adapters up to date). Of `2026-11-08-002`: D-1 (a refresh leaves its files uncommitted for the project's own session to commit), D-3 (step 12 is soft), D-4 (an engine writes only the adapters that name its own root), D-6 (the fleet never writes the user scope), D-8 (a release with nobody present runs step 12 as a person's does), D-9 (any uncommitted change in the adapters' files holds a refresh back). A criterion of `2026-11-08-002` is written `its AC-n`; this item's own are `AC-n`.

## Goals

1. Every session start of an engine that knows the mark (this release or later), in a checkout whose refresh ended `updated` and whose refreshed adapter files are uncommitted, says so and gives the commit command, on any engine root, until those files are committed or restored. Two limits follow from the wording and are in Risks: an older engine never reads the mark, and a run killed inside an install leaves none.
2. `crew status` says the same.
3. The fleet prints the commit command for a project it holds back because those files are uncommitted, so each release's log carries it again.
4. The commit command runs as printed: it names only paths git lists as changed and that no later commit touched.
5. The eleven advisories are settled:
   - the refresh's lock-and-append block exists once;
   - its AC-5 has a row that compares a start whose adapter step throws with the same start with no throw;
   - its AC-11 has rows through SessionStart for an active item, a task worktree and a folder that is no repository;
   - its AC-13 has a row for an entry that resolves outside the project, and the install's refusal has a row per link case;
   - its AC-16 has a fleet row for a failed project's register entry;
   - a killed step 12 has a row whose output holds the user scope line;
   - the killed step's text names the last project line it printed;
   - the killed step's text does not say the rest was not updated when it cannot know;
   - `crew runtime check` prints the root and the configuration's path through `quotedText`;
   - the loop resumes a pending release by the step's name;
   - the local install's step keeps the install it replaced.

## Non-goals

- Committing for the person. D-1 of `2026-11-08-002` left the commit to the project's own session.
- Changing when the version is recorded. D-1 of this item keeps the record's meaning; its AC-17 stands.
- A reminder for an adapter a person installed by hand with `crew runtime install`. That run is watched by the person who typed it, and the next refresh already says `stale (not committed: …); commit them to adopt the adapter, or run crew runtime install <name> again`.
- Asking again after a restore. A person who restores the files instead of committing them has refused that version's refresh; the next version's refresh updates them again.
- The advisories the user's earlier decisions accept: step 12 soft (D-3), the user scope never written (D-6), a release with nobody present as a person's (D-8), the raw paths in `crew runtime install --json` (the earlier item's recorded choice, data for programs).
- A dry run before a release's first real fleet write. The advisory is closed by the fact: on 2026-11-09 the real run updated the two projects the dry run from the tree had named, and the tarball's dry run afterwards read `0 would update, 2 up to date`.

## Open questions

None. D-1 is answered.

## Critical user journeys

1. **The project's Claude Code session.** Given a release that updated the Copilot adapter of a project and left 47 paths uncommitted, when the person opens a Claude Code session there, then the session's context holds `adapters: copilot updated by crew 0.23.0 and not committed. Commit: git add -A -- … && git commit -m 'adapters refreshed by crew 0.23.0'.` The agent proposes the commit; the person says yes; the next session start has no `adapters:` line.
2. **A session on the adapters' own root.** Given the same project, when a Copilot session starts at the recorded version, then it reads no adapter configuration and prints the same line.
3. **Nobody commits.** Given the same project at the next release, when step 12 runs, then the fleet prints `<name> <root>: copilot stale (uncommitted changes in …)` and, after the count line, `commit in <name>: <command>`. Sessions in the project keep printing the reminder.
4. **`crew status`.** Given the same project, when anyone runs `crew status`, then its output ends with `adapters not committed: copilot updated by crew 0.23.0 and not committed. Commit: <command>`.
5. **A killed step 12.** Given a fleet run killed at the bound after three project lines, when the release notifies, then the notification names the last project line and says where the project that may be written in part is listed. The projects updated before the kill remind their own sessions.
6. **A pending release after the steps moved.** Given a release the loop left pending at `the notification` when that step was number 12, when the loop resumes it with a script where `the notification` is number 13, then it resumes at step 13.
7. **The person's own edit, later.** Given a project whose refreshed adapters the person committed from a terminal, when they then edit `.codex/hooks.json` for a hook of their own and open a session, then no reminder is printed: a commit made after the refresh touched that path, so its change is theirs.

## Design

### The mark

A refresh that updates an adapter writes a *not-committed mark*: what it updated and where the checkout stood, kept beside the adapters lock.

- File: `.crew/local/adapters/uncommitted.json`. The folder `.crew/local/adapters` exists already: it is the folder `withLock` creates for the adapters lock. Everything under `.crew/local/` is engine-owned (`paths.ts:167`), ignored by git, and denied to any writer but the engine by the PreToolUse guard.
- Shape: a JSON object, canonical engine root → entry.

```json
{
  "/Users/x/.local/share/wizardingcode-developer-crew": {
    "version": "0.23.0",
    "at": "2026-11-10T09:00:00.000Z",
    "head": "905ae5a0c1d2e3f4a5b6c7d8e9f0a1b2c3d4e5f6",
    "runtimes": [{ "name": "copilot", "config": false }],
    "register": true
  }
}
```

- `version`: the engine version that updated. `at`: when. `head`: the commit the checkout's `HEAD` named when the refresh began to install. `runtimes`: each adapter that ended `updated`, with `config` true when the install wrote the configuration file (`configWritten`). `register`: true when the refresh appended an `adapters` entry to the register.
- The mark holds no path and no command. Every path comes from the reading engine's own runtime table (`RUNTIMES`). No text of the file reaches a line or a command except a runtime's name, checked against the table, and a version, checked against `^\d+\.\d+\.\d+$`. `head` is checked against 40 or 64 hexadecimal characters and reaches git as one argument, never a shell.

Why a file of its own. `loadState` rebuilds the state from the fields it knows (`state.ts:198-207`), so an engine that does not know a field drops it at its next write of `state.json`. Two engine versions read one checkout between a release and the restart of Claude Code. A file an older engine never opens survives it.

### The mark's paths

For an entry, the *adapter pathspecs* are, in this order, relative to the project root:

1. for each runtime with `config` true, `RUNTIMES[name].config.project`;
2. for each runtime, `<RUNTIMES[name].skillsDir.project>/crew-method`;
3. for each runtime with an agents folder, `<RUNTIMES[name].agentsDir.project>/crew-*`.

The *register pathspec* is `.crew/decisions.json`, when `register` is true. Duplicates are named once. A changed path *belongs* to a pathspec when it equals it (1 and the register), starts with it followed by `/` (2), or starts with it without the `*` (3).

One function gives a runtime's adapter pathspecs. The mark's reader uses it, and so does `gitHoldBack` (`adapters.ts:141-165`), which today builds the same set by hand: the paths that hold a refresh back and the paths the reminder watches are one set.

### Reading the mark: `uncommittedAdapters`

One function, in a new module `packages/engine/src/adapters-uncommitted.ts`, serves SessionStart, `crew status` and the fleet:

`uncommittedAdapters(paths, { clear, also })` → `null`, or `{ parts: string[], roots: string[], command: string | null, failed?: string }`. `roots[i]` is the engine root whose entry gave `parts[i]`. It never throws: a mark it cannot read counts as absent, a status that fails is said in `failed`, and a clear that fails removes nothing.

It runs in this order:

1. Read the mark. An absent file gives no entry. A file that is not a JSON object, or an entry that is not well shaped (a `version` that is not three numbers, a `head` that is not 40 or 64 hexadecimal characters, a `runtimes` that is not a non-empty list of `{ name, config }` with `name` in the table and not `claude`, a `register` that is not a boolean), counts as absent: no line, no throw. `also` is `{ root, entry }`, passed only when the refresh of this run failed to write its mark: the entry it holds in memory, which then stands for that root in place of whatever the file holds.
2. No entry: return `null`. No git command ran.
3. A checkout with no `.git` has nothing to commit: every entry is clean.
4. For each entry, one `git status` (`gitStatusEntries`) under its adapter pathspecs and its register pathspec. A path of kind `modified`, `renamed` or `untracked` is a change; an ignored path is never listed. A status that throws sets `failed` to the message through `quotedText`; that entry is kept, is neither clean nor uncommitted, and gives no part.
5. When the status lists a change: one `git log --ancestry-path --no-renames --format= --name-only <head>..HEAD` under the same pathspecs gives the paths a commit touched after the refresh, on top of the commit the refresh started from. A change *counts* when its path is not among them. A log that throws (the commit is not in this clone, or history was rewritten) leaves every change counting.
6. An entry is *uncommitted* when a counting change belongs to one of its adapter pathspecs. The register never makes an entry uncommitted: it changes with every item's decisions. Its part is `<names, joined by ", "> updated by crew <version> and not committed`.
7. `command`: `git add -A -- <pathspecs> && git commit -m 'adapters refreshed by crew <version>'`. The pathspecs are those of the uncommitted entries to which a counting change belongs, the register's included, in the order above, each once, single-quoted. The version is the newest among the uncommitted entries (`compareVersions`). `null` when no entry is uncommitted.
8. Every other entry whose status was read is *clean*. With `clear`, the clean entries of the file are removed under the adapters lock: one attempt at the lock, no wait; inside it the file is read again, an entry is removed only when its `at` is the one read at step 1, and the file is deleted when no key is left. A busy lock, or any other failure of the clear, removes nothing; the next reader does. Without `clear` nothing is written.
9. Return `null` when no entry is uncommitted and no status failed; otherwise the result.

So an entry leaves the mark when its adapter paths are clean in git, or when every change left in them is one a later commit already touched: the person's own.

### Writing the mark: the refresh's install step

The refresh numbers its steps in the comments of `refreshAdapters`; step 8 is the one that takes the adapters lock, checks again, installs, records the version and appends the register entry (`adapters.ts:410-481`). Inside that hold the order becomes:

1. Before the first install: `head`, the commit `HEAD` names (`baseCommitOf`). A refresh reaches this point only in a repository whose adapter files are clean in git, so a commit exists; with none, no mark is written.
2. Each install, as today. Right after an adapter's check says it is `updated`, the mark is written for it: the entry `{ version, at, head, runtimes: [that adapter], register: false }` merged into the file for the running root.
3. `recordAdapterVersion` when every adapter is `up to date` or `updated`, as today.
4. `writeEntry()`, as today.
5. When the entry was appended and an adapter was updated: the mark is written once more with `register: true`.

Merging: runtimes united by name with `config` true when either holds it, `register` true when either holds it, `version`, `at` and `head` the new ones. The whole entry of the run is also returned as `Refresh.entry`, with `Refresh.root` (the running root).

The mark comes before the record and before the register entry so that a throw of either, or a kill after an install, leaves the reminder. A refresh in which one adapter ended `updated` and another `refused` or `failed` records no version, as today, and has written the mark for the updated one.

The merge and the write live in the new module, as `noteUpdated(paths, root, entry)`. It takes no lock: its one caller holds the adapters lock, which is not reentrant. `adapters.ts` imports from the module; the module imports the `Refresh` type only, so the two have no import cycle. The write is the engine's `writeJson`: a temporary file renamed over the path, so a link someone put at the path is replaced, never followed.

Both writers, `noteUpdated` and the clear, keep what they do not own. They read the file's raw object, change only the key they act on, and write every other key back as it was read, whatever its shape. An entry a newer engine wrote, with a runtime this engine does not know, is no reminder here and survives this engine's writes. A file that does not hold a JSON object is treated as empty by a writer.

A write that throws does not undo the refresh: `Refresh.markFailed` carries the first message through `quotedText`, the refresh goes on, and the caller passes `Refresh.entry` as `also`, so this run still prints the command.

A dry run, a held-back refresh, and a refresh in which nothing ended `updated` write no mark.

`commitCommand(refresh)` is deleted. The command has one builder, step 7 of "Reading the mark". Its three callers move: `adaptersLine` takes the command from the reminder; the fleet takes it from `uncommittedAdapters`; the row `2026-11-08-002 AC-22` of `adapters.test.ts` (lines 425-440) reads it from `uncommittedAdapters(paths, { clear: false })` and keeps its three assertions (the `&& git commit -m` suffix, the `'.crew/decisions.json'` pathspec, a clean tree after running it).

### The lock-and-append block

The two blocks at `adapters.ts:376-382` and `390-396` become one local function, `entryUnderLock()`, called at both places. On a real run it calls `writeEntry` under the adapters lock. When another process holds the lock, this run does not write the entry and the next refresh writes it, as today.

### SessionStart

The adapter step of `onSessionStart` (`session-start.ts:87-123`), in order:

1. the refresh, skipped at the recorded version, as today;
2. the wait for the adapters lock, as today;
3. `uncommittedAdapters(paths, { clear: true, also })`.

`adaptersLine(refresh, extra, reminder)` builds the line. `refresh` may be `null`. `extra` and `reminder` are optional (`[]` and `null`), so the existing calls `adaptersLine(refresh)` stay valid: they give the parts and no `Commit:`.

- Parts, in order: the refresh's results and foreign adapters as today; each part of the reminder, except the part of the entry for `refresh.root` when this refresh updated an adapter (its `updated (<n> differed, <n> removed)` part already says it); `the not-committed mark was not written (<why>)` when `refresh.markFailed` is set; `not-committed check failed (<why>)` when the reminder's `failed` is set; then `extra`.
- No part: `null`, no line.
- `; applies from each updated runtime's next session` as today.
- `. Commit: <command>` once, from the reminder's `command`, when it is not `null`.
- The hold-back suffixes as today (`; it is updated at a session start with no active item, or by crew projects update`, `; commit or restore them first`, `; commit them to adopt the adapter, or run crew runtime install <name> again`).

The whole step stays inside its `try`: a throw gives `adapters: not checked (<message>).`, as its AC-5 says.

The step writes only the mark file, which no watch list covers, so the session's baseline, taken after the step, is not affected (its AC-27). Its cost is in Non-functional requirements.

### `crew status`

After the item's view and the `adapters: <last entry>` line (its AC-25), when `uncommittedAdapters(paths, { clear: false })` is not `null`: one more line, `adapters not committed: <parts joined by "; ">. Commit: <command>`; `adapters not committed: check failed (<why>)` when only `failed` is set; both joined by `; ` before `. Commit:` when both are. The line does not depend on the register holding an `adapters` entry. `data.adaptersUncommitted` is `{ parts, command }`. `crew status` never writes the mark.

### `crew projects update`

For each project the fleet refreshes (not for one it leaves out or finds gone), after `refreshAdapters` returns and before the project's line is printed: `uncommittedAdapters(paths, { clear: !dryRun, also })`, `also` as at SessionStart. When its `command` is not `null`, the run prints `commit in <name>: <command>` after the count line, as it does today for an updated project. So the line is printed for a project updated in this run, for a project held back whose mark is uncommitted, and for a project whose adapters are foreign to the running root. A project whose mark could not be written has the unit `the not-committed mark was not written (<why>)` in its line.

The fleet prints the `user scope: …` line as soon as the last project is done and the user scope is read, where today it keeps it for one write with the count line at the end. The bytes of the whole output and their order are the same. The earlier write tells a run killed after every project from a run killed between two projects: the first has the user scope line.

The project lines' format, the count line, the buckets, the exit status and the `--json` envelope (`{ ok, message, projects, user, counts }`) do not change. Exit 0: no project ended refused or failed. Exit 1: one did. The release reads the count line by its leading `<n> updated, ` and treats any exit as soft (D-3).

### The release's step 11

Step 11 swaps the local install: it renames the install to `<install>.previous`, renames the extracted release into its place, and today deletes `<install>.previous` (`release.ts:668-691`). Three changes:

- The last `rmSync(previous, …)` (`release.ts:686`), the one after a successful swap, is removed. `<install>.previous` then holds the install the release replaced, until the next release's step 11 removes it before its own rename (`release.ts:679`). A rollback of the local install is `mv <install> <install>.bad && mv <install>.previous <install>`. No adapter configuration names `<install>.previous`, so no refresh reads it.
- A step 11 that runs again for the release already installed (a resume) must not replace the rollback target with the install it just made. After the extraction, when `<staging>/<name>/dist/crew.mjs` and `<install>/dist/crew.mjs` both exist and have the same sha256, the install already is this release: the step removes the staging folder and changes neither the install nor `<install>.previous`. Two releases never share a bundle, since the bundle carries its version.
- A swap cut between its two renames leaves `<install>.previous` and no install, and today the step answers ok to that (`release.ts:667`). A step 11 that finds no install and a `<install>.previous` renames the previous one back, logs `the local install was missing and its previous one was put back (a swap cut short)`, and goes on with the swap. A person who removes the local install removes `<install>.previous` with it; a release that finds the previous one alone puts it back.

### The release's step 12, killed

When the fleet's process was ended by a signal, the notification's text for the projects depends on what the run had printed. Let *lines* be the non-empty lines before `user scope: ` (the whole output when that line is absent), *n* their number, *last* the last of them cut to 160 characters, and *count* the line matching `^\d+ updated, `.

| Output of the killed run | Text |
| :- | :- |
| no `user scope: ` line, n ≥ 1 | `cut at the bound (killed by <signal> after <n> project lines, the last one "<last>"; any project listed after it by crew projects update --dry-run may be written in part or not updated; each updated project's sessions print its commit command)` |
| no `user scope: ` line, n = 0 | `cut at the bound (killed by <signal> before any project line; the first project listed by crew projects update --dry-run may be written in part and no other is updated)` |
| a `user scope: ` line, no count line | `cut at the bound (killed by <signal> after every project's line, <n> of them; the count line was not printed; each updated project's sessions print its commit command)` |
| a count line | `<count> (killed by <signal> after the count line)` |

The first row does not say the rest was not updated: a kill between the last project and the user scope line leaves the same output as a kill between two projects. The fleet's lines are already through `quotedText`; the release reads them as printed.

### `crew runtime check`

`checkRuntime` passes through `quotedText(…, 200)` the root and every configuration path it prints: the lines `missing: <paths>`, `config: <path>`, `config: <path> holds no crew hook`, `root: <root> missing dist/crew.mjs` and `root: <root> ok`. The root is read from a file the repository holds.

### `adapterLinkProblem`

The function gains a fourth parameter, a resolver of real paths, `realpathSync` by default. It replaces both calls the function makes: the project's own real path and each entry's. It is the seam that lets a row reach `<rel> leaves the project`: with no link among a path's parents, which the walk refuses first, the real path of an entry leaves the project only through a mount, which a test cannot make.

### The loop's pending release

`state.pendingRelease` (the type `PendingRelease`, `scripts/improve-home.ts:11-14`) becomes `{ version, failedStep, failedName? }`, `failedName` the entry of `RELEASE_STEP_NAMES` for the failed step, written at both places the loop sets it (`improve-loop.ts:1419`, `1572`). At the resume (`improve-loop.ts:1405`):

- no `failedName` (a state an older loop wrote): `fromStep` is `failedStep`, as today;
- `RELEASE_STEP_NAMES[failedStep - 1]` equals `failedName`: the same;
- the name stands at another index: `fromStep` is that index plus one, and the log says `step "<name>" is now step <n>`;
- the name is not in the list: `fromStep` is not passed, so the release resumes at the first step after the push (`release.ts:750`); the log says `step "<name>" is gone from the release; resumed from the first step after the push`. Steps 7, 8 and 9 skip themselves when their result exists (their `done`, `release.ts:563`, `570`, `607`). Steps 10 to 13 run again, which is safe: the plugin update and the notification repeat, step 11 leaves an install that already is this release, and step 12 holds back what is uncommitted.

`improve-loop.ts status` prints the stored name: `pending release: <version> at step <n> (<failedName>)`.

## Alternatives considered

- **Record the version only once the adapters are committed** (D-10 as first proposed; option B of D-1). A session on another root stays silent, and those are the user's own sessions in the two projects; its AC-17 and D-2's record change meaning; every own-root start checks the adapters until the commit. Rejected by the user's D-1.
- **The mark as a field of `state.json`.** An engine that does not know the field drops it at its next state write. Rejected: it is lost exactly when two versions share a checkout.
- **The command's text stored in the mark.** A file's text would reach the agent as a command to run. Rejected by the rule of its AC-24.
- **No mark: `git status` over the adapters' paths at every start of a checkout that holds an adapter configuration.** A start would read adapter configurations and call git at the recorded version, for ever. Rejected: it breaks its AC-17.
- **Derive the reminder from the register's last `adapters` entry.** The entry is prose, does not say whether the configuration was written, and is committed with the files. Rejected: parsing prose, and no way to tell a committed entry from a pending one without the same `git status`.
- **Any change under the mark's paths counts, whoever made it.** The register changes with every item, and three configurations are files the person also edits (`.codex/hooks.json`, `.cursor/hooks.json`, `.gemini/settings.json`). The reminder would come back after the adapters were committed, and its command would commit the person's work as an adapter refresh. Rejected for the commit recorded in the mark.
- **A hash of each written file in the mark, compared with `HEAD`.** It ties a change to the refresh as exactly, and puts a list of paths into a file the engine reads back. Rejected: the mark holds no path.
- **Name the projects to commit in the release's notification.** It reaches the person once, outside the project. Rejected: D-1 of `2026-11-08-002` gave the commit to the project's own session.
- **The fleet commits.** A process with nobody present would write history in client repositories. Rejected by the same D-1.
- **Remove the `leaves the project` branch as unreachable.** It is the security lead's defence against a mount. Kept, with a seam to test it.

## Acceptance criteria

- AC-1: a refresh in which an adapter ends `updated` writes `.crew/local/adapters/uncommitted.json` with the running root's entry (`version`, `at`, `head`, each updated runtime with `config`, `register`), and `state.json` gains no key; a dry run, a held-back refresh and a refresh with nothing updated write no mark.

## Risks and rollback

| Risk | What happens | What answers it |
| :- | :- | :- |
| The mark is written and the person commits by another command | The paths are clean at the next read, or a later commit touched them | The entry is removed (AC-5, AC-27) |
| The person edits a file under the mark's paths after committing the adapters | The path is dirty again | A commit after the refresh touched it, so the change does not count (AC-27) |
| History is rewritten or the clone lacks the mark's commit | `git log` cannot tell what was committed since | Every change counts: the reminder errs towards saying it; it stops when the paths are clean |
| The mark file is edited or planted | A reminder for runtimes of the table, with a command built from the table | No text of the file reaches a line or the command (AC-9); a planted mark fires only when the adapters' paths are dirty in that checkout |
| The mark's write fails | Later sessions get no reminder | This run prints the command and says the mark was not written (AC-10) |
| A run is killed during an install | Files written in part, no mark for that adapter, no version recorded | An own-root start says `stale (uncommitted changes in …)`; every later fleet run says the same and counts the project as stale; the kill text says where the project is listed (AC-17). A session on another root is silent for that project: the residual, bounded to a kill inside an install. An install of five runtimes took 235 ms in the earlier item's timing row; the step's bound is 300 s |
| A run is killed after an install | The files are written, the version perhaps not recorded | The mark was written right after the install (AC-28), so every session reminds |
| An older engine shares the checkout | It never opens the mark file | Its own behaviour is 0.22.0's; the reminder comes from the engines that know the mark |
| The register holds other entries when the command names it | They are committed with the adapters' entry, under the adapters' message | The register is one file and its entries are the engine's records of this project; it is named only beside an uncommitted adapter path, when the refresh appended to it and no later commit touched it |
| `git status` is slow in a large tree | The adapter step takes longer | The status runs under the mark's pathspecs only, and only while a mark exists; the timing row measures it (Non-functional requirements) |
| The kept `<install>.previous` | One more copy of the install on disk | Replaced at each release; nothing names it |
| A swap cut between its two renames | No install, the previous one beside it | The next step 11 puts the previous one back and says so (AC-30) |

Rollback. The release is undone by installing 0.22.0 again (the plugin from the marketplace's earlier ref, the tarball from `<install>.previous` or the 0.22.0 asset). An engine of 0.22.0 ignores `.crew/local/adapters/uncommitted.json`; the file stays, ignored by git, and is read again by a later engine. An entry it left keeps naming its version until its paths are clean or committed, which is harmless and may read oddly after a rollback. ## Non-functional requirements

- Performance: a session start with no mark adds one read of a file that does not exist. With a mark it adds, per entry, one `git status` under the entry's pathspecs (up to three per runtime of the entry, and the register) and, when that status lists a change, one `git log` under the same pathspecs. A mark holds one entry per engine root that updated, so one or two. The plan's timing row logs three figures with `CREW_TIMING=1`, beside the earlier item's 235 ms: no mark, one entry with one runtime, one entry with the five runtimes. They are logged, not asserted: no threshold is set.
- Security: no text of the mark reaches a line or a command except a table runtime's name and a three-number version; the command's paths come from the table; the commit hash is checked and passed to git as an argument; every message of git passes `quotedText`.
- Compatibility: engines of other versions read the same checkout. The mark is a file they do not open; the pending release's new field is one they do not read.

An entry is recognised when its key is a non-empty string, `version` matches `/^\d+\.\d+\.\d+$/`, `at` is a string, `head` matches `/^[0-9a-f]{40}([0-9a-f]{24})?$/`, `register` is a boolean, and `runtimes` is a non-empty array whose every item has a `name` that is in `RUNTIME_NAMES` and is not `claude` and a boolean `config`.

Not exported: `readRaw(paths): Record<string, unknown>`. It reads `markPath` with `readText` and parses it inside one `try`; a throw (the path is a folder, `adapters` is a file, the text is not JSON), `null`, or a value that is not a plain object gives `{}`. `readMarks` filters its result.

`uncommittedAdapters`, in order. Nothing in it throws: every git call and the clear sit in a `try`.

1. `marks = readMarks(paths)`; with `also`, `marks[also.root] = also.entry`. No key: return `null`.
2. `repo = existsSync(join(paths.root, ".git"))`.
3. For each root in sorted order:
   - `adapterSpecs`: the runtimes' `runtimePathspecs(name, config)`, in runtime order, each once. `specs`: `adapterSpecs`, then `REGISTER` when `register`.
   - `repo` false: the entry is clean.
   - `gitStatusEntries(paths.root, { pathspec })`, the specs joined to `paths.root`. A throw sets `failed` to `quotedText(message, 200)` when it is unset; the entry is neither clean nor uncommitted; go to the next root.
   - `changes`: the paths of kind `modified`, `renamed` or `untracked`. None: the entry is clean.
   - `since`: the set of non-empty lines of `gitRun(paths.root, "log", "--ancestry-path", "--no-renames", "--format=", "--name-only", "<head>..HEAD", "--", …the same pathspecs)`. A throw gives the empty set.
   - `counting`: the changes not in `since`.
   - A path `p` belongs to a spec `s` when `p === s`, or `p` starts with `s + "/"`, or `s` ends with `crew-*` and `p` starts with `s` without the `*`.
   - The entry is uncommitted when a counting change belongs to one of `adapterSpecs`. Otherwise it is clean.
   - Uncommitted: `parts` gains `<names joined by ", "> updated by crew <version> and not committed`; `roots` gains the root; the entry's *named specs* are those of `specs` to which a counting change belongs.
4. `command`: `null` with no uncommitted entry. Otherwise the named specs of the uncommitted entries, in root order then spec order, each once, each wrapped in single quotes; then `git add -A -- <them, space-separated> && git commit -m 'adapters refreshed by crew <v>'`, `v` the newest `version` among the uncommitted entries by `compareVersions`.
5. With `opts.clear` and at least one clean root that came from the file (not from `also`): inside a `try`, `withLock(join(paths.localDir, "adapters"), fn, { what: "adapter refresh", waitMs: 0 })`, where `fn` reads the raw object and the recognised marks again, deletes each clean root whose recognised entry still has the `at` read at step 1, and then writes the raw object with `writeJson`, or removes the file with `rmSync(markPath, { force: true })` when no key is left. Any throw is swallowed: nothing is removed, and the next reader clears.
6. Return `null` when `parts` is empty and `failed` is unset; otherwise the reminder.
