# Findings 212 and 221: the release script

## Problem

Terms used below:

- **The release** is `scripts/release.ts`, the one flow that publishes a version, in thirteen steps: the version files, the build, two checks, the commit and the tag, the push, the tarball, the GitHub release, the marketplace entry, the plugin's update, the local install, the fleet's update, the notification.
- **The loop** is the improvement loop, `scripts/improve-loop.ts`, which launchd runs hourly on this machine. One run of it is a **tick**. It works in a checkout of its own, its **clone**, and calls the release when a tick adopts a change.
- **The fleet** is the set of registered projects the release updates in its twelfth step.
- **A resume** is the release run again with `--resume`, after its push, from the step that failed.
- **The bundle** is `plugins/core/dist/crew.mjs`, the build's output, committed with each release.

Two findings name five gaps in the release (`analysis.md`):

1. The named GitHub account's token is first read at step 8, after the commit and the tag are on origin.
2. The loop's probe, which says what the loop can reach, reads `gh auth status`: it says nothing of whether the release's account has a token.
3. A command that never returns holds the release, or a tick, with nothing logged: only the fleet's step has a time bound.
4. A release killed mid-step, before its push, leaves the version files written. The next release refuses the tree, and nothing puts the files back.
5. Two advisories of item `2026-11-01-003`: no row runs the script as a program, and the rollback's log never names the bundle, even when a session rebuilt it after the build step.

Who this reaches: the person who releases (a release that stops with its commit and tag out and nothing published, a tree left dirty by a kill) and the loop, which runs with nobody there (a tick held for ever by one command, a clone no later release can leave).

The user decided on 2026-11-12 that this item fixes points 3 to 5, and on 2026-11-13 two questions of design (D-1 and D-2 below).

## Goals and Non-Goals

Goals:

- A release whose account has no token stops before it writes or pushes anything, and says so.
- The loop's probe says whether the release's account had a token when the probe was written.
- No command of a release waits for ever: one that passes its bound is killed with the processes of its own group, and is a failed step, logged like any other.
- A release killed before its push is put back by the next new release: the files the release wrote, as its journal recorded them, and the bundle, the build's product.
- The two advisories are settled: the entry point has a row, and the rollback's log names a rebuilt bundle.

Non-Goals (the one list of what is left out):

- Catching signals in the release's process (declined by the user under D-1).
- A recovery by a resume, or of a release stopped after its push: that is the resume, unchanged.
- Changing what a step does, the order of the steps, or what a resume skips.
- A bound on the loop's own commands outside the probe's two `gh` calls (the clone's bootstrap, the model's runs): finding 206.
- Making the runner asynchronous, or showing a command's output as it comes.
- Removing a draft a killed `gh release create` left on GitHub.
- A tarball written beside and renamed, so that a kill from outside during step 7 leaves no part-written archive (`scripts/tarball.ts`).
- The engine's end record for a release finished by a resume (below, The engine's end record).
- The hardening the security reviewer named on item `2026-11-01-003` (one process importing both record functions), accepted by ADR 0015's note.

## Open Questions

None. D-1 and D-2 were the two questions and are answered.

## Critical User Journeys

- **A person releases while logged out of the release's account.** Given a clean tree on `main` and `gh auth token -u <account>` giving no token, when they run `bun scripts/release.ts --patch --reason "<why>"`, then the script says the account has no token and to log in to it, exits 1, and the tree, the tags and origin are as they were.
- **The loop resumes a pending release while logged out.** Given a release pending at step 9 in the loop's state and no token, when the tick resumes it, then the resume stops before any step, reports step 9 as the failed step, and the loop keeps the release pending at step 9. Given one pending at step 10, the resume runs: nothing left needs the token.
- **A check hangs.** Given a release at step 3 and `bun run check` never returning, when its bound passes, then the command and the processes of its group are killed, step 3 fails with a message that says it timed out and after how long, the tree is put back as for any failure before the push, and the log and the notification name the step.
- **The push hangs.** Given a release whose `git push` is killed at its bound, when the release asks origin for the tag, then with the tag there it goes on from step 7, with the tag absent it puts the tree back, and with origin unreachable it changes nothing, keeps the journal and says how to go on.
- **A release is killed during the checks.** Given a release killed at step 3 (the version files and the bundle written, nothing committed), when the person next runs a new release, then the script says an earlier release was killed before its push, puts back the version files and the bundle, names each, and goes on with the new release.
- **A person edited a version file after the kill.** Given the same kill and a version file changed since, when the next release runs, then that file is left as it is and named, the others are put back, and the release stops at its own precondition (the tree has uncommitted changes) naming that file.
- **A release was killed between its commit and its push.** Given a release killed after step 5, when the next new release runs on `main`, then the release's own commit is taken off `main` (kept in the reflog), its local tag is deleted, the files are put back, and the script says so.
- **A release was killed in the loop's clone.** Given a release killed in the clone at any step before the push, and the next tick's reset of the clone to `origin/main`, when the clone's next release runs, then it finds nothing of the killed release in the tree, deletes the killed release's local tag if one is left, removes the journal and goes on, with nobody there.
- **A person interrupts a release with Ctrl-C.** Given a release at step 3, when the person presses Ctrl-C, then the release's process ends and the check it was running goes on in a process group of its own. When they next run a new release, it kills that check if it still runs, then puts the tree back from the journal.
- **A person interrupts a release after its push and resumes it.** Given a release at step 12 whose fleet update still runs after a Ctrl-C, when they run the resume the log named, then the resume kills that update before its first step, and runs step 12 once.
- **A second release is started while one runs.** Given a release at step 3 in this checkout, when a second `bun scripts/release.ts` starts, then it stops saying a release is running, and the first one's check is not signalled.
- **The loop is stopped during its release.** Given a tick whose release waits on its check, when a person runs `bun scripts/improve-loop.ts stop`, then the check's group is killed, step 3 fails, the tree is put back, and the tick ends.
- **A session rebuilds the bundle during a release that then fails.** Given a release whose build step recorded the bundle's hash, and the bundle rebuilt afterwards, when a later step fails before the push, then the rollback's log names the bundle among what it discarded.

## Design

### The order of a new release's start

1. The check of its arguments, and the refusal of a release the caller holds pending (a pending release is resumed first), as today.
2. The recovery of a killed release (below). With no file of a killed release it runs no command.
3. The preconditions that read the repository, as today: the branch, the clean tree, origin reachable, the version.
4. The token's read.
5. The journal's write, the title line, the engine's start record, and step 1.

### The token before step 1

A release that still has step 8 or step 9 to run reads the account's token once and holds it in memory for them. That is every new release, and a resume from step 9 or earlier. A resume from step 10 or later reads none, as today: nothing it runs needs one. A dry run reads none: it runs the preconditions' git commands, prints the plan and writes nothing.

The read is one function of `scripts/release.ts`, `accountToken`, which runs `gh auth token -u <account>` quietly and answers the token, or none, and whether the command passed its bound. The release and the loop's probe both call it, so the rule for a token being there (the command exits 0 with a non-empty output) is written once.

With no token:

- a new release stops with `gh auth token -u <account> gave no token: nothing written, nothing pushed by this release; log in to that account with gh auth login`, exit 1, no failed step reported;
- a resume stops with `gh auth token -u <account> gave no token: nothing resumed; log in to that account with gh auth login` and reports the step it would resume from as the failed step, so the loop keeps the release pending where it was. Today a resume that fails with no failed step clears the loop's pending release;
- a read that passed its bound says `gh auth token -u <account> timed out after 120 s` in place of `gave no token`.

Each of those three lines names the account and the cause alone. The output of the token's read is never written out or shown: whether the command gives a token, gives none, fails or passes its bound, its output and its error go into no file, no log line and no notification. Neither the token's read nor the journal's write adds a line to the log of a release that goes through.

When the recovery put a killed release's files back before the token was found missing, the recovery's own lines said so before the no-token line: "by this release" is exact.

### The probe

`runProbe` (`scripts/improve-loop.ts`) gains one field, `releaseToken`: `found` or `missing`, from `accountToken` on `marketplace.account`. A command that fails, gives nothing or passes its bound reads as `missing`. The token itself is never held, written or printed: the probe file, the loop's state and the printed lines hold the word alone. `printProbe` prints `release token (<account>): found` or `missing`, and takes the account as a parameter, which the install reads from the loop's configuration. The probe's other fields stay as they are. The probe's two `gh` calls (`gh auth status` and the token's) are each given 2 minutes.

The field is a snapshot of when the probe was written, at the install or at the first tick that finds no usable probe file; it is not the token's state at a later release, which the release's own read before step 1 settles. A probe file that is absent, does not parse or has no `releaseToken` is probed again by the tick that finds it, and written. `printProbe` given a probe without the field prints `release token (<account>): not probed`.

### A bound on every command of a release

The release gives a bound to every command it runs, on the call. The runner itself has none of its own: called with no bound it waits as today, which the loop's other commands rely on. Three constants of `scripts/release.ts` hold the bounds:

| Constant | Bound | Commands | Measured here on 2026-11-13 |
| :- | :- | :- | :- |
| local | 2 minutes | a local git command, `gh auth token`, the notification, and any command with no row of its own | under 0.1 s |
| remote or build | 5 minutes | `git fetch`, `git ls-remote`, `git push`; a `gh` call to GitHub (the release with its upload, the marketplace's read and write); `bun run build`, the tarball, `bun run plugin:check`; `claude plugin marketplace update`, `claude plugin update`; the install's `tar` | fetch 2.0 s, ls-remote 1.7 s, a `gh` read 0.5 s, the build 0.03 s, the tarball 0.15 s (604 KB, which is also the upload), the plugin check 5.4 s, the two plugin updates 3.7 s and 3.3 s; a push and an upload were not measured apart |
| check | 45 minutes | `bun run check` | about 11 minutes (its test part alone 590 to 664 s in this item's sessions) |

The fleet's step keeps its own bounds, as today: its dry run 1 minute, and its dry run and its update 5 minutes together.

A command killed at its bound is a failed command whose message says so: `<what> timed out after <n> s` as the first line, then the line it has today, with the output it gave written to the step's log as for any failure (the token's read apart), and `processes that left the command's group may still be running`. The runner's result says a timeout by a field of its own, `timedOut`, optional, so the loop's and the tests' runners hold without change. A precondition's command that times out stops the release with its own line (`origin is not reachable: timed out after 300 s`).

### D-2: a bounded command runs in a process group of its own

The user decided on 2026-11-13: each bounded command runs in a process group of its own, and that group is killed whole at the bound. The option not taken is under Alternatives considered.

The runner starts a bounded command as the leader of a new process group. When the command passes its bound, the runner sends SIGKILL to that group, so the command and everything it started in that group end together. Nothing outside the command's own group is ever signalled: not the release, its ancestors (under launchd, the loop's first tick), the shell that launched it, nor any other process of the caller. This is the rule the engine's own asynchronous runner follows (`killTree` in `packages/engine/src/run.ts`: a detached group killed whole), in the form the release's synchronous runner allows; `run.ts` itself is not called, since the release's runner is synchronous and making it asynchronous is a Non-Goal.

Probed on this machine under Bun 1.4.3: a command started this way with a 1.5 s bound returned 4 ms after it, with the error code `ETIMEDOUT` and its process id, while a child of it held its output; killing the group then removed that child. If the row that proves this on the real runner is red, the item is not built further and D-2 goes back to the user.

Three things follow from a command being in a group of its own, and each has its own part below: it cannot ask the terminal for anything; a Ctrl-C no longer reaches it; and the loop's `stop`, which signals the tick's group, no longer reaches it either.

### No terminal for a bounded command

A bounded command's standard input is never the terminal's: it is the input the release gives it, or nothing. Every git command of the release carries `GIT_TERMINAL_PROMPT=0`, and `GIT_SSH_COMMAND` is set to `ssh -o BatchMode=yes` when the caller's environment sets none. So a credential that would ask (a key's passphrase, a user name) fails at once with git's or ssh's own message, as a failed step, and never waits out its bound. A release needs credentials that ask nothing: an agent, a helper, a token. The loop and a release run from a session have no terminal today. Probed on 2026-11-13 with those two settings: `git ls-remote origin HEAD` answered from this checkout (1.7 s) and from the loop's clone.

### The command a killed release left running

A release that is killed (a Ctrl-C, a kill of its process, the session's end) leaves the command it was running alive, in its own group: a check, a build, a push. The next release must not act while that command can still write.

Each bounded command is started through a small `sh` wrapper that writes four lines to `dist/release-in-progress.command`, through a file written beside it and renamed: its own process id and its start time, as the system gives it, and the process id and start time of the release that started it, which the runner hands the wrapper. It then becomes the command (`exec`), so the first id is the command's and the group's. The release removes that file when the command returns.

The file is read at the start of every new release and of every resume, before any other thing they do, whether or not a journal exists. A dry run reads it and kills nothing. The read answers one of four ways:

- **No file**: nothing to do.
- **A file off its shape** (not exactly four lines; an id that is not a decimal integer above 1; an empty start time): it is no release's. It is removed, nothing is killed, and a line says so.
- **The release that started the command is still running** (its process is alive, and its start time is the file's or cannot be read): the release stops with `a release is running (pid <n>): wait for it; if no release is running, delete dist/release-in-progress.command`. Nothing is killed and the file is kept. So a second release, or a new release beside a running resume, never kills the first one's command.
- **That release is gone, or its id is another process's now**: the command was left running. It is killed only when all three hold: its process is alive, its start time as the system gives it now is present and equal to the file's, and it leads a process group of its own. Then its group is ended (the engine's `killGroup`: asked to end, given a second, then killed), the release waits until it is gone (10 seconds at most, then it stops with a line naming the process), logs `the command a killed release left running was killed (pid <n>)`, and removes the file. When one of the three does not hold (the process is gone, the id is another process's, or it leads no group), nothing is killed and the file is removed.

The rule for the kill is stricter than the rule for the stop: a start time that cannot be read stops a release, and never kills a process. So no command of a killed release runs while the recovery asks origin or puts anything back, a push left running cannot land afterwards, and a resume never starts a step's command beside the one a killed run left (two updates of the fleet, two `gh release create`). A resume that killed a command removes its version's archive under `dist/` when one is there, so step 7 builds it again and a part-written one is never published.

**The loop's `stop`.** `bun scripts/improve-loop.ts stop` ends the running tick by a signal to the tick's group (ADR 0015's note of 2026-10-28), and until now that signal also ended the command a release of that tick was waiting on. A bounded command is no longer in that group. So `stop`, after its signal to the tick, reads the clone's command file and, when the release it names is the tick it signalled and the three conditions of the kill hold, kills that command's group. The step then fails as it does today: before the push the tree is put back, after it the release is held pending, and the tick ends at its next step.

### After a timed-out or failed step

- Steps 1 to 5: the tree is put back and the journal removed, as for any failure before the push.
- Step 6, the push, whose outcome nobody knows when it was killed or failed: the release asks origin for the tag.
  - The tag is on origin: the push went through. The step counts as done, the end record is made, once, before step 7, and the release goes on from step 7.
  - The tag is not on origin: the tree is put back as today.
  - Origin cannot be asked: nothing is reset, the journal is kept, and the release stops reporting step 7 as failed and pending, with `localUnconfirmed` set on the outcome (defined under The loop's one change). Its line:

    `the push's outcome is unknown: origin could not be asked; nothing was reset; run bun scripts/release.ts --resume v<v> when origin answers: it goes on if the tag is there; if it says there is nothing to resume, the next new release puts the tree back`
- Step 7, the tarball: the archive is removed when the step fails, so a resume builds it again and never publishes a part-written one.
- Steps 8 to 13: the resume is named, as today.

### Git's locks

A git command killed at its bound, or a release killed during a git write, can leave `.git/index.lock`, and every git write after it then fails.

- The release removes `.git/index.lock` in one case only: right after the runner said a git command that writes the index (`add`, `commit`, `reset`, `checkout`) and that the release itself started timed out, when that command's group has been killed and the lock is its leftover. Then the rollback runs. A timed-out `fetch`, `ls-remote` or `push` takes no index lock, and removes none.
- Any other git write of the rollback or of the recovery that fails stops the release with git's own first line, which names the lock, changes nothing further and keeps the journal, so the next run tries again. The line adds: `if no git command is running, remove the lock file git names and run the release again`. A rollback that could not reset does not say the tree is back.

### D-1: a release killed before its push is put back by the next new release

The user decided on 2026-11-13: a journal and the next run. The options not taken are under Alternatives considered.

**The journal** is one file, `dist/release-in-progress.journal`, under the root's `dist/`, which git ignores and the rollback leaves, read and written by the release alone. It holds: the version, the tag, the release's title, the head the release started from (`HEAD` at its start, which in the loop's clone is after the adoption's merge), the process's id and its start time as the system gives it, when it was written (an ISO 8601 UTC time), each file step 1 will write with the hash of the content it will have, and, after the build, the bundle's hash. It holds no secret.

- It is written before step 1 writes anything, with the engine's own writer (a temporary file and a rename, the folder made when missing), so a kill leaves the whole journal or none. A journal that cannot be written stops the release before step 1 with nothing written. For the hashes, the version bump is split in two: a plan (each release file and test literal with the text it will have, read from the tree and written nowhere) and the write of that plan. `bumpVersion` stays, as the plan and its write together.
- It records no commit: the release's commit is recognised by what the journal held before it existed (rule 4a below), so no kill falls between a write and its record.
- It is removed when the push went through and by the rollback of a step that failed before the push. A resume removes a journal of its own version only once origin has shown it the tag; a resume that finds the tag absent answers that there is nothing to resume and leaves the journal, so the next new release's recovery takes the release's commit and tag off. A resume leaves a journal of another version. A dry run writes none.

**The recovery** runs at the start of every new release that is not a dry run, at the second place of the order above. A resume runs none.

After the read of the command file (above), the recovery reads the journal. With none it does nothing more. A file that does not parse stops the release with a line naming the file; nothing is changed.

It takes from the journal only what git confirms, since the journal directs a reset, a checkout and a tag's deletion and `dist/` is not a folder the engine guards. A miss stops the release with a line naming the file and the field, nothing changed: the version has the release's version form and the tag is `v` plus it; the head is a full hash that resolves to a commit; the process id is a positive integer; every path is one a bump can write (the release's files as it reads them from `CLAUDE.md`, and the two test literals' files), relative, with no `..` segment. No value of the journal reaches git as an argument unless it passed these.

The recovery's rules follow, in the order they run:

1. **A release is running.** The journal's process is the same process: the release stops with `release <v> is running (pid <n>, written <at>): wait for it; if no release is running, delete dist/release-in-progress.journal`. The identity check is the engine's rule, composed from two functions the engine exports (`processGone` and `processStart` in `packages/engine/src/open.ts`): a process that is gone or a zombie is gone; a living one whose start time is the recorded one, or for which either start time is missing, is the same process; a living one with another start time is another process. Gone or another: the journal is a dead release's. The release takes the two functions as parameters, the engine's own when the caller gives none, so a test can answer in their place; the journal's start time is written through the same one.
2. **The checked-out branch is not `main`.** The release stops with the journal kept and a line that says so: the recovery changes something only on `main`.
3. **The tag is on origin.** The push went through and the kill came after it. The release stops, the journal kept: `release <v> is on origin and was not finished: resume it with bun scripts/release.ts --resume v<v> --from-step 7`, and it reports the journal's version with step 7 as failed and pending, with `localUnconfirmed` set. If origin cannot be asked, the release stops, nothing changed, and nothing is reported to the caller.
4. **The release was killed before its push.**
   - 4a. The release's commit is a commit git shows to have exactly one parent, the journal's head, the journal's title as its subject, and changes to no path but the journal's and the bundle.
   - 4b. `HEAD` is the release's commit: it is taken off by a mixed reset to the journal's head, which keeps the working tree; the line says the commit is kept in the reflog. `HEAD` is the journal's head: nothing to take off.
   - 4c. `HEAD` is anything else, and something of the killed release is left in the tree (a journaled file or the bundle differs from `HEAD`'s): nothing is put back, the journal is kept, and the release stops with a line that says so and what to do by hand.
   - 4d. The local tag `v<v>` is deleted when it points at the release's commit; a tag of that name pointing elsewhere is left and named. This runs in every case that goes on, the next one included.
   - 4e. `HEAD` is anything else, and nothing of the killed release is left in the tree (the loop's clone after its reset): the journal is removed and the release goes on.
   - 4f. Otherwise each journaled file whose content is what the journal says the release wrote is put back to its content at the journal's head (`git checkout <head> -- <file>`; the head always has the file, since the bump's plan holds only files that were in the clean tree it started from); one already at that content is left and not named; one that is neither was changed since, and is left as it is and named. The bundle is put back when it differs from the journal's head's: it is the build's output, made again by the build, and it is put back even when a session rebuilt it since. The line names it, and says it was rebuilt since when the journal holds the build's hash and the bundle no longer matches it.
   - 4g. The journal is removed, and the lines say what was put back and what was left.

The release then goes on with its preconditions. A file left as it is makes the tree dirty, and the precondition that refuses an unclean tree names it.

**A dry run with a journal present** runs the recovery's reads (the command file, the parse, the shape, rules 1 to 3) and changes nothing, kills nothing and keeps both files. It prints `would kill the command a killed release left running (pid <n>)` when the command file names one the next new release would kill, then `the next new release would stop: <the stop's line>` at a stop, and otherwise `would take the commit <short> off main` (4b), `would remove the journal: nothing of the killed release is left` (4e), `would put back: <files or none>` and `would leave: <files or none>` (4f). It then goes on as a dry run does today: its preconditions read the tree as it is. So a tree the killed release left dirty stops the dry run at the unclean-tree precondition, exit 1, after the recovery's lines; with a clean tree (the clone's case, or a stop that left nothing in the tree) it prints the plan and exits 0.

### The engine's end record

The engine's end record (item `2026-11-01-003`: the pushed commit becomes the session's baseline) is made by the run whose own step 6 went through, or was found on origin after its command failed. A resume makes none, as today, and rule 3's stop makes none. A session whose release was killed after its push holds the start marker of a dead process, which the marker's reader already ignores, and keeps its earlier baseline: its Stop rule reads the released commit as it reads any commit made outside an item. That is older than this item, and a Non-Goal.

### The loop's one change

The loop calls the release after it merged an adoption into its clone's `main` and committed its ruling on top. Its branch for a pending release keeps that merge, since until now a pending release meant the merge went out with the release's push. Two outcomes break that, and both carry a new optional field of the outcome, `localUnconfirmed`: the commits the caller made for this run are not confirmed to be on origin.

- Rule 3 sets it: an earlier run's version is pending, and this run's merge went nowhere.
- The push whose outcome is unknown sets it: the merge, the ruling and the release's commit are in the clone and nobody knows whether origin has them.

On a pending outcome with `localUnconfirmed`, the loop:

1. holds the reported version pending at step 7, and records the failure in the day's failures once, as its pending branch does today;
2. takes its clone's `main` back to the head before the merge, as its branch for a failure before the push does, the run's ruling committed again on that head and the kept branch left for a later tick;
3. logs `release <v> is held pending at step 7 and is not confirmed on origin: this run's adoption waits`.

So nothing unreleased reaches `origin/main` by the tick's own push. What then happens, by whether the unknown push landed:

- it did not land: the next tick's resume answers that there is nothing to resume, the loop clears the pending release, the journal is left, and rules 4d and 4e take the tag and the journal at the clone's next release;
- it did land: the tick's own push fetches and rebases onto an `origin/main` that already holds the ruling's files, so git drops the ruling commit as already applied. The tick still writes the day's report, which names the failure, and pushes it: `origin/main` gains that one commit, under `docs/improve/`, and nothing else; the merge and the release's commit are there once, as the unknown push left them. The next tick's sync brings them to the clone, and its resume finds the tag and runs steps 7 to 13.

A pending outcome without the field keeps the merge, as today. For rule 4 the loop needs no code: each tick resets its clone to `origin/main`, which drops a killed release's commit and files.

### The rollback's log names a rebuilt bundle

Today the list of what a rollback discards leaves the bundle out always. With this item the bundle is named when the build step recorded its hash and the file no longer matches it: a session rebuilt it since. A bundle that still matches the build's hash, or a failure at or before the build step, names nothing, as today.

### The entry point has a row

A row runs `bun scripts/release.ts` as a program, in a process of its own, with `--root` naming a fixture repository with its origin (without it the entry point uses this repository) and a home of its own: once with `--dry-run`, which prints the title and the thirteen steps and exits 0, and once with no reason, which prints the usage and exits 1. The row shows that the entry point parses its arguments, reads the loop's state and builds the deps without throwing, and reaches the release. A dry run ends before step 1, having run the preconditions' git commands alone, so the row does not exercise a real `gh` call, the notification or a step's command: the real runner and the engine's records have rows of their own.

### The records

`CLAUDE.md`'s Releasing section, ADR 0015 (a dated note, as each earlier change of the flow added one) and the two findings' records say what changed. ### What the reviewers' round added

The six reviewers of the delivery found three defects and a list of advisories. What they changed in the design:

- **A GitHub release left half made.** A `gh release create` killed at its bound can leave a draft, or a release with no archive. A resume's step 8 therefore counts the release as done only when GitHub shows it published and holding the version's archive; over anything less it deletes that release (the tag stays) and creates it again, and logs `the GitHub release of v<v> was left unfinished: deleted and created again, with this run's notes`. An archive GitHub lists as still uploading is unfinished. The notes of the release made again are the resume's own, and a draft somebody made by hand for that tag is deleted with the rest. An answer that cannot be read (the network, a bound, a text that does not parse) is no answer: step 8 fails with `the GitHub release of v<v> could not be read: <why>`, deletes nothing, and is resumed.
- **The bound's own kill.** The runner ends a command at its bound with SIGKILL, so a leader that ignores a request to end cannot hold the release; the group's kill follows as before.
- **The fleet's step.** Its two calls keep their own bounds and their own wording: a timed-out one never carries another command's bound in its line.
- **A killed push asked twice.** A push killed at its bound may still land a moment later. When the first answer says the tag is absent after such a kill, the release waits 5 seconds and asks once more before it puts the tree back; a tag in the second answer counts as the first would. A push that failed by itself is asked once. A push that lands later still is the window that stays: the next release then stops at `origin/main is ahead`, and the resume of that version finishes it.
- **Whose tag is on origin.** A tag on origin counts as this release's only by its commit. After a failed push: the tag's commit on origin is the release's own commit. In the recovery's rule 3: the tag's commit is one of rule 4a's shape; a tag of that name on any other commit stops the recovery with `the tag v<v> on origin is not the killed release's commit: nothing put back; delete dist/release-in-progress.journal if that release is another's`, and nothing is reported to the caller.
- **A commit origin already has.** The recovery never takes off `main` a commit that `origin/main` holds: it stops with `the commit <short> has the shape of release <v>'s and is on origin/main: nothing put back; delete dist/release-in-progress.journal if that release is finished`.
- **The command file's own limits.** A file that names this process's own process group kills nothing and is removed. A directory at the file's path is removed like a file off its shape. Every removal of the two files is one that cannot stop a step.
- **The resume's version.** A `--resume` whose version has not the release's version form is refused before any command, since the version names files under `dist/`. A resume given `--dry-run` leaves a journal of its version. A `--from-step` that is no step from 7 to 13 is refused before any command: a resume never runs the steps before the push again.
- **The ssh command git is configured with.** When git's own configuration names an ssh command (`core.sshCommand`), every git command of the release keeps it, with batch mode added, since the environment's setting would otherwise replace it.
- **Stops before step 1 are notified.** No token, a journal that cannot be written, a stop of the recovery and a release that is running each send the notification a failed step sends, with their line: under launchd the log is otherwise the only place they are said. A dry run notifies nothing. A notification carries its bound and no command file, on every path: sent through the file it would replace, then remove, the record of a release that is running when this one only stops beside it.
- **The loop's install and uninstall.** Each ends a running tick through launchd, which no longer ends that tick's bounded command: each kills that command's group afterwards, as `stop` does.
- **A probe that says missing is taken again.** A tick probes again while the probe file says the release's token is missing, so the word follows a login.

What stays, said plainly: a resume still takes its version by the tag's name on origin, as an operator or the loop's own state asked for it; the check that `origin/main` holds a commit reads this clone's own ref, as fresh as its last fetch or push, with rule 3's ask as the live check; a `core.sshCommand` that is a script with its own arguments gets ` -o BatchMode=yes` added and fails at the first fetch if it refuses it, where the caller's `GIT_SSH_COMMAND` is the way out; a tick with the account logged out runs the probe's commands each hour.

Left as they are, each with its reason: `bumpVersion` stays exported for the rows that compare the plan's write with it; the loop's `stop` keeps its own reading of a group's leader, through the `sh` it is given, and sends SIGKILL at once, since it is a person's order to stop; the runner reads its own start time from the engine directly, having no deps of its own. Whether a tick should skip its improvement run while the probe says the token is missing was put to the user, who decided on 2026-11-13 that it does; that is the loop's own behaviour, built in the loop's next item (finding 206), not in this one.

## Alternatives considered

- **Putting a killed release back (D-1), detecting it and stopping with the commands to put it back by hand.** The smallest version: no git write is directed by the journal. Rejected: the user decided on 2026-11-12, on finding 221, that a release killed mid-step puts the version files back; and in the loop's clone nobody reads an instruction, so every later release of the loop would stop.
- **Putting a killed release back (D-1), signal handlers in the release's process** (SIGINT, SIGTERM, SIGHUP run the rollback before the exit). It puts the tree back at once. It cannot catch SIGKILL, a crash or a power loss, and while a command runs the handler waits for that command to return, since the runner is synchronous. Declined by the user.
- **Putting a killed release back (D-1), both the handlers and the journal.** It covers every death and puts back sooner, at the cost of two mechanisms to keep and to test. Declined by the user.
- **Killing a timed-out command's processes (D-2), a list of the release's own process group taken before the command, the newcomers killed at the bound.** A person's Ctrl-C would still reach every child. It could kill an unrelated process that joined the group while the command ran (one the same shell or session started), and it needs two process listings per command. Declined by the user.
- **The token, read at step 8 as today with a separate check command before step 1.** Two reads, with a window between them in which the answer can change, and two places that state the rule for a token being there.
- **The probe, reading `gh auth status` for the account's own line.** That command says an account is known to `gh`, not that it holds a token the release can use; the release's own read is the only one that says what the release will find.

## Risks and rollback

- **A bound stops a good release.** A check slower than 45 minutes, or a push slower than 5, fails a release that would have gone through. Before the push the tree is put back and the release is run again; at the push origin is asked; after it the release is resumed. The bounds are three constants, changed in one place.
- **The release that ships this item is the first to run under it.** `bun scripts/release.ts` runs the tree's own script, so that release writes the first journal and runs under the bounds. If a bound misfires there: before the push the tree is put back, the constant is raised in a commit of its own and the release is run again; after the push the release is resumed, and a resume runs the same bounds, so the constant is raised first.
- **A command left running after a Ctrl-C or a kill (D-2).** It runs to its end, and a command that hangs runs until the next new release's recovery kills it. Until then a check uses the machine, and a build can finish writing the bundle, which the recovery puts back after it killed the command.
- **A credential that asks.** A release run by hand with a key that needs its passphrase typed now fails at the fetch with ssh's message, where today it asks. The Releasing section says what a release needs.
- **Processes that left the command's group.** The kill reaches the command's own group. The engine's tests start process groups of their own, so a check killed at its bound can leave some of them running; the failed step's message says so, and `ps` shows them by their command.
- **The check's bound outlives the session's permit.** The bounds before the push add up to more than the 45 minutes the engine's release marker keeps a session's permit: a check near its bound ends after the marker's age, and the Stop hook holds that session's turn again. That is older than this item, which only puts a bound where there was none.
- **The recovery writes into a tree a person touched.** It puts back only a file whose content is exactly what the journal says the release wrote, and the bundle; anything else is left and named. The reset it makes keeps the working tree, and is made only for a commit git shows to be the release's. A commit it takes off stays in the reflog.
- **`dist/` is trusted as the checkout is.** The two files are not signed: whoever can write `dist/` can already change the scripts the release runs. The checks below bound what a stale or mistaken file can do.
- **A journal or a command file written by something else.** A journal made by hand can name only the paths a bump can write and the bundle, can reset only a commit that has the shape of a release's, and can delete only a tag that points at it; any other value stops the recovery with nothing changed. A command file made by hand can have a process group ended only when the release it names is gone and the process it names is alive, started at the time the file gives, as the system reads it now, and leads its own group; an id of 0 or 1, a negative one and an empty start time are off the file's shape and reach no signal. Whoever can write `dist/` can end such a group without the release. The file is written beside and renamed, so a link left at its path is replaced, not followed. In the loop's clone a journal can also make one tick's adoption wait and an existing tag's release be resumed, which a person running `--resume` can already do.
- **A stale lock.** A lock the release did not leave is never removed by it: the release stops and says so, and in the loop's clone the tick's own git commands fail on the same lock first, as today.
- **A `gh release create` killed at its bound** may leave a draft on GitHub, or a release with no archive; the resume's step 8 deletes a release that is not published with its archive and creates it again.
- **Rolling this item back** is reverting its commit: the two files are under `dist/`, read by nothing else, and files left by the new code are ignored by the old.

## Non-Functional Requirements

- Performance: with no file of a killed release the recovery runs no command. With a journal it runs at most eleven local git commands and one `git ls-remote` (1.7 s measured). The token's read is one `gh` command. Each bounded command costs one `sh`, one `ps` and one `mv` more.
- Security: the journal and the command file hold no secret: paths, hashes, a title, a head, process ids and times. The token's output is never written out or shown.

## What the runtime was probed for

Two behaviours of the runtime carry D-2, and both were probed on this machine under Bun 1.4.3 before this plan was written:

- `spawnSync` with `detached: true` and `timeout: 1500` returned 4 ms after the bound while a grandchild held the output pipe, with the error code `ETIMEDOUT` and a `pid`; `process.kill(-pid, "SIGKILL")` then removed the grandchild.
- `sh -c '<wrapper>' <file> <release pid> <release start> <command…>` under that `spawnSync`: the `$$` the wrapper wrote equals `spawnSync`'s `pid`, that process leads its group (a child's `pgid` is it), the start time the wrapper wrote (`LC_ALL=C TZ=UTC ps -o lstart= -p $$`, trimmed) equals what the engine's `processStart` reads for the same living process, the file holds its four lines with no file left beside it, the command's standard input is the null device, and a command word with quotes, a space and a `$` reaches the command as one word.
- `git ls-remote origin HEAD` with `GIT_TERMINAL_PROMPT=0` and `GIT_SSH_COMMAND="ssh -o BatchMode=yes"` answered from this checkout and from the loop's clone on 2026-11-13, so the release at the close can reach origin with no terminal.

## Phase 6: the recovery (AC-52, AC-46, AC-53) and the loop's change
