# 0015. The harness-improvement loop runs always and releases what it proves

- Status: accepted (the user, 2026-10-25). Supersedes points 2 and 4 of [ADR 0013](0013-harness-improvement-loop.md).
- Date: 2026-10-25

## Context

ADR 0013 made the loop a development script run on demand, whose kept harness waited on a branch for a person. The user's direction of 2026-10-25: the loop and the fixes "have to run always", in the background of this Mac with Claude Code open or closed, so that every step a user takes runs the best proven harness. The decisions D-1 to D-9 of item `2026-10-25-005` set how.

## Decision

1. **Where and when.** A launchd agent (`io.wizardingcode.crew-improve`, `~/Library/LaunchAgents`) runs the launcher `~/.wizardingcode/crew-improve/tick.sh`, which brings a clone without the loop's script to origin/main first and then runs `bun scripts/improve-loop.ts tick` (finding 169: the tick itself never syncs to an origin/main without the loop), at minute 0 of every hour (`StartCalendarInterval`, so an hour slept is caught up at wake) and once at load. A run is due when the plugin's text changed on `origin/main`, a CTO plan is newer than the last run, the harness lessons grew, or a case went seven days unmeasured; the targets are the cases never measured first, then the oldest, two a run. The loop runs while a session is open here (D-6).
2. **Its own clone, never the user's checkout (D-1, D-3, D-7).** The loop lives in `~/.wizardingcode/crew-improve` (`WIZARDINGCODE_HOME` honoured): its configuration (`paused: true` holds the ticks without removing the agent), its state, its own clone of this repository where the runs happen, its logs. Every run's record and the day's report (`docs/improve/<run>/`, `docs/improve/daily/<date>.md`, D-7: the runs, the cost by provider, the releases, the failed steps; the notification carries the day's total) are committed and pushed to `origin/main`, release or not; a kept branch is pushed too. The user's checkout is fast-forwarded only when it is clean and on `main`.
3. **The adoption (D-4, D-5, D-9).** A kept harness passes a gate in code (the figures are a win by the run's own rule; the diff touches only the skill and the agents), then the judge rules the one clause code cannot, "no rule of the method weakened", headless and read-only, its answer parsed strictly. `holds` on a run measured on Claude models merges the branch into `main` and releases a patch; each adopted harness is its own release. Anything else keeps the branch as evidence and says why.
4. **The provider (D-2, D-8).** `config.json` names the provider: the runtime's own login by default, an Anthropic key, or an Anthropic-compatible gateway (OpenRouter, Ollama, LM Studio) with its base URL and the models it serves. A secret lives in the macOS keychain under `wizardingcode-crew-improve`, read into memory and passed only to the processes that need it; every line and file the loop writes is redacted of it. The provider's token sits in the kit's environment as `ANTHROPIC_API_KEY` did, the kit's OS sandbox confining it, and a gateway's base URL receives it by design. A run measured on models that are not Claude's is never released: the plugin's users run Claude.
5. **One release flow (finding 163).** `bun scripts/release.ts` is the release for a person and for the loop: the version written into every file CLAUDE.md names, the build, the checks, the commit and the tag, the push, the tarball, the GitHub release, the marketplace entry, the plugin update and the local install here, the notification; a failure before the push puts the tree back, a failure after it is resumed step by step.
6. **The hook's home rule.** The PreToolUse hook matches the engine's home at a word end, so a sibling under `~/.wizardingcode` is another tool's.
7. **Policy.** The loop never touches a project's `.crew/policy.json`: ADR 0012 does not apply to it.

## Consequences

- A user receives a better harness without asking for it; the day's report and the notification say what changed and what it cost. No daily cap: the cost is managed through the report (the user's decision).
- The loop's first unattended run is watched through `bun scripts/improve-loop.ts status`; the documentation does not confirm that a LaunchAgent reads the Claude login from the keychain, so the install probes it and prints the fallback (`claude setup-token` in the keychain).
- The eval kit's environment allowlist admits the provider's names and the credentials it needs, and nothing else that looks like a secret.
- A run's verdict holds for the models it was measured on; the record says which.
- A tick that fails after the model was paid keeps the run on record and backs off (an hour, then double, up to a day), so a run that cannot be saved is not paid for every hour; `config.maxRunUsd` is a ceiling a person may set on one run, none by default.
- The marketplace call uses the personal account's `gh` token, which carries more authority than the one file needs; a token limited to the marketplace repository is the better key and the next step.

## Note of 2026-10-28 (item 2026-10-28-001)

The loop gained the person's levers point 2 left out: `pause`, `resume` and `stop` (`stop` pauses, writes a marker and ends the running tick with `SIGTERM` to its group after checking the lock, the run recorded as stopped by the user with exit 4; finding 187). A tick whose sync changed the loop's code relaunches itself once on the new code (finding 188), so a fix is taken at once rather than one tick late. A proposal whose probe set the run's ceiling cannot pay is `unprobed` before any spend, and the commit names a ceiling stop as such, never as an error (finding 189). A stale lock's takeover records the dead tick, removes the run folder it left without a record, notifies once and reports it (finding 190).

## Note of 2026-10-30 (item 2026-10-30-001)

The clone now holds a browser. The `ui` eval cases copy Playwright's headless shell into their scaffold, so the clone's bootstrap installs it in the clone's own `node_modules/.cache/ms-playwright` with the clone's pinned bin (`node_modules/.bin/playwright`), and a tick about to run bootstraps a clone with no finished shell, after a pending release's resume, the back-off and the ceilings, so a tick not due, a dry run and a pending release wait on no download, save on the tick whose sync brings a new lockfile, whose bootstrap still installs it (finding 206). A failed download fails that tick under the back-off, and the next due tick tries again; while it keeps failing no run starts, ui case or not. A person's install in a checkout goes through `bunx`, since a person reads what it fetches; the unattended one names the pinned bin. The own folder and not the shared cache, since an install in another project cleans the shared cache of a build no live package links (finding 205). The lockfile pins the package and the build number, not the browser's bytes, which are trusted on TLS as any developer's `playwright install` is; where the release runs in the clone, `bun run check` can run that shell outside the kit's sandbox under the identity that holds the release's access.

## Note of 2026-10-31 (item 2026-10-31-002)

The GitHub release step takes the same token as the marketplace call. It ran under the account active in `gh`, and the release of 0.17.0 stopped there with another account active. With no token the step stops and never falls back to the active account. The configuration key `marketplace.account` keeps its name and now names the account of both steps. The token limited to the marketplace repository, named above as the next step, would not reach this repository, so the release step then needs its own key.

## Note of 2026-11-02 (item 2026-11-01-003)

A failed step of the release (findings 217 to 219) now names the lines of its output that name a failure (bun test's `(fail)` lines and biome's headers first, then the `error`, `×`, `✗`, `error TS` and `Found N error` lines, at most twenty), bun test's `N fail` summary whatever the cap, and the output's last ten lines, under a first line with the step's exit status (the signal and the spawn error when they apply) and the output file, `dist/release-<version>-step-<n>.log`, which holds the whole output and survives the rollback; the script's one synchronous runner captures 64 MiB per stream and passes a null exit through instead of a made-up 1. Run inside a Claude Code session, the script records the release in the engine in-process, through `packages/engine/src/release-record.ts`: a start record after the title line writes a marker under `.crew/local/running/` when no item is active and the tree is one the Stop rule would let end by its content, and the Stop hook then lets every turn end while the script's process lives and the marker is under 45 minutes old; an end record right after the push, on the recorded head's first child, clean, tagged and fingerprinted, takes the pushed commit's fingerprint as the session's baseline and removes the marker. Step 5 commits only what step 1 wrote and step 2 built, on the commit the release started from, or fails before any commit. The loop wires no record and records nothing. The record works when the checkout's engine source and the plugin the session's hooks load both know the marker's folder; a mismatch fails safe. The trust boundary stays the engine's: a script of the session's own making could import the same functions, the same class as a script that writes an engine file under `.crew`.

## Note of 2026-11-11 (item 2026-11-11-002)

Decision 3 keeps a kept branch as evidence when the adoption does not release it. For one ending, an adoption that ruled nothing because no judge could answer, [ADR 0024](0024-a-run-not-ruled-is-named-for-a-person.md) adds that the tick names the branch for a person, who may adopt it by hand under the preconditions in `docs/improve/README.md`.
