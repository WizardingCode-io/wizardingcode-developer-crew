# 0023. A release reaches the runtime adapters of every project

- Status: accepted (the user, 2026-11-06 to 2026-11-08: decisions D-1 to D-9 of item 2026-11-08-002).
- Date: 2026-11-08

## Context

A runtime adapter is the copy of the crew's skill, its agents and a hook configuration that Copilot, Codex, Cursor, Gemini or OpenCode keep inside a project (ADR 0011). A release refreshed the plugin root the configuration names (the tarball install, `scripts/release.ts` step 11) and nothing installed the copies inside a project again: on 2026-11-06 the Copilot adapters of two client projects were stale by 30 skill files and 16 agents, and no checkout recorded which engine version last updated it (finding 226; finding 223's analysis).

A session with no active item takes a baseline of the files the gates watch and stops a turn while one differs from it, measured against the session's baseline commit, so a refresh that rewrites a watched file after another session's baseline blocks that session's Stops until it starts a new session. Of an adapter's files only the configuration files, OpenCode's plugin file and Codex's `crew-*.toml` agents are watched.

## Decision

1. **Own root only.** An engine refreshes only the adapters whose configuration names its own plugin root, and never re-roots an adapter: one on another root is reported (gone, an older folder of Claude Code's plugin cache with the command that fixes it, another engine's), never rewritten (D-4).
2. **The record is a skip key.** The checkout's local state (`.crew/local/state.json`, never committed) records, per canonical root, the engine version that last brought that root's adapters up to date; it is written only once a check after the refresh says every adapter is ok, and read only to skip the check at the same version. An engine shipped before this item erases it at its next write, at the cost of one check per start.
3. **When nothing is written.** A refresh writes nothing in a task worktree, while the checkout has an active item, in a resumed or compacted session or beside a live one when a configuration or a Codex agent would change (D-5: the watch list is kept), over a register changed outside the engine, outside a git repository, and over adapter files that are uncommitted, untracked or ignored, the engine's own earlier refresh included (D-1, D-9). Each reason is said; the exact commit command is printed when a refresh wrote.
4. **Every own-root adapter is installed together**, under one hold of the checkout's `adapters` lock, the checks run again first, the link walk and the git status repeated under the hold, the deadline checked before each install; the install writes the configuration last and only when its value differs, prunes only the leftovers git can bring back (tracked and unchanged), and refuses a symbolic link or a path that leaves the project; the check compares the configuration with what the install would write, and its parts are data.
5. **SessionStart** runs the refresh inside an 8 s deadline before it takes its baseline, then waits for the `adapters` lock before the baseline whatever it did, so no baseline is taken while a refresh writes; its line follows the engine's, and `crew status` prints the last register entry for the runtimes with no context at start.
6. **`crew projects update [--dry-run] [--json]`** does the same for every registered project under its rules, checks the user scope and never writes it (D-6), and is asked by the PreToolUse guard before a real run (D-7). The release runs it from the tarball's bundle as step 12, soft and bounded at five minutes (D-3), an unattended release by the improvement loop too (D-8).
7. **Every text a repository controls** (a root, a path, a message) passes `quotedText` at 200 characters before it reaches a context line, a register entry or the command's output, and every git call on these paths passes `-c core.fsmonitor=false`.

## Consequences

- An engine shipped before this item erases the record; while such a session is open each start pays one check per own-root adapter and writes nothing when the adapters are ok.
- A project whose item stays active for days, or that never commits a refresh, keeps a stale adapter until the item closes or a person commits; the line and the fleet's count say so.
- One window remains where a refresh blocks a live session's Stops: a neighbour idle for more than 10 minutes, only when a watched file changes; a new session ends it. A start whose wait for the lock outruns its deadline is named.
- The undo of a refresh in a project is git's, by hand: `git restore` of the paths the commit command names brings every rewritten or removed tracked file back, since only tracked, unchanged files are written or removed; a file the refresh created (a skill file or an agent the root added) is untracked and stays until a person deletes or commits it, and the adapter is held back (`not committed`) until then. A run the release's bound kills leaves the projects it reached written, with their lines printed, and the project it was cut in written in part, with no line and uncommitted files: that project is held back at every later start (`uncommitted changes`) until a person commits or restores them, as the spec's Risks say; the projects it never reached are refreshed at their next session start or by the next `crew projects update`.
- The shared `.agents/skills/crew-method` follows the engine that ran last when two roots meet in one project; reported, not fixed.
- Alternatives (the spec's "Alternatives considered"): the running engine refreshing every adapter from the root each names; a child `crew runtime install` per adapter; no record and a hash check at every start; `crew projects update` alone; re-rooting to the running root; leaving crew's paths out of the watch list; writing the user scope; the skill copy as its own unit; an older engine never touching a newer record; `removeRuntime` then `installRuntime` as the prune; no committed copy at all; one lock hold per install.

## The not-committed mark (2026-11-09, item 2026-11-09-001)

Decision D-1 of item 2026-11-09-001 (the user, 2026-11-09): the commit command of a refresh keeps reaching the person until the adapter files are committed, on any engine root.

- **The gap.** Point 3 prints the commit command once, in the run that wrote. For a release that run is step 12, whose output is the release's log; the next start on the adapters' root skips at the recorded version (point 2), and a session on another root never names the adapter (point 1). On 2026-11-09 the 47 paths of each of two client projects were committed only because the releasing session read the log (finding 229).
- **The mark.** A refresh that updates an adapter writes `.crew/local/adapters/uncommitted.json`, beside the `adapters` lock: per canonical root, the version, the time, the commit `HEAD` named when the installs began, each updated runtime with whether its configuration was written, and whether the register gained an entry. It holds no path and no command.
- **A file of its own.** `loadState` rebuilds the state from the fields it knows, so an engine that does not know a field drops it (the first consequence above, for the record). The mark has to survive two engine versions sharing a checkout, between a release and the restart of Claude Code; a file an older engine never opens does. Its writers write back every key they do not recognise.
- **Written right after each install**, before the version is recorded and before the register entry, so a throw of either, or a kill after an install, leaves the reminder.
- **Read by every engine** at SessionStart, by `crew status` and by the fleet: per entry one `git status` under the runtimes' paths, taken from the reader's own table, and, when it lists a change, one `git log` for the paths a commit touched after the mark's commit. A change counts only when no later commit touched its path, so the person's own later edit of a configuration they share with the crew is not the refresh's. The register never makes an entry uncommitted: it changes with every item.
- **One command builder.** The command names only the mark's pathspecs that hold a counting change, so it runs as printed in a project that ignores `.crew/`. The per-run builder of point 3 is gone.
- **Cleared** by SessionStart and by a real fleet run, under the `adapters` lock in one attempt, once an entry's adapter paths are clean or hold only changes a later commit touched. `crew status` reads and never writes.

What follows from it:

- An engine shipped before this item never reads the mark: the reminder comes from the engines that know it.
- A run killed inside an install leaves files written in part and no mark for that adapter. The own-root start and every later fleet run say `uncommitted changes`; a session on another root is silent for that project.
- A clone that lacks the mark's commit, or a rewritten history, makes every change count: the reminder errs towards saying it, and stops when the paths are clean.
- When the command names the register, it commits every entry pending in it under the adapters' message.
- A person's edit of one of the mark's paths, made after the refresh and before the first commit, is staged with the refresh's own change: git cannot split a file, and the command names the path.

## An install cut short, a hand install (2026-11-09, item 2026-11-09-003)

The user's word of 2026-11-09 ("tudo") took the two proposals the mark's item left, P-1 (a mark for a hand install) and P-2 (the mark written before the installs), and the open findings a change could settle.

- **A note before each install.** The refresh and `crew runtime install` run one sequence, `installUnderMark`: the mark names the runtime *unfinished* before its install begins, and finished once the install has returned. A refusal, and a throw from before the install's writes, put the mark back as it was; an `InstallFailed`, whatever number of files it counts (a copy cut partway counts as none), leaves the runtime unfinished; a kill leaves the note on disk. Unfinished means one thing: an install that began and did not return. An install that returned wrote its files whole, so a check that then fails is the refresh's result (`failed`), not the mark's matter.
- **One root per runtime.** The root that installed an adapter last owns its mark: a note under one root takes the runtime out of every other root's entry, and the reader takes one entry per runtime (the roots in the order of their names), so a file of any size gives at most five entries and no cap is needed.
- **What the reader says of an unfinished runtime.** On its own root: `<runtime> left unfinished by crew <version> (an install cut short or failed): run crew runtime install <runtime> again, then commit`; on another root the same, with the crew of its root, such as the tarball's. While the adapters lock is still held (a lock is broken once ten seconds old) the mark alone cannot tell a running install from one cut short, so the reader says only that the install has not ended and to look again in ten seconds. No commit command is given while an entry holds an unfinished runtime: the skill folder is shared by every runtime, so a command for the finished ones would commit a part-written copy. The entry is judged whole for the same reason.
- **The clear compares the whole entry**, under the lock, with the one the reader judged: every write of an entry changes it, so a reader that judged an entry clean before its install wrote a file never removes the entry written a moment later.
- **The hand install and the remove** at project scope, with a commit to name, run under the adapters lock with the wait of a command (ten seconds, the age at which a dead process's lock is broken), write the mark, and end with the `adapters not committed:` line. With no commit to name, and at user scope, they run as before.
- **A removal keeps the shared skill folder** while another runtime's configuration of the scope still holds crew's hook, or cannot be read, and says `kept <folder> (still used by <runtimes>)`; the last adapter takes the folder with it (finding 232).
- **What the refresh could not write** (the version record, the register entry) is a sentence of its account, no longer a throw; SessionStart reads the mark in a fence of its own, so a refresh that throws hides no reminder.
- **D-9 stands.** The refresh never writes over an uncommitted change, so it never finishes an install an earlier run left unfinished: the person runs the install again.
