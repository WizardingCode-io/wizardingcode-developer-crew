# ADR 0011: runtime adapters, one table and the plugin folder as the distribution

Date: 2026-10-20. Status: accepted. Subproject: SP6, Task 4 (`docs/plans/2026-10-20-sp6-packs-adapters-and-benchmark.md`, decisions 8, 9 and 10).

## Context

The engine's six hooks spoke Claude Code's shapes and nothing else: the method was enforced in one runtime, and the vision's §13 named the others as a tier to reach. The official pages of Codex CLI, Cursor, GitHub Copilot CLI, Gemini CLI and OpenCode, read on 2026-10-20 by the item's researcher, give each runtime its own events, payload fields, answer shapes, configuration files and limits, and leave fields undocumented that the engine's rules read (a tool input's path, a subagent's name, a transcript's format). Finding 113 records what they said against the plan's decision 9.

## Decision

- **One table.** `packages/engine/src/runtimes.ts` holds one row per runtime: the events by the engine's names, a reader of the runtime's payload into the engine's `HookPayload`, a writer of the engine's answer in the runtime's shape, the hook configuration and its merge, the folders of skills and agents, the agent file in the runtime's format, the guarantee table and the trust step. The Claude Code row is today's reader and writer behind the table, byte for byte (the golden payloads prove it); the rules the hooks share changed for every runtime, Claude Code included, as the consequences say. `crew hook <event> --runtime <name>` runs the table; the engine's rules never change per runtime.
- **The tiers per guarantee, from the pages.** A guarantee (context at start, the status line per prompt, the denial of engine files, the denial of forbidden commands, the hold at Stop, the roles' answers filed, the roles read-only) is `enforced` only where the page documents the mechanism and the engine's own reading of the input can promise it, and `requested (<why>)` elsewhere (a mechanism the page does not document, or an input the engine reads by text, as Copilot's `powershell` tool is for the denial of forbidden commands); the reader still tries the likely field names so a documented name later costs one line. `crew runtime check <name>` prints the table from the engine, and `references/runtimes.md` and the README repeat it line for line (a test compares them).
- **Nothing runs unseen in translation.** An `ask` the engine answers becomes a `deny` on every runtime but Claude Code, Copilot included: its `powershell` lines the reader cannot place are answered as an ask by the engine and denied by Copilot, never asked of a person there; a patch's every path goes through the Write rule, made absolute against the session's working folder; Copilot's `powershell` line is denied when it names an engine file at all, then rewritten for the POSIX reader within a bounded subset of pwsh's argument mode, and wherever the reader cannot place it the line is asked in every policy and denied where nobody watches, in a session opened by mail and on Copilot, whether or not it names `crew`, so outside the declared class (a crew command built without the word crew on the line) every literal line that could run a crew command on that tool is answered, which is why its tier for the denial of forbidden commands is `requested` (the reading's grammar, form by form, is the module comment of `packages/engine/src/hooks/powershell.ts`; the subset it reads and the pwsh 7 run are the last consequence below); a tool the table does not map reaches no rule and is read-only in every documented case; the hook verb is denied from any command, so an item's observed runtimes are what the hooks saw. The rollback of an install is `crew runtime remove <name>`: crew's entries out of the merged configuration, the foreign ones and the other keys kept, `crew-method/` and the agents under the `crew-` prefix removed.
- **The session files where the hook cannot.** `crew answer file <id> --role <role> --file <path> [--as <agent>]` uses the one filing function the SubagentStop hook uses, marks the record `filedBy: "session"`, never clears a role wait, and is refused where every runtime the item ran under files by hook; the judgement, the validation and the gate run say `answers filed by the session`.
- **Names crew owns, merges that keep what is not crew's.** The install writes the skill as `crew-method/` under `.agents/skills` (every runtime reads it; the Agent Skills standard asks the folder to match the skill's name), the agents as `crew-<role>` in the runtime's folder and format, and merges the hook configuration per event, replacing crew's entries alone; a file that is not JSON is refused. The hook commands name the absolute root of the running bundle; `check` reports a gone root and stale copies by hash.
- **The plugin folder is the distribution.** The release attaches `wizardingcode-developer-crew-<version>.tar.gz` (`bun scripts/build.ts --tarball`): the plugin as it runs, `bin/crew` executable and following a symlink, no evals. A user extracts it, puts `bin/` on PATH and runs `crew runtime install <name>`.
- **One reference.** `references/runtimes.md` names the actions the skill uses (launch a role, file an answer, read the status, confirm a decision) and what each runtime does for them: one reference for every runtime in place of the mapping file per runtime the vision's §13 named, since what differs per runtime is data the engine prints, not prose the skill keeps.
- **Gemini CLI over Antigravity CLI.** The `gemini` row targets Gemini CLI (paid API keys, enterprise Code Assist); Antigravity CLI, which replaced it for unpaid users on 2026-06-18 with another hook format, is a later row.

## Alternatives

- A plugin per runtime, each with its own hook code: six copies of the rules to keep in step; the rules belong in the engine once.
- A generic hook protocol every runtime would have to speak: no runtime speaks it; the adapters speak each runtime's.
- A mapping file per runtime in the skill (the vision's wording): the differences are field names, shapes and tiers, which the engine holds as data and prints; prose would drift from it.

## Consequences

- The method's guarantees are said per runtime by the engine, and the record of an item names the runtimes that observed it with their tiers.
- The rules every runtime shares changed with the item, Claude Code included: `crew hook` is denied from any Bash command; a crew verb carrying a comma or a space is unreadable; every `find -exec` group is handed on under both finds' readings; the words after `env -S`'s string belong to its script; `node.exe`, `bun.exe`, `npx.cmd` and `bunx.exe` are runners; every hook of a Claude Code session records `claude` among the item's observed runtimes. Each tightens and each is proven; the spec's AC-9 (the Claude Code path unchanged) covers the golden payloads and the hooks' answers to them, not every Bash line.
- A runtime's page changing after 2026-10-20 is a finding: the recorded payloads (`tests/fixtures/runtimes`, embedded in the table as `check`'s samples) are the record, and the table follows the page.
- A person-only decision cannot be approved through the agent outside Claude Code; the person runs the command.
- A hook written for Codex or Gemini runs once the person trusted it; the install prints the step.
- A real-use session per runtime (the first outside installer, SP7 design §16) is where the requested tiers are settled or turned into findings.
- The PowerShell layer reads a bounded subset of pwsh's documented argument mode (about_Parsing; the split of a word that begins with a quoted part, issue #6467): word splitting, the doubled quote, that split, a balanced group with one group nested inside it, a handed rest to a depth of eight, the hand-ons beyond it flattened to the command they run (their quotes not decoded; the crew word's rule asks what that misses), a fold behind an opening quote bounded by that string's close and none behind a closing one, the quotes read in PowerShell's two kinds with a `#` line comment dropped first where both modes start one and asked about where they read it apart, and a subexpression of a double-quoted string read as nesting its quotes. The subset was taken from the documentation; the comment rule and the split of a word that begins with a quoted part were then run through pwsh 7 on 2026-10-21 (`echo "a"#b ; echo z` prints `a` alone; `a"b"#c`, `x=#y`, `a]#b` and `a>#b` are one word each; `a,#b` and `"$( # x )"` are parse errors that run nothing; `"a""b"#c` is one string and a comment; `a$(1)#x` and `a${x}#y` are one word each and `${x}#y` prints `#y`, while `$(1)#x` and `(1)#x` take a comment; `${#x}` is an empty braced variable, not a comment; `a(#x`, `a{#x`, `"$( 'a'#x )"` and `"$( ('a') # x )"` are parse errors that run nothing), and each form is read as pwsh reads it or asked about; the real-use session on Copilot confirms the rest or turns it into a finding, and a further statement rule is a new decision, not a round's fix.
