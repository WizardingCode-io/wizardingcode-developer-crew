# SP6: Packs, runtime adapters and the public benchmark. Implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task in this session, through the crew method (each task is a crew work item in this repository, as SP7a, SP7b, SP3, SP8 and SP4 were). Steps use checkbox (`- [ ]`) syntax for tracking.
>
> **Written on 2026-10-20**, from the vision's §11 (packs), §13 (runtimes: the enforced and the requested tiers, skills written once with a mapping file per runtime), §14 (packaging: a small core plus packs that install separately, from the marketplace, bundled), §15 (proof: evals per part, the corpus, a public benchmark reproducible by anyone) and §16 row 6; the SP7 design's §6.1 (`team.template`, `team.specialists`), §6.3 (stack specialists as the one expert with a pack knowledge file; agentic OS as a pack team), §16 (SP6's acceptance: a pack installs and an eval shows the difference; an external skill's claims measured before any line enters an agent) and §18 decision 6; the SP1 design's §7 (packs can ship detectors); ADR 0007 §5 (what SP6 closes with) and ADR 0008 (one release, 0.11.0, the whole suite once before the real-use phase). The official hook pages of the five runtimes were read on 2026-10-20 (decision 9 lists what each gives); the item's researcher reads them again before the table is coded.

**Goal:** Knowledge installs apart from the core and the engine serves it: a stack pack carries what a model gets wrong about a technology, how work in it is verified and where its current documentation is; a domain pack carries the checklists the gap round uses; a team pack carries a template (a team's path rule, teams added) and a detector refines the profile's gates. A pack is data, installed from the marketplace or added from a path, registered and checked by the engine, read by the one skill and the one expert, published only with an eval that shows the difference against the core without it, and an external skill enters a pack only with the case that measured its claim. The same engine and the same skill run in Codex, Cursor, Copilot, Gemini CLI and OpenCode through one table of adapters, each guarantee recorded as enforced or requested per runtime. A benchmark anyone can run reports functional pass rate, security pass rate, cost and time with the system and without it.

**Architecture:** No model runs inside the engine and a pack carries no code: a folder with `pack.json` and Markdown files (`checklists/`, `knowledge/`), a detector rule as JSON, a team template as JSON. The engine registers packs under the user's crew directory (`~/.wizardingcode/crew/packs/<name>.json`, written only by the `crew` command), checks each at registration (shape, core range, files present, secrets, tighten-only template, provenance with proof), loads their detector rules after the core's, merges their templates into the team registry without ever removing or loosening, and serves their files by absolute path (`crew pack files`), which the skill reads as it reads its own. In Claude Code the packs are discovered at SessionStart from the plugin registry the runtime keeps, read-only and fail-open; everywhere else `crew pack add <path>` registers a checkout. The runtime adapters are one table (`runtimes.ts`): the engine's six hook events mapped to each runtime's events, a payload reader and a response writer per runtime, and a config writer per runtime and scope; `crew hook <event> --runtime <name>` is the one entry. The benchmark is a tag on the suite's cases, a category per case and a script that turns the eval kit's aggregate result into a record; no figure is typed by hand.

**Tech Stack:** TypeScript (dependency-free engine, Bun for tests, Biome), Node 20+ at run time, `claude plugin eval` for the cases (one plugin loaded, a no-plugin baseline arm, `--ablation with-without`), the mods API of `plugins/core/hooks/register.js`, the `wizardingcode-plugins` marketplace (`git-subdir` entries).

**Spec:** the sections named above. The rules the engine enforces in this release: 13 (a pack's team template and a pack's files never cross a workspace: a pack is the user's, registered per machine, and the knowledge it serves is the pack's own, never an entry of the base), 10 (process follows risk: a pack tightens, never loosens) and 18 (measure everything: the benchmark's figures from the kit's result alone). The vision's publishing rule: a pack ships only with evals that show a difference against the agent without it, and its content states the version it was verified against.

## Global Constraints

- The engine stays dependency-free; Node 20 or later runs the hooks and the command in every runtime.
- The files the engine owns are written only by the `crew` command: the registrations under `~/.wizardingcode/crew/packs/` are protected already (`isProtectedPath` covers the user directory); a pack's own files are the pack's, read by path, never copied into `.crew/` or the user directory.
- Hooks fail open: a pack whose root is gone or whose manifest no longer parses serves nothing, is listed as `missing` or `unreadable` with the reason, and never throws inside a hook; an adapter that cannot read a runtime's payload answers `{}` in that runtime's shape.
- Roles are read-only, with no network and no key; a pack adds no agent (every agent description costs every session: finding 60, SP7 design §2) and no hook.
- The skill page `plugins/core/skills/crew/SKILL.md` stays within 9254 bytes (it is at 9245; the Packs and Runtimes references and `--observed` beside `--preserve` enter by trims, finding 109).
- Biome; imports with an explicit `.ts` extension; TDD (the test fails first); repository documents in English.
- One release at the close: 0.11.0 in `package.json`, `packages/engine/package.json`, `packages/engine/src/version.ts`, `plugins/core/.claude-plugin/plugin.json`, `version.test.ts` and the `--version` line of `cli.test.ts`; the bundle rebuilt; the marketplace entry at `v0.11.0` plus one entry per pack.

## Review Focus

1. A registered pack whose root was deleted, whose `pack.json` is garbage or whose `core` range the engine does not satisfy: `crew pack list` says `missing` or `unreadable (<reason>)`, `crew pack files` prints nothing for it, its detector rules and its template are not loaded, the SessionStart line says `packs: 2 (1 missing)` and the session goes on. Pinned in Task 2 (`listPacks` over a deleted root and a garbage manifest; `detectTargets` and `teamsFor` with the registration present and the root gone).
2. A pack cannot loosen: a template that names a team the registry does not have, removes a team, widens a cap or lowers a mandatory rule (`always` to `paths`) is refused at registration naming the key, like every key of `policy.ts`; a template may add path globs to a `paths` team and teams to `always`. Pinned in Task 2 (`registerPack` on the four templates; `plannedSeats` with the merged registry).
3. A pack's text through the secrets scanner at registration: a planted key in `knowledge/<stack>.md` refuses the whole registration naming the rule and the file, nothing written; a file changed after registration is served and `crew pack list` says `changed since registration` with the file (the hash recorded at registration). Pinned in Task 2.
4. An adapter given a payload short of a field (a Cursor `preToolUse` without `workspace_roots`, a Gemini `BeforeTool` with a tool name the map does not know): the hook answers allow in that runtime's shape and never a crash; `crew runtime check <name>` names what the runtime cannot give (the context per prompt in Cursor and Copilot, the hold at Stop in OpenCode) as `requested`. Pinned in Task 4 (one recorded payload per event per runtime, from the official pages; the short payloads; the check's table).
5. The benchmark's figures come from the aggregate result alone: the record is generated from the JSON, the script refuses a result whose schema it does not know (`schemaVersion`), and a test pins the record against a fixture aggregate with known numbers. Pinned in Task 5.

**Decisions taken while writing this plan** (each a reading of the vision and the design where they left a detail open; the leads may return any):

1. **A pack is data, served by the engine.** A folder with `pack.json`, `checklists/*.md`, `knowledge/<stack>.md`, a `README.md` that states what it was verified against, and `.claude-plugin/plugin.json` so the marketplace installs it; no code, no skill, no agent, no hook. Named `wizardingcode-pack-<name>`, kept in this repository under `packs/<name>`, published as a `git-subdir` entry of the marketplace at the release tag, and installable from a path everywhere (`crew pack add <path>`). The core skill reads a pack's files through the paths the engine prints; a pack never changes what the skill says, only what it reads. ADR 0010 records it.
2. **The manifest and the registration.** `pack.json`: `{ "name", "version", "kind": "stack" | "domain" | "team", "core": ">=0.11.0", "verifiedAgainst": { "<technology>": "<version>" }, "detectors": DetectorRule[], "checklists": string[], "knowledge": { "<stack or tag>": "<path>" }, "team": { "template": "<name>", "teams": { "<team>": { "mandatory": { "kind": "paths", "globs": string[] } } }, "always": TeamName[] } | null, "evals": string[], "provenance": Provenance[] }`. `crew pack add <path>` reads the manifest, checks it (the shape field by field; `core` against `VERSION`; every named file present under the root's real path; every Markdown file through the secrets scanner; the template tighten-only, review focus 2; every `provenance[].measuredBy` a case named in `evals`, decision 6) and writes `~/.wizardingcode/crew/packs/<name>.json` (`{ name, version, root, registeredAt, by: "command" | "discovery", files: { "<path>": "<sha256>" }, manifest }`) under `withLock`; `crew pack remove <name>`, `crew pack list` (name, version, kind, root, state: `ok`, `missing`, `unreadable (<reason>)`, `changed since registration (<files>)`), `crew pack show <name>`, `crew pack files checklists <kind> | knowledge <stack>` (one absolute path per line, the packs in registration order; nothing for a pack not `ok`), `crew pack sync` (the Claude Code discovery run by hand). Discovery at SessionStart: when `CLAUDE_PLUGIN_ROOT` is set, the engine reads `~/.claude/plugins/installed_plugins.json` (read-only, fail-open), takes the entries whose name starts with `wizardingcode-pack-` and whose `installPath` holds a `pack.json`, and registers or refreshes them as `by: "discovery"`; a pack removed from the registry is unregistered at the next start; a pack added by command is never touched by discovery. The status line part `packs: n` (`packs: 2 (1 missing)`) in the SessionStart context and the prompt hook, `crew status --json` with the registrations, each command appended to the decision register (kind `pack`).
3. **Detectors as data.** `DetectorRule { stack: string, extends?: Stack, markers: string[], packageManager: string, gates: Partial<Record<GateName, string>>, testScoped?: string }` in `detect/types.ts`; `dataDetector(rule)` builds a `Detector` that matches a folder when every marker exists in it. `DETECTORS` stays the core's; `detectTargets(root, rules)` runs the core first and the rules after. A rule with `extends` refines the target the core found at that folder with that stack (the gates it names, `packageManager`, `testScoped`) and adds its `stack` id to `Target.tags: string[]` (new, empty by default; the profile's `targets[].tags`); a rule without `extends` is a new stack and the target's `stack` is its id. `Stack` widens to `string` with `CORE_STACKS = ["node", "php", "python", "other"]` kept where the engine lists them; a rule whose `stack` is a core id, whose `extends` is not a core id, or whose gate command is empty is refused at registration. The profile refresh at SessionStart and the gate run read the registered rules, so a pack installed after the first detection reaches the profile at the next start (finding 23's rule, nothing by hand); `crew profile` prints a target's tags and the pack a gate came from (`test: php artisan test (pack laravel)`).
4. **Team templates and specialists.** `team.template` accepts `core` or the template of a registered pack (the policy's `values` list is built from the registrations at load; an unregistered name falls back to `core` with the warning the policy prints today); `teamsFor(policy, packs)` in `team.ts` merges the core registry with the template: a `paths` team gains the template's globs (today the policy names the paths for `agentic-os`; the template gives defaults and the policy adds), `always` adds teams; `plannedSeats` reads the merged registry and the seat's reason says `pack <name> (<glob>)`. The expert's knowledge files are derived: the packs whose `knowledge` keys match a target's `stack` or `tags` of the item's changed files, plus the files `team.specialists` names as `<pack>:<key>`; `crew pack files knowledge --item <id>` prints them for the launch line, and `crew team <id>` prints them under the expert's seat.
5. **The skill's reads.** `references/conclave.md`: the gap round's checklists are the core's for the kind plus every path `crew pack files checklists <kind>` prints; the expert's launch passes every path `crew pack files knowledge --item <id>` prints, under a `## Knowledge` paragraph the expert's page reads first; `references/packs.md` (new): what a pack is, the commands, the states, the external-skill rule, how a pack is written and measured; SKILL.md gains the reference row cell and `--observed` beside `--preserve` within the ceiling by named trims (the regex pins of the Conclave and Mail rows read first, finding 107).
6. **The external-skill rule.** `Provenance { source: string (http(s) URL), licence: string, commit: string | null, measuredBy: string }`; a pack that folds an external skill's content lists one entry per source and each `measuredBy` names a case in its `evals`; registration refuses a pack with provenance and no such case (`folded in without proof: <source> names no case`). The loop, in `references/packs.md`: write the case first, with the external skill's claim as its criterion; run it with the core alone and record the figure; fold the content into the pack; run it again; the pack ships when the second run shows the difference. The researcher's verification applies to the sources as it does to a debate's facts.
7. **The two first packs.** `packs/laravel` (kind `stack`): `knowledge/laravel.md` (what a model gets wrong in the version named, how work is verified: `php artisan test` or Pest, Pint, Larastan, migrations fresh on SQLite, `route:list`; where the documentation is, by version), `checklists/eloquent-model.md`, `checklists/job-or-listener.md`, `checklists/artisan-command.md`, the detector rule `{ stack: "laravel", extends: "php", markers: ["artisan", "composer.json"], packageManager: "composer", gates: { test: "php artisan test", lint: "vendor/bin/pint --test", typecheck: "vendor/bin/phpstan analyse --no-progress" }, testScoped: "php artisan test {files}" }`, `verifiedAgainst` the Laravel version the researcher confirms at build time. `packs/agentic-os` (kind `team`): `knowledge/agentic.md` (what a model gets wrong writing agents: injection surfaces, tool scopes, non-determinism in tests, cost of context, evals before ship), `checklists/agent.md`, `checklists/tool.md`, `checklists/prompt.md`, the template `{ template: "agentic-os", teams: { "agentic-os": { mandatory: { kind: "paths", globs: ["agents/**", "skills/**", "prompts/**", "hooks/**", "**/*.prompt.md", ".claude/**"] } } } }` (SP7 design §6.3 and §18 decision 6: a pack team until real use shows otherwise). Each pack's README states its `verifiedAgainst`, its cases and their figures.
8. **Runtime adapters: one table, one distribution.** `packages/engine/src/runtimes.ts`: `RUNTIMES` (`claude`, `codex`, `cursor`, `copilot`, `gemini`, `opencode`), each with the events (the engine's six mapped to the runtime's names or `null`), `readPayload(raw): HookPayload` (ids, cwd, tool name and input mapped; the runtime's tool names mapped to `Bash`, `Write`, `Edit`, `Agent` where the engine's rules read them), `writeResponse(event, response): { stdout: string, exitCode: number }` (the engine's `permissionDecision`, `decision: block` and `additionalContext` translated), `configPath(scope)` and `writeConfig(root, scope)`; `crew hook <event> --runtime <name>` (the default `claude`, today's behaviour unchanged), `crew runtime list`, `crew runtime install <name> [--scope project|user]` (writes the runtime's hook config pointing at `node <plugin root>/dist/crew.mjs hook <event> --runtime <name>` with the absolute root, the skill as a copy in the runtime's skills folder in the Agent Skills format with `references/runtimes.md` beside it, the agents generated from `plugins/core/agents/*.md` into the runtime's agents folder where the runtime has subagents, and prints every file written), `crew runtime check <name>` (reads the config back, runs the six events with a sample payload through the adapter, and prints the guarantee table: context at start, the status line per prompt, the denial of engine files and of the forbidden commands, the hold at Stop, the roles' answers filed, each `enforced` or `requested (<why>)`). The plugin folder is the distribution on every runtime: a release asset `wizardingcode-developer-crew-<version>.tar.gz` of `plugins/core` attached to the GitHub release, `bin/crew` on PATH. ADR 0011 records it.
