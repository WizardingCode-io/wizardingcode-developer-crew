# SP4: The knowledge base, the learning and the CTO. Implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task in this session, through the crew method (each task is a crew work item in this repository, as SP7a, SP7b, SP3 and SP8 were). Steps use checkbox (`- [ ]`) syntax for tracking.
>
> **Written on 2026-10-19**, from the SP7 design (`docs/specs/2026-10-17-sp7-teams-agents-workflows-and-rules-design.md`, §5 rules 13 and 17, §6.5 (metrics and the CTO's plan), §12 (the knowledge base), §15 (the three cases), §16 (the acceptance), §18 decision 1), the vision's §9 (the validated-solutions base) and its phases 1 and 9 (Recognize looks the base up; Learn writes it), and ADR 0008 (one release at the close: 0.10.0).

**Goal:** What one project learned is read in the next under a confidentiality mark: a solution proven in one item, a root cause found by an issue, a fact a researcher sourced and a workspace's stack tendency enter one base at the end of the item, are listed by the engine when the next item is recognised, may be cited by the strategy, the spec and the analysis, are refused across workspaces when marked, and are refused a second time when they are the same root cause; the CTO's plan reads the records and the learning cycles and enters the base itself.

**Architecture:** No model runs inside the engine. The base is one protected JSON file under the user's crew directory (`~/.wizardingcode/crew/knowledge/base.json`), written only by the `crew` command under a lock; every entry carries its origin workspace and its mark. The engine looks the base up deterministically when an item enters `recognize` (stacks, paths and words), writes the hits into the item's `knowledge.md`, and, when Jev is configured, asks one Noul per hit and reorders without dropping (the rerank shape of the TypeSafe cookbook; Jev only tightens, SP3 §11). A new phase `learn` follows `deliver`: `crew learn <id>` writes the entries from the item's records with its evidence as the ticket, confirms the entries the item cited, and refuses a root cause already in the base. The strategy's `[K:<id>]` marks, refused since SP8, are accepted when the id is listed in the item's `knowledge.md`. `crew cto review` prepares the CTO's inputs from `crew metrics` and the base's cycles; `crew cto record` files the plan and writes it as an entry under the workspace's mark.

**Tech Stack:** TypeScript (dependency-free engine, Bun for tests, Biome), Node 20+ at run time, the mods API of `plugins/core/hooks/register.js`, `claude plugin eval` for the cases, the TypeSafe System One API through the engine's own `askJev` (`jev.ts`, the canned transport in tests).

**Spec:** the SP7 design, sections named above. The rules the engine enforces in this release: 13 (boundaries: only unmarked solutions are reused; the mark and the refusal) and 17 (learn once: the root cause of each issue goes to the base; the same one twice is refused). The TypeSafe guidance read for the lookup: the re-ranking cookbook (one Noul per query-candidate pair, the probability itself as the order, no threshold needed to rank) and the Noul page (a value near 0.5 is an even split, not a degree; one question per candidate; several questions per call over the same state).

## Global Constraints

- The engine stays dependency-free; Node 20 or later runs the hooks and the command (no `node:sqlite`, which is Node 22).
- The files the engine owns are written only by the `crew` command: everything under the user directory is protected already (`isProtectedPath`), so `knowledge/` and `cto/` need no new rule; the item's `knowledge.md` joins the work folder's engine-written files.
- Hooks fail open: a base that cannot be read lists nothing and says why; it never throws inside a hook.
- Roles are read-only, with no network and no key: the engine alone asks Jev (SP3 §11); `verify.send: claims` keeps an entry's text on the machine.
- The skill page `plugins/core/skills/crew/SKILL.md` stays within 9254 bytes (it is at 9247).
- Biome; imports with an explicit `.ts` extension; TDD (the test fails first); repository documents in English.
- One release at the close: 0.10.0 in `package.json`, `packages/engine/package.json`, `packages/engine/src/version.ts`, `plugins/core/.claude-plugin/plugin.json`, `version.test.ts` and the `--version` line of `cli.test.ts`; the bundle rebuilt; the marketplace entry at `v0.10.0`.

## Review Focus

1. A `base.json` that is missing, unparsable or of a later `version` than the engine knows: the lookup lists nothing and `knowledge.md` says `none (base unreadable: <reason>)`; `crew learn` and `crew knowledge add` refuse naming the reason and never overwrite it. Pinned in Task 2 (`readBase` on garbage and on `version: 2`).
2. Two sessions learning at the same moment (two projects of one workspace closing items): the ids never repeat and no entry is lost. Pinned in Task 2 (two `addEntry` calls under the lock from two `CrewPaths` of the same user directory; `K-1` and `K-2`, both present).
3. A project with no workspace (`mail.workspace` null): its marked entries are visible to that project alone, never to another project with no workspace. Pinned in Task 2 (`visibleTo` with two alone projects).
4. A request whose title holds no word of four letters and a profile with no stack the base knows: the lookup lists nothing, `knowledge.md` says `none`, the status line says `knowledge: none`, and classification goes on. Pinned in Task 3.
5. Jev configured with `verify.send: claims`: the request body carries each entry's id, kind and title and never its `text`; with `claims-and-snippets` the text goes, cut at 4000 characters. Pinned in Task 3 (the canned transport's captured body).

**Decisions taken while writing this plan** (each a reading of the spec where it left a detail open; the leads may return any):

1. **The store is the engine's protected JSON, always.** `~/.wizardingcode/crew/knowledge/base.json` (`{ "version": 1, "next": <n>, "entries": KnowledgeEntry[] }`, honouring `WIZARDINGCODE_HOME`), read whole and written whole under `withLock` on `knowledge/.lock`. §18 decision 1 named the brand's memory plugin when installed: its store is SQLite (`~/.wizardingcode/mem/wizardingcode-mem.db`), which a dependency-free engine on Node 20 cannot open inside a hook, and the lookup must run in `applyClassification` deterministically. The memory plugin already reads the crew's records; it reads this file too, in its own release. ADR 0009 records this reading of decision 1. **This is the one decision that departs from the design as written: the user's word before Task 2.**
2. **Entries, visibility and the mark.** `KnowledgeEntry { id: "K-<n>", kind, title, workspace: string | null, project: string, confidential: boolean, item: string | null, commit: string | null, stacks: Stack[], paths: string[], words: string[], text: string, source: string | null, createdAt: string, confirmedBy: KnowledgeRef[], contradictedBy: KnowledgeRef[] }`, `KnowledgeRef { item: string, project: string, at: string, reason?: string }`, `KnowledgeKind = "stack-preference" | "validated-solution" | "documentation" | "root-cause" | "general"`. `confidential` defaults to true for `validated-solution`, `root-cause` and `stack-preference` and to false for `documentation` and `general` (§12); `--confidential` on `crew knowledge add` marks. `visibleTo(entry, scope: { workspace, project })`: an unmarked entry everywhere; a marked entry inside its workspace (`entry.workspace === scope.workspace`, both non-null), or, with no workspace on either side, inside the same project. Removing a mark is a person's decision alone: `crew knowledge unmark K-n` refuses `--mode` and `--validator` in the CLI and in the hook's rules, as `crew approve <id> audit` does.
3. **The lookup is deterministic first, Jev second, nothing dropped.** `lookup(base, query: { scope, stacks, paths, words, kinds? }, limit = 10)` returns `LookupHit { entry, score, reasons }` over the visible entries: a reason per overlap (`stack <s>`, `path <p>`, `word <w>`), score `2 × paths + stacks + words`, hits with a score above zero, by score then `createdAt` descending, capped. `words(text)` is lower-case `[a-z0-9]+` runs of four characters or more minus a fixed stop list (`that, this, with, from, into, when, then, what, have, will, every, each, their, there, which, about, after, before, also, only`). With Jev configured (`jevConfig` has a key or a canned transport): `rerankHits(cfg, verify, request: { title, kind }, hits)` asks one `noul` per hit (at most `verify.maxClaimsPerItem`) over the state `{ request: { title, kind }, entry: { id, kind, title } }` (`text` added, cut at 4000 characters, under `verify.send: claims-and-snippets` alone), instructions "Does this knowledge entry bear on the request: would a developer doing the request need to read it before designing?", criteria `true` "the entry's solution, cause, fact or tendency applies to what the request asks" and `false` "the entry concerns another need, another layer or another stack". The verdict per hit: `likely` at or above `verify.threshold`, `unlikely` at or below `1 − threshold`, `unverified` between; `likely` hits first by noul, then the rest in the deterministic order; nothing dropped. Unavailable: every hit `unverified (jev unavailable: <reason>)` and the deterministic order stands. The `Verification` records (`what: "knowledge K-n"`) are appended to the item's evidence as the research pass's are.
4. **The item's knowledge record.** `.crew/work/<id>/knowledge.md` is written by the engine at `applyClassification` (the step from `receive` to `recognize`): `# Knowledge for <id>`, then one bullet per hit, `- K-4 · validated-solution · "<title>" · <workspace or shared> · <reasons joined by ", "> · <jev verdict or "jev not configured">`, or `- none`. `crew knowledge <id> lookup` rewrites it (after a kind raise, after the analysis); `crew analyse` rewrites it with the origin's paths added and the kind `root-cause` first. `work.json` gains `knowledge: { readAt: string, listed: string[] }`. The skill reads it in Recognize; the strategy, the spec and the analysis cite an entry as `[K:<id>]`. `checkStrategy(text, researcherText, listed: string[])`: a `[K:<id>]` whose id is listed counts as a mark like `[R<n>]`; an unlisted one is refused: `K-9 is not listed in knowledge.md: not in the base, or marked for another workspace (rule 13)`. `RESEARCH_ALONE` becomes `from the research and the base`; the status line and the report say it.
5. **Learn is a phase after deliver**, on every route and every kind but `audit` (an audit's findings are the report's; nothing is learned from it in this release). The guard into `learn` is the guard into `deliver` plus the verdict proven on the current fingerprint; there is no guard out (it is the last phase). The Stop hook holds nothing for an item in `deliver` or `learn` with a clean tree (learning is not proof). The status line in `deliver` says `proven; crew phase next, then crew learn <id> writes the base`; in `learn` before `crew learn`, `proven, not learned: crew learn <id>`; after it, `learned: K-7, K-8`. `references/deliver.md`'s last step is the phase change and `crew learn`. An item at `deliver` from before 0.10.0 is taken to `learn` by `crew phase next` as any other.
6. **What `crew learn <id>` writes** (refused outside `learn`, refused on a second run naming the entries already written): a `validated-solution` (title the item's title; text the spec's summary and its criteria lines, cut at 4000 characters; paths the item's changed watched files from `changedWatchedPaths(root, profile, baseCommit)`; stacks of the targets whose path contains a changed file; commit `HEAD` when `artifacts` is `commit`, null otherwise; marked); for an issue a `root-cause` (title `Root cause: <item title>`; text the `Cause` section of `analysis.md`; paths `origin.paths`; marked); a `documentation` entry per line under `## What the documentation says` of `conclave/researcher.md` that names a URL source and is not marked `disputed` by the research pass (title the source and the first sixty characters of the quote; text the line; source the URL; unmarked); one `stack-preference` per workspace (title `Stack preference of <ws>`, text the count of registered projects per stack from their profiles, marked), rewritten in place under its own id, none when the project has no workspace. `confirmedBy` gains `{ item, project, at }` on every listed entry cited `[K:<id>]` in `spec.md`, `strategy.md` or `analysis.md`. When `mail.workspace` is set, a `notice` goes to each other registered project of the workspace through `send` (subject `K-7 entered the base`, the text the title and the kind). `work.json` gains `learned: { at, entries: string[], confirmed: string[] }`; the decision register gets the line `learned K-7, K-8; confirmed K-4`.
7. **Rule 17 twice.** On the learn side: a visible `root-cause` entry sharing at least one path with `origin.paths` and at least three words with the new cause is the same root cause; `crew learn` is refused naming it (`K-4 already records this root cause (item <id>, commit <sha>): crew learn <id> --confirm K-4 confirms it, crew knowledge contradict K-4 --reason "<why>" --item <id> disputes it`); `--confirm K-4` writes the confirmation and no new entry. On the issue side: `crew analyse` runs the lookup with `kinds: ["root-cause"]` and the origin's paths, writes `knownRootCauses: { id, title, item, commit }[]` into `analysis/origin.json` and the hits into `knowledge.md`; the guard out of `analyse` refuses while a known root cause is neither cited `[K:<id>]` in `analysis.md` nor contradicted by this item (§16 says "refused by the gap round": the analysis comes before the conclave on an issue, so the refusal lands at the earliest point the engine can name the cause, and the gap round inherits it): `K-4 is a known root cause of src/accounts.mjs (item <id>): cite it in analysis.md with what this fix does differently, or crew knowledge contradict K-4 --reason "<why>" --item <id>`.
8. **The CTO.** `crew cto review --workspace <ws>` writes `~/.wizardingcode/crew/cto/<ws>/<date>-inputs.json` (`{ at, workspace, metrics: Metrics, lastPlan: string | null, knowledge: KnowledgeFigures }`) and prints its path, the last plan's path and the line that launches the CTO; `crew cto record` (SP7a) files the plan as today and writes a `general` entry marked under the workspace (title `CTO plan <date> (<ws>)`, text the plan cut at 4000 characters, source the plan's path); `computeMetrics` gains `knowledge: KnowledgeFigures { entries: Record<KnowledgeKind, number>, confirmed: number, contradicted: number, cited: number }` (cited: the items whose `learned.confirmed` is non-empty) and `metricsText` prints it; the report of every project of the workspace links the latest plan (`CTO plan: <path> (<date>)`, or `none`).
9. **The commands.** `crew knowledge list [--kind <k>]` (the visible entries, one line each: id, kind, title, workspace or shared, confirmed and contradicted counts), `crew knowledge show K-n` (the entry; refused when not visible, naming rule 13), `crew knowledge add --kind general|documentation --title "<t>" --file <path> [--source <url>] [--confidential]` (the user's material; other kinds are the engine's alone: refused), `crew knowledge unmark K-n` (a person's), `crew knowledge contradict K-n --reason "<why>" [--item <id>]` (the agent's, recorded in the register), `crew knowledge <id> lookup`, `crew learn <id> [--confirm K-n]`, `crew cto review --workspace <ws>`.
10. **The skill page stays within 9254 bytes.** The Learn row and the two verbs (`crew learn`, `crew knowledge`) enter `SKILL.md` by trimming words elsewhere, never past the page's ceiling; the method goes to `references/learn.md` and the existing references.
11. **The evals** are the three of §15 under the tag `knowledge` (added to `SANDBOX_TAGS`), confined to their scaffolds, needing no opener, each seeding `base.json` under the sandbox's `WIZARDINGCODE_HOME` from its fixture: `confidential-entry-not-reused`, `root-cause-not-repeated`, `cto-report-from-records`.
12. **The hardening item is Task 1, red first**, over findings 98 to 103 (the judge's advisories of SP8's six items): the `bash -o pipefail` gap of 98 first, then the rest by what each names as a defect in waiting.
13. **The version is 0.10.0**; ADR 0009 is the store; the debt of this subproject's judgement rounds is recorded as findings 104 on.
