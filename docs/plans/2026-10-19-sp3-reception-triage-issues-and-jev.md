# SP3: Reception, triage, issues and Jev. Implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task in this session, through the crew method (each task is a crew work item in this repository, as SP7a and SP7b were). Steps use checkbox (`- [ ]`) syntax for tracking.
>
> **Written on 2026-10-19**, from the SP7 design (`docs/specs/2026-10-17-sp7-teams-agents-workflows-and-rules-design.md`, §7.1, §7.2, §7.4, §10, §11, §15, §16, §18 decision 3), the SP1 design §14 (the typed questions and the replay log), the vision §8 (typed decisions: escalate only, measured by replay) and ADR 0008: SP3 is built right after 0.7.0, with no real-use phase between, and ships as 0.8.0. It carries the debt SP7b deferred (findings #73 to #81) in its first task. The TypeSafe docs read for the Jev half, on 2026-10-19: the HTTP API reference, the state page, the confidence page, the noul, choice and score pages, the citation-check cookbook, the models page and the jaggedness notes (`typesafe:typesafe-ai` invoked before this plan was written, as `CLAUDE.md` asks; invoke it again before Task 6's code).

**Goal:** A request enters from the CLI, a task manager or a document with its source on record; its urgency is confirmed or lowered against the business priorities the user signed once, never raised; a doubt becomes a recorded question echoed to the channel it came from and the work waits without a person; an issue is analysed to its origin (the commits, the items, the roles) before it is understood, and a fix is proven with a regression test and preserve criteria; Jev, when its key works, gives a second, independent verdict on an upheld defect, a validator's rule, a researcher's fact and a triage, recorded as Jev's and never loosening what the rules decided.

**Architecture:** No model runs inside the engine. The kind of work (`WorkItem.kind`) is a typed answer or a derivation the engine records, and it picks the phases: `phasesFor(work)` is the route's list with the kind's phases inserted (`analyse` for an issue), with guards like every phase. The source is a block of the item written at `crew start --source`; the engine never calls a task manager: the skill reads a ticket or a document with the tools the session holds and passes the fields. The business priorities are a file under the user's crew directory the engine signs by hash. A question is a record on the item with the channels it was posted to; the wait is the Stop hook's `awaiting: user` as today. The issue analysis is a command over git (`log`, `blame`, `show`) and the project's own records, written to `analysis/origin.json`. Jev is one module (`jev.ts`) that builds a state and typed questions, calls `POST /v1/systemone` with `fetch` (Node 20, no dependency), reads probabilities and lets code decide; a `file://` endpoint answers from a canned file for the tests and the eval. Every ask is recorded in `Evidence.verifications[]`; a verdict only marks `verified`, `disputed` or `unverified`, never changes a severity, a verdict or an approval on its own.

**Tech Stack:** TypeScript (dependency-free engine, Bun for tests, Biome), Node 20+ at run time (`fetch`, `AbortController`), the mods API of `plugins/core/hooks/register.js`, `claude plugin eval` for the four cases, TypeSafe's HTTP API (`https://api.typesafe.ai/v1/systemone`, `Authorization: Bearer`, `model: jev-latest`, request `{ state, model, questions }`, answers `noul` | `choice { choice, probabilities, confidence }` | `score { score, legend, probabilities, confidence }`, errors 400/401/413/422/429/529).

**Spec:** the SP7 design, sections named above. The rules the engine enforces in this release: 7 (a doubt stops the work and asks; with nobody present the question goes to the channel and the work waits), 11's first half (a fix never creates: a regression test and preserve criteria as guards of the issue kind), 15's second half (a disputed validator verdict waits for a person), 6's Jev half (a disputed defect is said in the report).

**Decisions taken while writing this plan** (each a reading of the spec where it left a detail open; the leads may return any):

1. **The nine typed questions stay required; `kind` and `priority` are optional answers.** `QUESTIONS` gains `kind` (choice: `client-request`, `cross-project`, `new-project`, `feature`, `issue`; `audit` arrives with SP8) and `priority` (score: `low`, `normal`, `high`, `blocker`, each level described concretely as §10.2 words them); both are validated when present and logged for replay with the nine. When `kind` is absent the engine derives it and says from what: `--origin` → `cross-project`; a `--source` whose channel is `task-manager` or `document` → `client-request`; `work_type: new-product` → `new-project`; `work_type: fix` → `issue`; else `feature`. The `priority` answer sets the item's priority only when neither `--priority` nor a proposal (an origin message, a source) gives one.
2. **`phasesFor(work)` replaces `PHASES_BY_ROUTE[work.route]` in every reader.** `Phase` gains `analyse`, placed after `recognize` in `PHASE_ORDER`; an `issue` has it on every route (one screen on fast, the design says: the phase exists, the reference keeps it short); `new-project` is never fast (the route is raised to `standard` naming the kind); `strategy` and `audit` arrive with SP8. The guard out of `analyse` (into `understand`, or `build` on fast) needs `analysis/origin.json` when the project is a git repository and `analysis.md` with the three headings `## Origin`, `## Cause`, `## Blast radius`, checked for structure as `conclave.md` is. The guard into `build` for an `issue` needs at least one `preserve` and one `behavior` criterion (rule 11); the full gate run on the merged tree is already what proves an item with handed tasks (SP2c), named in the issue reference.
3. **The source is a block the engine validates and never fetches.** `WorkItem.source?: { channel: "cli" | "document" | "task-manager"; connector?: "clickup" | "jira" | "notion" | "other"; externalId?: string; url?: string; documentPath?: string; proposedPriority?: MailPriority }`, from `crew start --source '<json>'`: `task-manager` needs `connector` and `externalId`; `document` needs a `documentPath` that exists under the root; `cli` is the default when the flag is absent and is not written. The brief gains a `## Source` section: the channel and its reference on one line, then the original text verbatim: the request's text, or the document's whole text for a document (the engine reads it). A document is one item; a split is a decision the lead proposes with `crew decision add`.
4. **The business priorities are a signed file.** `~/.wizardingcode/crew/workspaces/<ws>/priorities.md` (honouring `WIZARDINGCODE_HOME`), written by the user in plain sentences; `crew workspace priorities accept [--file <path>]` (user-only, asked, in the decision register) copies the file there when `--file` is given and records `priorities.json { hash, by, at }` beside it; `crew workspace priorities` prints `signed (<date>)`, `changed since signing`, `unsigned` or `none`. A project with no `mail.workspace` has no business priorities (`none`).
5. **The triage is the lead's confirmation, recorded on the item.** `WorkItem.triage?: { proposed: MailPriority; confirmed: MailPriority | null; by: string; reason: string | null; against: "signed" | "unsigned" | "none"; at: string; jev?: { level: MailPriority; confidence: number; capped: boolean } }`. At `crew start` with a `--source` that proposes a priority: no `--priority` confirms it; `--priority` below it lowers with a mandatory `--reason`; above it is refused ("the source proposed high; the lead confirms or lowers, never raises"), the same words as `crew mail accept`. Without a signed file, `confirmed` stays `null`, the item's priority is the proposal, `crew status` prints `priority high (proposed, unconfirmed: no signed business priorities)` and the report says so. A mail origin keeps its `priorityDecision` as the record; `triage` is for a source.
6. **A question is a record with channels, and the wait is the one the engine has.** `WorkItem.questions?: { id: "Q-n"; text: string; askedAt: string; channels: { kind: "cli" | "mail" | "ticket" | "document"; posted: boolean; ref: string | null }[]; answer: string | null; by: string | null; answeredAt: string | null }[]`. `crew question <id> add "<text>"` records it, marks the item `awaiting: "user"` and moves an origin message to `blocked` as `crew await` does; the channels: `cli` (posted, no ref) when a person is present; `ticket` (`ref`: the source's `url` or `externalId`, `posted: false` until the skill says `crew question <id> posted Q-n --channel ticket --ref <comment>`) when the source is a task manager; `document` (the engine appends the question to `<documentPath>.questions.md` beside the document and marks it posted) when the source is a document; `mail` (a notice to this project's own box, `to: .`, so `crew workspace status` shows it unread) whenever the policy names a workspace. `crew question <id> answer Q-n "<answer>"` is a person's decision (asked; relayed under `relay`; refused with `--mode` and nobody present: a doubt waits for a person), clears the wait as `crew resume` does, moves the origin back to `in-progress` and appends to the decision register. `crew status --json` gains `questions` (open first) and the mod prints them first in the panel.
7. **`crew analyse <id> --paths <a,b>` is git plus the records, nothing else.** For each path: `git log --format=%H%x09%aI%x09%an -- <path>` (the newest 20), `git blame --porcelain -- <path>` for the lines per commit, and for each commit the item folders it touched (`git show --name-only --format= <sha>` filtered to `.crew/work/<id>/`), so an item whose artifacts were committed (`artifacts: commit`, the default) is found; for each item found at HEAD: its title, kind, roles (`evidence.roles[].agent`), tasks (`T-n`), the count of its register entries and of its mail. Written to `analysis/origin.json` (engine-owned) as `{ at, paths: [{ path, commits: [{ sha, at, author, lines, items }] }], items: [{ id, title, kind, roles, tasks, decisions, mail }] }`. Outside git the file says `{ at, paths: [], items: [], note: "no git repository" }` and the guard asks for the analysis document alone.
8. **Jev is reached through `fetch`, with a timeout, two retries and a canned transport.** `WIZARDINGCODE_JEV_API_KEY` is the key (environment only, never in a file the engine writes, never printed); `WIZARDINGCODE_JEV_ENDPOINT` and `WIZARDINGCODE_JEV_MODEL`, or `crew config jev.endpoint <url>` and `crew config jev.model <name>` (the environment wins), default `https://api.typesafe.ai/v1/systemone` and `jev-latest`. Jev is *configured* when a key is set, or when the endpoint is a `file://` path: a JSON object keyed by question id whose values are answer objects as the API returns them (`model: "file"` in the record), for the tests and the eval, said as such in the reference. `askJev(request, options)` returns `{ ok: true, answers, model, usage }` or `{ ok: false, unavailable: "<reason>" }` and never throws: a 429 or 529 is retried after 1 s then 2 s, then unavailable; 401 is `unauthorised`; a 4xx names the status and the body's message; a timeout (20 s) and a network error name themselves.
9. **The policy's `verify` block is `{ send: "claims" | "claims-and-snippets"; maxClaimsPerItem: number; threshold: number }`**, defaults `claims`, 50, 0.8 (design §18 decision 3), set with `crew policy set verify.send|verify.maxClaimsPerItem|verify.threshold` (user-only, asked, in the register; `threshold` 0.5 to 0.99, the confidence page's floor; `maxClaimsPerItem` 1 to 200). Under `claims` no code leaves the machine: a defect is sent as its file, line, text and the rubric's question, and the question is a `noul` ("does the finding, taken at its word, describe a defect of the kind the rubric names?"); under `claims-and-snippets` the cited lines of the diff (the hunk's lines, five around the cited one) are sent too and the question is the citation-check `choice` (`supports`, `contradicts`, `says_nothing`). The conclave's text, the decisions, the objections, a researcher's claim and excerpt, a request's text and the business priorities are not code and are sent under either value.
10. **The four asks, their state and their questions** (one request per ask; the questions of one ask go together, as the primitives page advises; question ids are code's and never carry meaning):
    - *Defects*, at `crew judgement record` (item and todo), for each finding of a `not-proven` ruling with `severity: defect` that is inside the change and names a line inside a hunk of `review/diff.patch` (the deterministic check first; a finding with no line or outside the hunks is `unverified: <reason>`): state `{ findings: { d1: { file, line, text, rubric, lines? } } }`; `d1` a `noul` under `claims`, a `choice` `relation` under `claims-and-snippets`. Up to `maxClaimsPerItem` findings per ask; the rest `unverified: over verify.maxClaimsPerItem`.
    - *The validator's rule*, at `crew approve <id> spec --validator complete-gap-round` after `validatorPreconditions` pass: state `{ conclave: <conclave.md>, decisions: [{ id, question, answer, default }], objections: [{ id, severity, status, criterion }] }`; two `noul`s whose yes means the rule holds: "Is every decision listed in `conclave` under the heading 'Decisions only the user can make' present in `decisions` with an answer or a stated default?" and "Is every warning listed in `conclave` under 'Warnings' that names a security, data or payment risk present in `objections`?".
    - *A researcher's facts*, at `crew research <id> verify`: each line of `## What the documentation says` in `conclave/researcher.md` (`- <URL or document> · "<quote>" · <what it means for D-n>`); the engine fetches an `http(s)` URL (15 s, 2 MiB, text) or reads a path under the root, normalises whitespace and curly quotes and looks for the quote; not found is `not-found` and asks nothing; found: state `{ facts: { f1: { claim, quote, excerpt } } }` with the excerpt the 600 characters around the match, `f1` a `choice` `relation`. Written to `conclave/researcher.verification.json` (engine-owned) with the researcher file's hash; `crew debate <id> close` refuses when Jev is configured and no verification matches the current file ("run crew research <id> verify first"); the conclave reference passes the file to the experts.
    - *The triage*, at `crew start --source` when Jev is configured: state `{ request: { text, channel, connector, proposed_priority }, business_priorities: <priorities.md or null>, queue: [{ kind, priority }] }`; `priority` a `score` over `low`, `normal`, `high`, `blocker` with §10.2's descriptions, and three `noul`s: `is_production_down`, `names_a_signed_deadline`, `is_vague`. The level is the highest-probability level (never the weighted score, the jaggedness notes); with confidence at or above the threshold it is printed as a proposal to the lead with its probabilities, capped at the source's proposal (`capped: true`); below it the lead decides with no proposal; the lead's confirmation is always the record.
11. **Marks and effects, escalate only.** A `noul` at or above `threshold` is yes, at or below `1 - threshold` is no, between is unverified; a `choice` counts when its `confidence` is at or above `threshold`. A defect: `supports` or yes → `verified`, `contradicts` or no → `disputed` (the defect stays a defect; the report's Judgement table says "disputed by Jev"), else `unverified`; the exit code of the record does not change. The validator: both yes → `verified` and the approval proceeds; any no → `disputed`, the approval is refused naming the condition and its probability, the item is marked `awaiting: user` (rule 15); unverified proceeds and the record says so. A fact: marked in the verification file and quoted by the experts' prompts. A triage: a proposal, never the record. `JudgementFinding.verification?: { status: "verified" | "disputed" | "unverified"; reason?: string; confidence?: number }`; `Evidence.verifications[]: { what: "defect" | "validator" | "fact" | "triage"; ref: string; question: string; answer: unknown; confidence: number | null; model: string; at: string }`.
12. **Mandatory when configured, and down means unverified.** The four commands ask when Jev is configured (the record is never made "without its verdicts" because the command itself asks); when `askJev` is unavailable the records are marked `unverified (jev unavailable: <reason>)`, the verdict stands on the judge's, the validator's or the lead's word, and on the full route the item is marked `awaiting: user` after the record (the command says so). The roles never call Jev: no agent file changes.
13. **`crew metrics` reports the agreement.** `verifications: { verified, disputed, unverified, agreement }` where `agreement` is `verified / (verified + disputed)` over defects, or `null`; the replay the vision asks of every backend is the recorded verifications against the judge's verdicts, read from `evidence.json` alone. No threshold is lowered before the first real-use run measures it.
14. **The hardening item is Task 1, red first, small.** Findings #74 (the test fixtures removed at the suite's end, a `bunfig.toml` with the same timeout for both `bun test` forms), #78 (a resumed tech lead's answer joins `conclave/lead-<team>[.delivery]-reply.md` and `crew validation record` reads the last validation block of a file), #79 (`crew tdd before` refuses when a watched source path, tests aside, already differs from the item's base), #81 (`updateEvidence(paths, id, apply)` re-reads under the work folder's lock and the long commands, `tdd` and `gate run`, merge their records into it), #80's `SCAFFOLD_STATE` assertions and the tag list read from `scripts/eval.ts`, and the smaller advisories of #73, #75 and #76 named in the task. The advisory that cannot be tested here (a client name in a fixture: the names are not in the repository) stays a build-time grep.
15. **The skill page stays within 9254 bytes.** `kind` and `priority` as optional answers, the source, the questions and the analysis go into `references/receive.md`, a new `references/analyse.md` and a new `references/jev.md`; `SKILL.md` gains the `Analyse` row and the `crew question` verb by trimming words elsewhere, never past the pin.
16. **The evals** are the four of §15 under the tags `reception`, `jev` and `issue`, each confined to its scaffold and needing no opener: `ticket-triaged-against-business` (the ticket's text given in the prompt as read from ClickUp, since the sandbox holds no MCP server; the business priorities signed by the fixture with `--file`), `document-entry-opens-item`, `jev-tightens-never-loosens` (the canned transport through `crew config jev.endpoint file://$PWD/jev-answers.json` set by the fixture, the validator's second condition answered no: the approval is refused and the item waits), `issue-root-cause-named` (an earlier item's artifacts committed by the fixture with the bug). `fast-route-overhead` is the guard. They run with `--case`; the whole suite runs once before the real-use phase (ADR 0008).

## Global Constraints

## Review Focus

Six input classes the spec implies and no task's tests would otherwise exercise; each line names the task that owns the test.

1. **A source that proposes `blocker` for a cosmetic change, with a signed file**: `crew start --source … --priority normal --reason "<why>"` records `triage { proposed: blocker, confirmed: normal, against: signed }` and prints the lowering with the reason; the same without `--reason` is refused; `--priority blocker` on a source proposing `high` is refused naming the raise. Test in Task 3.
2. **A question added in a session nobody watches** (`--mode` given) **with a task-manager source**: the record carries a `ticket` channel `posted: false` with the ticket's ref and a `mail` channel posted, the item waits, and `crew question answer` with `--mode` is refused. Test in Task 4.
3. **`crew analyse` on a path whose commits carry no item folder** (code written before the crew): `origin.json` lists the commits with `items: []`, the guard still asks for `analysis.md`, and the ending can say the origin is outside the records. Test in Task 5.
4. **Jev answers `contradicts` at 0.95 on an upheld defect**: the finding is marked `disputed`, the ruling's verdict stays `not-proven`, the exit code stays 1, the report says "disputed by Jev". Test in Task 6.
5. **Jev is configured and the endpoint returns 401**: the ruling is recorded `unverified (jev unavailable: unauthorised (401))`, nothing waits on the standard route, and a full-route item is marked waiting for the user after the record. Test in Task 6.
6. **A canned transport whose file lacks a question's id**: `unavailable: no canned answer for <id>`, recorded as unavailable, never as a verdict. Test in Task 6.

Three more, cheaper, folded into their tasks: a `--source` whose `documentPath` is outside the root or missing is refused before anything is created (Task 3); `phasesFor` of an `issue` on the fast route lists `analyse` between `recognize` and `build` and the old `PHASES_BY_ROUTE` readers are gone (Task 2); a validator ask whose second `noul` is 0.5 is `unverified` and the approval proceeds, said in the output (Task 6).
