# WizardingCode Developer Crew

Guided delivery for coding agents where done is proven, by **WizardingCode**: the engine, not the model, says when work is finished.

Brand conventions: products, plugins and skills are called `wizardingcode-<thing>`; variables `WIZARDINGCODE_<THING>_*`; data in `~/.wizardingcode/<thing>` (honouring `WIZARDINGCODE_HOME`). Until commit 68c1fc4 this was shibaox-developer-crew; nothing was published under that name, so there is no compatibility code. Never reintroduce the old names; `docs/plans/` keeps the names it was written with. See `docs/adr/0001-wizardingcode-brand.md`.

## Where things are

- The whole system, its principles and its roadmap: `docs/vision.md`
- Designs: `docs/specs/`; implementation plans, task by task: `docs/plans/`
- Decisions: `docs/adr/` (read the latest before changing a name, a path or a convention)
- The engine: `packages/engine` (dependency-free TypeScript; `src/hooks/` is what each Claude Code event runs, `src/cli.ts` the `crew` command)
- The plugin: `plugins/core` (`dist/crew.mjs` is the bundled `crew` command, `hooks/` the hook wiring and the mod, `skills/crew` the method, `agents/` the roles, the goldfish reviewers of a document among them, `skills/wizardingcode-spec-*` the document review's seven skills and `skills/wizardingcode-journey` the session of a mission with nobody present; ADR 0019 and ADR 0020)
- The eval suite: `plugins/core/evals/` (inside the plugin, where `claude plugin eval` looks for it; `results/` there is ignored, the recorded runs live in `docs/evals/`)
- The real-use phase between subprojects: `docs/real-use/` (the plan of the phase, the findings, the corpus of real requests)
- The rules taken from outside sources, each with where it lives and what proves it: `docs/sources/ledger.json`
- The brand's lockup and mark, as the README uses them: `docs/brand/` (not covered by the MIT licence)

## Commands

- `bun run check` — typecheck, lint and the engine tests
- `bun run build` — bundles the `crew` command into `plugins/core/dist/crew.mjs`
- `bun run format` — formats and fixes lint
- `bun run plugin:check` — `claude plugin validate --strict` and the mod's tests (they need the plugin runtime; `bun run check` does not run them)
- `bun scripts/eval.ts [--case <name>] [--max-cost-usd <usd>] [--judge-model <model>]` — runs the eval suite with the PATH and the environment it needs and prints an estimate first; the whole suite has no default cap since the user's decision of 2026-10-22 (finding 63: no hard limit, managed), so run only the affected cases with `--case` (about 0.3 to 2.3 USD each, capped at 5 unless given); the suite is about 95 USD a run at three runs and two arms; the llm graders' judge is `claude-fable-5-2`, and `claude-opus-5-5` for the whole run when Fable cannot judge at its start, unless `--judge-model` names another (the user's decisions of 2026-11-09); exit 5 when no judge answers
- `bun scripts/site-distinctness.ts <folder> <folder> ...` — compares built sites: the six dimensions per pair and each site's proportion limits (exit 1 on a pair too alike or a limit broken); `bun scripts/build-design-library.ts` regenerates `plugins/core/design/library/` from checkouts of its sources
- `bun scripts/benchmark.ts [--from <aggregate.json>] [--out <dir>]` — runs the benchmark set through the kit (about 35 USD, no default cap; `--max-cost-usd` sets one) and writes `docs/benchmark/<date>-<version>.{md,json}` from the aggregate alone (`docs/benchmark/README.md`)
- `claude --plugin-dir ./plugins/core` — loads the plugin for one session
- `node plugins/core/dist/crew.mjs status` — where the work stands (`crew help` lists the commands)

Node.js 20 or later on `PATH` runs the hooks and the command; development uses Bun, and `bun run check` needs `php` on `PATH` as well (the Laravel pair's rows run the fixture's `artisan`, a PHP script with no framework, through it). The `ui` eval cases need Playwright's headless shell on the machine (`PLAYWRIGHT_BROWSERS_PATH=node_modules/.cache/ms-playwright bunx playwright install chromium-headless-shell`, macOS arm64); without it `bun run check` skips those rows.

## Releasing

The plugin installs from the `WizardingCode-io/wizardingcode-plugins` marketplace, whose entry points at this repository's `plugins/core` at a tag (`git-subdir`, `ref: vX.Y.Z`). The release is one script, for a person and for the loop (ADR 0015): `bun scripts/release.ts --patch|--minor|--major|--version X.Y.Z --reason "<why>" [--dry-run]`. It writes the version into every file this section names (`package.json`, `packages/engine/package.json`, `packages/engine/src/version.ts`, `plugins/core/.claude-plugin/plugin.json`, and the packs' `packs/laravel/pack.json`, `packs/laravel/.claude-plugin/plugin.json`, `packs/agentic-os/pack.json`, `packs/agentic-os/.claude-plugin/plugin.json`, `packs/frontend/pack.json`, `packs/frontend/.claude-plugin/plugin.json`, `packs/nuxt/pack.json`, `packs/nuxt/.claude-plugin/plugin.json`, `packs/next/pack.json`, `packs/next/.claude-plugin/plugin.json`, with the lower bound of `core`, which `packs-content.test.ts` pins to the engine's version or its next minor) and the two tests that assert it (`packages/engine/tests/version.test.ts`, the `--version` line in `cli.test.ts`); then runs `bun run build`, `bun run check`, `bun run plugin:check`; commits and tags `vX.Y.Z`; pushes; builds the tarball (`bun scripts/build.ts --tarball`, the release asset for the runtimes that are not Claude Code, `dist/wizardingcode-developer-crew-X.Y.Z.tar.gz`, ADR 0011; a user installs it with `tar xzf`, the extracted `bin/` on PATH and `crew runtime install <name>`); creates the GitHub release with it (`gh release create vX.Y.Z dist/wizardingcode-developer-crew-X.Y.Z.tar.gz`); updates the marketplace entry (`version`, `ref`, `metadata.version`, committed as `wizardingcode-developer-crew X.Y.Z`) through the contents API; both GitHub steps use the personal account's token (`gh auth token -u andreagroferreira`), whichever account is active in `gh`, and stop when it has none; runs `claude plugin marketplace update wizardingcode-plugins` and `claude plugin update wizardingcode-developer-crew@wizardingcode-plugins` here (a restart then reloads the installed copy, finding #66); refreshes the local tarball install when there is one, keeping the install it replaced beside it as `<install>.previous` until the next release, so a rollback is one move, and putting a previous install it finds alone back in place before the swap, so removing the local install means removing `<install>.previous` with it (item 2026-11-09-001), and removing each staging folder (`.wizardingcode-developer-crew-next-*`) an earlier kill left beside the install (item 2026-11-09-003); runs that install's `crew projects update --dry-run`, the fleet's dry run, a record of the projects the update is about to write (never a gate, item 2026-11-09-003), then its `crew projects update`, which refreshes the runtime adapters of every registered project (soft, the two bounded at five minutes together, item 2026-11-08-002) and leaves each refreshed project a not-committed mark, so every session start there repeats the commit command until the files are committed, or, for an install the bound cut short, says to run the install again (items 2026-11-09-001 and 2026-11-09-003); and notifies, saying of a fleet run killed at its bound only what its output proves: the last project line it printed and where the project that may be written in part is listed, or that every project's line was printed (item 2026-11-09-001). A failure before the push puts the tree back; a failure after it is resumed with `--resume vX.Y.Z --from-step N` (the step the log named). A failed step's log names the lines of its output that name a failure and its last lines, and keeps the whole output with the exit status under dist, in a file named after the version and the step, which exists only for a failed step (finding 217). Run inside a Claude Code session, in the background, the script records the release's start after its title line and its end right after the push through the engine's own module (`packages/engine/src/release-record.ts`), so the Stop hook lets the turn end while the release runs and takes the pushed commit as the session's baseline once the installed plugin carries the reader; the loop wires no record and records nothing; step 5 commits only what the release wrote, on the commit it started from (finding 219). The repository must stay public for the install to work. Nothing is built on install: `dist/crew.mjs` is committed.

The release reads the personal account's token before step 1, so a release with none writes and pushes nothing, and every command it runs has a time bound (item 2026-11-13-004, findings 212 and 221): 2 minutes for a local command, 5 for a remote one or a build, 45 for `bun run check`, the fleet's step keeping its own. A command past its bound is killed with its process group and is a failed step. A bounded command has no terminal, so a release needs credentials that ask nothing (an agent, a helper, a token). After a push that failed or was killed, the release asks origin for the tag before it resets anything. Before step 1 it writes `dist/release-in-progress.journal`: a release killed before its push is put back by the next new release from it (the version files it wrote, the bundle, its commit and its tag), and one whose push went through is resumed. While a command runs, `dist/release-in-progress.command` names it and the release that started it: the next new release or resume ends a command a killed release left running, and stops while that release still runs; the loop's `stop` ends the command of the tick it stops.

The harness-improvement loop runs on this Mac by itself (ADR 0015): `bun scripts/improve-loop.ts install [--clone-from <checkout>]` installs the launchd agent that ticks hourly, `bun scripts/improve-loop.ts status` says where it stands, `tick [--dry-run]` runs one tick by hand, `uninstall` removes the agent, `secret set <account>` puts a provider's token in the keychain; its home is `~/.wizardingcode/crew-improve` (its configuration file names the provider), its records land in `docs/improve/` (`docs/improve/README.md`).

## Conventions

- TDD: the test is written and seen failing before the code.
- Lint and format with biome; imports with an explicit `.ts` extension.
- The files the engine owns, in `.crew/` and `~/.wizardingcode/crew`, are written only by the `crew` command, and by the release script through the engine's own module (the release marker and the session's baseline, 2026-11-01-003); the PreToolUse hook denies anything else.
- Hooks fail open: a hook that cannot decide answers `{}`, so a bug in the engine never blocks the user's session (`packages/engine/src/hooks/index.ts`).
- Repository documents (README, vision, specs, plans, ADRs, this file) are written in English, and every text the crew writes (documents, comments, commit messages, reports) follows `plugins/core/skills/crew/references/writing.md`.
